## 我的答案

Test-Time Scaling 的上限可拆成“生成上限、判断上限和资源上限”。更多计算只能重新分配已有模型的概率与探索，不能保证创造训练中从未形成的知识或技能。

### 1. 基础模型限制

- 若正确轨迹的单次概率 $p\approx0$，增大采样数仍几乎命不中；
- 知识缺失、错误世界模型、上下文理解失败会让所有候选共享同一偏差；
- 模型可能缺少候选多样性，温度升高虽增探索，也会增加无效分支；
- 长轨迹存在误差累积、上下文遗忘和“反思后改错”的风险。

### 2. 验证器限制

Best-of-N 的最终质量不仅要看 pass@N，还要看从候选中选对的能力。Outcome verifier 只判断结果，信号便宜但难定位步骤；process verifier 可早期剪枝，却需要可靠的步骤标签，且局部看似合理不代表全局正确。验证器与生成器共用偏差或训练数据时，错误可能高相关；指标代理不完整还会出现 reward hacking。

### 3. 搜索空间与算法限制

自然语言推理的分支因子大、等价表述多、状态难规范化。固定 beam 容易丢掉低概率但正确路径；穷举成本指数增长；过早剪枝无法恢复。搜索还需要在 exploration 与 exploitation 间取舍，并决定状态、动作、价值估计与停止条件。

### 4. 系统和任务限制

在线有 token、显存、费用、deadline 和并发预算；搜索的串行依赖难完全并行。部分现实任务的 ground truth 延迟或不可观测，无法在请求内验证。简单题存在饱和，极难题则进入“再多算也不会”的区域，中等难度通常最能受益。

因此我会画 accuracy-cost frontier，而不是只报最高分；同时报告 oracle pass@N、verifier-selected accuracy、候选多样性、按难度收益和 P95 延迟。若 oracle 高而 selected 低，应改验证器；oracle 本身低，则优先提升 base model、工具或知识，而不是继续加搜索。

### 面试简答版

Test-Time Scaling 受三道天花板限制：基础模型必须能以非零概率生成正确且多样的候选；验证器必须能识别正确路径而不被代理奖励欺骗；搜索必须在巨大分支空间里有效探索而不过早剪枝。再加在线成本和串行延迟，收益通常集中在中等难度题。诊断时分开看 oracle pass@N 与 verifier 选中率：前者低要改模型/知识，前者高后者低要改验证器。
