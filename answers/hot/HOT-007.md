> **问题：** Expert Capacity、Token Dropping 和 Dropless MoE 有何区别？

## 我的答案

MoE 的动态路由会让每个专家收到的 token 数不同。传统实现为了把动态工作负载映射成规则张量，会给每个专家设固定容量。若 routing group 有 $T$ 个 token、每 token 选 $K$ 个专家、共有 $N$ 个专家，常见估算是：

$$C=\left\lceil \text{capacity factor}\times\frac{TK}{N}\right\rceil$$

$C$ 是每个专家最多接收的 assignment 数。capacity factor 大于 1 可吸收负载波动，但会增加 padding、显存和计算浪费。

### Token dropping

当专家收到的 assignment 超过 $C$，固定容量方案可能：丢弃溢出路径、转给次优专家，或让 token 只走 residual/shared 路径。优点是 buffer 和通信量有上界，易于做 dense batched GEMM；缺点是信息路径被改变，训练与推理可能出现质量损失，而且某些领域/语言若更常命中热专家，会遭受系统性丢弃。

这里的“drop”通常是跳过某条专家计算路径，不是从序列中删除 token；具体 fallback 必须看实现。

### Dropless MoE

Dropless 的目标是让所有被路由的 token 都完成专家计算。MegaBlocks 一类方法用 block-sparse operation，其他系统可用 variable-size grouped GEMM、动态 buffer 或 padding 到实际最大负载。它避免了容量截断造成的模型质量问题，但代价没有消失：

- 热专家仍会导致更大的临时内存、更多通信和 straggler；
- 动态形状和小 block 可能降低 kernel 效率；
- 极端不均时，峰值资源与尾延迟不再有固定容量的硬上界。

因此 fixed-capacity 与 dropless 是“可预测资源/简单 kernel”和“保留全部 token/动态负载”之间的取舍。实践中还要配合负载均衡、容量告警和 backpressure。训练能 dropless 不代表在线服务可以无界等待；服务侧仍需 batch、deadline 和过载降级策略。

### 面试简答版

固定容量 MoE 通常令每专家容量约为 $\lceil\text{factor}\cdot TK/N\rceil$，超额 token 路径会被丢弃或降级。它让 buffer、通信和 GEMM 规则可控，但可能损害质量并产生群体偏差。Dropless 用稀疏或可变形状计算处理全部路由 token，避免路径丢失，却仍受热专家内存、通信和尾延迟影响；所以 dropless 不是不需要负载均衡，而是把容量截断问题转成了动态系统调度问题。
