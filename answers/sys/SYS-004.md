## 我的答案

调度器需要同时解决四件事：紧急请求先服务、租户不能超预算、长期来看资源分配公平、取消后立即停止无效计算。LLM 请求长度差异很大，因此核心计量单位应是 **token、KV Cache 和 GPU time**，不能只数请求。

### 请求模型与队列

每个请求携带不可由用户任意抬高的 `tenant、service_class、model/version、input_tokens、max_new_tokens、deadline、cost_budget、cancel_token`。业务身份映射到服务等级，客户端不能直接声明最高优先级。

采用层级队列：先按在线/批处理和优先级分层，再按租户维护子队列。每个模型/GPU 池独立调度，避免不可执行的请求占据全局队头。队列必须有长度、token 和等待时长上限；预计无法在 deadline 内完成时尽早拒绝、降级或转批处理。

### 优先级与公平性

严格优先队列会饿死低优先级，纯 FIFO 又无法保障交互请求。可组合：

1. 服务等级决定基础优先级和最大排队预算；
2. 同等级租户使用 Weighted Fair Queuing 或 Deficit Round Robin；
3. 低优先级等待越久获得 aging 提升，但不能越过安全或实时硬边界；
4. 大请求按预计 token/GPU cost 扣减 deficit，防止拆成大量小请求或用超长上下文占便宜。

若请求 $i$ 的预计服务量为 $L_i$、租户权重为 $w_i$，WFQ 可用近似虚拟完成时间排序：

$$
F_i=\max(V(a_i),F_{i-1})+\frac{L_i}{w_i}
$$

实际 LLM 输出长度未知，可先按输入与 `max_new_tokens` 的保守估计准入，运行中按实际 token 结算并更新预测。

### 配额与准入

租户采用层级 token bucket：短时 burst + 长期 input/output token、并发、GPU-second 和日预算；组织配额下再分项目/用户。资源侧检查模型实例、KV page、batch slot 和显存水位。只有业务配额和资源容量都满足才接收。

配额最好在中心服务持有权威账本、边缘持有短期租约，避免每个 token 都做跨网络同步。超额请求返回可解释的 429、`Retry-After` 或降级选项；不能排进无限队列。

### 与 continuous batching 协作

全局调度器决定哪些请求进入模型池，worker 调度器再按长度、LoRA、prefix 和 deadline 组成 batch。吞吐优化不能破坏公平：需要限制单租户在一个 batch/worker 的份额，并持续按已生成 token 计费。超长 prefill 可切块或单独分池，减少对 decode 请求的阻塞。

### 取消语义

取消来源包括客户端断连、主动取消、deadline、上游失败和管理员终止。`cancel_token` 贯穿网关、队列、worker 和流式输出：

- 排队中：原子标记取消并惰性/主动移除，释放配额预留；
- 运行中：在 decode step 等安全点停止，移出 batch，释放 KV page，并按实际使用结算；
- 已产生副作用：取消不能当回滚，工具写操作需幂等、事务或补偿；
- 取消/完成竞争：状态机用 CAS 保证只有一个终态，重复取消幂等。

### 可观测性与验证

监控各等级/租户的队列 token、等待时间、deadline miss、配额拒绝、实际/预计 token 偏差、公平份额、饥饿时间、batch 利用率和取消释放延迟。压测包括突发高优请求、大象/老鼠混合、恶意拆单、租户抢占、慢客户端与取消风暴，验证高优 SLO 的同时低优仍有最小进展。

### 面试简答版

我会使用按模型分池的层级队列：服务等级控制基础优先级，租户间用加权公平或 Deficit Round Robin，等待 aging 防饿死。资源按输入/输出 token、并发、GPU-second 和 KV 占用计量，配额用层级 token bucket；准入会判断 deadline 和预计服务量，超载尽早 429/降级。worker 再做长度、prefix、LoRA 感知的 continuous batching，并按实际生成 token 结算。取消信号端到端传播，排队请求移除，运行请求在 decode 安全点退出并释放 KV；状态机 CAS 保证终态幂等，外部副作用另用事务和补偿处理。
