## 我的答案

多 Agent 只有在任务可并行、需要不同工具/权限/专长，或独立复核能显著提高质量时才值得使用。否则多个模型会增加通信、错误传播和成本。设计上应采用**中心化任务契约与状态、去中心化的受限执行**。

### 架构

```text
User Goal → Supervisor / Task Graph
                 │
          Shared Artifact Store
          Event Log / Blackboard
      ┌──────────┼──────────┐
      ▼          ▼          ▼
 Researcher   Executor    Reviewer
      └──────────┬──────────┘
            Reducer / Verifier → Result
```

Supervisor 将目标转成有向无环任务图。每个 task contract 包含输入 artifact ID、输出 Schema、成功标准、依赖、deadline、预算、允许工具/数据、风险和 owner。Agent 不直接互发大段自由对话，而是通过事件总线和共享制品库交换版本化产物，消息携带 task/version/provenance，减少上下文污染。

### 任务分解与调度

先按可验证边界拆分，而不是按“你做第一段、我做第二段”机械分工。满足以下条件的节点并行：输入已就绪、写集合不冲突、预算可用；依赖节点由调度器等待。动态发现新任务时更新图并检测环，限制 fan-out、深度和总 token/工具调用。

角色应由能力和最小权限定义，例如检索 Agent 只能读公开源，数据 Agent 只能查特定只读视图，发布 Agent 才有受审批的写权限。不同 Agent 使用独立凭据，不能把 supervisor 的权限继承给所有子 Agent。

### 冲突类型与处理

1. **事实冲突**：保留各结论、证据和时间，优先权威/当前来源；独立 verifier 检查，仍冲突则向用户披露或人工裁决，不做无依据多数投票。
2. **写冲突**：artifact 使用不可变版本和 optimistic concurrency/CAS；同一资源指定单 writer，其他 Agent 产出 patch，由 reducer 合并。数据库/外部写由中心工作流串行化、幂等和审批。
3. **计划冲突**：目标、约束和优先级以 task contract 为准；supervisor 可重规划，但不能修改系统安全边界。预算冲突按关键路径与业务优先级仲裁。
4. **格式冲突**：输出先过 Schema 和单元验证；reducer 只消费合格产物。对代码、计算等使用测试/执行结果，不让模型凭语言争论。

多数表决只有在错误相对独立且答案空间明确时才有意义。同源模型往往“一致地错”，因此更偏好异构证据、确定性验证器和明确 tie-breaker。

### 容错与终止

任务状态使用 lease/heartbeat 和事件历史；worker 失联后重派，写操作要求幂等。瞬时错误有限重试，语义失败由 supervisor 用新信息重规划。检测反复互相委派、无新证据争论和预算耗尽，触发终止、降级单 Agent 或人工。

每个 Agent 的输入、产物、工具、版本和成本形成独立 span，再由父 trace 串联。评测除了最终正确率，还看任务图完成率、冲突解决正确、重复劳动、关键路径延迟、token/工具成本、权限违规和单 Agent 基线增益。若多 Agent 没有显著提升，就应简化。

### 面试简答版

多 Agent 我会用 supervisor 生成带依赖的任务 DAG，每个节点都有输入/输出 Schema、成功标准、预算和最小工具权限；Agent 通过共享制品库和事件日志交换带版本、来源的产物，而不是无限自由聊天。可独立且写集合不冲突的节点并行。事实冲突按证据权威性和 verifier 处理，写冲突用单 writer、不可变 artifact 与 CAS，计划冲突由 task contract 和 supervisor 仲裁，高风险外部写统一串行审批。系统还需 lease、心跳、幂等、循环/预算终止和父子 trace，并以相对单 Agent 的质量增益与额外成本决定是否值得。
