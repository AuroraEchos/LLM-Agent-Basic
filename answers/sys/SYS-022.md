## 我的答案

这个系统应将线上信号转成版本化的**Case 资产、根因簇和自动回归门禁**。关键不是收集最多，而是覆盖沉默失败、减少选择偏差，并确保每个修复能在相同和邻近样本上被验证。

### 架构

```text
Feedback / Traces / Business Outcomes / Safety Events
                         │
                 Privacy Filter + Sampler
                         ▼
            Case Store → Dedup/Cluster → Label Queue
                         │                 │
                         └→ Root Cause / Owner
                                      │
                                Fix + Eval Registry
                                      │
                              CI Gate / Canary Monitor
```

### 发现与采样

显式来源包括点踩、申诉、客服和人工接管；隐式来源包括重复提问、用户大改答案、任务/工具/Schema 失败、低引用支持、异常拒答、循环和高成本；安全来源包括 DLP、越权、红队和事故。再按任务、语言、租户、模型版本和风险做随机/不确定性分层抽样，发现用户没有反馈的错误。

采集时保存 trace 和原始对象的权限化引用、模型/Prompt/索引/工具版本、业务结果及采样概率。先脱敏和最小化；完整 Prompt 只进入隔离取证库，不复制到普通工单或外部标注平台。

### Case、去重和聚类

统一 Case Schema 包含输入/期望/实际、症状标签、严重度、影响规模、版本、证据、工具轨迹、来源、复现状态和 owner。exact error/signature、规范化哈希先去重，再用 embedding、主题和结构字段产生候选簇。

语义相似不代表根因相同，因此聚类同时使用产品、语言、检索/工具错误码、模型版本等特征，由人命名、拆并和抽检纯度。Case 与 cluster 多对多：一个请求可同时有检索过期和指令不遵循；同一根因也可产生不同表面症状。

### 标注与归因

标注指南定义事实、忠实度、指令、检索、工具、安全、UX 等标签和边界，采用盲审、gold canary、重叠标注与一致率监控；争议或领域 Case 升级专家。模型预标只用于加速，不能自证正确。

归因沿链路排查输入/期望、路由/Prompt、检索/ACL/新鲜度、生成、工具选择/参数/执行、验证器、后处理/UI，记录症状、近因与系统根因。通过可复现 trace 和组件替换/消融验证，例如固定生成器替换检索结果，避免凭感觉把错误都归给模型。

### 修复与回归闭环

优先级结合危害、频率、用户规模、趋势、可检测与修复成本；泄漏、跨租户和不可逆副作用单独最高级。每个根因簇指定 owner、SLA、修复层和监控。

代表 Case 转成最小测试夹具，固定必要的数据/工具快照。回归集包含原 Case、同簇未见样本、反事实/边界变体和邻近正常样本；数据划分按 cluster/source，防止近重复泄漏。CI 先跑确定性和小型关键集，夜间跑 Judge/大集，发布后 canary 看真实业务结果。只有原问题消失、同族泛化、正常能力无回退且线上指标稳定才能关闭。

### 指标

监控发现覆盖、采样偏差、去重率、聚类覆盖/纯度、标注一致、复现率、根因确认时间、MTTR、同类复发率、人工负载，以及每次修复的任务/安全净收益。评测集也要版本化、设置 owner 和过期审查，避免历史题库与当前产品脱节。

### 面试简答版

我会从用户反馈、业务结果、trace 异常、安全事件和分层主动抽样收集 Case，采集前脱敏并绑定完整版本。先用错误签名/哈希去重，再结合 embedding 与结构字段做候选聚类，由人校正；统一标注体系、gold 样本和重叠标注保证质量。归因沿 Prompt、RAG、模型、工具、权限、后处理逐层做消融，区分症状、近因和根因。每个根因簇有 owner，修复前转成最小回归夹具，修复后测试原样本、同簇未见变体和邻近正常样本，再经 CI 与 canary 才关闭。核心指标是复现率、MTTR 和复发率。
