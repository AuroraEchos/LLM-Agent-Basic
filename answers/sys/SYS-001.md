## 我的答案

我会先澄清目标：支持哪些模型与上下文长度，峰值 QPS/输入输出 token 分布，TTFT、TPOT、总时延和可用性 SLO，是否允许降级，以及租户、安全、数据驻留和成本约束。LLM 推理的瓶颈不是普通 HTTP QPS，而是**prefill 计算、decode 显存带宽、KV Cache 容量和每秒 token**。

### 总体架构

```text
Client
  │ HTTPS / SSE / gRPC streaming
  ▼
Global LB → API Gateway → Auth / Quota / Safety / Request Normalizer
                           │
                           ▼
                    Model Router / Admission
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
        Model Pool A   Model Pool B   Fallback Pool
        Scheduler      Scheduler      Scheduler
             │             │             │
       GPU Workers    GPU Workers    GPU Workers
         KV Cache       KV Cache       KV Cache
             └─────────────┬─────────────┘
                           ▼
                  Stream Aggregator / Guard
                           │
                     Metrics / Trace / Logs
```

控制面负责模型注册、版本、路由规则、容量和灰度；数据面保持精简，负责请求校验、调度、推理和流式返回。各模型/版本使用独立 worker pool 和熔断域，避免一个超长请求或 OOM 拖垮所有模型。

### 请求与多模型路由

网关完成认证、租户配额、限流、最大上下文与输出长度、Schema 和内容安全校验，生成 `request_id/trace_id`。路由器依据：

- 必需能力：文本/视觉、上下文长度、tool calling、结构输出、地区；
- 质量等级与任务类型：代码、对话、embedding、低风险摘要；
- SLO：剩余 deadline、候选池队列时间、预计 token 速率；
- 成本与配额：模型单价、租户套餐、预算；
- 健康与灰度：错误率、负载、版本 cohort 和 fallback 规则。

先过滤不满足硬约束的模型，再在候选中优化质量、延迟和成本。一次会话或请求应固定到具体版本，防止中途切换导致 KV Cache、工具格式和行为不兼容。降级必须显式：可从大模型到小模型、缩短输出或进入排队，但高风险任务不能静默降级到能力不足的模型。

### GPU 调度与高并发

请求进入有界队列，准入控制根据预计 prefill token、最大生成 token、KV Cache 和 deadline 决定接收、排队或返回 429。按 token 而非请求数计量，防止一个 100k 上下文等同一个短请求。

worker 内使用 continuous batching：每个 decode step 动态加入新请求、移除完成/取消请求；长短上下文可分桶，减少 padding 和队头阻塞。结合 paged KV Cache、prefix cache 和张量/流水/数据并行。若规模足够，可分离 prefill 与 decode 池，但需衡量 KV 传输、调度和故障复杂度。

容量可先用 token 流量估算：

$$
Demand_{tok/s}=QPS\cdot\bigl(E[T_{in}]+E[T_{out}]\bigr)
$$

再用压测得到每种模型、硬件和上下文组合的有效吞吐，按峰值、冗余和 P95 分布配容；不能直接用理论 FLOPS。

### 流式输出、背压和取消

外部可用 SSE（浏览器简单单向流）或 gRPC streaming；事件含 `request_id`、递增 `sequence_no`、delta、finish reason 和 usage。网关/聚合器只保留有界缓冲：客户端消费慢时暂停读取、降低窗口，超过阈值则取消，避免慢消费者耗尽内存。

客户端断连、主动取消或 deadline 到期后，取消信号要贯穿网关→调度器→worker，在下一个安全点释放 batch slot 和 KV Cache。已发送 token 不承诺“撤回”；工具或外部写操作需独立使用幂等、事务和确认。重连若支持续传，应基于短期事件缓冲和 sequence number，不能无条件重复整个生成。

### 高可用和可观测性

网关、路由和调度前端跨可用区无状态部署；配置通过版本化控制面下发，本地保留 last-known-good。GPU worker 做健康检查、故障隔离和优雅摘流，节点故障时通常重新生成而非迁移庞大 KV Cache。每个池保留容量余量，采用熔断、超时和受控 fallback；在线请求使用短有界队列，避免故障时排队雪崩。

核心指标包括 QPS、输入/输出 token/s、队列长度、准入拒绝、TTFT、TPOT、E2E P95/P99、batch size、KV Cache 占用/命中、GPU 利用率、取消释放时延、流中断率、路由分布、错误率和每成功请求成本。Trace 串联网关、路由、排队、prefill、decode 与输出审核。

### 面试简答版

我会把系统拆成版本化控制面和低延迟数据面：网关做认证、配额与输入校验，路由器按能力、SLO、成本和健康选择具体模型版本，请求进入各模型隔离的 token-aware 有界队列，再由 GPU worker 通过 continuous batching、paged KV Cache 和并行策略推理。流式层使用 SSE/gRPC，带 sequence number、有界缓冲、背压和端到端取消，及时释放 KV。网关和路由跨 AZ 无状态部署，模型池独立熔断并保留 fallback。容量与扩缩容依据 token/s、队列和 KV 占用，而不是只看 QPS；核心 SLO 是 TTFT、TPOT、P99、成功率和每成功请求成本。
