## 我的答案

模型网关的职责不是简单按名字转发，而是把逻辑模型请求解析成一个可审计、可复现的**基础模型版本 + Adapter 版本 + 推理配置 + 路由策略**，并在容量、兼容和灰度约束下选择健康实例。

### 控制面

模型注册表为每个不可变版本保存：artifact digest、tokenizer、runtime、量化/并行配置、上下文长度、模态、tool/JSON 能力、显存需求、数据驻留、质量/安全评测和生命周期状态。

LoRA 注册表保存 adapter digest、rank、目标模块、兼容的 base model digest、tokenizer/Prompt 版本、训练来源、租户所有权、评测和状态。兼容性必须以具体基座 digest 校验，不能只看“同一个 7B 模型名称”。禁止在未知基座上强行加载 adapter。

路由配置、租户 allowlist、版本权重、fallback 和阈值存于强一致/版本化控制面，经签名或校验后发布；数据面本地缓存 last-known-good，控制面故障时不应让所有在线请求失败。

### 数据面路径

1. 网关认证并从可信身份得到租户和权限，校验输入、配额、deadline 及所需能力；客户端不能访问未授权模型/LoRA。
2. 将逻辑别名解析为具体版本和灰度 cohort；同一会话固定版本，返回响应元数据用于追踪。
3. placement/router 根据已加载 base/adapter、GPU/KV 水位、队列预计等待、数据区域和健康选择实例；请求只在兼容池内负载均衡。
4. worker 调度器按 base model、LoRA、长度和 prefix 组 batch，执行并流式返回；usage、质量与故障回传路由系统。

### 多 LoRA 管理

基座权重常驻 GPU，adapter 使用 GPU/CPU/本地磁盘分级缓存，按热点预加载并用 LRU/LFU + 租户配额驱逐。并发 serving 可在 runtime 支持时对同基座不同 LoRA 做 adapter-aware batching；否则按 adapter 分桶，避免频繁换载导致尾延迟。

必须限制 adapter 数量、rank、显存和加载并发；校验文件格式与 digest，隔离租户制品，防供应链和 DoS。冷 adapter 请求可等待加载、路由到已加载实例或异步预热，但不能把整个网关阻塞。监控 adapter 命中率、加载时延、驱逐和每 adapter 质量/成本。

### 灰度、回滚和 fallback

灰度规则基于稳定哈希，例如 `hash(tenant,user/session,experiment)`，而不是每次随机，使多轮会话一致。按内部→白名单租户→1%→逐步扩大，每阶段比较任务成功、安全、TTFT/TPOT、错误和成本；严重指标触发自动停止。

版本别名更新使用原子配置快照。回滚只需把路由指向上一套 base+LoRA+Prompt 配置，并保留旧 worker 至摘流完成。fallback 必须满足能力、权限和安全下限；adapter 不兼容时不能悄悄丢掉 LoRA 回基础模型，除非产品明确允许并向调用方标示。

### 一致性与安全边界

- 请求和 trace 记录解析后的 base/adapter/config digest；缓存键也包含这些版本、租户和权限上下文。
- 工具 Schema 和结构输出按模型版本做契约测试，避免换模型后调用格式漂移。
- 权限在网关与制品存储两侧校验，短期凭据拉取 artifact；模型/adapter 原文和敏感训练信息不进入普通日志。
- 每个模型池有独立限流、熔断和资源预算，防止一个低质量 adapter 或 OOM 影响其他租户。

### 面试简答版

我会把网关分成版本化控制面和无状态数据面。注册表保存不可变 base model 与 LoRA digest、tokenizer、兼容关系、能力、资源和评测；请求经认证后解析为具体 base+adapter+配置版本，再按已加载状态、队列、KV、区域和健康路由。基座常驻，LoRA 采用 GPU/CPU/磁盘分级缓存、热点预热和 adapter-aware batching，并限制租户数量、rank 与加载并发。灰度按用户/会话稳定哈希分桶，每阶段设质量、安全、延迟和成本门槛；回滚原子切回上一配置。所有缓存、trace 和契约测试都绑定完整版本，fallback 也必须满足能力与权限下限。
