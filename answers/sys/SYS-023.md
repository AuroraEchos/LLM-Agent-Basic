## 我的答案

Text-to-SQL 的生产目标不是生成“语法正确的 SQL”，而是用用户有权访问的数据回答正确的业务问题，并保证查询不会泄漏、修改或拖垮数据库。模型负责语义映射，**权限、SQL 语法树、资源预算和执行必须由确定性系统控制**。

### 架构

```text
Question/Auth → Intent + Semantic Layer → Schema Retrieval
              → Constrained SQL Generation → AST/Policy Validation
              → EXPLAIN / Sandbox Replica → Execute
              → Result Validation / Narrative + Lineage
```

### Schema 与语义检索

从 catalog 同步表/列、类型、PK/FK、注释、样例值的安全摘要、owner、新鲜度、行列权限和数据库 dialect。建立业务语义层：指标定义、粒度、默认过滤、同义词、时间口径和批准 join，避免模型自己猜“收入”“活跃用户”。DDL/注释也视作不可信数据，不能包含能改变系统指令的有效权限。

先识别实体、指标、维度、时间和过滤条件，混合检索相关表/列/指标；再沿 FK/语义 join graph 扩展少量邻居。只向模型提供用户可见、与问题相关的 Schema，不能把全库 DDL、PII 列名和样例行放进上下文。Schema snapshot 与问题一起版本化。

### 生成与静态验证

优先让模型输出结构化查询计划或受 grammar 约束的 SQL：选用指标、维度、过滤、join 和 limit，并显式列出假设。参数值与 SQL 结构分离，使用 prepared parameters。

服务端解析成 dialect-aware AST 并重新生成 SQL，拒绝无法解析或包含 DDL/DML、存储过程、任意函数、注释绕过、多语句和未授权 catalog。只允许 allowlist 表/列/join/function；强制租户/行级策略、列掩码、时间范围、聚合和行数上限。权限条件由数据库/策略层注入，绝不能让模型负责添加 `tenant_id`。

### 执行验证与限制

使用只读、短期、绑定用户/租户的数据库角色，在只读副本/仓库或隔离计算池执行。先 `EXPLAIN` 检查扫描分区/字节、join 规模、全表扫描和预计成本，超预算则拒绝、改写或请求缩小范围。设置 statement timeout、memory/slot、并发、返回行/字节、网络出站和费用上限；支持 cancel。

执行错误可把规范化错误和相关 Schema 返回模型有限修复，但每次仍完整验证，限制轮数。成功后检查结果是否为空/异常大、单位/时间粒度和聚合守恒；敏感小群体可设置最小聚合阈值。最终自然语言回答绑定 SQL digest、Schema/数据快照、使用列、行数和时间，并展示可审计查询或受控摘要。

### 正确性与安全评估

SQL exact match 不够，因为等价 SQL 很多。优先看受控数据库上的 execution accuracy、result equivalence、业务指标正确、权限零泄漏、危险查询拦截、执行成本和 P95。测试覆盖歧义问题、同名列、复杂 join、时间/时区、空值、重复行、Schema 变化、注入和超大扫描。

对歧义如“上个月收入”缺地区、币种或确认状态时，系统应追问或明确假设。高风险财务/运营决策可要求数据 owner 审核或只返回预览，不能用流畅解释掩盖错误 SQL。

### 面试简答版

我会先用业务语义层和 Schema catalog 识别指标、维度、时间与批准 join，只检索用户有权看到的相关 Schema。模型生成结构化计划/SQL，服务端解析 AST，限制为单条 SELECT、allowlist 表列函数、参数化值，并由数据库策略强制 tenant/RLS/列脱敏。执行前在只读副本做 EXPLAIN 成本检查，设置扫描、行数、时间、内存和并发上限；错误只能有限修复且重新验证。结果绑定 SQL、Schema 和数据版本。评估以执行结果等价、业务口径、权限零泄漏、危险查询拦截和成本为主，而不是 SQL 字符串完全匹配。
