## 我的答案

可靠 Agent 的关键不是让模型“更聪明地循环”，而是用**确定性编排器约束概率性的规划与工具提议**。模型可以决定候选下一步，但权限、状态转换、预算、重试和副作用必须由系统执行。

### 总体架构

```text
User → Gateway/Auth → Orchestrator / Durable State Machine
                         ├→ Planner / Replanner
                         ├→ Tool Registry + Policy Engine
                         ├→ Sandbox / Tool Workers
                         ├→ Validator / Human Approval
                         └→ State Store + Event Log + Trace
```

请求先被解析成 `goal、constraints、success_criteria、deadline、risk_level、budget`。规划器输出受 Schema 限制的 DAG 或短期步骤：依赖、所需工具、预期结果、验证方法与失败分支。不要一次生成几十步后盲目执行；采用“有限规划—执行—观察—验证—再规划”，且每轮都受最大步数、token、时间和费用约束。

### 工具与执行边界

工具注册表保存名称、版本、输入/输出 Schema、风险等级、幂等性、权限、超时、成本和副作用。模型只产生 `tool_name + typed_args`，执行器再做：

1. 从可信会话确定主体与租户，按 `subject-action-resource` 重新鉴权；
2. 校验 allowlist、JSON Schema、范围和业务前置条件；
3. 为写操作生成 idempotency key，必要时展示影响并审批；
4. 在隔离 worker 执行，规范化结果并标注来源、时间和可信等级；
5. 使用独立验证器判断步骤是否达成，而不是相信模型自称成功。

外部网页、邮件、文档和工具输出是数据，不得提升为系统指令。秘密由工具代理按需注入，不进入模型上下文；每个工具只拿短期最小权限凭据。

### 状态与恢复

状态拆成不可变事件历史和物化快照：任务/步骤状态、计划版本、工具请求及结果引用、预算、审批、产物 digest 和错误。状态机可用 `PENDING→READY→RUNNING→WAITING_APPROVAL/RETRYING→SUCCEEDED/FAILED/CANCELLED`。每次跃迁使用版本/CAS，防止重复 worker 同时提交。

大对象放对象存储，状态只放引用与哈希；敏感字段加密、脱敏和 TTL。checkpoint 位于已验证且副作用已提交的边界，进程重启后从历史恢复，不把模型隐藏推理当持久状态。

### 重试与失败处理

先分类错误：瞬时网络/限流可在剩余 deadline 内指数退避加抖动；参数/权限/安全错误不重试；模型格式错误可做一次受控修复；业务冲突需要重新规划或人工。重试必须有上限并扣预算。

读取通常可重试；写入需要幂等键、去重表或事务 outbox。多步事务采用 Saga/补偿，例如预订成功但付款失败时取消预订。补偿也可能失败，必须进入人工处理，不能声称通用 rollback。

### 沙箱与观测

代码、文件转换和浏览器自动化在一次性沙箱运行：非 root、只读基础镜像、临时文件系统、CPU/内存/进程/时间限制、默认无网络、出站 allowlist、seccomp/VM 级隔离。不同租户和任务不共享沙箱。

每个任务有 trace，span 覆盖规划、排队、模型、工具、验证、审批和重试；记录版本、参数脱敏摘要、授权理由、成本和状态转移。指标包括任务成功率、步骤成功/重试、人工率、循环/预算耗尽、越权拦截、P95 和每成功任务成本。固定任务集、故障注入和端到端 Harness 验证“结果与副作用”，而不只评价最终文本。

### 面试简答版

我会用持久化状态机包住模型：模型只输出受 Schema 约束的短期计划和工具提议，编排器负责依赖、预算、权限、状态和验证。工具注册表描述版本、Schema、风险与幂等性，每次调用都基于可信身份重新鉴权；写操作经审批和幂等键执行。状态采用事件历史+快照，checkpoint 只落在已验证边界；瞬时错误有限退避重试，业务错误重规划，多步副作用用 Saga 补偿。非可信代码进入默认断网、限资源、非 root 的一次性沙箱。Trace 覆盖规划到副作用，并用故障注入和任务 Harness 评估真实成功率。
