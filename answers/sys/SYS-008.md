## 我的答案

亿级文档往往对应数亿到数十亿 chunk。设计重点是**稳定的数据主键、可水平分片的多索引、增量变更日志和可无停机重建**，而不是只选择某种 ANN 算法。

### 数据与索引架构

```text
Sources → CDC/Event Log → Raw Object Store (SSOT)
                   │
            Parse/Chunk/Enrich
                   │
         ┌─────────┴─────────┐
         ▼                   ▼
  Inverted/Sparse Index   Vector ANN Index
         └─────────┬─────────┘
                   ▼
          Metadata/ACL Store + Query Gateway
```

对象存储保存原始文件和解析制品；事件日志是增量更新与重放来源。每个 chunk 具有稳定 `(tenant_id, document_id, chunk_id, version)`、内容哈希、语言、时间、来源、ACL 和 tombstone。解析与 embedding 任务以版本+哈希幂等，重复事件不会生成重复记录。

稀疏索引负责精确实体、编号和关键词，向量索引负责语义召回。元数据和 ACL 尽量进入两类索引的可过滤字段，避免检索后才权限过滤。原文/大字段留在对象存储或文档存储，搜索节点只放召回所需数据和引用指针。

### 分片与容量

优先按 tenant/地域/语言或稳定哈希分片，在数据局部性、热点均衡和 ACL 隔离间权衡；超大租户再二级哈希。查询路由先裁剪目标分片，不能每次 fan-out 全集。每个 shard 有副本，协调器并行召回局部 top-k，再全局融合与重排。

向量索引选择由召回、内存、写入和时延决定：HNSW 通常低延迟、召回高但内存与构建成本大；IVF/PQ 等压缩方案更省内存，需训练量化器并接受召回损失。可以热数据用高召回索引、冷数据用压缩/磁盘层。容量估算至少包含：

$$
Storage_{vec}\approx N\times d\times bytes\_per\_dim + ANN\ overhead + replicas
$$

实际还要加倒排、元数据、构建峰值和 30% 左右运行余量，并用真实向量压测。

### 混合检索

查询解析后并行执行 BM25、向量 kNN，必要时加实体/规则召回。由于各路分数尺度不同，可用 RRF：

$$
RRF(d)=\sum_j\frac{w_j}{k+rank_j(d)}
$$

融合后去重，按权威性、时效和 ACL 过滤，再对有限候选使用 cross-encoder rerank。没有标注数据时 RRF 是稳健起点；有足够点击/相关性数据后可训练 LTR，但要防位置偏差。

### 增量更新与重建

CDC 事件含 source version、operation 和 event id。更新采用新版本 upsert，再让 alias/可见版本原子前移；删除写 tombstone，查询立即屏蔽，后台异步从所有索引、缓存和副本物理清除。乱序事件按源版本拒绝旧写，失败进入 DLQ 并可从事件日志重放。

embedding、分词器或 chunk 策略变化不能在同一向量空间原地更新。创建 `index_v2`，从 SSOT/日志回填，期间双写新变更；校验文档数、抽样一致性、Recall、权限和延迟后原子切读 alias，再观察并延迟回收旧索引。这样支持零停机升级和快速回滚。

### 可用性与评估

对搜索、embedding、事件消费分别做背压和熔断；单 shard 超时可返回标记为 partial 的结果，高风险问答则拒绝使用不完整证据。监控索引滞后、DLQ、tombstone SLA、shard 热点、fan-out、Recall@k、P95、缓存命中、权限漏检和每查询成本。定期做带时间、精确实体、多语言和权限条件的真实查询评测。

### 面试简答版

亿级知识库以对象存储为 SSOT、CDC 日志驱动增量索引，chunk 使用稳定 ID、版本、内容哈希、ACL 和 tombstone。稀疏倒排与向量 ANN 分开水平分片，查询先按租户/地域裁剪 shard，再并行 BM25 和向量召回，用 RRF 融合并重排。HNSW 与 IVF/PQ 按召回、内存和写入成本选择，热冷数据可分层。更新通过幂等 upsert、源版本防乱序；删除先逻辑屏蔽再物理清除。embedding 或切块升级时新建索引、回填+双写、校验后原子切 alias，保留旧版回滚。
