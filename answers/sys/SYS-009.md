## 我的答案

客服系统的目标不是尽可能自动回复，而是在可验证范围内提高一次解决率，同时确保**政策回答有出处、账户操作有授权、低置信或高风险问题无损转人工**。

### 核心链路

```text
Channel → Identity/Consent → Intent & Risk Router
              ├→ FAQ/Policy RAG ─┐
              ├→ Account Tools ──┼→ Evidence-bound Answer
              └→ Workflow Engine ┘       │
                                   Citation/Policy Guard
                                          │
                                   Reply or Human Handoff
```

入口统一 Web、App、IM 与电话转写，完成认证、语言识别、会话绑定、限流和 PII 处理。路由器区分公开 FAQ、需登录的订单/账单、投诉、退款等业务流程及安全风险。模型只负责理解和表达，订单状态、退款资格等事实必须来自当前 API 或版本化政策，不能靠参数记忆猜测。

### 检索、工具与引用

政策文档按产品、地区、渠道、生效时间、版本和权限切块，使用关键词+向量混合召回、重排和时效过滤。账户工具从可信会话获取 customer/tenant id，后端逐次鉴权，输出最小必要字段；模型不能自行传入另一个用户身份。

上下文中的每个证据分配 `source_id`。模型生成答案及引用 ID，服务端映射成文档标题、版本、生效日期和可访问链接；对“退款需 7 天内”这类主张做 claim-evidence 支持检查。用户无权访问的内部操作手册可以用于约束流程，但不能生成可点击引用或泄露原文；面向用户应引用公开政策或给出可解释的政策摘要。

当政策与账户数据冲突、证据过期或无召回时，系统明确说明无法确认并进入澄清/人工流程，而不是混合多个版本拼答案。

### 转人工设计

触发条件包括：用户主动要求、身份验证失败、多轮未解决、低证据/冲突、模型或工具异常、投诉升级、敏感群体、高金额/法律/安全风险。阈值按风险等级校准，并监控过度转接。

Handoff package 包含用户授权范围内的会话摘要、原始关键诉求、已验证身份、已尝试步骤、工具结果、引用、失败/转接理由和建议下一步；所有字段有 provenance，人能跳回受控原始 trace。不要只给一段模型自由摘要，以免遗漏或编造。转接使用统一 case id，队列按技能、语言和优先级路由；机器人停止重复回复，人工接管和再交还都有明确状态。

### 安全与可靠性

外部用户文本和知识文档都视作不可信数据，工具使用最小权限，退款、修改地址、发送信息等写操作由状态机验证前置条件，展示关键参数并确认，使用幂等键和审计。输出做 PII/DLP、内容安全、Schema 和引用审核。

依赖故障时采用风险感知降级：公开 FAQ 可使用缓存的最新有效政策并标明版本；账户事实 API 不可用时不猜测，建立工单或转人工。会话、Prompt、模型、政策和工具版本写入 trace，支持回放与复盘。

### 评估指标

离线覆盖 FAQ、账户流程、无答案、政策变更、注入、多语言和转人工边界，评估 Recall@k、答案正确/忠实、引用 precision/coverage、工具/流程成功和 PII 零泄漏。线上看一次解决率、复联率、转人工率及人工推翻率、平均处理时间、CSAT、投诉、成本；不能只用机器人拦截率，因为强行不转人工会让该指标虚高。

### 面试简答版

我会先认证和识别意图，将公开政策问题走带时间/地区过滤的混合 RAG，账户事实走重新鉴权的业务 API，退款等操作走确定性工作流。模型只做理解与表达，每个事实绑定 source ID，服务端映射到用户有权访问的政策版本并检查引用支持。证据缺失、冲突、多轮未解决、工具异常或高风险时转人工，同时传递结构化 handoff package：身份、诉求、已尝试步骤、工具结果、引用和转接原因。写操作采用最小权限、确认和幂等。指标以一次解决率、引用正确、人工推翻、CSAT 和安全为主，而不是只追求机器人拦截率。
