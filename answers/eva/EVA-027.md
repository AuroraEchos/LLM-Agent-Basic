> **问题：** Trace、Metric 和 Log 在 LLM 应用可观测性中的分工是什么？

> **分类：** 评估、安全与可观测性

## 我的答案

三者分别回答不同问题：**Metric 告诉我是否普遍异常，Trace 告诉我一条请求在哪一步异常，Log 告诉我该步骤当时记录了什么事件。**它们通过统一的服务、版本、`trace_id` 等上下文关联，而不是互相替代。

| 信号 | 数据形态 | 适合回答 | LLM 应用示例 |
|---|---|---|---|
| Metric | 聚合时间序列 | 系统整体是否异常、趋势和 SLO | QPS、成功率、P95 延迟、token/请求、拒答率、每成功任务成本 |
| Trace | 一次请求的 span 因果树/DAG | 慢或错发生在哪一跳、调用关系是什么 | 网关→模型→检索→重排→模型→工具→验证器，每步耗时、版本和状态 |
| Log | 带时间和上下文的离散事件 | 具体发生了什么、为何做出某决策 | 授权拒绝理由、Schema 错误、工具重试、策略命中、脱敏异常摘要 |

### Metric：发现与报警

Metric 成本低、适合长期聚合，用于 SLI/SLO、容量规划和异常报警。需要按模型、任务、区域、语言、状态等有限维度切片，但要控制标签基数：完整 Prompt、用户 ID、文档 ID 不能成为 label。它能发现“RAG 无结果率从 2% 升到 15%”，却不能单独重建某个失败请求。

### Trace：端到端归因

每个请求生成 `trace_id`，每个模型、检索、工具、Guardrail 和人工升级形成 span，记录父子关系、开始/结束时间、状态、模型/Prompt/索引/工具版本、token 和调用结果摘要。Agent 有并行工具或循环时，Trace 能显示 DAG、关键路径和预算消耗。

Trace 应支持从异常 metric 的 exemplar 跳到具体样本。采样可采用“正常低比例 + 错误/高延迟/高风险全量或高比例”的 tail-based 策略，但敏感内容仍须脱敏和受控存储。

### Log：局部证据和审计

Log 应采用结构化字段，而不是自由文本拼接。记录状态变化、异常栈、策略理由码、授权主体、参数摘要和审批结果；通过 `trace_id`、`span_id` 与 Trace 关联。安全审计日志需防篡改、单独授权；API Key、Cookie、Authorization Header、完整 PII 和思维过程不应进入普通日志。

### 联动示例

告警发现“每成功任务成本”异常（Metric）→ 跳转高成本 exemplar（Trace）→ 看到 Agent 在检索与工具间循环 9 次 → 检查对应事件（Log），发现工具一直返回可重试错误而状态机未扣减预算。修复后，再由 Metric 验证成本恢复，并把该 Trace 转成回归测试。

因此设计时要统一语义约定、时间戳、版本字段和传播上下文，同时设置采样、保留期与访问等级。缺少 Metric 会看不见全局，缺少 Trace 难以跨服务归因，缺少 Log 则缺乏局部错误和安全决策证据。

### 面试简答版

Metric 是聚合时间序列，用来监控 SLO、发现趋势和报警；Trace 描述单次请求跨模型、RAG、工具和验证器的调用因果链，用来定位瓶颈与失败步骤；Log 则记录某一步的结构化事件、错误和授权理由。三者通过 `trace_id/span_id` 与版本字段关联：从异常 Metric 的 exemplar 跳到 Trace，再查具体 Log。实现上要控制 Metric 高基数，对 Trace 采用风险/错误优先采样，并对所有信号做脱敏、分级访问和保留期管理。
