## 我的答案

模型升级本质上是一个可能改变概率行为、接口契约、成本和安全边界的依赖升级，不能把 API 返回 200 当成兼容。策略应是：**先定义兼容契约，离线与影子验证，再按风险灰度，并保证配置级快速回滚。**

### 1. 定义兼容性

至少覆盖四类契约：

- **接口兼容**：上下文长度、tokenizer、角色/多模态格式、tool calling、JSON Schema、停止条件、错误码、流式事件和速率限制；
- **行为兼容**：核心任务成功、指令遵循、事实/忠实度、引用、语言、拒答和输出风格；
- **安全兼容**：越狱、注入、PII、工具越权、过度拒答，以及不同群体/语言的最差切片；
- **非功能兼容**：P50/P95 延迟、吞吐、token、每成功任务成本、可用性和可观测字段。

把 Prompt、模型、采样参数、路由、Guardrail、索引、工具 Schema 作为一个版本化配置包测试。新模型往往需要重新调 Prompt 和阈值，但必须区分“只换模型”的影响与配套优化后的整体收益。

### 2. 发布前验证

运行固定 golden set、安全回归、历史 Bad Case、工具契约测试和代表性线上重放。对旧、新版本做盲测或成对比较，既看平均值，也看不可接受的单项回退。结构输出、权限和金额等硬约束必须由确定性测试通过。

随后做 shadow traffic：复制经授权/脱敏的真实请求给新版本，但禁止其产生真实写操作；比较回答质量、工具提议、延迟和成本。注意影子结果缺少真实用户反馈，不能替代灰度。

### 3. 分阶段灰度

先内部与测试租户，再选择低风险、可回滚的 1% 左右流量，逐步到更大比例；按**稳定用户或会话哈希**分桶，防止同一会话来回切模型。高风险场景和自动写操作最后开放，并独立审批。

每一阶段设置观察窗口和自动停止条件，例如严重安全事件、任务成功率下降、P95 超标、Schema/工具失败或单位成功成本增长。指标按任务、语言、租户和长上下文切片，避免总体平均掩盖关键群体退化。

### 4. 回滚与兼容兜底

- 保留旧模型和完整配置包可用，通过 feature flag/路由开关在分钟级切回；不要在灰度期间同时移除旧 Prompt 和工具适配器。
- 对会话状态、缓存、embedding 和结构输出设置版本字段；跨版本恢复时提供兼容适配或固定会话版本。
- 数据库写入、邮件和付款等不可逆副作用不能靠“模型回滚”撤销，应使用幂等键、事务、延迟提交和补偿操作。
- 回滚后冻结故障版本、保留脱敏 trace，确认指标恢复，再做根因分析和回归补充；避免反复自动切换形成振荡。

发布决策应有清晰 owner、审批和变更记录。供应商强制下线旧模型时，要提前维护替代模型、兼容测试和容量预案，不能等到停服当天再迁移。

### 面试简答版

模型升级先定义接口、行为、安全和非功能四类兼容契约，把模型、Prompt、阈值、索引和工具 Schema 作为版本化配置包。上线前跑 golden set、历史 Bad Case、安全与工具契约，再做禁止真实副作用的 shadow。灰度按稳定用户/会话分桶，从内部和低风险流量逐级扩大，每阶段都有任务成功、安全、P95 和单位成功成本的停止线。旧模型及配置通过 feature flag 保留，状态和缓存带版本；不可逆动作另用事务、幂等和补偿保护，不能指望模型回滚消除已发生的副作用。
