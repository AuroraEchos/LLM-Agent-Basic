## 我的答案

这些方法针对的是不同失效模式，没有一种方法能单独消除幻觉。先定位错误来源，再组合控制手段，通常比盲目“加 RAG”更有效。

| 方法 | 主要缓解的问题 | 关键局限 |
|---|---|---|
| RAG | 缺少私域、长尾、时效知识造成的事实错误；为回答提供可引用证据 | 检索遗漏、召回错误、文档过期或模型忽略证据时仍会失败；外部文档还可能包含间接 Prompt Injection |
| 微调 | 输出风格、领域术语、固定流程、指令遵循和拒答行为不稳定 | 不适合作为频繁更新的事实数据库；错误训练数据会固化幻觉，模型也不保证逐条复现知识 |
| 验证器 | 可判定的数学、代码、结构、业务规则、引用和部分事实错误 | 只能覆盖可验证部分；验证器自身可能误判、被规避或与生成器犯相关错误 |
| 自洽性 | 随机采样导致的推理波动、偶发路径错误 | 多个样本可能共享同一错误认知；成本增加，开放式问题也不容易可靠投票 |
| 拒答机制 | 证据不足、超出知识边界、高风险且不确定的回答 | 阈值太低会乱答，太高会过度拒答；它降低风险但不增加知识 |

### 分类型选择方法

- **外部事实错误**：优先使用高质量 RAG 或权威工具，再由事实/引用验证器把关；证据不足时拒答或明确不确定性。
- **上下文不忠实**：要求逐主张绑定证据，并做蕴含校验。RAG 只负责“给材料”，不能保证生成器真的使用材料。
- **推理或计算错误**：使用计算器、代码执行、约束求解等确定性工具；无法直接验证时，再考虑自洽性或独立模型复核。
- **格式和流程违规**：微调可改善行为习惯，但线上仍应使用 JSON Schema、状态机、参数校验和权限门禁。
- **高风险未知问题**：基于校准后的置信度、证据质量和风险等级触发澄清、转人工或拒答。

### 推荐的组合链路

一个常见的生产链路是：

$$
\text{问题}\rightarrow\text{风险分类}\rightarrow\text{检索/工具}\rightarrow
\text{带证据生成}\rightarrow\text{验证}\rightarrow
\begin{cases}
\text{通过并回答}\cr
\text{修正或重试}\cr
\text{澄清、拒答或转人工}
\end{cases}
$$

例如客服问“我这笔订单能否退款”：RAG 检索当前政策，业务 API 查询真实订单，模型负责解释，规则引擎验证退款条件；若订单状态缺失，则请求补充信息，而不是让模型猜测。

落地时还应注意三点：

1. **验证器应尽量异构**：不要只让同一个模型评价自己的答案；能用数据库、编译器、Schema 和权限系统，就不用模糊的语言判断。
2. **重试必须有新信息**：原样重试通常只是增加成本。应更换查询、补充证据、调用工具或升级验证强度。
3. **同时评估安全与可用性**：除了幻觉率，还要看检索覆盖率、引用正确率、过度拒答率、延迟和成本。

### 面试简答版

RAG 主要补充时效和私域事实，微调主要改善行为、风格和指令遵循，验证器适合拦截可判定的事实、代码、结构和业务规则错误，自洽性减少偶发推理波动，拒答机制则控制证据不足时的风险。它们都不是万能的：RAG 会检索错，微调不能可靠充当知识库，多个样本也可能一致地错。我通常采用“检索或工具提供证据—模型生成—异构验证—不通过则修正、澄清或拒答”的分层方案，并同时监控正确率和过度拒答率。
