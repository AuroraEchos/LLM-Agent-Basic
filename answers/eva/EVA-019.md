## 我的答案

这三类问题本质上都是：系统把模型生成的“不可信动作建议”误当成了可信授权或可直接执行的参数。

- **权限提升**：低权限用户通过 Agent 获得本不具备的工具、数据或操作能力。
- **参数注入**：模型产生的路径、URL、SQL、命令、收件人或自由文本逃逸预期数据位置，改变了执行语义。
- **Confused Deputy（困惑代理）**：拥有高权限的 Agent/工具没有正确区分“谁请求、替谁操作、作用于什么资源”，于是替攻击者滥用了自己的权限。

### 防护设计

1. **端到端传播可信身份**：用户、租户、会话、委托范围来自认证系统，并作为不可由模型覆盖的结构化上下文传递。不要让模型自己填写 `tenant_id`、`role=admin` 等授权字段。
2. **每次调用重新鉴权**：策略引擎根据主体（subject）、动作（action）、资源（resource）和环境（context）判断：

   $$
   \operatorname{allow}=Policy(subject, action, resource, context)
   $$

   工具能被模型看到不等于用户有权调用，前序读取成功也不代表后续写入获权。
3. **最小权限和能力令牌**：按任务只暴露必要工具，使用短期、限定资源与动作的凭据；读写工具分离，默认只读，网络目标采用 allowlist。避免把全局管理员令牌放进 Agent 进程或上下文。
4. **强类型工具接口**：参数使用 JSON Schema/枚举/范围限制；服务端重新获取关键字段。不要把自由文本拼接到 shell、SQL、URL、HTML 或路径中，应使用参数化 API、规范化路径和固定模板。
5. **防 SSRF 与路径逃逸**：解析 URL 后检查 scheme、DNS/IP、重定向每一跳和目标网络；路径在规范化后验证仍处于允许根目录。仅靠字符串前缀检查不够。
6. **绑定意图与确认**：高风险动作展示对象、数量、目标和影响，用户确认时对规范化参数及身份生成摘要或签名；执行端校验一致，防止确认后参数被替换。
7. **事务与损害限制**：采用 dry-run、额度上限、幂等键、可撤销队列、双人审批和速率限制。发送、转账、删除等操作不要在模型第一次提议时立即提交。
8. **审计与检测**：记录主体、授权决策、工具版本、参数摘要、数据来源、确认和结果；秘密和 PII 脱敏。对跨租户访问、罕见工具链和大量失败尝试告警。

### 一个典型错误与改法

错误接口是 `delete_file(path: string)`，Agent 持有整个文件系统权限，模型可从文档中接收任意路径。更安全的接口是 `delete_document(document_id)`：服务端用可信会话查找该 ID，验证文档属于当前租户，将其移动到可恢复的回收站，返回变更预览，用户确认后才提交。模型从未获得真实路径，也不能改变租户。

测试时要覆盖跨租户 ID、角色伪造、批量范围扩大、命令/SQL 元字符、路径穿越、URL 重定向、确认后换参、重复提交，以及从外部文档触发这些调用。成功标准应看后端是否发生未授权副作用，而不只是模型是否生成了调用 JSON。

### 面试简答版

防止权限提升和 Confused Deputy 的关键是：模型只提议动作，后端依据可信认证上下文，对每次“主体—动作—资源”重新鉴权，绝不信任模型传来的用户、租户或角色。工具采用最小权限、短期能力令牌和强类型 Schema，关键参数服务端绑定；SQL、命令、URL 和路径使用参数化 API 与规范化校验。高风险写操作要预览、确认并绑定参数摘要，再配合额度、幂等、可撤销和审计。评测最终看是否发生真实越权或副作用，而不是模型是否尝试调用。
