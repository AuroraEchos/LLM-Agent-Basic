> **问题：** System Prompt 为什么不能被视为真正的安全边界？
>

## 我的答案

System Prompt 是影响模型行为的高优先级上下文，但不是强制执行的访问控制机制，因此只能作为**行为引导层**，不能被视为真正的安全边界。

### 原因

1. **同一概率模型处理所有文本**：系统指令、用户输入和外部文档最终都进入模型上下文。角色标签提供训练出的优先级倾向，却不像进程隔离或数据库 ACL 那样具有确定性强制执行。
2. **自然语言规则存在歧义与组合漏洞**：指令可能冲突、遗漏边界条件，长上下文中也可能被稀释。攻击者可利用多轮、混淆、跨语言或间接内容改变模型行为。
3. **模型没有真正的授权事实来源**：它可能声称用户是管理员、编造资源标识或错误理解“只读”。如果工具层相信这段文本，就形成权限提升。
4. **提示内容可能被推断或泄漏**：隐藏不是访问控制。即使系统提示未逐字泄漏，攻击者仍可通过行为探测推测规则；其中不应放 API Key、密码或必须保密的安全逻辑。
5. **模型与配置会变化**：模型版本、温度、上下文裁剪和新工具都会改变遵循概率，无法提供可证明的安全不变量。

一个简单判断标准是：如果模型完全忽略 System Prompt 后，用户就能读取秘密、跨租户访问或执行危险动作，那么架构已经把安全职责放错了位置。

### System Prompt 应该做什么

它仍然很有价值，适合定义角色、任务边界、回答风格、何时澄清、何时请求工具和如何处理不可信内容。它能降低攻击成功率、改善用户体验，也为审计提供清晰的预期行为，但不应承载以下职责：

- 身份认证和授权；
- 租户、行列级数据隔离；
- 密钥保密；
- 工具参数和业务约束验证；
- 资金、删除、发布等副作用的最终批准。

### 真正的安全边界

这些约束应由模型外的确定性组件执行：身份由认证会话绑定；授权由策略引擎和数据层 ACL 判断；秘密存储在密钥管理系统中，只给具体工具短期最小权限凭据；工具调用通过 allowlist、JSON Schema 和业务规则验证；高风险写操作使用预览、确认、幂等键与审计；输出进入不同下游上下文前做转义、DLP 和内容审核。

例如提示词可以写“只能查询当前用户订单”，但工具必须从可信会话获取 `user_id`，而不是让模型传入任意用户 ID；SQL 查询也必须在数据层强制租户条件。这样即使模型被注入，最多生成一个被拒绝的调用提议。

### 面试简答版

System Prompt 是概率性的行为引导，不是确定性的安全边界。所有上下文最终都由同一模型解释，可能受冲突指令、长上下文、间接注入和版本变化影响；隐藏提示也不等于保密。因此它适合描述角色、任务和拒答策略，但认证、租户隔离、工具授权、参数校验、密钥保护和高风险审批必须在模型外完成。我的判断标准是：即使模型完全忽略 System Prompt，后端权限与数据边界仍应阻止泄漏和越权。
