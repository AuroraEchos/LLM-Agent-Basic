## 我的答案

三者切分的对象不同：**Data Parallel（DP）切请求，Expert Parallel（EP）切 MoE 专家，Context Parallel（CP）切同一请求的序列上下文**。它们分别解决吞吐扩展、MoE 权重与计算扩展、超长上下文扩展问题。

### 一、Data Parallel：复制模型，分发独立请求

每个 DP replica 持有完整模型，路由器把不同请求或 batch 发给不同副本。常规 Dense 模型在线推理时，各副本之间通常不需要为一次前向做梯度同步，因此通信主要发生在负载均衡、指标汇总或权重更新，而不是模型计算路径。

收益：

- 吞吐接近随副本数水平扩展，故障隔离和弹性伸缩简单；
- 每个副本有独立 KV Cache，可独立调度连续批处理；
- 适合模型已能装入一个 TP/PP 实例，但整体流量很大的场景。

边界：模型权重会重复占显存；某会话的 KV Cache 通常只在一个副本中，所以需要 session affinity 或 prefix-aware routing，否则迁移请求会丢失缓存收益。在线 DP 也不是训练中的“梯度 All-Reduce”。

### 二、Expert Parallel：分散 MoE 专家

MoE 层有很多专家，但每个 token 通常只激活 Top-k 个。EP 将不同专家放在不同 GPU 上：路由器确定专家后，先用 All-to-All 把 token 发到专家所在卡，专家计算完再用 All-to-All 把结果送回原位置。

若第 \(i\) 个 token 的路由集合为 \(G(x_i)\)，MoE 输出可写为：

\[
y_i=\sum_{e\in G(x_i)}g_{i,e}E_e(x_i)
\]

收益是不用在每卡复制全部专家权重，并能并行执行专家计算；问题是 token 路由不均会形成热点，且 Decode 小 batch 时 All-to-All 的通信延迟可能压过计算。工程上需要 capacity 控制、负载均衡损失、专家复制、分层 All-to-All 或 DP+EP 组合。

### 三、Context Parallel：切分同一条长序列

CP 沿 sequence 维把一个请求的 token 或 KV 状态分到多张卡，使单卡不必保存全部长上下文，并让长序列 Attention 计算并行化。不同实现可能采用 Ring Attention、All-Gather KV、分块 Attention 或序列并行。

直观上，原本单层 KV Cache 约为：

\[
M_{KV}=2Tn_{kv}d_hb
\]

其中 \(T\) 是上下文长度，\(n_{kv}\) 是 KV 头数，\(d_h\) 是头维度，\(b\) 是每元素字节数。理想切到 \(c\) 个 CP rank 后，每卡持有量约降为 \(M_{KV}/c\)，但计算 Attention 时必须交换 K/V 分块或部分统计量。

CP 主要用于单请求上下文极长、单卡 KV 放不下，或者长 Prefill 延迟过高的情况。短上下文和 Decode 阶段常会因通信与同步开销得不偿失。

### 四、如何组合

一个大型 MoE 服务可能采用：

```text
DP：多个服务副本，切总体请求流量
└── CP/TP：副本内部切长上下文和稠密 Attention
    └── EP：在 MoE 层切专家
```

但并行度不是越大越好。总 GPU 数近似满足某些并行维度的乘积，而每增加一维都会引入新的通信组、调度约束和故障面。需要用真实的输入长度、输出长度、并发、专家负载和网络拓扑压测。

### 五、选型口诀

- **模型能放下、请求很多**：优先增加 DP replica。
- **MoE 专家权重放不下或需要扩展专家吞吐**：使用 EP，并重点观察 All-to-All 和专家负载偏斜。
- **单条上下文太长，KV 或 Attention 成为瓶颈**：考虑 CP，并评估通信是否抵消收益。

### 面试简答版

DP 复制完整模型并把独立请求分给不同副本，主要扩总吞吐和可用性，在线推理通常不需要训练式梯度同步，但要处理会话与前缀缓存亲和性。EP 把 MoE 专家分散到不同 GPU，token 经两次 All-to-All 完成 dispatch 和 combine，节省专家权重显存，但容易受通信和负载偏斜影响。CP 沿序列切同一请求的上下文或 KV Cache，用于超长上下文，能降低每卡 KV 占用，但需要交换 KV 分块或 Attention 统计量。三者分别切请求、专家和序列，生产中可以组合使用。
