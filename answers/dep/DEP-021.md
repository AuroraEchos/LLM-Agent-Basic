## 我的答案

部署方案不是先选框架，而是先定义目标函数和硬约束。吞吐、延迟和成本通常存在 Pareto trade-off：增大 batch 往往提高吞吐和降低单位成本，却可能增加排队时间；为低延迟预留大量空闲容量，则会提高成本。

### 一、先统一指标

- **吞吐**：requests/s、input tokens/s、output tokens/s，以及更有意义的 goodput——在 SLO 内完成的请求数。
- **延迟**：TTFT、TPOT/ITL、端到端延迟的 P50/P95/P99，不能只看平均值。
- **成本**：GPU-hour、每百万 input/output token 成本、每个成功请求成本，也要包含 CPU、内存、网络、存储和空闲冗余。
- **质量约束**：量化后任务指标、最大上下文、生成策略与可用性不能因优化而跌破底线。

### 二、吞吐优先

适合离线生成、批量评测、数据合成或可容忍排队的异步任务。

典型方案是：

- 连续批处理并提高 `max_num_seqs`、token budget，让 GEMM 尺寸更大；
- 允许适当排队形成 batch，采用 chunked prefill 混合不同长度请求；
- 用足够的 DP replicas 扩总吞吐，模型过大时再在副本内 TP/PP；
- 开启高命中率的 prefix cache、投机解码和适合硬件的低精度；
- 调度上优先提高 GPU 有效计算占比，但设置最大等待时间防止饿死。

主要观察稳态 tokens/s/GPU 和 goodput，而不是单请求最低延迟。batch 继续增大到显存紧张或排队使 SLO 违约时就应停止。

### 三、延迟优先

适合实时对话、代码补全、语音交互和强 P99 SLO。

典型方案是：

- 控制 batch 上限和排队时间，为高优先级流量保留容量；
- 模型能单卡放下就避免不必要的跨卡通信；模型较大时用低延迟互联和合适 TP；
- 使用 CUDA Graph、融合 kernel、prefix cache、投机解码，分别优化固定开销和生成步数；
- 用短请求/长请求分池、chunked prefill 或 P/D 分离减少长 Prompt 对 Decode 的干扰；
- 做 admission control，过载时拒绝、排队或降级，而不是让所有请求一起进入延迟雪崩。

延迟优先通常需要较低目标利用率和更多副本冗余。重点看 TTFT、TPOT 和 P99，而不能用高 GPU 利用率作为唯一目标。

### 四、成本优先

成本优先的正确含义是：**在质量、可用性和 SLO 约束下最小化总成本**，不是简单买最便宜 GPU。

可以采用：

- 量化、蒸馏或更小但能力达标的模型，减少权重带宽和 GPU 数；
- 按工作负载选择 GPU，而不是只看峰值 FLOPS；比较 tokens/s/元和显存容量；
- 稳态基线用保留资源，弹性流量用按需/可抢占资源，异步任务可容忍中断；
- 自动扩缩容、请求分级、模型路由：简单问题走小模型，困难请求升级到大模型；
- 缓存重复结果和公共前缀，批量处理非交互任务；
- 让实例运行在单位成本最优的 batch 区间，但保留足够 SLO 余量。

低价卡若需要更多卡、跨卡通信或更高运维成本，总拥有成本反而可能更高。

### 五、一个实用决策表

| 目标 | 调度倾向 | 容量水位 | 常见并行策略 | 最重要的验收指标 |
|---|---|---|---|---|
| 吞吐优先 | 大 batch、可等待 | 高利用率 | DP 扩流量，必要时 TP/PP | goodput、tokens/s/GPU |
| 延迟优先 | 小 batch、短排队、优先级 | 保留冗余 | 尽量少通信，必要时低延迟 TP | TTFT、TPOT、P99 |
| 成本优先 | SLO 内尽量聚合 | 动态扩缩 | 量化/小模型/模型路由 | 元/百万 token、总拥有成本 |

同一个服务常常要做分层：交互流量进入延迟池，批量任务进入吞吐池，低优先级流量使用廉价弹性容量。这样比用一套参数同时满足所有请求更可控。

### 面试简答版

我先定义质量和 SLO，再决定优化目标。吞吐优先会允许排队并扩大连续 batch，用 DP 扩总流量，关注满足 SLO 的 tokens/s/GPU；延迟优先会限制 batch 和排队、保留容量、减少跨卡通信，并用 prefix cache、CUDA Graph、chunked prefill 或 P/D 分离优化 TTFT、TPOT 和 P99；成本优先是在 SLO 下通过量化、小模型路由、合适硬件和弹性扩缩容降低每百万 token 总成本。三者不能只看一个数字，生产中通常按交互、批量和低优先级流量分池。
