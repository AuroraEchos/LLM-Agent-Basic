## 我的答案

容量规划的目标不是算一个“理论 tokens/s”，而是回答：在真实峰值流量、长度分布和 SLO 下，需要多少实例，并预留多少故障与增长余量，其总成本是多少。

### 一、建立工作负载画像

至少从生产日志提取：

- requests/s 的均值、P95、峰值、突发持续时间和日周期；
- input/output token 的联合分布，而不只看各自平均值；
- 模型、LoRA、租户、优先级、采样参数与并发分布；
- prefix 重复率、cache 命中率、取消率和流式连接时长；
- TTFT、TPOT、E2E P99、可用性和质量约束。

输入和输出 token 的成本不对称：Prefill 可并行处理输入，Decode 必须逐 token 迭代。只用“总 token 数”会掩盖 P/D 比例变化。

### 二、先做显存可行性估算

粗略显存账本为：

\[
M_{GPU}\ge M_{weights}+M_{KV}+M_{workspace}+M_{runtime}+M_{margin}
\]

其中权重可按参数量乘实际 bits-per-weight 估算，KV 则与层数、并发序列的当前长度、KV heads、head dim 和 dtype 有关。量化 scale、CUDA Graph buffer、通信 workspace 和碎片都要计入，不能把卡的标称显存全部用于权重与 KV。

先由此确定单副本是单卡还是 TP/PP/EP，以及最大上下文和并发上限。能装下不代表满足性能 SLO，后续仍需压测。

### 三、设计可复现的压测

压测请求应重放真实的二维输入/输出长度、到达过程和热门前缀；固定输出文本会受 EOS 和采样影响，可用实际数据或可控 synthetic tokens。至少覆盖：

1. 单请求基线：测最低 TTFT/TPOT 和冷启动；
2. 逐级加压：画 offered load 与 goodput、P50/P99、队列长度曲线；
3. 稳态峰值：持续足够久，包含 cache 达稳和热平衡；
4. 突发与长尾：短时间倍增流量、混入超长 Prompt/输出；
5. 故障场景：少一个副本、节点重启、扩容预热、网络降速；
6. 多租户噪声：高优先级与批量任务同时到达。

报告框架版本、模型、精度、GPU、功耗、并行度、batch/token budget、上下文和所有 cache 设置，保证结果可复现。最大吞吐点若 P99 已违约，不能作为服务容量。

### 四、从压测换算实例数

设峰值到达率为 \(\lambda_{peak}\)，单副本在 SLO 内的安全服务率为 \(\mu_{safe}\)，则基础副本数可估为：

\[
N_{base}=\left\lceil\frac{\lambda_{peak}}{\mu_{safe}}\right\rceil
\]

这里的 \(\mu_{safe}\) 应取压测中满足 TTFT/TPOT/P99 的 goodput，而非 OOM 前的最大吞吐。再加入增长、流量预测误差、扩容时延和 N+1/N+zone 故障余量：

\[
N_{plan}=\max(N_{base}+N_{failure},\lceil N_{base}(1+r_{growth}+r_{burst})\rceil)
\]

也可用 Little 定律做交叉检查：

\[
L=\lambda W
\]

若到达率 \(\lambda=20\) req/s、平均系统时间 \(W=5\) s，系统平均会有约 100 个在途请求；它们的 KV 能否装下必须单独验证。排队系统接近饱和时尾延迟会非线性上升，因此不能按理论 100% 利用率规划。

P/D 分离时应分别按每秒 input tokens 和 output tokens 规划两个池，并验证 KV 网络带宽；多模型还要考虑低流量模型无法共享 batch 的碎片化容量。

### 五、成本核算

月度基础设施成本可写为：

\[
C_{month}=\sum_j N_j(C_{GPU,j}+C_{CPU,j}+C_{mem,j}+C_{storage,j}+C_{network,j})\cdot H + C_{ops}
\]

其中 \(H\) 为计费小时，`ops` 包含运维、人力、监控和故障损失。单位成本应按成功且满足 SLO 的业务量计算：

\[
C_{1M\ tokens}=\frac{C_{period}}{\text{SLO 内完成的 tokens}}\times10^6
\]

若输入和输出定价或资源成本差异大，应分别计算 input/output token 成本。还要分摊副本空闲、故障冗余、权重加载、cache miss、重试、跨区网络和被取消但已消耗的 token。

### 六、上线后形成闭环

- 用队列长度、TTFT、KV 水位、tokens/s 而非仅 GPU 利用率驱动扩缩容；
- 扩容阈值要覆盖模型加载与 warmup 时间，缩容前完成请求 draining；
- 每次模型、量化、框架、GPU 或长度分布变化都重新压测；
- 比较预测容量与实际 SLO/goodput，持续修正安全系数。

### 面试简答版

我先用生产数据建立请求到达率、input/output 长度联合分布、并发、前缀命中和 SLO 画像，再做权重、KV、workspace 与余量的显存账本，确定单副本并行方式。压测要重放真实分布，逐级加压并覆盖峰值、突发、长尾和少一个副本的故障场景；容量必须用满足 TTFT、TPOT 和 P99 的安全 goodput，而不是最大 tokens/s。副本数先按 \(\lceil\lambda_{peak}/\mu_{safe}\rceil\) 估算，再加增长、突发和 N+1 余量，并用 Little 定律检查在途请求与 KV。成本则按 GPU、CPU、内存、网络、冗余和运维总成本除以 SLO 内成功 token 计算。
