## 我的答案

共用 GPU 时要同时隔离四种资源：**显存容量、计算/带宽时间、队列等待和缓存空间**。只限制请求数并不公平，因为一个 128-token 请求和一个 128k Prompt、生成 4k token 的请求成本完全不同。

### 一、先区分三种共享形态

- **多模型**：权重不同，切换或同时驻留会占大量显存，并可能污染 kernel/权重 cache。
- **多 LoRA**：共享 base model，只切换较小 adapter；可在同一 batch 中计算不同 LoRA，但 adapter 加载、rank 和热门程度不同。
- **多租户**：模型可能相同，但不同客户有独立配额、优先级、数据安全和 SLO。

三者可以重叠，例如多个租户分别使用同一 base model 上的不同 LoRA。

### 二、准入、配额与公平调度

在入口先估算请求成本，至少考虑 input tokens、允许的 max output、模型大小和优先级。可为租户设置：

- 并发上限、tokens/min、requests/min、KV token 配额；
- 最大上下文、最大输出和每请求 deadline；
- 独立队列、权重、保底份额与突发额度；
- 超额后的排队、降级、转小模型或拒绝策略。

调度可用 Weighted Fair Queuing 或 Deficit Round Robin 的 token 版本，让每个租户按权重消耗“token credit”。若仅轮询请求数，长 Prompt 会占用远多于短请求的 GPU 时间。高优先级请求可抢占或暂停低优先级序列，但要计入被抢占 KV 的重算/换出成本，并用 aging 防止低优先级永久饥饿。

### 三、显存和缓存隔离

- 给每个模型/租户设 KV block 上限和 prefix cache 上限，使用 LRU/LFU 或带权淘汰；
- LoRA adapter 采用 GPU 热缓存、CPU 冷缓存，限制同时驻留数量并按热度预取；
- 对大型模型做静态放置或专属实例，避免频繁加载权重造成抖动；
- 监控 allocator 碎片，避免某租户用大量小序列耗尽 block 元数据；
- 请求取消、超时和 worker 故障时必须回收其 KV 与 adapter 引用。

多 LoRA batching 的优势是共享 base model 的 GEMM，但如果一个 batch 中 adapter 过多、rank 差异很大，分组 kernel 和访问离散会降低效率。因此 scheduler 要同时考虑 LoRA ID、rank、序列长度和 deadline，而不是只追求最大 batch。

### 四、物理隔离与性能隔离

隔离强度可分层：

1. 单进程内逻辑配额：利用率最高，但故障和性能干扰最大；
2. 独立进程配合 MPS/容器配额：进程边界更清晰，但显存和带宽隔离仍非绝对；
3. MIG 或独占 GPU：性能、安全和故障隔离更强，但资源切片较刚性，统计复用降低。

强合规、付费保底或噪声邻居不可接受的租户，应使用更强物理隔离；低成本共享套餐可以接受逻辑隔离。不要把 Kubernetes 的 CPU limit 误认为能自动保证 GPU kernel、HBM 和 KV 的公平性。

### 五、安全、可观测与验收

- cache key 必须包含租户、模型版本、adapter 和权限域，不能跨租户错误复用 Prompt/KV；
- 日志、trace、临时文件和 adapter 权限均按租户隔离；
- 记录每租户 TTFT/TPOT/P99、排队时间、token 使用、KV/LoRA cache 命中和抢占次数；
- 用“一个租户突发长请求”的 noisy-neighbor 压测验证其他租户 SLO；
- 公平不等于每人相同：应验证实际服务份额接近配置权重，同时满足保底与总集群利用率。

### 面试简答版

我会把共享 GPU 的隔离拆成显存、计算/带宽、队列和缓存四层。入口按 input/output token、模型和优先级做 admission control，为租户设置并发、token、KV 和 deadline 配额；调度用 token 化的 WFQ/DRR、保底份额、突发额度和 aging，避免按请求数轮询导致长请求霸占资源。多模型做放置和权重热缓存，多 LoRA 共享 base model 但限制 adapter 驻留并按 LoRA ID/rank 组 batch。强隔离租户使用独占 GPU/MIG，普通租户用逻辑配额。最后通过 noisy-neighbor 压测、租户级 P99 和实际服务份额验证公平与 SLO。
