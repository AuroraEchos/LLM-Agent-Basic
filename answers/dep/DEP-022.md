> **问题：** GPU 利用率很低但显存占满时，应如何分析和优化？

## 我的答案

“显存占满”和“GPU 计算繁忙”是两件事。权重和预留的 KV Cache 可以长期占用显存，但如果请求少、batch 小、CPU 没及时提交 kernel，SM 利用率仍然很低。排查时先确认指标含义，再做分层 profiling。

### 一、先确认不是监控误判

- `nvidia-smi` 的 GPU utilization 是采样窗口内是否有 kernel 执行的粗粒度指标，不能直接代表 Tensor Core 利用率或有效吞吐。
- 同时看 SM active、Tensor Core、HBM 带宽、kernel duration、功耗、PCIe/NVLink、CPU、网络和请求队列。
- 区分 Prefill 与 Decode：Prefill 可能计算利用率高；Decode 常是权重/KV 带宽受限，SM 利用率低不一定异常。
- 用 Nsight Systems/Compute、PyTorch Profiler 或 runtime 自带 metrics 找时间线，不凭单个面板下结论。

### 二、拆显存账本

显存大致可分为：

\[
M_{total}=M_{weights}+M_{KV}+M_{workspace}+M_{graph}+M_{allocator}+M_{other}
\]

- `weights`：模型权重、量化 scale、可能的多份权重；
- `KV`：按最大并发和上下文预留的 KV block；
- `workspace`：Attention/GEMM/通信临时空间；
- `graph`：CUDA Graph 为不同 batch/shape 固定的 buffer；
- `allocator`：缓存和碎片，reserved 不等于真正 active；
- `other`：LoRA、prefix cache、NCCL、视觉 encoder 等。

很多 serving runtime 会主动占据大部分可用显存作为 KV 池，这是为了减少碎片和提高可接纳并发，并不表示当前请求正在使用这些空间。应看 KV block 使用率、active/reserved bytes 和碎片率。

### 三、按现象定位原因

#### 1. 请求不足或 batch 太小

队列经常为空、单请求 Decode 会启动大量小 kernel，GPU 难以吃满。可增加副本汇聚范围、连续批处理 token budget、允许极短的 batching window；离线任务直接增大 batch。延迟 SLO 很严时，低利用率可能是有意的容量冗余。

#### 2. CPU、Python 或调度器供给不足

时间线上 kernel 之间有明显空洞，CPU 忙于 tokenization、采样、JSON 约束、日志或 Python 调度。可异步化前后处理、批量 tokenization、减少同步点，使用 CUDA Graph/编译图，或把调度与模型执行进程隔离。

#### 3. 内存带宽受限而非算力受限

Decode 每 token 都要读大量权重，SM 利用率不高但 HBM 带宽接近上限。可采用硬件真正支持的权重量化、增大有效 batch 以复用权重、投机解码，或换更高带宽硬件；盲目增加 TP 可能引入更多通信。

#### 4. KV 预留过大、碎片或上下文配置过激

`max_model_len`、最大序列数、KV dtype 和 block 配置导致显存被占满，但真实流量用不到。可依据长度分布下调上限、启用分页 KV、prefix cache 淘汰、KV 量化，或者把长上下文流量单独分池。不能只清 allocator cache，因为活跃 KV 不会因此消失。

#### 5. 通信、I/O 或同步等待

TP 的 All-Reduce、EP 的 All-to-All、跨节点 KV 传输、权重 offload 或 page fault 都可能让 GPU 等待。检查 NCCL 时间、链路带宽、拓扑放置和 CPU/NVMe 读取；尽量把高频 TP 通信留在高速互联域。

#### 6. kernel/shape 不适配

极小 batch、特殊 hidden size、某种量化格式或 fallback kernel 可能导致占用率差。确认 FlashAttention、融合 MoE/GEMM、量化 kernel 是否真正启用，检查 graph break 和频繁重新编译，用微基准定位具体算子。

### 四、优化后的验收

优化不能只让利用率曲线更高。应比较同一负载下的 TTFT、TPOT、P99、tokens/s/GPU、KV 使用率、OOM/抢占次数和单位成本。若为了“吃满 GPU”而扩大 batch，导致排队和尾延迟失控，就不是有效优化。

### 面试简答版

显存满但利用率低通常不矛盾：权重和预留 KV 池长期占显存，而 GPU 可能因低并发、小 batch、CPU 调度、通信或内存带宽瓶颈而空闲。我会先用时间线和 SM/HBM/NCCL 指标确认瓶颈，再把显存拆成权重、KV、workspace、CUDA Graph 和 allocator。随后分别检查请求供给、连续批处理、CPU/Python 空洞、Decode 是否带宽受限、KV 是否过度预留、通信等待和 fallback kernel。最终以 TTFT、TPOT、P99、tokens/s/GPU 和成本验收，而不是单纯追求高利用率。
