## 我的答案

先定义“成功率”是基础设施完成、格式正确、工具执行成功，还是任务质量 evaluator 通过；HTTP 200 不是 Agent 业务成功。将下降按 app/model/prompt/tool-schema/knowledge/config 版本和任务类型分 cohort，对照最后正常版本与失败样本。

一条 Agent trace 可设计为：

```text
agent.run
 ├─ state.load / transition(version, from, to)
 ├─ context.build(token_count, truncation/retrieval refs)
 │   └─ retrieval(query, index_version, hit_count, scores)
 ├─ model.generate(model/revision, prompt_version, tokens, finish_reason)
 ├─ tool.select / tool.call(name, schema_version, attempt, outcome)
 ├─ state.commit(expected_version, conflict)
 └─ evaluator(category, score, reason_code)
```

### 归因证据

- **模型**：provider/model revision、finish_reason、rate limit、格式/schema violation、token usage、TTFT变化；同一冻结上下文重放到旧/新模型做差分，区分服务错误与能力退化。
- **上下文**：prompt/template版本、token budget、截断位置、retrieval query/index/corpus版本、文档 ID/score、权限过滤。看答案所需证据是否未召回、被截断或被错误旧缓存替换。
- **工具**：选择是否正确、参数 schema校验、tool版本、timeout/retry、返回码/摘要、幂等与部分失败；区分模型没调用、调用参数错、工具环境失败。
- **环境**：image/config/region/host/GPU、依赖版本、队列/连接池、网络/DB/provider异常；通常可从多任务同时基础错误和资源饱和看出。
- **状态管理**：run/task version、event seq、CAS conflict、重复/乱序消息、checkpoint load、取消与恢复；检查成功工具结果是否因旧 writer 覆盖或未提交。

Trace 只能提供因果候选，语义质量还需版本化 eval/rubric 和人工标注。做最小反事实实验：固定输入/context只换模型；固定模型只换 prompt/index；mock 工具；在旧 image 重放。结合受影响比例和变更时间建立证据链，不用“最后改了模型所以一定是模型”替代验证。

Prompt/tool结果可能含 PII/秘密，trace 默认只存 digest、长度、版本、文档 ID和安全摘要；原文进入受控加密采样库并有 TTL/审计。高基数 ID 用于 trace 搜索，不做 metric labels。

### 面试简答版

先把成功定义成可观测 outcome/eval reason，并按模型、prompt、索引、工具 schema、应用版本分 cohort。Trace 覆盖 state load/commit、context/retrieval、model generate、tool select/call 和 evaluator：模型看 revision/finish/schema，context 看 token截断与检索版本，工具看选择/参数/timeout，环境看资源与依赖，状态看 version/sequence/CAS/重复。最后用固定其他变量的重放或 mock 做反事实验证；敏感内容只记录 digest/版本/安全摘要。
