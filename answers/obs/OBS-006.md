## 我的答案

先定义“哪一层内存增长”：进程 RSS/cgroup usage、Python heap、native allocator、page cache、GPU allocated/reserved 不是同一指标。做可重复的恒定负载，记录请求数/时间趋势，在停止流量、清理请求并经过正常 GC 后取多轮 snapshot；不要只看一次 `top`。

### 五类情况的证据

1. **缓存增长**：对象按 cache key/entry 类型增长，hit/eviction/bytes 与流量相关，达到 max size/TTL 后应平台化。若无上限、key 含 request/user 高基数或过期任务不运行，它实际就是逻辑泄漏。检查 entry count、总 bytes、最大 key、TTL 分布；施加小上限后增长应停止，命中率/下游负载变化可验证。
2. **对象泄漏**：Python/Java heap 的某类对象在稳定负载后仍单调增长。用 `tracemalloc`/heap dump 的 snapshot diff 找 allocation site，再看 dominator/referrer path，常见 owner 是全局 dict、callback、未完成 Future、异常 traceback、队列。修 owner/生命周期后做 soak test，而不是定时 `gc.collect()`。
3. **连接泄漏**：pool active/checked-out 与 fd/socket 数只增不减，waiters/pool timeout 随后上升；`lsof/ss` 显示大量连接或 CLOSE_WAIT。按 acquisition stack/age 找未 close 的 response/session，确保异常、取消、流提前结束都走 context manager/finally。
4. **Tensor 未释放**：框架 allocated tensor bytes/活跃 tensor 数和 autograd graph 增长，常因把 loss/output 存列表、未 `detach`、推理未关梯度、hook/closure 保引用。用框架 memory snapshot/profiler；推理使用 inference/no-grad 语义、只保存 `detach().cpu()` 的必要摘要并删除引用。`empty_cache` 只可能归还未占用缓存块，不能释放仍有引用的 tensor。
5. **碎片/allocator 缓存**：语言 heap 的 live bytes/对象数回落，但 RSS 不降；GPU `allocated` 回落而 `reserved` 较高。allocator 为复用保留 arena/block或外部库碎片。先确认无 live leak，再调整 allocation pattern/batch、allocator 参数；有界 worker recycle可止血，但需监控和根因记录。

还要检查 C/CUDA 扩展、mmap/page cache、共享内存和 fork COW，这些可能不在 Python profiler 中。观测维度至少有 service version、worker、model 和请求类型，但 heap dump/prompt 可能含敏感数据，采集与访问要受控。

### 面试简答版

我先同时画 RSS/cgroup、语言 heap、fd/pool、GPU allocated/reserved，在恒定负载与停流后做 snapshot diff。缓存增长应与 entry/TTL 命中相关且达到上限；对象泄漏看类型增长和 referrer/dominator；连接泄漏看 checked-out/fd/CLOSE_WAIT；Tensor 泄漏看活跃 tensor/autograd graph，`empty_cache` 不会释放仍被引用的数据；live heap 已降但 RSS/reserved 不降更像 allocator 缓存/碎片。修复后用同负载 soak test 证明斜率归零。
