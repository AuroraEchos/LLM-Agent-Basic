## 我的答案

四类信号回答的问题不同：

| 信号 | 回答什么 | 典型形态 | 局限 |
|---|---|---|---|
| Log | 某个离散事件发生了什么、带哪些上下文 | 结构化 event、错误、审计记录 | 高流量下昂贵；跨服务因果需关联；自由文本难聚合 |
| Metric | 系统整体是否异常、何时开始、影响多大 | counter、gauge、histogram；rate/error/p99 | 聚合后丢失单请求细节；高基数 label 会爆炸 |
| Trace | 一个请求跨组件走过哪条路径、时间花在哪、因果如何 | trace 中的 spans、events、links | 常采样；未埋点/上下文断裂就有盲区；不是函数级热点分析 |
| Profile | CPU/内存/off-CPU 等资源由哪些代码栈消耗 | sampling flame graph、allocation profile | 通常缺业务请求全链路；采样/探针有开销和偏差 |

典型排障闭环：metric 告警显示某版本 p99/错误率上升；用 exemplar 或时间/属性定位代表 trace；trace 发现 tokenizer span 或 DB span 最慢；profile 再找该进程具体函数/锁栈；关联日志查看错误码、重试和安全上下文。修复后用 metric 和回归压测验证。

### 为什么不能只依赖日志

1. 日志是离散样本，很难可靠计算请求总量、错误比例、分位延迟和饱和度；“没日志”可能是没故障，也可能是进程死了/管道丢了。
2. 每请求/每 token 全量打日志会增加 I/O、成本和隐私风险，故障时还可能反压业务；抽样又会漏低频尾部。
3. 单服务日志无法天然重建并发 fan-out、重试、消息异步边的临界路径；trace context/link 更适合表达因果。
4. “CPU 100%”的根因在调用栈时间分布，普通日志无法无侵入地给出。

也不能只依赖 trace 或 metric：指标发现异常但不解释具体事件；trace 被 sampling 后不适合作精确计费；profile 不替代审计。四类信号要共享 service/version/region 等资源属性和 trace ID，但 metric label 必须低基数。遥测系统自身也需监控 dropped spans/logs、export queue、采样率与时钟偏差，避免观测失真。

### 面试简答版

日志解释离散事件，指标发现趋势、比例和分位数，Trace 还原一个请求的跨服务因果与耗时路径，Profile 定位进程内 CPU、分配或锁等待的代码栈。不能只打日志，因为它难以准确算全局 rate/p99/饱和度，跨服务路径和函数热点也不清楚，而且成本、隐私和丢失风险高。实践是 metric 告警→代表 trace→相关日志/profile→metric 验证，并监控遥测管道本身。
