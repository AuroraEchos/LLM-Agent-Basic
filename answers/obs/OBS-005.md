## 我的答案

先用 trace 把端到端时间拆成 queue、应用 CPU、DB、外部 API、GPU 和网络 spans，再用资源 USE 指标验证；相关性不是因果，最好通过受控限流/压测复现。

| 瓶颈 | 典型证据 | 进一步验证 |
|---|---|---|
| CPU | 每核 user/system 高、run queue、CPU throttle；吞吐随核数增长 | on-CPU profile/flame graph，区分 Python、序列化、tokenizer、syscall；整体 CPU 低也可能单核/GIL 热点 |
| 内存 | RSS/cgroup memory 逼近 limit、reclaim/major fault/swap、OOM/PSI | heap/allocation snapshot、smaps；区分可回收 page cache、native/GPU 与对象泄漏 |
| 磁盘 I/O | iostat latency/queue、IO PSI、D-state、major faults；CPU未满 | 按 device/process 看 IOPS/throughput、fsync、page cache miss；util 100% 对不同设备含义不同 |
| 网络 | connect/TLS/read 分段升高、retransmit/drop、socket queue | ss、NIC/host/region 指标、抓包/合成探测；区分带宽、RTT、丢包、DNS和代理 |
| 数据库 | DB span 长、pool wait/active 满、lock wait、slow query | EXPLAIN ANALYZE/buffers、连接/锁、行数估算；应用“DB耗时”也可能含 pool queue |
| 外部 API | 某 provider span/错误/429 上升，本地资源空闲 | provider/region/model切片、deadline/retry次数、其 request ID/status；防重试放大 |
| GPU | utilization/memory、kernel queue、OOM、CPU-GPU gap；TTFT/TPOT异常 | profiler 分 H2D、kernel、同步、batch；GPU util 低可能在等 CPU/tokenizer/网络，100%也未必吞吐最优 |

排查顺序：确定影响窗口、版本/模型/租户范围和基线；看是否到达率/输出长度变化；沿一条慢 trace 找**排队时间**与服务时间；对可疑资源看 utilization+saturation+errors；用 profile/执行计划等深入；通过回滚、减少并发、替换依赖或隔离实验验证。

排队论提醒：资源接近饱和时，哪怕平均服务时间变化不大，等待和 p99 会非线性增长。应同时看 QPS、in-flight、queue age、timeout/cancel，而不是看到 CPU 70%就排除容量问题。多资源 pipeline 还可能有 backpressure：下游慢导致上游线程池/连接池满，表面故障出现在上游。

### 面试简答版

我先用慢 Trace 拆 queue、DB、外部 API、GPU 和应用段，再对每个资源看利用率、饱和度、错误。CPU 用逐核/run queue+profile，内存用 RSS/PSI/OOM+heap/native快照，磁盘用 latency/queue/D-state，网络拆 DNS/connect/TLS/read/retransmit，DB看 pool/lock/plan，外部 API看 provider span/429/retry，GPU看 util/memory/queue并用 profiler拆数据传输和 kernel。最后通过限流、回滚或替换依赖验证因果。
