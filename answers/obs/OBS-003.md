## 我的答案

三套方法从不同视角减少“该监控什么”的遗漏：

### RED：面向请求型服务

- **Rate**：每秒请求/任务/token 数；
- **Errors**：失败数量/比例，按超时、5xx、业务失败、降级分类；
- **Duration**：延迟分布，至少 p50/p95/p99，并区分 queue、TTFT、完整生成。

适合 API、RPC、工具和 consumer handler，回答“用户看到的服务表现怎样”。错误率分母和成功定义要明确，例如 HTTP 200 但 Agent 未完成目标不能算业务成功。

### USE：面向资源

对 CPU、memory、disk、network、GPU、线程池、连接池等逐项看：

- **Utilization**：资源在多大比例时间/容量被使用；
- **Saturation**：超过即时服务能力而排队/等待的程度，如 run queue、pool waiters、GPU queue、memory PSI；
- **Errors**：硬件/系统/配额错误、OOM、packet drop、throttle。

利用率低不代表无瓶颈：单核/单 shard/单 GPU stream 可饱和，整体平均被稀释；saturation 往往比 utilization 更早解释尾延迟。

### Golden Signals：面向服务健康

Google SRE 常用 **Latency、Traffic、Errors、Saturation**。它与 RED 高度重叠，但显式加入饱和度，适合从服务/SLO 层建立 dashboard 和 alert。延迟应区分成功/失败请求，因为快速失败会让总体延迟“变好”。

Agent 可组合为：入口 RED/Golden Signals；模型看 request/token traffic、TTFT/TPOT、错误、queue/GPU saturation；工具按 tool/provider 看 rate/error/duration；基础资源按 USE。告警优先基于用户 SLO/error budget 的多窗口 burn rate，并用容量信号做诊断/提前告警，避免每个 CPU 瞬时尖峰都叫醒人。

这些是检查表，不是固定指标名。每个指标要有 owner、单位、低基数维度、预期动作和 runbook；若告警没有可执行响应，就是噪声。

### 面试简答版

RED 从请求看 Rate、Errors、Duration，适合 API/RPC；USE 从资源看 Utilization、Saturation、Errors，适合 CPU、内存、磁盘、连接池和 GPU；Golden Signals 是 Latency、Traffic、Errors、Saturation，从用户服务健康和 SLO 看。Agent 中入口/工具用 RED，资源用 USE，模型额外拆 TTFT、TPOT、token traffic 和队列。告警以 SLO/error-budget 为主，并明确成功定义、低基数维度和 runbook。
