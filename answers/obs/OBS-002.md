## 我的答案

结构化日志应是稳定 schema 的事件，而不是把所有信息拼成一句话。常见 JSON 字段：

```json
{
  "timestamp": "...",
  "severity": "ERROR",
  "event": "tool_call.finished",
  "service": "agent-worker",
  "service_version": "sha256:...",
  "environment": "prod",
  "trace_id": "...",
  "span_id": "...",
  "request_id": "req_...",
  "task_id": "task_...",
  "tenant_id_hash": "...",
  "tool_name": "search",
  "attempt": 2,
  "duration_ms": 831,
  "outcome": "timeout",
  "error_type": "ToolTimeout",
  "error_code": "TOOL_DEADLINE"
}
```

各 ID 含义应分开：

- **Trace ID**：一次分布式因果链的主关联键，按 W3C Trace Context 等标准跨 HTTP/gRPC 注入；一个 trace 有多个 span。
- **Request ID**：入口请求/响应的业务运维标识，可返回客户端；重试是沿用同一逻辑 ID还是生成新 attempt ID要明确定义。
- **Task ID / Run ID**：长 Agent 任务的持久身份，可跨多个 HTTP 请求、进程重启甚至多个 trace；消息队列中还要传播 correlation/causation ID，用 span link 表达异步 fan-out，而不强造错误父子关系。
- **User/Tenant ID**：授权、影响范围和成本归属。必须来自认证上下文而非信任客户端 header；日志中用内部 ID/不可逆受控 hash，按最小权限检索，不能记录邮箱等 PII。

在入口生成/验证 ID 并绑定 request context；每个下游 client、线程/协程任务和消息 producer/consumer显式传播。日志框架自动注入公共字段，业务只写 event/attributes，避免遗漏。跨信任边界要防攻击者伪造 trace/baggage 或塞超大值，并限制 baggage 传播。

日志规则：事件名和 error code 稳定，异常保留 stack/chain但限制大小；时间、duration、bytes、tokens 用明确单位；成功高频事件采样，错误/审计按策略保留。Prompt、response、tool args、Authorization、secret 默认不记录；若为调试需要内容，先同意、分级、脱敏/加密、TTL 和访问审计。`tenant_id/task_id` 可用于日志/trace搜索，但绝不能直接作为 Prometheus metric label 造成高基数。

### 面试简答版

结构化日志用稳定 event schema，包含时间、级别、service/version、outcome/error code、duration 和关联 ID。Trace ID 串一次分布式链，Request ID 标入口请求，Task/Run ID 跨请求和重启标长任务，Tenant/User 从认证上下文获取并脱敏。同步调用传播 trace context，消息异步边传播 correlation/causation 并用 span link。公共字段自动注入，限制 baggage 与高基数，prompt、密钥和 PII 默认不落日志。
