## 我的答案

NCCL timeout 常是**结果**：某 rank 数据慢、OOM/异常退出、进入了不同 collective，其他 rank 最后都在 NCCL 等它。排查应先建立所有 rank 的统一时间线，而不是先把 timeout 调大。

### 1. 先分类和止损

记录最后完成的 global step/micro-batch、每 rank heartbeat、当前 collective 序号/shape、GPU utilization、数据等待和主机日志。区分：

- **Straggler**：所有 rank 仍前进，但 step P99 被某卡/某节点拖慢；
- **Hang**：进度完全不动，可能 collective 顺序不一致、kernel死等或进程故障；
- **Timeout**：watchdog 检测等待过久，本身不说明根因。

先保留现场和最近健康 checkpoint，再终止 gang，避免大量 GPU 空等。

### 2. 从最早异常 rank 反查

1. **代码/collective**：条件分支令部分 rank 少调用一次；shape/dtype/group/调用顺序不一致；某 rank 在 barrier 前抛异常。给 collective 加单调 sequence id，比较各 rank trace/stack。
2. **数据/CPU**：坏样本重试、远端存储抖动、worker死锁、CPU/NUMA 饱和；比较 data wait 与 batch id，复现最后样本。
3. **GPU/kernel**：异步 CUDA 错误、OOM、ECC/Xid、降频/温度、某 kernel输入异常；检查设备日志、时钟、显存和同步后的最早报错点。
4. **网络**：NIC/link error、丢包/拥塞、错误 GPU-NIC 绑定、某交换路径热点；对故障节点做节点内/跨节点 collective benchmark，查端口计数器。
5. **负载不均**：变长序列、MoE 热专家、pipeline stage 不平衡导致合法但极慢的 rank。

### 3. 最小化定位

固定数据与 seed，缩到可复现的节点/rank，分别跑 compute-only、data-only、collective-only；替换可疑节点或链路看故障是否随硬件移动。调大 timeout 只适合已证明是合法长操作的场景，否则会延迟发现并增加浪费。

### 面试简答版

我先把 timeout 当症状：收集每 rank 最后 step、collective序号、stack、data wait、GPU和NIC日志，找最早偏离的 rank。再按 collective顺序/shape、坏数据或worker、CUDA OOM/ECC/kernel、网络端口与拓扑、MoE/长序列负载不均逐层排查，并用 compute/data/collective 单项最小复现。不要先盲目增 timeout；先保存现场和健康 checkpoint，避免整个 gang 空等。
