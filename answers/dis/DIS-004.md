> **问题：** Pipeline Parallel 为什么会产生 Bubble，如何通过 Micro-Batch 和调度减少？
>
> **分类：** 分布式训练与 AI Infra

> **来源：** [INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md](../../INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md)

## 我的答案

Pipeline Parallel 把模型分成 $P$ 个 stage。一个 micro-batch 必须依次经过 stage 0 到 $P-1$；启动时后面的 stage 等输入，排空时前面的 stage 已无新工作，这些空闲槽就是 bubble。stage 计算不均、跨 stage 通信慢还会增加额外等待。

把一个 global batch 切成 $M$ 个 micro-batches 后，各 stage 可以像流水线一样交错处理。在 stage 时间相等的理想 flush 调度中，bubble fraction 常粗略写为：

$$\text{bubble}\approx\frac{P-1}{M+P-1}$$

所以 $M\gg P$ 时利用率提高。但 micro-batch 太小会令 GEMM 利用率下降，太多 micro-batches 会增加调度/通信次数，并可能增加需要保存的激活。

### 常见调度

- **GPipe / all-forward-all-backward**：先完成所有 forward 再 backward，概念简单，但要同时保存很多 micro-batch activation；可配合重计算。
- **1F1B**：warmup 后每个 stage 交替一个 forward、一个 backward，steady state 激活数更少，bubble 仍来自 warmup/cooldown。
- **Interleaved 1F1B / virtual stages**：每个设备放多个非连续模型 chunk，增加虚拟流水深度并缩短 bubble，但通信与调度更复杂。

减少 bubble 还要按实测计算量平衡层分配，将 embedding/loss/MoE 重层单独考虑；重叠 stage P2P 通信，选择足够大的 micro-batch；必要时使用 zero-bubble 类调度，但要承担更复杂的 backward 拆分、权重版本或内存约束。

Micro-batch 数还与 gradient accumulation 相关，但两者概念不同：pipeline micro-batch 首先用于填满 stage；梯度累积决定多少 micro-batch 后 optimizer step。配置时需保证 loss 按累计数正确缩放。

### 面试简答版

PP 的 bubble 来自流水线 warmup/cooldown：后级最初等输入，前级最后先空闲。理想 bubble 比例约 `(P-1)/(M+P-1)`，增加 micro-batch 能摊薄，但过小 batch 会伤 GEMM、过多会加调度和激活压力。实践用 1F1B 降激活、interleaved virtual stages 降 bubble，并按实测 FLOPs平衡 stage、重叠 P2P 通信。
