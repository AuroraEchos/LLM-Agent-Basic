> **问题：** 大规模训练中如何保证数据顺序、随机性和断点恢复的一致性？

## 我的答案

目标要先区分：**统计上随机充分**与**故障后逐样本完全复现**。大规模训练通常首先保证数据无意外重复/遗漏、各 DP rank 不重叠和恢复语义明确；bitwise deterministic 还受 kernel、collective归约顺序和硬件影响，成本更高。

### 数据版本与全局顺序

1. 用不可变 manifest 列出 shard URI、size/checksum、样本数/token数、过滤/去重版本，训练运行引用 manifest id，不能读取会原地变化的“latest目录”。
2. 每个样本/文档有稳定 global id。用 `(base_seed, epoch)` 生成确定性全局 shuffle，或先确定性打乱 shard、再在 shard内打乱；随后才按 DP rank 分配，保证同一步不同 rank 不重复。
3. 变长 packing、curriculum、数据混合权重、最大长度和 tokenizer 都会改变 token顺序，必须版本化并把其 scheduler状态放进 checkpoint。

### 随机性

明确模型初始化、dropout、数据 shuffle、augmentation 的 seed派生规则，例如 `seed(base, dp_rank, worker_id, epoch)`；保存 Python/NumPy/CPU/CUDA generator状态。DataLoader worker 的 seed和持久化行为也要控制。若 elastic world size改变，rank-based seed无法逐样本复现，可按 global sample id派生随机性。

### 断点恢复

保存的是**已提交 optimizer step**对应的 consumed sample/token cursor，而不只是 DataLoader迭代次数。prefetch worker可能已经读取但尚未训练的数据，不能把“已取到内存”误算成已提交。恢复后从已提交边界重放未完成 accumulation window，保证模型状态与数据进度同一事务点。

验收方式是在固定小规模下比较 uninterrupted run 与 save-resume run 的下一批 sample ids、loss、LR和参数 hash/容差；再测试不同 worker数、节点故障和world size。若只保证统计等价而非精确顺序，也要在实验元数据中明确。

### 面试简答版

我用不可变数据manifest和稳定sample id定义语料，以base seed+epoch生成确定性全局shuffle，再按DP rank切分；tokenizer、packing、mix/curriculum也全部版本化。Checkpoint保存已提交optimizer step的sample/token cursor及各类RNG，而不是prefetch位置。恢复重放未提交accumulation窗口，并用 uninterrupted vs resume 对比下一批ID、loss和参数。弹性变world size时需全局调度或sample-id随机性。
