## 我的答案

重叠的目标不是减少通信字节，而是让通信发生在关键路径之外。例如反向传播从后层到前层：某些梯度 ready 后立即启动其 collective，同时 GPU 继续计算更前层的 backward。

### Bucket Size 的作用

DDP 会按参数顺序把梯度放进 bucket；一个 bucket 的所有梯度 ready 就启动异步 All-Reduce。bucket 太小，能更早启动、重叠窗口大，但消息多、collective latency 和调度开销高；太大，带宽效率高但必须等更多梯度，最后出现长 communication tail。最优值依模型层时、网络和梯度 ready 顺序，不是固定常数。

FSDP/ZeRO 可预取下一 unit 参数 All-Gather，并把当前梯度 Reduce-Scatter 与其他 backward 重叠；PP 可重叠 stage send/recv；MoE 可把 token 分块，让 All-to-All 与 expert GEMM 重叠。前提是计算与通信使用可并发的 stream/engine，且没有争用同一 HBM/PCIe/NIC 到反而互相降速。

### 异步 Collective 的正确性

`async_op` 通常只表示调用立即返回一个 work handle，不保证通信已经完成或一定与计算并发。消费结果前必须 `wait()` 或建立正确 CUDA event/stream dependency；发送 buffer 在完成前不能覆盖/释放。各 rank collective 调用顺序仍必须一致，否则异步只会让 hang 更难定位。

优化步骤：

1. profiler 标出 gradient ready、collective start/end 和计算 kernel，算 exposed communication，而非只看通信总时长；
2. 调 bucket 顺序/大小，让 ready 顺序匹配反向；
3. 使用 reduce-scatter/all-gather、预取和 fusion 减少等待与小消息；
4. 检查 stream 隐式同步、`.item()`、allocator、CPU launch gap 和链路争用；
5. 比较开启重叠后的端到端 step time，防止通信和 GEMM同时变慢后“时间线看似重叠”。

### 面试简答版

反向中梯度按 bucket ready 就异步发 collective，同时继续算前层。小 bucket 启动早但消息/延迟多，大 bucket 带宽高却启动晚、通信尾巴长，要按 profiler 调。异步返回不等于完成，消费结果前要 wait/event，buffer 不能提前复用，各 rank 顺序必须一致。真正指标是 exposed communication 和总 step time，而不是时间线上有重叠颜色。
