## 我的答案

弹性训练包含两个问题：**进程组成员如何变化**，以及变化后**模型更新与数据消费语义是否仍正确**。常见可靠实现不是在 collective 中途热插拔，而是故障被 agent/rendezvous 检测后终止整个 worker group，从最近提交 checkpoint 以新 membership 重启。

### 节点退出与加入

1. rendezvous 服务为本次 restart 分配新 rank/world size 和 generation id，所有 worker 必须加入同一代；旧代迟到消息不能混入。
2. 从 sharded checkpoint 恢复并按新 DP size reshard。TP/PP/EP 通常要求固定拓扑，弹性优先只改变 DP degree；任意改变模型并行度需要 checkpoint 格式和 stage/expert 重映射支持。
3. world size 改变会改变 global batch：`micro × DP × accumulation`。要么调整 accumulation 保持 global batch和LR语义，要么明确采用变 batch训练并校准 scheduler/optimizer，不能悄悄改变。

### 数据进度一致性

仅保存“epoch=3”不够。应有不可变数据 manifest、全局样本/sequence id、确定性 shuffle seed、已提交 optimizer step 对应的 consumed sample/token cursor。数据消费和 checkpoint 以 optimizer-step 为边界提交：故障最多重放未提交窗口，不跳过已提交数据。

若重新用 `rank::world_size` 切流，world size 改变会让各 rank 的未来样本重排，可能重复/遗漏。可由协调器维护全局 chunk lease/完成日志，或使用确定性的全局 sample stream再按当前 membership派发。Exactly-once 很贵，训练通常接受有界 at-least-once 重放，但必须量化并防止评测/数据混入。

RNG 也要处理：rank-based seed 在 rank 改变后不再精确复现；需要严格一致时用 `(global_sample_id, layer/op id, seed)` 派生样本级随机性，或恢复每个逻辑 shard 状态。

### 面试简答版

弹性通常是 membership 变化后整组从已提交 checkpoint 重启，而不是 collective 中途加卡。rendezvous 产生新 generation/rank，checkpoint按新 DP 重分片；TP/PP通常固定。数据侧保存不可变 manifest、shuffle seed和已提交 token/sample cursor，以 optimizer step为事务边界，允许最多重放未提交窗口。world size变化还要保持或显式调整 global batch、LR和RNG语义。
