## 我的答案

梯度累积是在多次 micro-batch forward/backward 后才执行一次 optimizer step。若累计 $G$ 次，要么每次 loss 除以 $G$，要么最后把梯度除以 $G$，使其等价于大 batch 的平均 loss：

```python
optimizer.zero_grad(set_to_none=True)
for i, batch in enumerate(loader):
    loss = model(batch) / grad_accum_steps
    loss.backward()
    if (i + 1) % grad_accum_steps == 0:
        torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm)
        optimizer.step()
        lr_scheduler.step()
        optimizer.zero_grad(set_to_none=True)
```

DP 下的 nominal global batch：

$$B_{global}=B_{micro\ per\ rank}\times D_{DP}\times G$$

变长/packing 训练更应记录有效 non-padding tokens，而非只看 sequence 数。DDP 若每个 micro-batch 都 All-Reduce 会浪费通信，前 $G-1$ 次通常用 `no_sync()`，最后一次再同步；FSDP/ZeRO 要使用其支持的累积方式，不能假设同一个 context 完全等价。

Pipeline micro-batch 的第一目的，是把一个 batch 切片填充 PP stages；gradient accumulation 决定多少 micro-batch 后更新权重。很多 1F1B 实现让一次 pipeline schedule 中的 micro-batch 数恰好等于 accumulation 数，因此配置上看似相同，但概念不相同：还可以多个 pipeline flush 后再 step，或一个 accumulation window 内采用别的 schedule。

正确性细节：AMP 要累计 scaled grads，step 前只 unscale 一次并 clip；NaN/overflow 时所有 rank 对是否跳步达成一致；scheduler、EMA、global step 每 optimizer update 前进一次，不是每 micro-batch。Dropout RNG、BatchNorm 统计和按 batch 计算的 loss 会令累积与物理大 batch 不严格等价。

### 面试简答版

梯度累积让 G 个 micro-batch 的梯度相加后只做一次 optimizer step，loss 通常除以 G；global batch 是 `micro_batch_per_rank × DP × G`。DDP 前 G-1 次可 no_sync，最后才同步。PP micro-batch 用来填流水线，gradient accumulation 决定更新频率，两者常共享同一配置但概念不同。clip、AMP unscale、scheduler 和 global step 都应按 optimizer step 执行。
