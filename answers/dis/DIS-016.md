## 我的答案

容错 checkpoint 的目标不是“写出几个权重文件”，而是得到一个**一致、完整、可验证、可重分片恢复**的训练事务快照。

### 必须保存的状态

- 模型参数、optimizer states、LR scheduler、AMP GradScaler/overflow 状态、EMA；
- global optimizer step、已消费样本/token、gradient accumulation/pipeline 边界；通常只在完整 optimizer step 后提交；
- CPU/CUDA/Python RNG，数据 sampler/shuffle seed 与 cursor；
- 模型/并行配置、tokenizer、数据 manifest/version、代码 commit、依赖/镜像和 checkpoint schema version；
- 若要精确续训，所有 rank 的局部 RNG/数据状态都要有定义。

### 原子提交协议

各 rank 写带 checkpoint id 的临时 shard，流式计算 size/checksum；所有 shard 成功后生成 manifest，记录 shard 到逻辑 tensor 的映射。只有协调者确认完整后才写 commit marker/原子更新 `latest` 指针。恢复只读取已提交且校验通过的版本，半写目录不能被视为成功。定期做 restore drill，包括少 rank/换 world size、坏 shard 和旧 schema。

### 控制吞吐影响

1. 使用 distributed/sharded checkpoint，让各 rank 并行写自己的 shard，避免 rank 0 聚合 full state 导致内存、网络和单点 I/O峰值；
2. 先把一致快照复制/分阶段搬到 CPU buffer，再异步写对象存储；训练不能在 I/O期间继续修改同一 buffer；
3. 大块顺序写、压缩真正可压缩部分、限制并发，避免所有作业同时冲击共享存储；将上传与下一步计算重叠，但观测 exposed checkpoint time；
4. full + incremental/delta 需权衡恢复链长度和写放大；设置 latest、周期 milestone 和保留/删除策略；
5. checkpoint 间隔结合保存耗时、故障率和可接受回滚计算量，而不是固定“每 N step”不随规模变化。

成功标准是恢复后下一 step 的 loss、LR、数据 batch 和参数更新符合预期，而不只是文件存在。

### 面试简答版

我把 checkpoint 当事务：保存模型、优化器/scheduler/scaler、RNG、数据 cursor、global token/step及代码数据配置；各 rank 写临时 shard和checksum，manifest 完整后才原子写 commit/latest。用分布式 shard、CPU staging和异步大块 I/O降低停顿，但不能让训练修改正在保存的 buffer。必须定期做校验和恢复演练，包括改 world size、坏 shard 和旧版本迁移。
