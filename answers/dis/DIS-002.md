## 我的答案

我会按“先能放下，再减少最昂贵通信，最后扩吞吐”的顺序设计，而不是先指定一个漂亮的并行度乘积。

### 1. 建立容量与计算模型

先估每层参数、训练状态、保存激活、临时 buffer，长序列还要估 $O(L^2)$ attention 和 CP 通信；做一张硬件拓扑图，标出同卡 HBM、节点内 NVLink/NVSwitch、节点间 NIC 带宽/延迟以及 NIC-GPU 亲和性。再确定 global batch、micro-batch、序列长度、MoE Top-K 和精度。

### 2. 选择各并行维度

1. **单卡能放且模型不大**：优先 DP/DDP，简单且算子效率好；状态放不下再用 ZeRO/FSDP。
2. **单层权重或 GEMM 放不下**：加 TP。TP 每层通信，应尽量限制在节点内高速互联；TP 太大会让每卡矩阵变小、通信占比上升。
3. **模型深度仍放不下**：加 PP，把连续层分 stage；按实测 FLOPs/激活而不是层数平均，MoE、embedding、loss 层都可能不等重。
4. **超长序列激活/attention 放不下**：加 SP/CP/Ring Attention；短序列不应为追求维度齐全而承担额外通信。
5. **MoE**：用 EP 分专家，优先让 All-to-All 留在高带宽域；跨节点时做分层通信、负载均衡和计算重叠。
6. 其余设备给 DP，提高吞吐和 global batch；若 DP 太大导致 batch 超出优化区间，用更多梯度累积调整不能解决“最小全局 batch 已过大”的问题。

### 3. 验证而非只算理论

候选配置要 benchmark 每 stage 时间、collective 字节/链路、MFU、峰值显存和 bubble。并行网格需满足 world size，process group 映射要符合物理拓扑；NIC 争用、TP 与 DP collective 重叠、EP 热 rank 都可能让理论最优失效。

经验上把高频/细粒度通信（TP、EP、部分 CP）放节点内，把通信较少的 PP 放跨节点，DP 可跨更大范围；但最终以 profiler 和故障域要求为准。

### 面试简答版

我先按参数、优化器、激活和长序列临时量判断能否放下，再结合 NVLink 与跨节点网络选并行：TP 解决单层并尽量节点内，PP 解决深度并平衡 stage，CP/SP 只在长上下文需要时用，MoE 的 EP 尽量限制 All-to-All 拓扑，剩余卡做 DP/ZeRO 扩吞吐。最后用峰值显存、stage 时间、通信、bubble 和 MFU 实测搜索，而不是只看并行度乘积。
