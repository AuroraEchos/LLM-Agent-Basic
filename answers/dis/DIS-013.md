## 我的答案

训练显存不能只用“参数量 × 2 bytes”估。至少拆成长期模型状态、随 batch/序列变化的激活，以及瞬时/系统开销。

### 1. 参数与训练状态

典型 BF16 + Adam 的一种布局是：BF16 参数 2B、BF16 gradient 2B、FP32 master weight 4B、FP32 first/second moments 8B，合计约 16 bytes/parameter。若 gradient 是 FP32、没有 master weight、用 8-bit optimizer、冻结 base 或采用不同精度，数字都会变，不能把 16B 当恒等式。

DP 会复制这些状态；ZeRO-1/2/3 分别切 optimizer、gradient、parameter，TP/PP/EP 也切部分参数。即使长期 shard 是 $1/D$，FSDP 参数 All-Gather、optimizer step 或 checkpoint 仍可能产生瞬时 full/flat buffer 峰值。

### 2. 激活

粗略随 $B\times L\times layers\times hidden$ 增长，还包含 QKV、attention/softmax、FFN 中间值、dropout mask、MoE dispatch 等。普通 attention 的 score 可达 $O(L^2)$；FlashAttention 避免保存完整 score。Activation checkpoint/recompute、SP/CP、micro-batch 都会显著改变它，因此最好用模型级 estimator + 实际 profiler。

### 3. 其他不可忽略项

- CUDA context、allocator reserved/fragmentation；
- NCCL/TP/EP communication buffer、bucket；
- cuBLAS/cuDNN workspace、fused kernel 临时区；
- logits/loss，超大 vocab 时很显著；
- dataloader prefetch 到 GPU、编译/cudagraph 固定内存；
- checkpoint gather 和评估 generation 的 KV Cache。

排查 OOM 时同时看 `allocated`、`reserved` 和峰值时间线，按 forward 各层、backward、optimizer step、checkpoint 分阶段采样。容量规划保留余量，并用真实最大 sequence、最坏 MoE 负载和完整 optimizer step 测，不应只跑一个平均短 batch。

### 面试简答版

我把显存拆为：参数、梯度、master weight 和 Adam m/v等长期状态；随 batch/长度增长的激活；以及通信 bucket、kernel workspace、allocator 碎片、logits和checkpoint等瞬时峰值。BF16+Adam 常粗估约16 bytes/参数，但取决于具体 dtype。ZeRO降低长期 shard，不消除 All-Gather 峰值；最终要在最大序列和完整 forward/backward/step 上 profile allocated/reserved。
