## 我的答案

这类故障应先判断最早出错的阶段：数据/forward、Loss、backward、optimizer，还是 collective communication。NaN 往往会快速传播，最后报错的位置通常不是根因。最有效的方法是保留可重放现场，并定位“第一个非有限张量或第一个未完成 collective”。

### 建立最小现场

出现异常时记录并保留：

- global step、microstep、rank、host/GPU ID；
- checkpoint、optimizer/scheduler/loss-scaler 状态；
- 数据 shard、样本 ID、token IDs、长度、mask 与有效 label 数；
- Python/CPU/CUDA 各 RNG 状态；
- 学习率、Loss、grad norm、clip 系数、参数/update norm；
- collective 序号、各 rank stack、网络/NCCL 日志。

如果 dataloader 不能精确恢复到坏 batch，诊断成本会成倍增加。

### NaN/Inf 的定位

按流水线插入有限值断言：

1. 输入 token、label、mask 和位置 ID 合法；
2. Embedding 和每层 residual/Norm/Attention/MLP 输出有限；
3. logits、logsumexp 和 Loss 有限；
4. backward 的每层梯度有限；
5. unscale 后梯度、global norm 有限；
6. Adam $m/v$、master weights 和 optimizer update 有限。

使用 hook 时先按层记录 `min/max/RMS/nonfinite_count`，不要每步 dump 全张量。找到首个异常层后再细化到算子。可在固定坏 batch 上启用 anomaly detection、关闭融合算子或改 FP32 重放；这些模式很慢，不应长期全量开启。

典型数值原因包括：softmax 全 mask 行、FP16 overflow、`log(0)`、除零、负数开方、Norm 方差/epsilon 问题、FP8 scale 失效、极端 logits，以及 Inf 梯度在动态 scaler 跳步前被错误写入 optimizer。

### 梯度异常但仍有限

分别检查：

- global grad norm 与逐层/逐参数 norm；
- zero-gradient 比例和哪些参数始终 `grad=None`；
- $\|\Delta\theta\|/\|\theta\|$；
- Adam $m$、$v$ 分布和 clipping 触发率；
- 不同 rank 的同一参数梯度 checksum。

梯度全 0 可能是 loss mask 全空、detach、冻结参数、FP16 下溢或条件分支未走；异常大可能是 Loss 用 sum 未除 token、梯度累积未缩放、坏 batch 或 LR/二阶矩问题。global norm 会掩盖局部层，必须按深度画分布。

### 通信超时的分类

超时不一定是网络坏了。最常见的逻辑原因是各 rank 进入了不同 collective 序列：

- 某 rank 因异常数据提前 `continue/return`；
- 条件分支只让部分 rank backward；
- 某 rank OOM、assert 或 NaN 后退出，其他 rank 仍在 all-reduce；
- gradient accumulation/no_sync 次数不一致；
- 动态 shape、MoE routing 或 unused parameters 导致 collective 次序不同；
- checkpoint/评测只在 rank 0 执行却缺少正确 barrier。

基础设施原因包括 GPU/网卡故障、链路丢包、拓扑配置、超载文件系统、进程被抢占以及 kernel hang。

排查时收集所有 rank 的 stack 和最后 collective ID，判断是同一 collective 有 rank 未到达，还是所有 rank 卡在传输。先缩小为单机/少节点，再交换节点或网卡；做独立 collective benchmark 和硬件诊断。单纯增大 timeout 只适用于合法的长尾操作，不能修复 collective 次序不一致。

### 推荐二分法

```text
同 checkpoint + 同 batch 是否可复现？
├─ 否：查 RNG、异步数据、硬件与竞态
└─ 是
   ├─ 单卡也失败：数据/模型/数值/optimizer
   └─ 仅多卡失败：collective 次序、分片、通信或硬件
```

单卡失败时再比较 FP32 vs 低精度、eager vs fused、正常 batch vs 坏 batch。多卡失败时用小 world size 和同步执行定位首个 rank divergence。

### 恢复策略

若 non-finite 只在 backward 被 scaler 捕获且 optimizer 未更新，可按策略跳步并降低 scale；频繁发生仍需修复。若权重或 moments 已污染，回滚完整 checkpoint。通信超时后不能假设各 rank 状态一致，通常应终止整个 job，从最近原子 checkpoint 恢复，而不是仅重启一个 worker 继续。

### 面试简答版

我先保存 step、坏 batch ID、所有 RNG、各 rank 和完整 checkpoint，按 input→逐层 activation→logits/Loss→grad→unscale/clip→Adam update 查第一个非有限量。梯度异常还要看逐层 norm、zero/None 比例和 update/weight ratio。通信超时先查各 rank 是否进入同一 collective：某 rank OOM、提前跳过 batch或分支不一致，比网络故障更常见；收集所有 rank stack 和 collective 序号，再用单卡/少节点二分。Inf 若已写入参数或 moments 必须回滚完整状态，通信超时也应整体重启，不能只增加 timeout 掩盖。
