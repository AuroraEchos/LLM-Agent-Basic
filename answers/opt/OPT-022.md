## 我的答案

四个指标回答不同问题：tokens/s 和 samples/s 是业务层吞吐；MFU 衡量完成模型理论有效计算相对硬件峰值的比例；HFU 衡量硬件实际执行的总浮点计算相对峰值的比例。比较前必须说明是单卡还是全局、是否含 padding、是否含数据/评测时间以及 FLOPs 计数约定。

### tokens/s

$$
\text{tokens/s}=\frac{\text{统计窗口内处理的 token 数}}{\text{wall-clock 秒数}}
$$

最好同时报告：

- global tokens/s 与 per-device tokens/s；
- input tokens、non-pad tokens、loss tokens 中用了哪一种；
- 是否包含梯度累积、通信、checkpoint 和数据等待；
- 序列长度、global batch、模型配置和并行度。

预训练 Packing 充分时三种 token 数较接近；SFT 中 prompt 不参与 Loss，若只报所有 input tokens/s，可能高估有效监督吞吐。不同 Tokenizer 的 token 含义不同，跨模型还可报告 bytes/s 或样本原始字符/s。

### samples/s

$$
\text{samples/s}=\frac{\text{完成的样本数}}{\text{秒数}}
$$

适合图片尺寸固定或序列长度近似固定的任务。LLM 文档可能从几十到几万 token，一个 packed block 也可能含不同数量原始样本，因此 samples/s 很容易误导。报告它时必须同时给长度分布或 tokens/s。

### MFU：Model FLOPs Utilization

设单位时间完成的、由模型数学定义所需的有效 FLOPs 为 $F_{model}/s$，集群理论峰值为 $N F_{peak}$：

$$
\operatorname{MFU}=
\frac{F_{model}/s}{N\cdot F_{peak}}
$$

若使用稠密模型近似每 token $6P$ 训练 FLOPs，则：

$$
\operatorname{MFU}\approx
\frac{6P\cdot\text{global tokens/s}}
{N\cdot F_{peak}}
$$

MFU 把通信、内存访问、kernel 空洞、pipeline bubble、数据等待以及 activation 重计算视为未贡献于模型所需计算的时间，因此更接近“端到端训练效率”。但 $6P$ 忽略长序列 Attention 等项，MoE 还应使用每 token 激活计算，严谨实现要按实际模型 FLOPs 公式。

### HFU：Hardware FLOPs Utilization

$$
\operatorname{HFU}=
\frac{\text{硬件实际执行的 FLOPs/s}}
{N\cdot F_{peak}}
$$

它把 activation checkpointing 的重算等“实际执行但不是模型一次前后向最低必要量”的计算也计入分子。因此开启重算时常出现：

$$
\operatorname{HFU}\ge\operatorname{MFU}
$$

例如 GPU 很忙地重算 activation，HFU 可能较高，但有效 token 吞吐和 MFU 较低。HFU 适合判断计算单元是否繁忙，MFU 更适合判断为了训练模型完成了多少有用工作。

硬件计数器、Profiler 和论文对 HFU/MFU 的 FLOP 范围可能不同，例如是否计通信相关计算、稀疏/低精度操作、乘加算 1 还是 2 FLOPs。引用数值必须附定义。

### 为什么峰值分母也容易选错

- 要用实际 dtype/稀疏模式对应的峰值，不可拿 FP8 峰值评估 BF16 kernel；
- 不同 GPU 型号、频率和功耗上限不同；
- Tensor Core 峰值不适用于大量非矩阵算子；
- 若只用部分 GPU 或有异构节点，不能简单按统一峰值相乘；
- 峰值是理论上限，不是预期必须达到 100%。

### 如何联合解读

| 现象 | 可能解释 |
|---|---|
| tokens/s 低、MFU/HFU 都低 | 数据等待、通信、bubble、小 kernel 或同步阻塞 |
| HFU 高、MFU 明显低 | 重计算很多，硬件忙但有效工作比例低 |
| MFU 高但 samples/s 低 | 样本很长，不能据 samples/s 判断效率差 |
| tokens/s 高但 loss tokens/s 低 | Padding 或 prompt mask 占比高 |
| 单卡快、扩容后 global MFU 降 | 通信/并行扩展效率变差 |

还应报告 scaling efficiency：

$$
E_N=\frac{\text{throughput on }N\text{ devices}}
{N\times\text{throughput on 1 device}}
$$

并用 profiler 将时间拆成 GEMM、Attention、通信、输入、重算和空闲，指标才可转化为优化行动。

### 面试简答版

tokens/s 是每秒处理的 token，要说明全局/单卡以及 input、non-pad 还是 loss tokens；samples/s 对变长 LLM 容易误导。MFU 是模型理论所需有效 FLOPs/s 除以集群对应 dtype 的峰值，稠密模型可粗用 $6P\times tokens/s$；HFU 则把硬件实际执行的全部 FLOPs都算入，包括 activation 重算，所以重算时 HFU 常高于 MFU。HFU 高只说明硬件忙，不代表有效吞吐高；应结合 tokens/s、MFU、扩展效率和 profiler 判断通信、padding、重算或数据瓶颈。
