> **问题：** 如何判断一次训练出现了 Loss Spike，常见根因有哪些？

## 我的答案

Loss Spike 是训练 Loss 相对其正常趋势突然出现异常上升。不能用固定绝对阈值判断，因为不同阶段、数据域和 batch 的自然方差不同；关键是结合局部基线、持续时间、梯度/参数状态和各 rank 一致性判断。

### 如何定义“异常”

可维护 Loss 的鲁棒滑动基线，例如过去窗口的中位数 $m_t$ 和 MAD：

$$
\operatorname{MAD}_t=operatorname{median}(|L_i-m_t|)
$$

当：

$$
L_t>m_t+k\cdot1.4826\operatorname{MAD}_t
$$

时标为候选 spike。也可用 EMA 均值/方差，但中位数对异常点更稳健。阈值只用于告警，还要区分：

- 单个困难 batch 后立即恢复；
- 连续多个 step 偏高但仍有限；
- 伴随 grad/update norm 激增；
- 出现 NaN/Inf 或 Loss 永不恢复。

数据分布切换、序列长度提升时的可解释阶跃不一定是故障，但应有预期基线。

### 常见根因

#### 数据与标签

- 乱码、极端长文本、异常重复或新领域 batch；
- label 越界、全被 mask、有效 token 分母过小；
- Packing 跨样本泄漏或 shift/off-by-one；
- 某个数据 shard 损坏，单 rank 读到不同内容；
- curriculum/混合比例在边界处突然切换。

#### 优化器和调度

- peak LR 过高、warmup 太短或 scheduler 在恢复时跳变；
- Adam 二阶矩跟不上梯度分布突变；
- 梯度累积缩放错误、每 microbatch 都 step；
- clipping 顺序错误、weight decay 或参数组配置变化；
- 只恢复模型权重，未恢复 optimizer/scheduler 状态。

#### 数值与算子

- FP16 overflow/underflow、loss scale 不当；
- softmax、norm、除法、log/sqrt 的非法值；
- FP8 scale/amax 过期或校准失败；
- fused kernel、编译器或自定义算子 bug；
- Attention mask 出现全 `-inf` 行导致 softmax NaN。

#### 分布式与硬件

- 某 rank 梯度非有限但未全局同步 found-inf；
- all-reduce 不完整、通信超时后状态分叉；
- 参数 shard、optimizer state 或 checkpoint 损坏；
- 硬件 silent data corruption。后者概率低，应在软件与数据排查后用重放、换卡和校验和确认。

### 排查流程

1. 保存 spike 前 checkpoint、step ID、data sample IDs、随机状态和各 rank 日志；
2. 检查是 Loss 本身、grad norm 还是 optimizer update 最先异常；
3. 按层记录 activation、logit、grad、parameter、update norm 及非有限计数；
4. 比较各 rank，找第一个出现差异的 rank/参数；
5. 固定 batch 单卡重放，依次切换 BF16/FP32、关闭 fused kernel、关闭 dropout；
6. 用相邻正常 batch 替换数据，区分数据触发与状态触发；
7. 从更早 checkpoint 二分重放，定位首次异常 step；
8. 检查 scheduler、loss scaler、optimizer step/zero_grad 和梯度累积顺序。

### 是否可以“跳过这个 batch”

若确认是损坏或不合法数据，可以隔离样本并记录规则；但如果只是困难样本，直接跳过会掩盖模型稳定性问题并改变数据分布。若 spike 已污染 Adam moments 或参数，仅跳过后续 batch 无效，应回滚到 spike 前的完整 checkpoint。

动态 loss scaling 检测到 overflow 时跳过一次 update 是预期机制；若频繁发生，则应降低 scale/学习率或修复根因。梯度裁剪可防止一次异常更新，但不能修复 forward NaN。

### 预防与监控

- 记录 raw 和 smoothed Loss、每域 Loss、grad norm、clip rate、loss scale；
- 记录逐层 update/weight ratio、激活 RMS 和 logits max；
- 数据样本有稳定 ID，checkpoint 能恢复 dataloader/RNG；
- 对 mask、长度、token ID 和有效 label 数设置在线断言；
- 定期保存完整 checkpoint，并做实际恢复演练；
- 告警时自动保留前后 batch 元数据，避免问题消失后无法重现。

### 面试简答版

Loss Spike 应相对训练阶段的局部趋势判断，可用滑动中位数和 MAD 做鲁棒告警，再看它是否持续、是否伴随 grad/update norm 或 NaN。根因通常分为数据/mask、学习率与 optimizer、低精度/算子、分布式状态四类。排查时保存 spike 前完整 checkpoint 和样本 ID，比较各 rank，定位 forward 激活、backward 梯度、optimizer update 谁先异常，再固定坏 batch 单卡高精度重放。损坏数据可以隔离；若参数或 Adam moments 已污染，应回滚完整状态，不能只跳过下一 batch 或用 clipping 掩盖。
