## 我的答案

可复现的推理 RL 管线，不只是“固定随机种子”。它要求第三方能够回答：**模型看了什么题、用什么方式生成、由哪个版本的程序判分、算法怎样聚合梯度、最终提升是否在独立测试上成立**。

对于大规模异步训练，逐 bit 完全复现往往受 GPU kernel、采样并发和调度顺序影响；更现实的目标是同时定义：

- **Artifact reproducibility**：给定 checkpoint 和评测容器，能复现报告分数；
- **Statistical reproducibility**：多个 seed 重跑后，提升及置信区间稳定；
- **Exact resume**：训练中断后能从 checkpoint 恢复同一数据与策略版本。

### 一、冻结实验身份

每次 run 都保存不可变 manifest：

```yaml
model: base checkpoint hash
tokenizer: files hash
chat_template: version/hash
data: dataset manifest + split hash
verifier: container image digest + tests hash
reward: code/config version
algorithm: GRPO/PPO/DAPO config
runtime: framework/CUDA/driver/container/hardware
seeds: data, rollout, dropout, evaluator
```

仅记录模型名称不够；tokenizer、prompt template、EOS 设置或答案抽取器变化，都可能显著改变结果。

### 二、数据与切分

1. 每题保存稳定 ID、原题、标准答案/测试、来源、许可、难度与类别；
2. 按题族、竞赛、代码仓库和时间去重/切分，防止近似题跨 train/test；
3. 检查基础模型预训练污染虽难完全证明，但至少做 n-gram、语义近邻和公开题复现审计；
4. 保留训练完全不可见的 final holdout，验证器实现也尽量独立；
5. 先用少量可核验的 SFT cold start，之后按可解率建立 curriculum，避免全错组没有梯度。

### 三、可信验证器

#### 数学任务

- 稳健抽取 final answer，规范化分数、单位、集合、区间和等价表达；
- 能符号验证时用 CAS，并设置超时与数值抽样复核；
- 区分“解析失败”“答案错误”和“验证器异常”；
- 用人工构造的等价答案、恶意格式和边界值测试 parser。

#### 代码任务

- 在无网络、最小权限容器中编译和运行，限制 CPU、内存、进程、文件和总时间；
- 使用隐藏单测、随机 fuzz、property/metamorphic tests，覆盖只对样例硬编码的解；
- 测试与参考答案不得通过文件、报错、环境变量或 timing 泄漏；
- 将 compile error、runtime error、timeout、unsafe action 和 wrong answer 分开记分。

验证器本身要有单元测试、版本号和 golden cases。reward 代码出 bug 时，最优策略会快速放大这个 bug。

### 四、可回放的 rollout

每批采样至少记录：

```text
prompt_id / prompt tokens / response tokens
policy checkpoint 或 version
seed / temperature / top-p / max_new_tokens
group size / stop conditions
old-policy token logprobs / reference logprobs
reward 各分量 / verifier trace / sandbox exit status
natural EOS or truncation / timing / token count
```

必须避免 learner 已更新而 actor 仍长期使用旧权重的无界 staleness；将 rollout 与明确的 old-policy version 绑定，才能正确计算 importance ratio，也能离线重放审计。

### 五、把算法细节写到可复现程度

以 GRPO/DAPO 为例，配置需明确：

- 每个 prompt 的采样数、reward 标准化公式与 \(\epsilon\)；
- all-correct/all-wrong 组是否过滤、如何重采样；
- clip 上下界、KL estimator、reference 更新与否；
- token mask、padding、截断与 EOS 如何进入 loss；
- 是 sequence-level 还是 token-level normalization；
- 学习率、warmup、optimizer、gradient clipping、累计步数和更新 epoch；
- reward shaping、长度缓冲区和各分量权重。

最好保存极小 synthetic batch，并在单卡上验证 reward、advantage、ratio、mask 与 loss 的手算结果，防止分布式系统把公式实现错。

### 六、Checkpoint 与恢复

完整 checkpoint 不只有 Policy 权重，还包括：

- optimizer、scheduler、mixed-precision scaler；
- old/reference/critic/reward model 的确切版本；
- Python、CPU、CUDA 与各 data worker RNG state；
- data sampler 游标、已处理 prompt、rollout queue 和 global step；
- 分布式拓扑、训练配置与代码 revision。

恢复后先跑一个短窗口，比较 loss、reward、样本 ID 和策略版本；异步系统若无法 exact resume，要清楚声明恢复只保证统计一致。

### 七、评估与防止自欺

主指标使用独立 verifier 的 pass@1，并根据场景报告 pass@k；同时报告：

- accuracy 按题型、难度、长度和语言的切片；
- 平均/分位数 response tokens、每道正确题的总 rollout tokens、吞吐和延迟；
- train reward 与 hidden holdout reward 的差距；
- entropy、KL、clip fraction、gradient norm、组内 reward 方差；
- 全对/全错组、invalid、timeout、截断、重复与 verifier error 比例；
- bootstrap 置信区间及至少多个 seed 的均值/方差。

基线至少包括 base/SFT、best-of-N 或 rejection sampling，以及合适的 offline preference 方法。消融实验一次只改一个关键变量，并固定**总训练 token、rollout token 或实际算力预算**；只固定 optimizer step 会偏向每步生成更多样本的方法。

### 八、最小端到端流程

```text
数据去重与不可见切分
→ SFT cold start
→ 冻结 manifest、容器和 verifier golden tests
→ versioned actor 组内采样
→ sandbox/verifier 产生分项 reward
→ advantage + clipped policy loss + 必要约束
→ 保存完整状态与逐步指标
→ 独立 holdout、多 seed、固定算力消融
→ 发布 checkpoint、配置、数据清单和评测脚本
```

若数据或 hidden tests 不能公开，也应发布哈希、生成规则、类别统计、污染检查方法和可替代的公开评测，以便别人知道哪些结论可以复核。

### 面试简答版

可复现的数学/代码 RL 管线要冻结模型、tokenizer、模板、数据 split、reward/verifier、容器与全部超参数；数学用稳健答案规范化和符号验证，代码用无网络限资源 sandbox、隐藏随机测试并防测试泄漏。每条 rollout 绑定 policy 版本，记录 token、logprob、采样参数、分项 reward 和 verifier trace；checkpoint 还要包含 optimizer、RNG、sampler 游标及队列状态。评估时用训练不可见的独立 verifier，报告 pass@1/pass@k、长度成本、KL、entropy、无信号组和异常率，做多 seed、固定 rollout-token 预算的基线与消融。大规模系统不一定能 bitwise 重现，但必须做到 artifact 可验证、恢复可追踪、结论统计可复现。
