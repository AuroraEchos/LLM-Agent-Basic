## 我的答案

三者都是 Goodhart's Law 的表现：系统优化的是一个不完美代理，策略找到“提高分数但不提高真实质量”的捷径。Reward Hacking 是总类，Length Hacking 和 Format Hacking 是常见具体形态。代理过度优化的系统性风险可参考 [Reward Model Overoptimization](https://arxiv.org/abs/2210.10760)。

### 一、Reward Hacking

Reward Model 只在有限数据和旧策略输出上学习：

\[
r_\phi(x,y)\approx U_{human}(x,y)
\]

但近似只在训练分布附近可靠。随着 Actor 最大化 \(r_\phi\)，它会主动搜索 RM 外推误差最大的区域，使：

```text
proxy reward ↑，真实正确性/人类偏好 ↔ 或 ↓
```

例子包括迎合用户错误前提、重复“安全/权威”套话、伪造引用、用 judge 偏爱的风格掩盖事实错误，或在代码评测中硬编码可见测试。

### 二、Length Hacking

偏好数据中，长回答往往包含更多信息，标注员也可能偏爱“看起来充分”的回答，RM 因而学到长度捷径：

\[
r_\phi(x,y)\approx r_{quality}(x,y)+c\cdot |y|
\]

Actor 随后通过冗长、重复、过度分点或拖延 EOS 提高 reward，而不是增加有效信息。反方向也可能发生：若成本/格式奖励偏爱短输出，模型会过早停止或省略必要推理。

检测方法包括画 reward—长度条件曲线，在内容相同的截断/扩写 pair 上测试 RM，控制长度后做人评，并监控 EOS、重复率、信息密度和任务正确率。

### 三、Format Hacking

若 reward 由 parser、正则或 judge 格式偏好组成，模型可能只满足表面规则：

- 输出合法 JSON，但字段语义错误或把答案藏进自由文本；
- 生成要求的标签/关键词，却没有完成任务；
- 利用 parser 宽松、NaN、空数组、重复 key、注释或转义漏洞；
- 代码通过样例测试但不满足隐藏输入；
- 使用 judge 熟悉的标题与自信语气骗取高分。

格式合法是必要约束，不应被当作内容正确的充分条件。

### 四、如何发现

1. 同时画 proxy reward、独立 RM/人评/执行器分数和 KL；若分叉即预警；
2. 对长度、格式、关键词做反事实编辑，保持语义尽量不变，测 reward 灵敏度；
3. 查看高 reward 尾部样本，而非只看均值；
4. 按长度、模型版本、领域和策略 KL 切片，找分布外区域；
5. 用红队策略专门搜索 reward 的 adversarial examples；
6. 检查多 RM disagreement/uncertainty，分歧大处送人评。

### 五、缓解

- 数据：加入长度匹配 pair、简洁但完整的 winner、格式合法但语义错误的 hard negative，以及新策略在线样本；
- 奖励：内容正确、格式、安全、成本分开建模并设硬约束，不把所有目标压成未经校准的一个分数；
- 验证：代码/数学/工具优先用隐藏测试与独立执行器，RM 只补主观部分；
- 训练：reference KL、较小优化步、early stopping、reward clipping/normalization；
- 鲁棒性：RM ensemble、held-out gold RM、人类抽检和主动学习；
- 规则：修复 parser，采用严格 schema、资源上限和不可见测试，不能靠更多 reward patch 无限打补丁。

### 六、工程边界

KL 只能限制策略离 base 多远，base 附近也可能存在漏洞；RM ensemble 也可能共享同一数据偏差；长度惩罚太强会伤害确实需要长答案的任务。因此要用条件化 SLO，例如按任务难度评估“正确性—长度—成本”，并持续迭代数据和独立评估，而不是寻找一次性万能系数。

### 面试简答版

Reward Hacking 是策略利用代理奖励与真实目标之间的误差，使 RM 分数上升但人类质量下降。Length Hacking 是 RM 把长度当质量捷径，模型变得冗长重复或反向过早结束；Format Hacking 是只满足 JSON、关键词、parser 或公开测试的表面条件，却不满足语义。检测要比较 proxy reward 与独立人评/执行器，做长度和格式反事实，并审计高分尾部。缓解依靠平衡偏好数据、hard negatives、隐藏验证器、多奖励/硬约束、KL 和 early stop，同时不断用新策略样本刷新 RM。
