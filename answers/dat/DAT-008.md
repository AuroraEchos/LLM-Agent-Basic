## 我的答案

Byte Fallback 是 Tokenizer 的最后可逆保底机制：**当某个字符或文本片段无法由普通字符/子词词表表示时，将它转换成 UTF-8 字节，再用为每个 byte 预留的 token 表示。** 因为任意 Unicode 字符串都有有限的 UTF-8 字节序列，而 256 种字节值可被完全覆盖，所以无需用 `<unk>` 丢失原文。

### 编码过程

假设词表中没有汉字“龘”及可组成它的字符级 token。它的 Unicode code point 是 U+9F98，UTF-8 编码为：

```text
E9 BE 98
```

若 Tokenizer 预留了 256 个 byte token，可输出类似：

```text
<0xE9> <0xBE> <0x98>
```

解码时，将连续 byte token 恢复为字节序列 `E9 BE 98`，再按 UTF-8 解码回“龘”。对 emoji“🚀”，UTF-8 为 `F0 9F 9A 80`，最坏可用 4 个 byte token 保底。

实际 Tokenizer 会先尝试普通词表分割，只对无法覆盖的字符/片段 fallback。若“龘”本身已是词表 token，就只输出一个 token，不会强制拆成字节。

### 为什么能避免 OOV

对任意经规范化后的 Unicode 字符串 $x$，UTF-8 编码是：

$$
\operatorname{utf8}(x)=(b_1,b_2,\ldots,b_n),qquad b_i\in\{0,\ldots,255\}
$$

如果词表为每个 $b_i$ 都保留一个 token，则至少存在一条合法分割：

$$
x\rightarrow
\langle b_1\rangle,
\langle b_2\rangle,
\ldots,
\langle b_n\rangle
$$

因此每个输入都有可表示路径，`<unk>` 不再是覆盖未知字符的必需选项。这是一个形式上的完备性保证，不依赖训练语料是否见过该字符。

### Byte Fallback 与 Byte-Level BPE 的区别

| 维度 | Byte Fallback | Byte-Level BPE |
|---|---|---|
| 底层策略 | 先尝试字符/子词，无法覆盖时才转 byte | 所有文本从一开始都映射为 byte 基础符号 |
| 常见 token | 可直接是 Unicode 片段 | 是 byte 或 byte pair 合并得到的片段 |
| 保底触发 | 只在普通词表失败时 | 无“失败后切换”，byte 始终是基础 |
| OOV | 配置正确时基本避免 | 天然基本避免 |

两者都可以实现字节完备覆盖，但分词模型和 token 语义不同。

### 优势

- 支持生僻字、新 Unicode 字符、emoji、混合语言、代码和噪声数据。
- 不把不同未知字符全部折叠成同一 `<unk>` ID，保留精确原始字节信息。
- 可以复原人名、URL、文件路径和罕见符号，对 copy 任务很重要。
- 词表训练可将容量主要分配给高频有意义片段，长尾由 byte 保底。

### 代价和边界

#### 序列膨胀

一个未见中文字通常变成 3 个 byte token，部分 emoji 变成 4 个或更多（复合 emoji 包含多个 code point）。这会消耗 context window、增加 Attention/KV Cache 和自回归生成步数。因此 fallback 率应被监控，不能因为“UNK=0”就认为 Tokenizer 已经良好支持某语言。

#### 语义学习困难

单个 byte token 可能只是某个 UTF-8 多字节字符的一部分，本身没有独立语义。模型需要用多层组合出完整字符。如果某类 byte 序列在训练中极少出现，虽能表示，模型也不一定理解。

#### 流式解码

一个 token 步骤可能只产生不完整的 UTF-8 字节前缀，不能立即转成合法 Unicode 字符。流式输出端应缓冲不完整字节序列，直到能安全解码；不应对每个 byte token 单独使用替换字符解码，否则会破坏可逆性。

#### Normalization 在 fallback 之前

Byte Fallback 只能保留**进入 fallback 阶段的字符串**。如果 normalization 已经删除重音、折叠全角字符、统一简繁体或删除零宽符号，byte fallback 无法恢复被前处理删掉的原始信息。因此“有 byte fallback”不等于“整个 Tokenizer pipeline 字节级无损”。

### 实现检查清单

- 256 个 byte token 的 ID 映射必须稳定、唯一，且不与特殊 token 冲突。
- Encoder 应明确哪些片段触发 fallback，Decoder 应能将 byte token 连续恢复。
- 对所有单字节值、多字节 Unicode、emoji、嵌套组合字符和乱序/无效输入做 round-trip 测试。
- 监控每语言/领域的 fallback 率和平均 expansion factor，将其作为词表覆盖质量指标。
- 模型训练数据中需有合理数量的 byte fallback 样本，否则预留了能力但参数从未学会使用。

### 面试简答版

Byte Fallback 是在普通字符/子词词表无法覆盖某个片段时，将它编码成 UTF-8 字节，再用 256 个预留 byte token 表示。因为任意 Unicode 字符串都能转成 0–255 的字节序列，所以每个输入都至少有一条可逆编码路径，无需折叠成 `<unk>`。它与 Byte-Level BPE 的区别是，前者只在普通词表失败时退化为 byte，后者从一开始就以 byte 为基础符号。Byte Fallback 避免了信息丢失，但未见中文或 emoji 会变成多个 token，不代表分词高效或模型理解它们。而且 normalization 先删掉的信息无法由 fallback 恢复。
