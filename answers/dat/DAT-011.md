## 我的答案

比较 Tokenizer 不能只看词表大小或几个手工例子，而应在**相同、分领域、可复现的语料集**上同时评估压缩效率、覆盖性、可逆性、结构保持和模型实际吞吐。最核心的问题是：同一份有效信息需要多少 token，以及这种切分是否保留任务需要的边界。

### 先建立公平测试集

四类语料应分别采样，不能混成一个总平均数：

- 中文：新闻、口语、古文、繁体、生僻字、中文夹英文和标点；
- 英文：通用文本、专业术语、大小写、重音字符和不同空白；
- 代码：多种编程语言、缩进、注释、长标识符、路径和运算符；
- 数学：纯文本公式、LaTeX、Unicode 数学符号、上下标和矩阵环境。

语料要逐样本完全相同，并固定 Normalization、特殊 token 和是否添加 BOS/EOS。若 A 在规范化后测、B 在原文上测，结果没有可比性。还应按文档长度分桶，避免少量超长样本支配均值。

### 核心效率指标

对样本 $x$，记 Unicode 字符数为 $C(x)$、UTF-8 字节数为 $B(x)$、token 数为 $T(x)$。常用指标有：

$$
\text{chars/token}=\frac{\sum_x C(x)}{\sum_x T(x)},
\qquad
\text{bytes/token}=\frac{\sum_x B(x)}{\sum_x T(x)}
$$

值越大，通常表示同样文本使用的 token 越少。`bytes/token` 更适合跨语言比较，因为一个中文字符通常占 3 个 UTF-8 bytes，直接拿中文与英文的 `chars/token` 比会误导。

也可以以基准 Tokenizer A 为参照，计算 B 的 token 膨胀率：

$$
\text{inflation}_{B/A}
=\frac{\sum_x T_B(x)}{\sum_x T_A(x)}-1
$$

例如同一批中文 A 产生 100 万 token，B 产生 130 万 token，则 B 相对 A 膨胀 30%。除总体 micro-average 外，还要报告样本级中位数、P90/P99 和最差样本，防止长尾语言、代码长标识符或公式被严重拆碎。

### 为什么 token 数会直接影响成本

在固定 token 上下文长度 $L$ 下，可容纳的原始信息大约与 `bytes/token` 成正比。若一个 Tokenizer 对代码多产生 25% token，那么：

- 可放入 context 的代码量减少；
- 自回归输出步数和 KV Cache 写入增加；
- 训练相同原始语料需要处理更多 token；
- Attention 在朴素估算下随序列长度呈 $O(L^2)$，长序列代价可能被进一步放大。

但实际 tokens/s 还受词表大小、LM Head、实现和硬件影响。词表更大可能让序列更短，却增加输出投影与 softmax 成本，所以必须补做端到端 benchmark。

### 分领域还要看哪些结构

#### 中文

检查高频汉字、词组、繁简体、emoji 和生僻字的切分。一个常用观察量是 fertility：

$$
\text{fertility}=\frac{\text{token 数}}{\text{语言单位数}}
$$

中文可按字符或经统一分词器得到的词为单位，但报告时必须说明定义。还要单独统计 byte fallback 和 `<unk>` 比例，避免常用中文也大量退化成 byte。

#### 英文

检查词干、前后缀、大小写变体、数字和专业术语。子词越短不一定越差：合理的词素共享有助于泛化；把每个高频词都做成单 token 虽能压缩，却会消耗词表并削弱组合共享。

#### 代码

除 token 数外，应统计：

- 缩进、换行和连续空格能否无损恢复；
- `==`、`!=`、`->`、`::` 等运算符切分是否稳定；
- camelCase、snake_case、长 API 名和文件路径是否过碎；
- 不同语言是否偏置明显；
- token offset 能否准确对应源码位置。

代码里保留空白的“冗余”往往是语义，不应为追求压缩而删除。

#### 数学公式

分别测 LaTeX 与 Unicode 公式，关注 `\frac`、`\begin{...}` 等命令、花括号、反斜杠、上下标、数字和希腊字母。除了平均 token 数，还应检查括号和环境边界是否清晰、稀有符号是否大量 byte fallback，以及 decode 后是否逐字节一致。

### 覆盖、可逆性与词表健康度

效率比较至少还要报告：

1. `<unk>` 率和 byte fallback token 占比；
2. `decode(encode(x))` 的完全一致率；
3. Normalization 碰撞和空白丢失率；
4. 词表在目标语料上的激活比例、低频/从不使用 token 比例；
5. 单字符、byte token 和超长 token 的频率分布；
6. 特殊 token 是否会与普通文本发生意外匹配。

一个 Tokenizer 即使 token 数更少，如果靠不可逆地删除空白、重音或公式符号实现，也不能算更高效。

### 最终还要做模型级实验

离线分词指标只是代理变量。严谨比较应控制模型参数量、原始训练数据和训练算力，观察：

- 每秒处理的原始 bytes/字符，而不只 tokens/s；
- 峰值显存、KV Cache 和端到端延迟；
- 固定原始数据量与固定 token 预算两种条件下的 Loss；
- 中文、英文、代码、数学各自的下游任务质量；
- 长上下文中可放入的有效内容和检索/复制能力。

两个 Tokenizer 会改变训练序列和 LM Head 参数量，很难只替换词表而绝对公平。因此应把离线统计用于筛选，再用小规模等算力消融确认质量—成本 Pareto 前沿。

### 面试简答版

我会用完全相同且分领域的中文、英文、代码和数学测试集，统一 Normalization 与特殊 token，比较 chars/token、bytes/token、相对 token 膨胀率以及中位数、P90/P99，而不是只看总均值。还会检查 UNK/byte fallback、无损往返、offset、空白和代码/公式边界、词表利用率。最后做模型级 benchmark，看每秒处理的原始 bytes、显存、KV Cache、延迟和下游质量，因为更大词表虽然能缩短序列，也会增加 Embedding/LM Head 与 softmax 成本；最优方案应是质量和系统成本的综合 Pareto 最优。
