## 我的答案

中文、多语言和代码对 Tokenizer 的共同要求是：**不能只在英文空格分词和平均 token 长度上优化，必须同时保证字符覆盖、信息无损、语种公平、结构符号保留和合理的序列压缩率。**

### 中文的特殊性

#### 没有显式词边界

英文常有空格分隔单词，中文“我喜欢机器学习”并不直接告诉 Tokenizer 应切成“我/喜欢/机器学习”还是其他粒度。不应将英文的 whitespace pre-tokenizer 直接当作中文词边界。

常见选择有：

- 以 Unicode 字符为底层，让 BPE/Unigram 从数据学习常见多字组合；
- 使用 Byte-Level 或 byte fallback 保证罕见汉字、异体字、emoji 和混合符号不 OOV；
- 谨慎使用外部中文分词，因为词边界本身有歧义，且领域词、新词和人名变化快。

#### Unicode 覆盖与规范化

中文包含简体、繁体、CJK 扩展字、全角/半角标点、生僻字和多种 Unicode 组合。Normalization 必须根据任务做可解释的选择：

- NFKC 等兼容规范化能合并多种视觉相似形式，提高统计效率，但也可能丢失样式或特定符号区别。
- 简繁转换不是纯技术去重，可能改变原文、地区用词和专有名词，不应在所有场景无条件合并。
- 对需要精确复原的 OCR、文献、法律和代码数据，应优先可逆性并保留原始字节。

#### 压缩率与语义粒度

纯 Byte 退化时一个常见汉字的 UTF-8 通常占多个字节 token，会浪费上下文窗口。词表应覆盖常见单字和稳定多字片段，同时避免为每个长尾词建立独立 token。需在“序列更短”与“组合泛化更强”之间折中。

### 多语言的特殊性

#### 共享词表与独立词表

共享词表可以让数字、标点、专有名词、近缘语言和代码片段在语言间共享 Embedding，有利于跨语言迁移。但固定词表容量下，高资源语言可能占据大量 merge/token，小语种被迫分成字符或字节，形成 vocabulary competition。

独立词表能针对每种语言优化压缩，但增加词表总量，减少跨语言共享，并使混合语言和代码切换更复杂。实践中常使用共享字符/byte 底层 + 按平衡语料学到的共享子词。

#### 数据不平衡

如果直接按原始语料频率训练 Tokenizer，大语种会主导 pair 统计。可以对语种做温度采样、上限截断或加权，使小语种在 Tokenizer 训练语料中获得更高比例。这个混合比例不一定与模型预训练比例完全相同，因为 Tokenizer 更关注覆盖和分割效率。

#### 不同书写系统

拉丁、CJK、阿拉伯、天城、泰文、粘着语等在空格、形态和 Unicode 组合上差异很大。评估不能只看英文 tokens/word，应按语言比较 chars/token、bytes/token、UNK/fallback 比例和下游效果。

同形异义字符、组合音标和 Unicode homoglyph 还带来数据质量与安全问题。规范化能减少碎片，但不应在身份标识、密码、URL 或代码等场景不可逆地折叠字符。

### 代码的特殊性

#### 空白和换行可能是语义

Python 缩进、YAML 层级、Makefile 的 tab、字符串中的空格和不同换行符都可能影响程序。针对自然语言的“压缩连续空格”或“统一标点”规范化可能直接破坏代码。代码 Tokenizer 应保证空白和换行可逆。

#### 标识符是开放词表

`get_user_profile`、`HTTPRequestParser`、随机变量名、hash、UUID 和路径无法用固定词级 vocabulary 覆盖。子词应能高效拆分：

- snake_case 下划线；
- camelCase/PascalCase 大小写边界；
- 常见 API、类型名和关键字；
- 数字、十六进制、版本号和路径分隔符。

但过度预切分也可能破坏用户自定义标识符的重复模式，需通过实验而非只依赖语法规则决定。

#### 运算符与结构片段

`==`、`!=`、`->`、`::`、`</`、三个反引号等多字符符号有稳定语义，可学成独立 token。同时必须保留单字节 fallback，以支持任意新语法、二进制片段、escape 和嵌入式语言。

代码模型还常需 FIM（Fill-in-the-Middle）等特殊 token，如 prefix/suffix/middle 边界。这些 token 必须在 tokenizer、数据构造和模型 Embedding 中一致注册，不能只当作普通文本字符串。

### 设计和评估方法

1. 构建分层且去重的评估集：简体/繁体中文、每个语种、混合语言、主要编程语言、JSON/HTML/SQL、emoji 和噪声文本。
2. 报告 chars/token、bytes/token、tokens/word、上下文窗口实际承载量、UNK 率和 byte fallback 比例，不只报一个全局平均数。
3. 验证 `decode(encode(x))` 对要求无损的文本逐字节相等，单独记录 normalization 允许的改动。
4. 比较同一内容在不同语言的 token fertility，避免小语种为表达同等信息消耗数倍 token 和推理成本。
5. 最终用下游 perplexity、生成/检索/代码测试和端到端吞吐验证；Tokenizer 压缩率好不代表模型效果一定好。

### 面试简答版

中文没有显式词边界，且有简繁体、CJK 扩展字和全半角符号，因此不能直接套用英文空格分词，需用字符/子词学习并保留 byte fallback，规范化也必须考虑是否丢失原文。多语言共享词表能促进跨语言迁移，但高资源语言可能占据大量 token，需通过语种平衡采样和分语效率分语种评估。代码中空格、缩进和换行可能是语义，标识符又是开放集，所以必须保证字节级可逆，同时高效表示常见关键字、运算符、camel/snake 标识符和 FIM 特殊结构。评估应同时看分语压缩、覆盖、回转无损性、语种公平和下游效果。
