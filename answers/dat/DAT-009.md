## 我的答案

特殊 token 不是普通词片段，而是模型协议中的**控制符号**。它们承担序列边界、角色、工具调用、模态占位等结构语义。因此设计时不仅要考虑 Tokenizer 能否编码，还要确保训练模板、推理模板、模型参数和停止逻辑对它们的解释完全一致。

### 常见类型

- 序列控制：`<bos>`、`<eos>`、`<pad>`、`<unk>`、`<mask>`；
- 对话协议：`<system>`、`<user>`、`<assistant>`、消息结束符；
- Agent 协议：工具调用开始/结束、工具结果、文档分隔符；
- 训练任务：FIM 的 prefix/suffix/middle token；
- 多模态：图片、音频、视频或其中一段特征的占位 token。

特殊 token 的数量应该够表达协议，但不宜为每种业务状态随意增加一个 token。很多结构用普通文本或外部元数据表达更容易维护。

### 设计原则

#### 1. 原子性与语义唯一

一个特殊 token 应被编码成**单个、固定 ID**，不能被拆成多个普通 token；一个 ID 也应只承担一种清晰语义。例如工具结果结束符不应同时兼任整段回答的停止符，否则模型可能过早停止。

还要规定它能否在无空格处匹配，以及前后空白是否属于 token。否则同一个模板可能因换行或空格不同得到不同 ID 序列。

#### 2. ID 稳定、只追加不重排

发布后的 token-ID 映射相当于模型参数的 ABI。升级词表时通常把新 token **追加到末尾**，不要重排已有 ID。若把原来的 ID 42 从 `the` 改成 `<tool>`，旧 Embedding 第 42 行仍表示 `the`，整个模型语义都会错位。

Tokenizer、模型配置、权重、聊天模板、服务端和导出产物都应记录同一版本。不能只替换 `tokenizer.json`，却继续使用未扩容的旧模型。

#### 3. 防止与用户文本冲突

若用户可以原样输入 `<assistant>`，服务端必须明确它是普通文本还是控制符。常见方法包括：

- 使用保留且难以自然出现的标记；
- 对用户文本中的保留串转义；
- 由模板层插入控制 ID，不把不可信文本直接拼成协议；
- 解析工具调用时校验状态机，不能只搜索字符串。

这不仅是分词问题，也是 prompt injection 和协议混淆问题。

#### 4. 明确 Attention、Loss 和停止语义

特殊 token 是否参与 Attention、是否计算语言模型 Loss、是否触发停止，要逐一规定。例如 `<pad>` 通常参与张量补齐，但其位置应被 attention mask 和 loss mask 屏蔽；`<eos>` 通常需要参与训练 Loss，使模型学会何时结束。

`<pad>` 与 `<eos>` 可以共用 ID，但有代价：若掩码仅按 `input_id == eos_id` 生成，可能把真实的 EOS 也屏蔽掉；批量生成时也更容易混淆“已结束”和“只是补齐”。共用前必须保证 masking 与 stopping 实现按位置和长度处理，而不是只看 token 值。

### 新增 token 后为什么必须调整 Embedding

设原词表大小为 $V$，隐藏维度为 $d$。输入 Embedding 为：

$$
E\in\mathbb{R}^{V\times d}
$$

token ID $i$ 通过取第 $i$ 行得到向量 $E_i$。新增 $k$ 个 token 后，ID 范围扩展到 $[0,V+k-1]$，因此矩阵必须扩成：

$$
E'\in\mathbb{R}^{(V+k)\times d}
$$

否则读取新 ID 时会数组越界；即使框架没有立即报错，也不存在与新 token 对应的可学习表示。

自回归语言模型的输出层通常还要把隐藏状态映射成对全词表的 logits：

$$
z=hW_{\text{out}}^{\top}+b,qquad
W_{\text{out}}\in\mathbb{R}^{V\times d}
$$

所以输出头也要扩为 $V+k$ 行，输出 bias 若存在也要扩容。输入 Embedding 与输出头权重绑定时，物理上可能只有一个矩阵，但这个共享矩阵仍然必须 resize；不绑定时，两边都要分别处理。

例如在一个 $V=32{,}000$、$d=4{,}096$ 的模型中追加 8 个控制 token，输入 Embedding 会新增：

$$
8\times4{,}096=32{,}768
$$

个参数。若输出头不共享权重，还会再增加同样数量的权重参数。

### 新行如何初始化与训练

常见初始化方法有：

- 按原 Embedding 的均值和方差随机初始化；
- 用新字符串原先拆分出的多个 token 向量的均值初始化；
- 对具有明确相近语义的 token，用相关旧 token 初始化后再训练。

初始化只是起点。新行没有从预训练中学到语义，新 token 对应的输出概率也未经校准。必须在继续预训练或微调数据中提供足够、位置正确的示例，并确认该位置参与 Loss。否则“加进词表”不等于模型会正确使用它，甚至可能在生成中随机吐出控制符。必要时可在训练充分前通过 logits mask 禁止模型生成某些仅供输入占位的 token。

如果新增的是普通子词，还应评估它是否改变既有文本的分词结果。大量旧文本从原有切分变成新 token 后，新 Embedding 尚未训练好，可能导致性能短期下降。特殊 token 则应通过明确的 added-token 匹配规则，只在协议需要时出现。

### 工程上需要同步检查什么

一次完整扩词表不只是调用 resize 接口，还要检查：

1. Tokenizer 文件和 `vocab_size` 配置是否一致；
2. 输入 Embedding、LM Head、输出 bias 是否都已扩容；
3. 权重绑定关系是否在 resize 后仍然成立；
4. 旧 checkpoint 加载时是否只允许预期的新行不匹配；
5. 优化器状态是否为新增参数行正确创建；
6. 张量并行对词表维度的整除、词表 padding 是否正确；
7. 量化、推理引擎和 ONNX 等导出产物是否重新生成；
8. 训练与推理的 chat template、loss mask、stop ID 是否完全一致；
9. 编码—解码、字面冲突、批量 padding 和断点续训测试是否通过。

### 面试简答版

特殊 token 是模型协议的控制符，应做到原子化、语义唯一、ID 稳定，并明确转义、Attention、Loss 与停止规则。新增 token 后，词表从 $V$ 变成 $V+k$，输入 Embedding 没有新 ID 对应的行，输出 LM Head 也不能为新 token 产生 logit，所以两者都必须扩容；权重绑定时扩共享矩阵即可，不绑定时需分别扩。新增行还要合理初始化并通过包含这些控制符的数据继续训练，同时同步模型配置、模板、优化器、并行和推理导出，否则只是“Tokenizer 认识”，模型并没有真正学会。
