## 我的答案

这三类数据的共同标准是：**输入完整、目标明确、过程与答案一致、可被外部系统验证、难度与覆盖可控，并保留生成和许可血缘。** 区别在于验证器：数学依赖符号/数值检查，代码依赖编译和测试，工具调用依赖 schema 与有状态环境。

### 通用构建流水线

```text
合法数据源/任务种子
→ 结构化解析与规范化
→ 去重、污染与隐私过滤
→ 生成/增强题目和解答
→ 确定性验证 + 模型复核
→ 难度/能力/语言分桶
→ 训练集与盲测按来源分组隔离
→ 沙箱重放、人工抽检与版本发布
```

每条样本至少保存 source、license/usage policy、生成器、验证器版本、随机种子、通过的测试和失败原因。只保存最终问答，会让错误无法追溯。

### 数学数据

#### 来源与表示

可使用经过授权的教材/论文、竞赛题、证明语料、程序化生成题和真实用户问题。应同时覆盖算术、代数、几何、概率、微积分、证明、应用题和不同难度，而不是只堆短答案竞赛题。

LaTeX 需要解析和规范化，但不能粗暴删除花括号、环境或单位。题目必须包含所有前提、变量定义、图表的文本/结构表示，并区分“求数值”“证明命题”“给反例”等目标。

#### 验证

- 数值题：高精度重算，检查容差、单位和定义域；
- 代数题：用 CAS 化简 $f_{pred}-f_{ref}$，并结合随机点代入；
- 方程/优化：把候选解代回原约束，检查漏解和增根；
- 几何：验证坐标化约束，不能只比较最终数字；
- 证明：形式证明器最好；否则做多模型批判、关键步骤标注和人工审核。

字符串不相等不表示答案错误，例如 $1/2$ 与 $0.5$；最终答案相等也不表示推理正确，错误步骤可能碰巧得到正确值。应分别标记过程质量和 final-answer correctness。

### 代码数据

#### 任务覆盖

除“从题目生成函数”外，还应包含补全、解释、单元测试、debug、重构、性能优化、API 使用、跨文件修改和依赖配置。按语言、版本、仓库规模、任务类型和安全性分层，保留真实代码上下文、文件树和依赖说明。

#### 执行验证

在隔离沙箱中依次执行：

1. 解析、格式和静态类型/静态分析；
2. 编译或解释器加载；
3. 公开测试、隐藏测试和属性测试；
4. 超时、内存、网络和文件权限限制；
5. 多随机种子、边界值和对抗输入；
6. 对优化题测复杂度或基准，而不只测输出。

Pass@1 标签不能由样例测试 alone 决定。生成式测试还要防止测试与答案来自同一模型而共享漏洞；可用参考实现做 differential testing，并进行 mutation testing 检查测试是否真能抓住错误实现。

代码数据还要做许可证扫描、秘密/API key 检测、仓库级去重。train/test 应按仓库或项目划分，不能把同一仓库相邻文件分别放入两侧。

### 工具调用数据

一条高质量 Agent 轨迹至少包含：

```text
用户目标 + 可见上下文 + 工具定义/schema
→ assistant 的工具选择与参数
→ 环境返回的 observation
→ 后续调用/纠错
→ 基于结果的最终回答
```

重点不是让模型背 API 名，而是训练：何时调用、选哪个工具、如何填参数、如何利用结果、失败后怎样恢复，以及何时不应调用。

#### 用可重放环境验证

- JSON/function schema 校验字段、类型、枚举和必填项；
- mock/sandbox 执行，确认调用在当前状态合法；
- 检查 observation 确实来自工具，而非模型编造；
- 对有副作用操作区分 read、write、delete，并训练确认/授权边界；
- 注入超时、限流、空结果、权限拒绝和部分失败，生成恢复轨迹；
- 最终回答必须能由 observations 支持，不泄漏隐藏环境状态。

工具版本、时间、身份权限和初始环境状态必须随轨迹保存，否则同一调用将不可复现。并行调用只有在无依赖时才正确，数据中也应包含依赖顺序的反例。

### 难度和多样性控制

高质量不等于全是最难题。应建立能力矩阵，例如：

- 数学：知识点 × 推理步数 × 表示形式；
- 代码：语言 × 任务类型 × 项目规模 × bug 类型；
- 工具：单/多工具 × 读/写副作用 × 成功/失败恢复 × 依赖深度。

每个桶设置数量、正确率和重复上限。用 MinHash/AST/程序行为或 embedding 去重，既删除表面复述，也避免把同一模板换数字生成十万遍。训练中保留一部分错误轨迹并配正确批注，可教会诊断；不能把未经标注的失败轨迹当正例。

### 数据切分和评估

- 按题源、模板族、仓库、API 场景和生成种子 group split；
- 对公开 benchmark 的题干、答案、测试与改写做污染扫描；
- 建立私有、动态和时间后移盲测；
- 报告分桶正确率，而不只报告平均 acceptance rate；
- 人工抽检高分、低分和阈值附近样本，校准自动验证器。

训练前还应做 tokenizer 往返测试，确保代码缩进、LaTeX 反斜杠、JSON 引号和 Unicode 符号不丢失。

### 面试简答版

数学、代码和工具调用数据都应以“可执行验证”为中心。数学用数值重算、代回约束、CAS 或形式证明器，分别验证过程和终值；代码在无网络沙箱中编译，跑隐藏/属性/变异测试并按仓库切分；工具轨迹保存完整 schema、状态、call、observation 和最终回答，用 mock 环境重放，覆盖参数错误、超时、权限和副作用确认。三者都要做许可、隐私、去重和 benchmark 污染过滤，按能力矩阵控制难度与多样性，记录来源和验证器版本。模型评分只能补充，不能替代外部执行结果。
