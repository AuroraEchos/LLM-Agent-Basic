> **问题：** Tokenizer 的 Normalization 和 Pre-tokenization 可能引入哪些信息损失？

## 我的答案

Tokenizer 通常不是直接在原始字符串上做 BPE/Unigram，而是先经过：

```text
原始文本 → Normalization → Pre-tokenization → 子词模型 → token IDs
```

- **Normalization（规范化）**会转换字符串本身，使不同写法更一致；
- **Pre-tokenization（预分词）**先按空白、标点或正则切出候选片段，再让子词算法在片段内部切分。

两者能降低词表碎片、提高统计效率，但也可能删除原始信息，或者限制子词模型可选择的边界。

### Normalization 可能损失什么

#### Unicode 规范化

NFC/NFD 主要在预组合字符和组合字符之间转换；NFKC/NFKD 还会做兼容性折叠，信息损失更明显。例如：

```text
①  → 1
Ａ → A
```

规范化后视觉或兼容形式的差异无法从 token IDs 中恢复。某些语言文字、数学符号、单位和版式字符的差异可能具有业务含义，不能默认都折叠。

#### 大小写、重音和文字体系

Lowercase 或 accent stripping 可能造成：

```text
US      → us
résumé  → resume
```

这会把国家缩写与代词、不同人名或外来词合并。繁简转换、假名统一等也可能把多个原始形式映射为一个形式，适合搜索召回，却未必适合精确生成或引用。

#### 空白、控制字符与标点

以下操作都可能丢失结构：

- 连续空格折叠为一个空格；
- 删除行首空格、Tab、换行或末尾空格；
- 删除零宽字符、方向控制符、emoji variation selector；
- 把全角标点转换成半角，或把不同引号、横线统一。

自然语言中影响可能不大，但对 Python 缩进、Markdown 表格、日志字段、诗歌排版、补丁文件、密码、签名串和精确复制任务可能是致命的。

从数学上看，如果两个不同原文 $x_1\ne x_2$ 经规范化后满足：

$$
N(x_1)=N(x_2)
$$

那么后续无论使用多大的词表，都无法仅凭 token IDs 判断原文是哪一个。这是多对一映射造成的不可逆信息损失。

值得特别注意：**Byte Fallback 只能保证覆盖规范化后的字节。** 如果大小写、空白或字符在此前已被删除或改写，转成 byte token 也无法找回原文。

### Pre-tokenization 可能损失什么

预分词有两类影响，应区分开来。

#### 1. 真正修改或丢弃分隔符

某些实现按 `split()` 切词后不保留空白，或者清洗标点再切分。这样：

```text
"a  b"、"a b"、"a\tb"
```

可能都变成相同的两个片段，无法无损解码。换行、缩进和标点同理。

#### 2. 文本仍保留，但强制了不可跨越的边界

更完善的预分词器会保留空白和标点，因此原文仍可恢复；但如果它先把 `3.14` 切成 `3`、`.`、`14`，后续 BPE 就无法学习跨越这些边界的 `3.14` token。这不一定是信息丢失，却会改变 token 长度、统计共享方式和模型学习难度。

典型风险包括：

- URL、邮箱、文件路径和版本号被标点规则切得过碎；
- `don't`、连字符词、小数和科学计数法被不合适地分割；
- `==`、`->`、`::` 等代码运算符不能形成稳定 token；
- 中文、日文等不以空格分词的文本被套用英文规则；
- emoji 的肤色修饰符、variation selector、ZWJ 组合被拆散；
- 日志 ID、哈希、电话号码等结构化字段失去边界特征。

因此，“解码能还原文本”只证明字节未丢失，不代表预分词策略没有造成表示效率和建模能力损失。

### Offset Mapping 也会失真

NER、抽取式问答、文本高亮和数据审计经常要把 token span 映射回原文字符位置。若规范化改变了长度，例如一个组合字符被拆成多个 code point，或多个空白被折叠，那么规范化文本上的 offset 不能直接当作原始文本 offset。

工程上需要同时区分：

- 字节 offset；
- Unicode code point offset；
- 用户看到的 grapheme cluster offset；
- 规范化前与规范化后的 offset。

否则模型预测的位置即使正确，前端也可能高亮错字符。只有保存 normalization alignment，或保留原文并维护映射表，才能可靠回溯。

### 安全性边界

规范化既可能降低攻击面，也可能制造新的混淆。例如统一大小写有助于规则匹配，但 Unicode 同形异义字符不一定会被统一；若安全过滤器和模型 Tokenizer 使用不同规范化流程，攻击文本可能在两侧呈现不同形式。

因此认证标识、域名、路径、策略匹配等安全敏感场景，不能把“看起来相同”直接当作“规范化后相同”，也不能让过滤层与模型层各用一套未经对齐的规则。

### 如何评估和缓解

1. **按任务选择最小规范化**：自然语言搜索、代码、数学和多语言文本应使用不同 profile；
2. **默认保留原文**：清洗结果用于建模，原文用于展示、审计和精确 span 回溯；
3. **保留分隔符与映射**：预分词不随意丢空白，记录每个 token 对原文的 offset；
4. **保护结构模式**：针对 URL、邮箱、数字、代码运算符、emoji grapheme cluster 做专项规则；
5. **做碰撞与往返测试**：测量 `decode(encode(x))`，并检查哪些不同样本规范化后发生碰撞；
6. **分领域统计效率**：比较字符数/token、byte 数/token、序列长度和 fallback 率，避免只在英语均值上评估；
7. **版本化整个流水线**：Normalization、Pre-tokenization、词表和后处理必须随模型一起锁定版本。

往返测试应根据目标定义：如果产品要求无损复制，就应和原始字符串逐字节比较；如果任务明确接受 NFC，则可以和约定的规范形式比较，但必须把这一契约写清楚。

### 面试简答版

Normalization 会直接改写字符串，例如大小写统一、NFKC、去重音、折叠空白和删除控制字符；不同原文可能因此映射成同一结果，这是不可逆的信息损失，而且 Byte Fallback 也救不回预处理前已删除的内容。Pre-tokenization 若丢弃空白或标点也会损失原文；即使保留全部字符，硬切分边界仍会阻止 BPE 跨边界合并，影响序列长度和建模效率。工程上要采用任务相关的最小规范化，保留原文和 offset 映射，保护代码、URL、数字、emoji 等结构，并用往返、碰撞和分领域效率测试验证。
