## 我的答案

评估 Tokenizer 不应只报一个“平均 token 数”。一个完整评估至少包含：**压缩效率、字符/字节覆盖、UNK 和 fallback 行为、词表利用率、可逆性和分语公平性**，并必须在 held-out 数据上按语言、领域和数据类型分层报告。

### 压缩率如何衡量

设一批原始文本经规范化后有：

- Unicode 字符数 $C$；
- UTF-8 字节数 $B$；
- 预分词后单词数 $W$；
- Tokenizer 输出 token 数 $T$。

常见指标有：

$$
\text{characters per token}=\frac{C}{T}
$$

$$
\text{bytes per token}=\frac{B}{T}
$$

$$
\text{token fertility}=\frac{T}{W}
$$

chars/token 和 bytes/token 越高，表示每个 token 承载原始内容越多；tokens/word 越低，表示词被切得越少。对跨语言比较，bytes/token 是比“词数”更一致的底层单位，但字节数也不等于语义信息量，所以最好同时报告多个指标。

还应注意：

- 是否将 BOS/EOS、聊天模板和其他特殊 token 计入 $T$；
- 是对每个文档先求比例再平均，还是对全部计数求宏平均；
- 不只看 mean，还要看 P50/P95/P99 和最差样本，避免少量极度碎片文本被平均数掩盖。

### 字符覆盖率

“字符覆盖”有两种常见口径，必须说清：

#### 按出现次数的 coverage

$$
\text{coverage}_{freq}
=
\frac{\text{能由基础字符表直接表示的字符出现次数}}
{\text{所有字符出现次数}}
$$

这是一些 Tokenizer trainer 中 `character_coverage` 类参数的直觉：保留能覆盖语料中绝大多数字符**出现次数**的 alphabet。

#### 按字符种类的 coverage

$$
\text{coverage}_{type}
=
\frac{\text{能直接表示的不同字符数}}
{\text{评估集中不同字符总数}}
$$

高频字符使 frequency coverage 很高，却仍可能遗漏大量生僻字、小语种字符和 emoji，因此 type coverage 可发现长尾覆盖不足。两者都应按 Unicode script/category、语言和领域分组。

Byte-Level 或 byte fallback 可让底层字节覆盖达到 100%，但不代表有 100% 的“高质量子词覆盖”。一个字符若每次都退化为 3–4 个 byte token，虽不 OOV，但仍有明显碎片和计算代价。

### 未知词问题如何衡量

#### UNK token rate

$$
\text{UNK rate}_{token}
=
\frac{\#\text{UNK tokens}}{T}
$$

还应报告：

- 含至少一个 UNK 的序列/文档比例；
- 发生 UNK 的 Unicode 字符、语种和数据类型；
- 一个 UNK 代替了多长的原始字节串。

单看 UNK token 比例可能误导：如果一整个长词被折叠成一个 `[UNK]`，UNK token 数只增加 1，但信息损失很大。因此可再计算被 UNK 覆盖的原始字符/字节比例。

#### Byte fallback rate

$$
\text{fallback rate}
=
\frac{\#\text{byte fallback tokens}}
{T}
$$

同时计算触发 fallback 的原始字符比例和每个 fallback 字符平均需要多少 byte token。这能区分“可逆但高度碎片”与“词表已学会高效表示”。

### 词表质量和分割稳定性

- **Vocabulary utilization**：词表中多少 token 在 held-out 数据出现，频次分布的长尾有多重。
- **Fragmentation**：长词、人名、URL、数字、代码标识符和 emoji 被切成多少 token。
- **Boundary quality**：分割是否经常与形态、汉语词组或代码标识符边界一致。这不是必须严格一致的目标，但可作为解释性诊断。
- **Perturbation stability**：只改大小写、空格、重音符号或一个字符时，token 序列是局部变化还是整段重切。
- **Round-trip**：对宣称无损的输入，验证 `decode(encode(x)) == x`。若有 normalization，应同时与 `normalize(x)` 比较并记录损失。
- **Normalization collision**：有多少不同原始字符串在规范化后变成相同 token IDs，对实体、代码和安全文本尤其重要。

### 评估协议

1. 使用与 Tokenizer 训练数据去重的 held-out corpus，防止词表记住评估片段。
2. 分别构建通用文本、每个语言、代码、数学、URL/JSON、emoji、噪声与对抗 Unicode 分层。
3. 报告 macro average（每语言同权）与 micro average（按字符/字节量加权），避免英文等大组掩盖小语种。
4. 将 token 指标转换为系统影响：固定 context 可容纳的原始字节、训练每 GB 的 token 成本、生成同等文本的解码步数。
5. 在同等数据/计算预算下训练小型 proxy model，用 bits-per-byte、下游任务和端到端吞吐做最终验证。

### 为什么不能直接比 token-level perplexity

两个 Tokenizer 将同一文本分成不同数量和粒度的 token，“每 token 平均 NLL”的单位已不相同。大 token 天然承载更多字符，其 token-level perplexity 不能与字节级模型横向解读。可将总 NLL 除以原始字节数，转为 nats/byte 或 bits-per-byte，在共同原始单位上比较。

### 面试简答版

压缩率可用 chars/token、bytes/token 和 tokens/word（fertility）衡量，并要分语言、领域报告均值与长尾分位数。字符覆盖要区分按出现次数的 frequency coverage 和按 Unicode 字符种类的 type coverage。未知词不只看 UNK token 比例，还要看被 UNK 覆盖的原始字节、含 UNK 的文档比例，以及 byte fallback token 率和每字符退化长度。Byte fallback 可使 OOV 为零，但不代表分词高效。还应检查词表利用率、round-trip、normalization collision 和语种公平性，最终用 bits-per-byte、下游效果和端到端吞吐验证。
