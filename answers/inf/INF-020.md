## 我的答案

核心方法是在每个解码步根据“当前已生成前缀对应的语法状态”计算允许 token 集合，把其他 logits 设为 $-\infty$。这样不是生成完再重试，而是从搜索空间中提前删除所有无法扩展成合法字符串的分支。

### FSM 约束

正则语言或固定格式可编译为有限状态机：

$$
M=(Q,\Sigma,\delta,q_0,F)
$$

$Q$ 是状态，$\Sigma$ 是字符/字节，$\delta$ 是转移，$F$ 是接受态。生成前缀后处于 $q_t$，token $v$ 对应一串 bytes/chars；只有整串能从 $q_t$ 逐字符完成合法转移，并且仍有机会到达接受态时才允许：

$$
v\in\mathcal A(q_t)
\iff\delta^*(q_t,\operatorname{text}(v))\text{ 有效}
$$

采样后将状态更新为 $\delta^*$ 的结果。EOS 只允许在接受态出现。

FSM 适合日期、枚举、固定 key 顺序、简单正则等；任意深度括号嵌套不是有限状态可完整表达，需要栈或限制最大深度。

### Grammar / Parser 约束

JSON、SQL、编程语言通常用 CFG、PEG 或增量 parser。状态不只一个 FSM node，还可能包含解析栈、候选 productions、当前字符串转义/数字状态等。

每一步：

1. parser 根据已生成 bytes 得到可接受的下一终结符/字符集合；
2. 将词表 token 映射为 token byte string；
3. 模拟该 token 通过 parser，保留不会报错且仍可完成的 token；
4. mask logits，在合法集合中 greedy/beam/sample；
5. 消费 token 更新 parser state；
6. 只在完整接受态开放 EOS。

为了避免每步扫描整个十万词表，可预计算 trie：词表 token bytes 共享前缀，沿 parser 合法字符边并行遍历；也可缓存 `(grammar_state, token_id)→next_state/invalid`。

### Tokenizer 是最容易犯错的地方

Grammar 通常定义在字符或 UTF-8 bytes 上，模型选择的是 token。一个 token 可能是：

- 多个字符，如 `"name"`；
- 一个关键字加前导空格；
- JSON 字符串的一部分；
- 跨越语法终结符边界，如 `": [`；
- 不完整 UTF-8 byte 片段。

不能只允许“下一个合法字符对应的单字符 token”，否则会误删大量合法 token，甚至候选为空。约束器必须消费 token 的完整解码 bytes，并正确处理 tokenizer 的前导空格映射、byte fallback 和增量 UTF-8 状态。

### JSON：语法、Schema 与语义层次

只用 JSON grammar 能保证括号、引号、转义、逗号和数字格式合法，但不能保证：

- 必填字段存在；
- 字段类型、枚举、范围和数组长度；
- 不出现额外字段；
- 字段之间的业务依赖。

JSON Schema 可编译为更强的解码状态，例如对象已生成哪些 keys、当前 value 应为何种类型。但复杂的 `oneOf`、递归 schema、浮点范围或跨字段条件可能导致状态爆炸，部分约束更适合生成后验证。

常见折中是 grammar 保证 JSON syntactic validity，schema validator 验证语义；失败时把精确错误反馈给模型做有限次数修复。即便 grammar 保证合法，也应使用标准 JSON parser 重新解析，不能信任字符串拼接。

### SQL：合法不等于安全或可执行

SQL grammar 只能保证语法属于某个方言。它不保证表/列存在、类型匹配、查询有权限、成本可控，更不保证无注入或无破坏操作。

安全方案应：

- 使用目标数据库方言与 schema-aware 标识符白名单；
- 只开放所需 AST 子集，例如只读 `SELECT`；
- 字面值用绑定参数，不让模型拼接不可信输入；
- AST 解析后再次执行 policy check；
- 使用只读、最小权限账号，设置 timeout、row/scan limit；
- 在事务/沙箱中执行，并审计实际 query plan。

Grammar 是纵深防御的一层，不是数据库授权替代品。

### 性能与失败处理

约束越强，合法集合计算越贵，但候选变少也可能让采样更快。应缓存 grammar state、使用词表 trie/bitset，并让 GPU mask kernel 批量处理不同请求状态。Continuous batching 中每条序列可处于不同 parser state，元数据与 kernel 分歧是重要开销。

如果合法集合为空：

1. 记录 grammar state、最近 bytes 和 tokenizer 版本；
2. 判断 schema 本身是否不可满足或 token 映射有 bug；
3. 返回结构化错误或从安全检查点回退；
4. 不应静默开放所有 token，因为这会破坏“保证合法”的契约。

### 面试简答版

将目标格式编译为 FSM 或增量 Grammar parser。每步根据当前状态计算合法 token 集合，把其他 logits 设为 $-\infty$，采样后更新状态，并只在接受态允许 EOS。关键是 grammar 在字符/byte 层，而 token 可能含多个字符或跨语法边界，所以要对完整 token bytes 模拟转移，通常用词表 trie 和状态缓存加速。JSON grammar 只保语法，JSON Schema再约束字段；SQL grammar 也不保证 schema 正确和安全，仍需 AST 白名单、参数绑定、只读权限和执行限额。合法集合为空必须报错/安全回退，不能解除约束。
