> **问题：** Draft 模型大小、候选长度和接受率如何共同决定投机解码收益？

## 我的答案

投机解码的收益取决于一次 target verification 能摊销多少输出 token，以及为了提出这些 token 付出了多少 draft 与验证成本。Draft 太小虽然便宜但接受率低；太大虽接近 target，却可能自身就接近 target 的延迟。候选长度太短摊销不足，太长则常在前面拒绝，后续 draft/verification 工作浪费。

### 期望每轮提交 token 数

候选长度为 $\gamma$。若每个位置条件接受率近似相同为 $\alpha$，一个 round 提交“接受前缀 + 一个 residual/额外 target token”，期望长度为：

$$
E[N_{out}]
=1+\alpha+\alpha^2+\cdots+\alpha^\gamma
=\frac{1-\alpha^{\gamma+1}}{1-\alpha}
$$

当 $\alpha\to1$ 时趋近 $\gamma+1$；当 $\alpha$ 很低时接近 1，再长候选也无收益。

若各位置接受率为 $\alpha_i$：

$$
E[N_{out}]
=1+\sum_{k=1}^{\gamma}\prod_{i=1}^{k}\alpha_i
$$

越靠后的候选只有前面全接受才有价值，所以早期位置准确率最重要。

### 简化速度模型

设普通 target 单 token Decode 时间为 $T_1$；draft 生成一个 token时间为 $D_1$；target 验证 $\gamma$ 个候选的批量时间为 $V(\gamma)$。忽略调度时：

$$
\text{speedup}\approx
\frac{E[N_{out}]\cdot T_1}
{\gamma D_1+V(\gamma)+T_{overhead}}
$$

投机成立的关键是 $V(\gamma)$ 远小于 $\gamma T_1$：target 对多个已知候选能用 Prefill 式并行矩阵运算，而普通 Decode 要串行加载 target 权重 $\gamma$ 次。

### Draft 模型大小

更大的 draft 通常：

- 与 target 分布更接近，$\alpha$ 提高；
- 但每个 draft step 更慢、权重和 draft KV 占显存；
- 与 target 同 GPU 时争用 HBM/计算，跨 GPU 时增加通信；
- 可能降低能同时服务的 batch 与 target KV 容量。

选择目标不是最高 draft accuracy，而是单位 draft 时间带来的 target 接受 token 数。可比较：

$$
\frac{E[N_{accepted}]}{\gamma D_1+\text{draft overhead}}
$$

蒸馏一个对 target logits 匹配的小 draft，往往比同参数但只按语言模型 Loss 训练的 draft 更合适。Tokenizer 和 chat/domain 分布也要一致。

### 候选长度 $\gamma$

增加 $\gamma$ 的边际收益约为“前 $\gamma$ 个都接受”的概率：

$$
\Delta E[N_{out}]=\alpha^\gamma
$$

而 draft 多一步的成本始终存在，target verification 的序列长度/Attention 也增加。因此有有限最优值。代码和格式化文本通常可预测性高，适合更长候选；创作、高温采样或推理分叉处接受率低，应缩短。

动态策略可以根据最近 acceptance、target/draft KL、token entropy 或请求长度调整 $\gamma$，但估计和变 shape 也有成本。

### 接受率受什么影响

- target 与 draft 模型能力/蒸馏质量；
- temperature：高温通常增加 draft/target 样本分歧；
- top-p、grammar、repetition 等是否两边一致；
- 任务：代码/固定短语高，开放创作低；
- 上下文长度和领域漂移；
- 量化误差与数值实现；
- greedy 接受与 exact sampling 接受定义不同。

不要只报告 token acceptance rate。应报告 average accepted length、rounds、实际 committed tokens/verification 和被拒 suffix 的浪费。

### 服务负载下为何可能不加速

单请求 Decode memory-bound 时投机收益大；高并发 continuous batching 已能很好复用 target 权重，verification 加长序列可能挤占 batch，边际收益下降。其他风险包括：

- Draft+target 双模型占显存，减少并发；
- Prefill 很长、输出很短，Decode 加速占总延迟比例小；
- target verification kernel 对变长候选支持差；
- TP target 与单卡 draft 的同步/传输开销；
- 拒绝时 cache rollback、sampling 和调度 CPU 开销；
- SLO 关注 TTFT，而投机主要改善 TPOT/Decode。

### 选型流程

在真实 prompt/output/temperature trace 上，对多个 draft sizes 和 $\gamma$ 网格测：接受长度分布、target verifications/output token、TTFT、TPOT、吞吐、P99、显存和功耗。用基线 continuous batching 做相同并发/SLO 对比，而不是只做 batch=1 微基准。

### 面试简答版

若每位置接受率约为 $\alpha$、候选长 $\gamma$，每轮期望提交 $1+\alpha+\cdots+\alpha^\gamma$ 个 token；速度近似是这部分普通 target 时间除以 $\gamma$ 次 draft 成本加一次 target verification。Draft 大会提高接受率但增加串行 draft 延迟和显存；$\gamma$ 增大的边际收益只有 $\alpha^\gamma$，低接受率时后半候选都浪费。最佳点要按任务、温度和并发动态/实测选择，高并发下 target 已充分 batching，双模型投机未必比单请求场景收益大。
