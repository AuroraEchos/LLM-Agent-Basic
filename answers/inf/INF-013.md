> **问题：** Iteration-Level Scheduling、Chunked Prefill 和 Decode-First 各解决什么问题？
>
> **分类：** 推理、解码与 KV Cache

> **来源：** [INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md](../../INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md)

## 我的答案

三者是逐层递进的服务调度概念：Iteration-Level Scheduling 把可调度边界从整请求缩小到单次生成迭代；Chunked Prefill 再把一个很长的 Prefill 拆成多个可抢占/交错的 token 块；Decode-First 是在每次迭代分配预算时优先保证已在流式生成的请求。

### Iteration-Level Scheduling

自回归 Decode 每一步只生成一个 token。传统 request-level batch 一旦开始，就要等所有请求完成才能换成员；[Orca 原论文](https://www.usenix.org/conference/osdi22/presentation/yu)提出每次只调度模型的一个 iteration，然后重新决定下轮 batch。

它解决：

- 输出长度不一致导致的 batch slot 空闲；
- 已完成请求不能及时返回；
- 新请求必须等待整批结束；
- 在线到达下 GPU 利用率低。

它是 continuous batching 的调度基础，但若一次 Prefill 仍不可分割，长 prompt 可以占满一个 iteration 很久，正在 Decode 的用户仍会卡顿。

### Chunked Prefill

把长度为 $S$ 的 prompt 拆为大小至多 $C$ 的 chunks：

$$
S=C_1+C_2+\cdots+C_k
$$

每个调度 iteration 只处理一个或若干 chunk，并把已完成部分的 KV 留下；下一轮继续 suffix。这样可在 chunks 之间插入 decode tokens。[Sarathi](https://arxiv.org/abs/2308.16369)以 chunked prefill 和 decode-maximal batching 解决 Prefill/Decode 干扰。

它解决：

- 超长 Prefill 的 head-of-line blocking；
- 单次 iteration 时长波动导致的 TPOT 抖动；
- Decode memory-bound、小 batch利用率低——与一块 compute-heavy Prefill 混合有时能提高 GPU 利用率；
- 给调度器更细的 TTFT/TPOT 权衡单位。

代价是多次调度和 kernel launch；每个 chunk 要读取此前 KV，Attention 计算/访存可能不如一次完整 Prefill 高效；chunk 太小开销大、TTFT 变差，太大又造成 decode stall。

### Decode-First

每轮先为所有或高优先级 active decode 请求各预留一个 token，再用剩余 token/显存预算安排 Prefill chunks：

```text
budget = max_tokens_per_iteration
schedule active decodes first
remaining budget → prefill chunks / new requests
```

它主要保护 TPOT/ITL：已经开始向用户流式输出后，长时间停顿非常明显。Decode tokens 数少、但有严格连续性 SLO，优先级通常高于尚未产生首 token 的 Prefill。

但无限制 Decode-First 会让等待队列中的长 prompt 饥饿，TTFT 爆炸。在持续高 decode 负载下可能永远没有足够预算完成 Prefill。

### 需要联合设计

常见策略是：

1. iteration 边界动态重排请求；
2. decode 获得基础优先预算；
3. Prefill 按 chunk 填充剩余 token budget；
4. waiting time/aging、deadline 或租户权重逐渐提高 Prefill 优先级；
5. KV 接近上限时停止 admission、抢占低优先级请求或缩小 batch；
6. 用性能模型约束预计 iteration duration，而不只数 token。

Token budget 并非等价计算预算：一个 decode token 要读取长 KV，一个 Prefill token 位于不同 chunk 时 Attention 长度也不同；MoE、GQA 和序列长度会改变成本。成熟调度器会用 profiling/预测模型估计时间。

### 指标权衡

- 增大 chunk：Prefill 效率和 TTFT可能改善，但 TPOT P99 变差；
- 缩小 chunk：decode 更平滑，但调度/kernel 开销和 Prefill 总时间上升；
- 更强 decode-first：已启动请求体验好，waiting TTFT 与公平性变差；
- 大 token budget：吞吐更高，单次 iteration 更长；
- 抢占：立即腾出 KV，但 swap 或 recompute 增加后续成本。

必须在真实输入/输出长度和到达率 trace 上测 TTFT、TPOT、端到端延迟、吞吐、SLO attainment 和 starvation，而不只离线满载 tokens/s。

### 面试简答版

Iteration-Level Scheduling 每生成一轮 token 就重新组成 batch，解决不定长请求让 slot 空闲的问题；Chunked Prefill 把长 prompt 拆成多个块，与 Decode 交错，避免一次 Prefill 阻塞流式输出；Decode-First 每轮先给活跃 Decode 分配 token，保护 TPOT。三者组合能提高利用率和尾延迟，但 chunk 太小会增加重算/调度开销，decode 永远优先又会让 Prefill 饥饿，所以需要 token/时间预算、aging/deadline 和 KV admission control，在 TTFT、TPOT、公平与吞吐之间权衡。
