## 我的答案

长上下文不是单一的“Attention 太慢”，而是四个相互耦合的瓶颈：Prefill 的二次 Attention 计算；随 token 线性增长的 KV 容量；Decode 每步扫描历史 KV 的带宽；以及长短请求混合造成的调度和尾延迟。优化一项常会把瓶颈转移到另一项。

### 1. Attention 计算

Prompt 长度为 $S$、隐藏维 $H$，全局 Prefill Attention 的 score/PV 计算约：

$$
O(S^2H)
$$

而投影/FFN 约 $O(SH^2)$。当 $S$ 足够大，二次项显著；即使 FlashAttention 不物化 $S^2$ 矩阵，FLOPs 仍存在。多卡 Context/Sequence Parallel 可分摊 token 维，但要交换 K/V、softmax统计或输出，通信随长度增长。

Decode 有 cache 后每步只一个 query，但要与 $S$ 个历史 keys/values Attention：

$$
O(SH_{kv})\text{ per output token}
$$

生成 $T$ 个 token 时历史继续增长，累计约含 $O(ST+T^2)$ Attention。

优化：FlashAttention、局部/滑窗/稀疏 Attention、层间混合全局/局部、上下文并行。局部/稀疏会改变模型可见信息，最好训练时适配，不能只在推理端无损替换。

### 2. KV Cache 容量

标准 cache：

$$
M_{KV}=2BSLn_{kv}d_hb
$$

128K context 即使单请求也可能占数 GB；并发数一高，KV 而非权重成为显存主项。分页只能减少碎片，不能改变每 token bytes。

容量优化：

- 架构层：GQA/MQA/MLA；
- 表示层：FP8/INT8/INT4 KV quantization；
- 范围层：sliding window、eviction、compression；
- 系统层：PagedAttention、prefix block sharing、host/offload。

量化有数值误差与 scale 开销；eviction/窗口会丢历史；offload 受 PCIe/网络带宽限制；prefix sharing 只对相同前缀有效。

### 3. Decode 的 KV 带宽

每生成一个 token，每层都要读取该请求保留的 K/V。若 cache bytes/token 为 $m_{tok}$，长度 $S$ 的单步 KV 读取量粗略与 $S\cdot m_{tok}$ 同阶，TPOT 会随 context 增长。长上下文下即使 KV“放得下”，HBM 带宽也可能让生成很慢。

GQA/MQA、KV 量化同时减少容量和带宽；合理 batch 可提高模型权重重用，但不同请求的 KV 仍各自读取。KV layout、block size、连续访问、L2命中和 paged kernel 会决定有效带宽，理论 bytes 下降不等于同比加速。

PD 分离时，Prefill 产生的大型 KV 还要传给 Decode 节点：

$$
T_{transfer}\approx M_{KV}/BW_{network}+T_{setup}
$$

超长 prompt 可能让网络传输抵消分离收益，需要高速互连、流式传输和拓扑感知路由。

### 4. 调度与长尾

长 Prefill 一次执行会阻塞正在流式 Decode 的请求，制造 TPOT spike；长生成会长时间占据大量 KV blocks。混合负载下会出现：

- head-of-line blocking；
- KV admission 后中途增长导致容量不足；
- 抢占后重算超长 Prefill代价巨大；
- 短请求被长请求拖累，P99远高于平均；
- chunk 太大阻塞 Decode，太小又降低 Prefill效率；
- prefix cache 中超长对象挤出更多高频短前缀。

需要 chunked prefill、decode优先但带 aging、长度/KV-aware admission、租户配额、deadline、最大 context/output限制和负载分流。可把超长请求送到独立池，避免污染普通交互 SLO。

### 位置与模型质量边界

“支持 128K position”不等于能有效利用 128K：

- RoPE 外推/缩放可能在远位置退化；
- 训练中长序列和远程依赖不足；
- 注意力随长度稀释，关键证据被噪声淹没；
- Prompt 中存在重复/冲突指令；
- 只测 needle retrieval不能代表多跳推理和全局理解。

因此还需评估不同证据位置、干扰项、多个 needle、长文档 QA、精确复制和真实 Agent 轨迹。很多任务先做 RAG/摘要减少无关 context，比盲目塞满窗口更高效，但检索会引入召回损失。

### 端到端容量规划

对真实 trace 同时测：

- TTFT 随 input length 的曲线；
- TPOT 随当前 context 和 batch 的曲线；
- KV bytes/token、碎片率和最大并发；
- Prefill/Decode/网络 KV transfer 占比；
- SLO goodput、preemption、cache hit 和 OOM margin；
- 长上下文任务质量。

再针对主瓶颈选择：Attention FLOPs 高用高效/稀疏 Attention；容量不足用 GQA/量化/分页；带宽高用KV压缩和布局；干扰严重用调度/PD分离。不能只用一个 128K 单请求 benchmark宣称系统支持生产长上下文。

### 面试简答版

长上下文 Prefill 的全局 Attention 是 $O(S^2H)$；Decode 虽有 cache，每步仍以 $O(S)$ 读取/计算历史 KV。Cache 本身按 $2BSLn_{kv}d_hb$ 线性占显存，并发时常成为容量上限；PD分离还要传输整份 KV。调度上，长 Prefill会阻塞 active Decode，长输出又长期占 blocks，造成队头阻塞和P99尖峰。对应手段是 Flash/局部 Attention、GQA/MQA/MLA与KV量化、PagedAttention、chunked prefill、admission/长请求隔离和高速KV传输；同时必须验证模型真的能利用远程信息，而不只是位置编码允许该长度。
