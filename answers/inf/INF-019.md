> **问题：** Logits Processor、Logits Warper 和受约束解码分别在什么阶段工作？

## 我的答案

三者都位于“模型输出下一 token logits”之后、“选择下一 token”之前，但职责不同：Processor 根据历史和规则修改分数；Warper 为随机采样重塑/截断概率分布；受约束解码根据一个外部状态机只允许能继续形成合法结构的 token。框架可能把它们都实现成同一种可调用接口，概念上仍值得区分。

### 通用流水线

```text
model forward
→ raw logits z
→ hard constraints / Logits Processors
→ sampling Warpers
→ normalization
→ greedy / multinomial / beam candidate selection
→ update grammar/stop/history state
```

具体顺序依库和版本而异，应以调用链为准。[Transformers 官方生成工具文档](https://huggingface.co/docs/transformers/internal/generation_utils)也将 LogitsProcessor 描述为修改模型预测 scores 的组件，并提供 temperature、top-p、min-p 等相应处理器/warper；名称不应当作跨框架协议。

### Logits Processor

Processor 一般是确定性的规则变换：

$$
z'=f(z,y_{<t},\text{config/state})
$$

常见例子：

- repetition/frequency/presence penalty；
- min length 前把 EOS 设为 $-\infty$；
- bad words、allowed tokens、forced BOS/EOS；
- no-repeat n-gram；
- classifier-free guidance；
- 修正/拒绝 NaN、Inf；
- grammar 当前状态的合法 token mask。

它既可用于 greedy，也可用于 sampling/beam。需要注意：Beam Search 中输入 `scores` 可能已是 log-softmax 加累计 beam score，而非原始 logits；自定义 processor 必须遵守框架契约。

### Logits Warper

Warper 主要定义 sampling distribution：

$$
z''=g(z';T,K,P,\ldots)
$$

典型是 temperature、top-k、top-p、min-p、typical sampling。它们不只是禁止非法 token，而是控制随机性、尾部质量和多样性，通常只在 `do_sample` 路径有意义。

Top-k/top-p 将被过滤项设为 $-\infty$；temperature 缩放剩余 logits；之后 softmax 并重新归一化。多个 warper 的顺序不交换，例如先 temperature 会改变 top-p/min-p 集合。

### 受约束解码

约束器维护状态 $q_t$，根据已生成前缀给出合法集合：

$$
\mathcal A(q_t)=\{v:\delta(q_t,v)\text{ 有定义且可到达接受态}\}
$$

然后硬 mask：

$$
z_v'=\begin{cases}
z_v,&v\in\mathcal A(q_t)\\
-\infty,&\text{otherwise}
\end{cases}
$$

采到 token 后更新 $q_{t+1}=\delta(q_t,v)$。FSM/正则适合固定格式，CFG/parser 适合嵌套 JSON、SQL 子集和编程语法；JSON Schema 还需要对象字段、类型和必填约束的状态。

约束解码可以作为特殊 Processor，也可以集成到 beam expansion/grammar-aware kernel。它保证的是约束所表达的合法性，不保证内容事实正确、SQL 安全或 schema 之外的业务规则。

### 顺序为什么重要

推荐优先级通常是：

1. 数值清理和不可违反的 safety/grammar mask；
2. forced token、min/max length、bad words；
3. repetition/frequency 等软行为规则；
4. temperature 与概率截断；
5. 在剩余合法集合采样。

如果先 top-k 后 grammar mask，top-k 的 K 个恰好都不合法，就会得到空集合；正确做法是 grammar 先删非法项，或过滤器保证合法候选最少数。若所有 logits 都是 $-\infty$，softmax 会 NaN，系统应返回明确约束错误/回退，而不是悄悄解除安全约束。

Beam Search 的 processor/constraint 可能破坏原 scores 的归一化。若搜索算法假设 log probabilities，需要重新 log-softmax或使用框架提供的 renormalization 选项，否则不同 beam 分数不可比。

### 可观测与测试

记录每一步 processor 名称/版本、约束状态、过滤前后候选数、最终 token 和 stop 原因。用边界测试验证：EOS、空合法集、Unicode/token 跨边界、重复规则与 grammar 冲突、beam parent reorder 和 batch 中不同 grammar state。

### 面试简答版

模型 forward 先给 raw logits。Logits Processor 根据历史做确定性规则修改，如 repetition、min-length、bad words、forced token；Logits Warper 主要服务采样，用 temperature、top-k/top-p/min-p 重塑或截断分布；受约束解码维护 FSM/Grammar 状态，把不能继续形成合法结构的 token 设为 $-\infty$。通常先执行硬 grammar/safety 约束，再做软惩罚和 sampling warper，最后归一化选择；否则 top-k 可能先把所有合法 token 删掉。框架可能统一接口和改变顺序，生产中需锁版本并处理空候选与 beam 重新归一化。
