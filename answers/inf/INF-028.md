> **问题：** 如何分析推理过程是 Compute-Bound 还是 Memory-Bound？
>
> **分类：** 推理、解码与 KV Cache

> **来源：** [INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md](../../INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md)

## 我的答案

判断 Compute-Bound 还是 Memory-Bound，不能只看 GPU utilization；核心是计算算术强度（Arithmetic Intensity）并与硬件 Roofline 的转折点比较，再用 profiler 的 Tensor Core、HBM 带宽和 stall 指标验证。

### 算术强度

$$
I=\frac{\text{FLOPs}}{\text{从慢速内存搬运的 bytes}}
\quad[\text{FLOPs/byte}]
$$

硬件峰值算力 $P_{peak}$、HBM 峰值带宽 $BW_{peak}$，ridge point：

$$
I^*=\frac{P_{peak}}{BW_{peak}}
$$

- $I<I^*$：理论上 $I\cdot BW_{peak}<P_{peak}$，偏 memory-bound；
- $I>I^*$：带宽足以喂饱计算单元，偏 compute-bound。

真实上限：

$$
P_{attainable}\le\min(P_{peak},I\cdot BW_{peak})
$$

### 用矩阵乘理解 Batch 的作用

权重矩阵 $W\in\mathbb R^{H\times H}$，对 $M$ 个 token 做 $XW$，粗略 FLOPs 为 $2MH^2$，若权重是 $b$ bytes 且主要读取一次，忽略输入输出：

$$
I\approx\frac{2MH^2}{bH^2}=\frac{2M}{b}
$$

Prefill 的 $M=B\cdot S$ 通常很大，权重重用高，GEMM 偏 compute-bound；单请求 Decode 的 $M=B$ 很小，每步读取整套权重，偏 memory-bound。增大 continuous batch 会线性提高这部分算术强度，直到其他瓶颈出现。

### Attention 还要单独分析

- Prefill 全局 Attention 计算 $QK^T/PV$，长序列 FLOPs 为 $O(S^2d)$；FlashAttention减少 HBM 中间量，使计算单元更忙；
- Decode 每步 query 与 $S$ 个 KV 做 Attention，FLOPs 与读取 bytes 都随 $S$ 增长，算术强度常不高，KV HBM 带宽明显；
- GQA/MQA/量化减少 KV bytes，会移动瓶颈；
- 很短序列/小 head 可能受 kernel launch/latency，而不是纯带宽或纯算力。

### Profiler 证据

Compute-bound 常见信号：

- Tensor Core/SM math throughput接近可达峰值；
- HBM 带宽未饱和；
- 增加算力/降低 FLOPs 能明显加速，单纯压缩权重收益小；
- 大 GEMM 占主导，occupancy 足够。

Memory-bound 常见信号：

- HBM read/write throughput接近实测带宽；
- Tensor Core 利用率低，memory dependency stalls高；
- 量化权重/KV、增大 batch 重用或融合 kernel 显著加速；
- 每 token 都重新流式读取大量权重/cache。

但“HBM 没达到理论 100%”不证明非 memory-bound：非连续访问、小 transaction、L2 miss、依赖链和并发不足都可能让有效带宽远低于峰值。

### 分层/分阶段而不是贴一个总标签

一个推理 step 可以同时包含：

- GEMM compute-bound；
- Norm/激活/采样 memory或latency-bound；
- TP all-reduce network-bound；
- CPU scheduler launch-bound；
- KV gather memory-bound。

应分别 profile Prefill/Decode、不同 batch/context 和每类 kernel，计算 weighted bottleneck。端到端 GPU idle 还可能是数据、同步或队列问题，Roofline 不覆盖网络与CPU。

### 诊断实验

1. 改 batch/token 数，看吞吐是否随权重重用上升；
2. 权重从 BF16 降 INT8/INT4，看 Decode 是否按 bytes 改善；
3. 改 context 长度，看 TPOT 与 KV 读取是否近线性增长；
4. 使用 FlashAttention/融合 kernel，判断中间 IO；
5. 降 GPU clock/功耗或比较不同算力—带宽比硬件；
6. 用 profiler 获取实际 FLOPs、DRAM bytes、L2 hit、SM active、stall 和通信时间。

优化应针对实测瓶颈：compute-bound 用更低 FLOPs/更高 Tensor Core效率；memory-bound 用量化、融合、批处理和更好布局；latency/network-bound 则处理 kernel launch、调度和通信。

### 面试简答版

先算算术强度 $I=FLOPs/bytes$，与硬件 ridge point $I^*=P_{peak}/BW_{peak}$ 比；可达性能上限是 $\min(P_{peak},I\cdot BW)$。Prefill 一次对大量 token复用权重，GEMM 强度高，常 compute-bound；小 batch Decode 每 token重读权重和长 KV，常 memory-bound。再用 profiler 验证 Tensor Core/SM 吞吐、HBM 带宽、L2 miss和 stall。必须按 kernel、阶段、batch和context分析，因为同一步还可能同时有网络、launch和memory瓶颈。
