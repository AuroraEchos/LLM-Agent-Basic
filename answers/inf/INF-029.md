## 我的答案

Roofline Model 用“算术强度—性能”图把硬件的计算上限和带宽上限放在一起，解释为什么同一 Transformer 在 Prefill 能接近大 GEMM 峰值，而 Decode 单请求却常只利用很少的 Tensor Core 算力。

### Roofline 公式

横轴是算术强度：

$$
I=\frac{FLOPs}{HBM\ bytes}
$$

纵轴是实际性能 $P$（FLOPs/s）。硬件上界：

$$
P\le\min(P_{peak},BW_{peak}\cdot I)
$$

两条线交点：

$$
I^*=\frac{P_{peak}}{BW_{peak}}
$$

- 左侧斜线区：多搬一个 byte 才能多做计算，memory-bound；
- 右侧水平区：数据重用已足够，主要受计算峰值限制，compute-bound。

### Prefill 为什么更靠右

Prefill 一次处理 $M=B\cdot S$ 个 prompt tokens。对 $H\times H$ 权重矩阵：

$$
F\approx2MH^2
$$

若权重主要从 HBM 读一次：

$$
Bytes_W\approx bH^2
$$

粗略：

$$
I_{prefill}\approx\frac{2M}{b}
$$

$M$ 很大时，每个权重元素服务很多 token，点向 Roofline 右侧移动；大矩阵也利于 Tensor Core tile 和 occupancy。中等上下文的 QKV/FFN 常 compute-bound。

长上下文 Attention 又有自己的 roofline：标准实现将 $S^2$ score/probability 写回 HBM，会把点向左拉；FlashAttention减少这些 bytes，提高算术强度和实际性能，但 $S^2$ FLOPs 本身最终仍可能成为计算瓶颈。

### Decode 为什么更靠左

Decode 每请求每步只有一个 token，矩阵乘的 $M=B$：

$$
I_{decode,dense}\approx\frac{2B}{b}
$$

单请求 BF16 时 $B=1,b=2$，仅约 1 FLOP/byte 的粗量级；每一步要从 HBM 流式读取整套模型权重。即使理论 Tensor Core 峰值巨大，也没有足够数据重用把它喂满。

此外新 query 必须读取历史 KV。对标准 Attention，每个 KV 元素参与有限的点积/加权运算，context 越长，总 bytes 越大，因此 Decode Attention也常带宽受限。

Continuous batching 增大 $B$，同一份权重为更多请求复用，使点向右移动；到达 ridge point 后，继续增大 batch 可能 compute-bound，同时 iteration 变长、TPOT恶化。

### 量化在 Roofline 中的解释

权重量化从 BF16 降到 INT4，理想上大幅减少权重 bytes，dense Decode 的 $I$ 提高；若有高效低精度 Tensor Core/kernel，带宽 roof 也能转化为更高 token throughput。但还要读取 scales、执行反量化，实际压缩和算力峰值都要按真实 dtype重算。

KV 量化同理主要移动 Decode Attention 的 bytes。Prefill 若本来 compute-bound，权重量化未必按存储倍数加速，甚至因反量化 kernel降低效率。

### Hierarchical Roofline

只画 HBM Roofline 可能漏掉：

- L2/shared memory/寄存器带宽；
- kernel launch 和依赖延迟；
- TP/PP/EP 网络带宽与 latency；
- CPU scheduler 与数据预处理；
- 小 shape 的 occupancy 和 Tensor Core tile浪费。

可分别建立 HBM、L2、互连 roofline，或在 profiler 中分析每层 memory hierarchy。若点远低于所有 roof，说明可能有同步、分支、低 occupancy 或实现问题，而非硬件物理上限。

### 如何实际绘制

1. 对目标 kernel/阶段统计真实 FLOPs，而不是全模型平均；
2. 从 profiler 取 DRAM bytes，避免把理论 tensor size 当成实际流量；
3. 用对应 dtype、频率和稀疏模式的实测 peak compute/bandwidth；
4. 标出不同 batch、prompt/context length、量化和 Attention kernel 的点；
5. 用端到端 TTFT/TPOT确认 kernel优化是否真正转化为用户收益。

### 面试简答版

Roofline 给出 $P\le\min(P_{peak},BW\cdot I)$，$I=FLOPs/bytes$，转折点是 $P_{peak}/BW$。Prefill 对 $B\cdot S$ 个 token复用同一权重，dense GEMM 的强度粗略为 $2BS/b$，通常在右侧、偏 compute-bound；Decode 每步只有 batch 个 token，强度约 $2B/b$，还要读取长 KV，常在左侧、偏 memory-bound。增大 continuous batch或量化会减少每 token bytes/提高复用，使 Decode 向右移动；FlashAttention则减少 Prefill Attention 的 HBM中间量。最终要用 profiler 的实际 FLOPs/DRAM bytes绘点。
