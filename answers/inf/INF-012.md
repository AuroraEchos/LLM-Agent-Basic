> **问题：** Continuous Batching 与静态 Batching 的调度差异是什么？
>
> **分类：** 推理、解码与 KV Cache

> **来源：** [INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md](../../INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md)

## 我的答案

静态 Batching 在一批请求开始后通常把成员固定到整批结束；Continuous Batching 则在每个或若干个模型迭代边界重新组成 batch，完成的请求立即退出，等待请求及时加入。后者更适合输出长度未知且差异巨大的自回归生成。

### 静态 Batching

```text
收集一批请求 → Prefill → 全批逐 token Decode → 最长请求结束 → 下一批
```

如果一批请求的生成长度是 `[20, 25, 200, 220]`，前两个很早完成，但其 batch slot 可能空闲到后两个结束；新请求也必须等待整批完成。Padding/finished mask 能保证语义正确，却无法充分利用空出的计算和 KV 容量。

优点是实现简单、shape 稳定，容易使用 CUDA Graph 和静态内存规划；离线吞吐、同长度任务或 beam search 可表现良好。缺点是 head-of-line blocking、长度长尾和在线到达会降低利用率并增加排队。

### Continuous Batching

调度器在 decode iteration 边界执行：

1. 移除已 EOS、达到长度或取消的请求；
2. 立即回收/复用其 KV blocks；
3. 从 waiting queue 选择新 Prefill 或已被抢占的请求；
4. 在 token/KV/计算预算内构造下一 iteration；
5. 每个活跃 decode 请求通常前进一个 token。

因此 batch size 和成员动态变化：

```text
iter 1: A B C D
iter 2: A B C D
iter 3: A   C D E   # B 完成，E 加入
iter 4: A   C D E F
```

[Orca](https://www.usenix.org/conference/osdi22/presentation/yu)将这种核心思路称为 iteration-level scheduling；后来系统通常把动态批处理与分页 KV 管理结合。

### 为什么吞吐与延迟更好

- 短请求无需等待同批长请求，可立即返回；
- 空 slot 很快被新请求填充，权重读取可被更多 token 摊薄；
- KV Cache 随请求进入/退出动态回收，提高并发；
- 可以根据 SLO、优先级、长度和预算做细粒度决策。

但 continuous 不等于“无条件越大越好”。活跃 batch 增大能提高吞吐，却会拉长一次 iteration，从而恶化每个请求 TPOT；新 Prefill 太大还会阻塞正在 Decode 的流。

### 调度器要同时管理什么

- GPU KV block 可用量；
- 每 iteration 的总 scheduled tokens；
- Prefill 与 Decode 混合的 kernel shape；
- FCFS、优先级、deadline 和租户配额；
- 抢占策略：swap KV、丢弃后重算还是拒绝；
- CUDA Graph 可覆盖的 batch buckets；
- 取消、超时、EOS 和流式回传；
- 多 GPU 各 rank 必须得到一致 batch 元数据。

若到达率超过可服务率，continuous batching 只能提高容量利用率，不能消除排队；必须有 admission control、限流和 backpressure。

### Prefill 是主要难点

Decode 每请求一 token，工作量较均匀；一个 100K prompt 的 Prefill 却可能占用很长 GPU 时间。简单把它一次插入 continuous batch 会造成 decode TPOT spike。因此常用 chunked prefill，把 prompt 切成 token chunks，与 decode iteration 交错，并限制每轮 token budget。

### 公平与饥饿

纯 decode-first 能保护已在生成的请求，却可能让长 Prefill 永远进不来；纯 FCFS 又可能被超长 prompt 阻塞。需要 aging、最大等待时间、预留 Prefill 配额或 deadline-aware 策略，并按 TTFT/TPOT 两类 SLO分别监控。

### 面试简答版

静态 batching 一批请求的成员固定到最长请求结束，短请求完成后的 slot 闲置，新请求产生队头阻塞；Continuous Batching 在每个 decode iteration 边界移除完成请求、回收 KV，并把等待请求加入，动态改变 batch，因此更适合不定长在线生成。它提升吞吐并降低短请求延迟，但 batch 太大和长 Prefill 会恶化 TPOT，需要 token/KV budget、chunked prefill、公平调度、抢占与 admission control。PagedAttention负责内存，continuous batching 负责调度，两者相关但不是同一机制。
