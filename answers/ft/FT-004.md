## 我的答案

Chat Template 是把结构化消息转换为模型 token 序列的协议。模型看到的不是 `role=user` 这个 JSON 字段，而是模板渲染后的特殊 token、换行、角色头和结束符。因此训练与推理模板不一致，本质上是输入分布和输出协议发生了变化。

### 一、常见不一致

- 训练用 `<|user|>`，推理却用 `User:`；
- system prompt 的位置、默认内容或是否存在不同；
- assistant header 在训练中由模型预测，推理时却已放进 Prompt，或反过来；
- 训练使用一种轮次结束 token，服务端却监听另一种 EOS/stop string；
- 换行、空格、BOS 重复添加或 EOS 被添加两次；
- 工具定义、tool call JSON、call ID 和 tool result 的序列化方式不同；
- 多模态 image token 的顺序或数量与 processor 不一致。

同样的可见文本，只要特殊 token ID 和边界不同，对模型而言就是不同输入。

### 二、会造成什么后果

1. **能力下降**：模型在陌生的角色标记下不能正确识别指令和回答位置，表现为答非所问或复述 Prompt。
2. **角色混淆**：模型可能继续生成 `user` 内容、伪造 system 指令，或把 tool result 当作自己应该生成的文本。
3. **停止失败**：EOS 不一致会导致过早停止、无限续写、重复角色头或吞掉下一轮消息。
4. **工具调用不可解析**：字段名、转义和 special token 不同，会令 JSON parser 或工具路由失败。
5. **Loss Mask 错位**：若训练 mask 是依据旧模板边界生成，换模板后可能把 user token 当 target，或者漏训 assistant 首尾 token。
6. **缓存失效**：系统 Prompt 多一个换行或 token，prefix/KV cache 的 token 前缀就不再相同。
7. **安全边界变弱**：system/user 分隔不清会增加 Prompt Injection 越权或角色伪造风险。

### 三、为什么少量格式差异也可能影响很大

特殊 token 是模型在 SFT 中学习到的控制信号。若模型主要在下面的条件分布训练：

\[
p_\theta(y\mid \texttt{[USER]}x\texttt{[ASSISTANT]})
\]

上线却查询：

\[
p_\theta(y\mid \texttt{User: }x\texttt{Assistant:})
\]

虽然人类认为语义接近，但第二种 token 前缀可能在训练中很少出现。较强模型有时能泛化，不代表协议可以不一致。

### 四、工程上如何保证一致

- tokenizer/model artifact 中只维护一个权威 `chat_template`，训练、离线评测和服务共同调用；
- 明确 `add_generation_prompt`、BOS/EOS、padding side、stop token 和 tool schema 版本；
- 保存 tokenizer、template、special token ID 与模型 checkpoint 的不可分割版本；
- 建立 golden tests：给定 messages，三条链路生成的 `input_ids` 必须逐 token 相同；
- decode 并可视化 role span 与 Loss Mask，覆盖多轮、空 system、工具调用、多模态和截断；
- 修改模板视为模型协议变更，需要回归正确率、工具成功率、停止率、安全集和缓存命中。

若线上必须迁移模板，稳妥方案是兼容旧协议一段时间，或用新模板继续 SFT，而不是直接切换字符串。

### 面试简答版

Chat Template 是消息到 token 的模型协议，训练和推理不一致会形成输入分布偏移。典型后果包括指令遵循下降、复述 Prompt、角色混淆、EOS 停止失败、工具 JSON 不可解析、Loss Mask 错位和 prefix cache 失效。工程上应把 tokenizer、special token、chat template 和 checkpoint 一起版本化，训练、评测、服务复用同一个渲染函数，并用 golden test 比较最终 input_ids，而不是只比较肉眼可见字符串。
