## 我的答案

这三类数据的共同难点是：一条样本中既有模型动作，也有外部输入或中间过程，而且目标长度差异很大。设计原则是**只监督希望模型生成且线上允许出现的 token，再显式控制不同区域与样本的权重**。

### 一、统一损失形式

可为第 \(i\) 个样本、第 \(t\) 个 token 定义 mask \(m_{i,t}\) 和权重 \(w_{i,t}\)：

\[
\mathcal L=
-\frac{\sum_{i,t}m_{i,t}w_{i,t}
\log p_\theta(x_{i,t}|x_{i,<t})}
{\sum_{i,t}m_{i,t}w_{i,t}}
\]

mask 决定“训不训”，weight 决定“训多少”。padding、system/user、环境观测通常 mask 为 0；assistant 输出通常为 1。必须对 next-token shift 后的实际 label 做检查。

### 二、Function Calling

典型轨迹：

```text
system(tool schema)
→ user request
→ assistant tool_call(name, arguments, call_id)
→ tool result
→ assistant final answer
```

常见 mask：

- system 中的工具 schema：0，是条件；
- user：0；
- assistant 发出的 tool name、JSON arguments、必要 call ID、结束 token：1；
- tool result：0，它来自外部环境；
- 最终 assistant answer：1。

若 call ID 由 runtime 生成，就不应训练模型生成随机 ID；若由模型协议要求生成，则需纳入目标并保证格式一致。工具错误、超时、空结果、重试和多工具并发也应有训练样本，不能只训 happy path。

权重上可适度提高稀有工具、参数边界和失败恢复，但不能让短 JSON 因 token 少被长自然语言回答淹没。可对 `tool_call` 和 `final_answer` 分区归一化，再组合两个 loss。

### 三、代码数据

用户题目、仓库上下文、错误日志通常作为输入 mask=0；模型应生成的代码、补丁、解释和结束 token mask=1。需先明确产品要什么：

- 只要代码，则不要把长解释作为 target；
- 需要“解释+代码”，两段都监督，但可分别加权；
- Fill-in-the-Middle 任务要使用正确的 prefix/suffix/middle special token；
- tool 返回的编译器/测试日志是环境观测，通常 mask=0，修复补丁则为 1。

长代码会在按 token 平均时自然贡献更大梯度。可采用每样本归一化：

\[
\mathcal L_i=-\frac{1}{N_i^{target}}
\sum_t m_{i,t}\log p_{i,t}
\]

再对样本平均，使一个 2000-token 文件不会自动等价于 20 个 100-token 样本。另一方面，若业务成本确实按 token 衡量，也可保留 token-level 平均；关键是明确目标并做消融。代码样本应以 compile、unit test、static analysis 和 patch apply 验证，而非只用文本 judge。

### 四、长思考/推理数据

先决定中间 reasoning 是否是线上允许模型生成的目标：

- 若训练显式 chain-of-thought，则 reasoning 与 final answer 都可计算 loss，但要验证每一步；
- 若中间过程只是 teacher 的私有草稿或生产不应暴露，应将其移除、mask 掉，或蒸馏成简洁 rationale/最终答案；
- 对 tool-augmented reasoning，assistant 的决策是目标，tool observation 仍是条件。

长 reasoning 会因 token 多主导训练，并可能教会模型无谓冗长、伪推理或把错误步骤合理化。可把 loss 分成：

\[
\mathcal L=lambda_r\mathcal L_{reasoning}
+\lambda_a\mathcal L_{answer}
+\lambda_f\mathcal L_{format}
\]

通常保证 final answer 和关键格式有足够权重，再通过验证集选择 \(\lambda\)。也可以用长度上限、步骤级过滤、正确性 verifier 和难度分桶控制数据，而不是仅靠 loss weight 修复坏 reasoning。

### 五、样本权重如何确定

权重可综合：

- 任务/工具的线上重要性与稀缺度；
- 人工、执行器或 verifier 的质量置信度；
- 难度和当前模型失败率；
- 来源可靠性与重复度；
- 样本长度，避免极长目标无意放大；
- 安全和格式关键性。

不要直接用 teacher 自报置信度当唯一权重，也不要让权重跨度过大造成少数样本主导。实际可以先做分桶采样，再在桶内用有限范围权重，并记录每个桶对总 loss 的有效贡献。

### 六、必须验收的指标

- 工具：选择准确率、arguments schema/执行成功率、无效调用率、恢复率；
- 代码：pass@k、编译率、单测、补丁应用率和安全扫描；
- 推理：最终正确率、过程 verifier、长度/成本、停止行为；
- 共通：逐 token mask 可视化、格式 parse、通用能力遗忘和不同长度切片。

### 面试简答版

Function Calling 中 system/tool schema、user 和 tool result 是条件，mask 为 0；assistant 生成的 tool name、JSON arguments、结束符和最终回答计算 loss。代码任务只监督产品希望生成的代码/补丁/解释，并用编译和单测过滤。长思考只有在允许输出且过程可靠时才监督，否则移除或 mask；reasoning、final answer 和格式可分别加权。由于长代码和长推理会在 token-level loss 中天然占更大权重，我会比较按 token 平均与先按样本/区域归一化，并用任务重要性、质量、难度和稀缺度设有限范围权重。
