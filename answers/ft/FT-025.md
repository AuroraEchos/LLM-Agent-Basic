## 我的答案

可复现不仅是“设置 random seed”，而是让另一个人能从不可变的 base、数据和代码重建训练，并知道每个效果变化来自哪个干预。体系应同时包含**制品血缘、确定性记录、基线/消融设计、统计不确定性和上线因果验证**。

### 一、冻结一份实验契约

每个 run 保存机器可读配置，至少包括：

- base model、tokenizer、Chat Template、special token 的 revision/hash；
- 训练数据 manifest、每条稳定 ID、split、采样权重与过滤版本；
- 代码 commit、未提交 diff、启动命令和配置文件；
- Python/CUDA/驱动、框架、kernel/依赖版本与容器 digest；
- GPU 型号/数量、拓扑、并行策略和环境变量；
- optimizer、LR schedule、batch/gradient accumulation、序列长度、packing；
- LoRA/QLoRA rank、alpha、target modules、量化与 compute dtype；
- 所有随机种子与确定性开关。

只记录模型名或数据目录路径不够，因为远程 revision 和目录内容会变化。核心制品要用 content hash 和只读对象存储。

### 二、保存足够的恢复状态

checkpoint 应包含权重/adapter、optimizer、scheduler、scaler、global step、epoch、已训练 target tokens、RNG、data sampler/dataloader cursor 和分布式状态。恢复后做短程一致性测试：下一批 sample IDs、loss 和 LR 应与未中断轨迹在允许误差内一致。

完全 bitwise deterministic 在不同 GPU、并行度和非确定性 kernel 下可能很昂贵或不可实现。因此要区分：

- **精确复现**：相同环境与并行度下尽量逐步一致；
- **统计复现**：不同 seed/run 的指标分布和结论一致；
- **功能复现**：制品能生成同等级质量，允许数值轨迹不同。

报告采用哪一级，而不是笼统宣称“可复现”。

### 三、建立不可缺少的 Baseline

至少包含：

1. 未微调 base；
2. 当前生产模型；
3. 简单 SFT/vanilla LoRA 基线；
4. 新方案，但与基线使用相同数据、target-token budget 和评测；
5. 若声称数据有效，比较同计算预算下的旧数据与新数据；
6. 若声称算法有效，固定数据、参数量与超参数搜索预算。

所有模型必须走同一推理模板、生成参数、评测代码和硬件设置。否则“新模型提升”可能来自 prompt、采样或更长输出。

### 四、效果归因用单变量与因子实验

一次实验同时更换数据、LoRA 变体、学习率和模板，就无法归因。先用 OFAT（一次一个变量）建立方向，再在关键变量上做 factorial design 观察交互。

例如数据改进 D 与算法改进 A 的交互可以写为：

\[
I_{D,A}=
(S_{D+A}-S_{base})
-(S_D-S_{base})
-(S_A-S_{base})
\]

若 \(I\neq0\)，说明两者效果不是简单相加。还应做：

- 数据源 leave-one-out / add-one-in；
- module/rank/训练步数消融；
- 固定参数量和固定 token budget 对照；
- 多个 seed，报告均值、标准差/置信区间，而非只挑最好 run；
- 预先定义主指标与停止规则，避免事后挑指标。

### 五、评测体系要能解释变化

建立分层指标：

```text
总体业务指标
├── 目标能力：正确率、执行成功、人工偏好
├── 保留能力：通用、语言、代码、知识
├── 协议：JSON/tool/EOS/格式
├── 安全：越权、隐私、拒答/误拒
└── 系统：TTFT、TPOT、吞吐、显存、成本
```

每个指标按来源、长度、难度、语言和时间切片，并保存逐样本输出与错误标签。LLM judge 要固定模型、prompt 和版本，并用人工/执行器校准；不能只保存一个平均分。

### 六、从离线到线上归因

离线通过后进行小流量 canary/A-B：随机化分流单位要与业务独立性匹配，例如用户级而非请求级，避免同一用户同时接触两个版本；记录模型、adapter、router、模板版本和曝光。监控主指标、护栏指标与置信区间，并预设停止/回滚条件。

如果线上同时修改检索、Prompt 和模型，应使用多臂/因子实验或分阶段发布，否则不能把收益全部归于微调。

### 七、自动化与报告

- CI 校验配置 schema、数据泄漏、mask、可恢复性和少量 smoke train；
- 实验追踪系统记录 config、metrics、artifact 与 parent run；
- 训练完成自动生成 model card/data card、评测矩阵和已知限制；
- promotion gate 只允许满足目标、保留、安全、系统门槛的制品进入 registry；
- 失败实验同样保留，防止重复踩坑和 publication bias。

### 面试简答版

我会把 base/tokenizer/template、数据 manifest、代码 commit、容器/硬件、完整训练配置和 seed 全部 hash 化记录，checkpoint 还保存 optimizer、scheduler、RNG 与 sampler cursor，并验证断点后下一批数据和 loss 可续上。归因上必须有 base、生产和简单 LoRA baseline；算法实验固定数据和 token budget，数据实验固定算法和计算，关键结论用单变量、因子交互和多 seed 置信区间验证。评测同时覆盖目标、保留、格式、安全和系统成本，逐样本可追溯；线上用版本化 A/B 与预设回滚门槛，避免把 Prompt、检索和模型的同时变化都归给微调。
