## 我的答案

消融的目标不是得到一张“去掉都变差”的漂亮表，而是验证每个组件通过什么机制、在哪些样本、以多少成本产生贡献。

### 1. 先画组件与假设

例如 Full = query rewrite + hybrid retrieval + rerank + memory + tool planner + verifier。为每个组件写预测：rerank应提升 context precision和噪声切片；verifier应减少事实/格式错误但增加调用和延迟；memory应只改善需要历史的多轮样本。

### 2. 实验设计

- **Leave-one-out**：Full、Full−A、Full−B，测边际贡献；
- **Add-one-in**：从简单基线依次加组件，理解累计路径；
- 有强交互时做 factorial，例如 retrieval×rerank四组，否则 leave-one-out会误判依赖组件；
- 用 identity/no-op替换，保持接口/调用路径，防“删除组件顺便减少token/延迟”混杂；
- 固定模型、数据、prompt、seed/重复、token/tool预算和 evaluator；同题 paired。

### 3. 观察多维结果

| Variant | Task success | 目标机制指标 | Safety | p95 | Tokens/Cost |
|---|---:|---:|---:|---:|---:|
| Full | ... | ... | ... | ... | ... |
| − rerank | ... | context precision ... | ... | ... | ... |

报告整体和预注册切片、差值置信区间、effect size。组件若质量只增0.2点却成本增30%，可能不在Pareto前沿；若只对高风险切片有价值，可按路由启用而非全量删除。

### 4. 防止错误结论

顺序组件存在交互：去掉检索后 rerank无输入，不说明 rerank无价值；动态 Agent移除一个工具会改变后续轨迹，需记录行为分布和中介指标。多重比较控制假阳性，test不反复用于选方案。离线完成后线上通过 feature flag对关键组件做受控 A/B，guardrail防风险。

最终结论应是“组件A在切片X通过机制M换来Y增益和Z成本”，而不是“组件A有用”。

### 面试简答版

我先为每个组件写可检验机制，再做 Full、leave-one-out和从基线add-one-in；有交互则做factorial。所有变体固定模型、数据、prompt、预算和evaluator，用同题paired、多次运行报告置信区间。除了端到端成功率，还看该组件应改变的中介指标、安全、p95和成本，并做目标切片。最后用线上flag验证。结论要具体到“在哪类样本通过什么机制、以多少成本贡献多少”，不能只看总分下降。
