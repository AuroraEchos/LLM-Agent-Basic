## 我的答案

要证明因果贡献，需要让“是否使用我的方法”成为主要变化，其他混杂因素保持一致，并检查结果是否超过随机波动。

### 实验矩阵

建立至少四组：

```text
A: 原基线数据 + 原 prompt + 无新方法
B: 原基线数据 + 原 prompt + 新方法       <- 方法主效应
C: 新/更多数据 + 原 prompt + 无新方法     <- 数据主效应
D: 新/更多数据 + 原 prompt + 新方法       <- 交互效应
```

若 prompt也变化，再做 factorial或单独一组，而不是把数据、prompt、模型和方法一次全换。所有组固定 model checkpoint/API revision、解码参数、token/tool预算、retrieval corpus、硬件与 evaluator。若新方法本身依赖额外计算，应在等成本比较和 Pareto比较都报告。

### 降低随机与评估偏差

- 同一题 paired运行；可控时固定多个 seed，不可控 API则多次重复并记录输出分布；
- 预注册 primary、切片和停止规则，测试集冻结；
- 对差值 bootstrap confidence interval/适合的配对检验，并报告 effect size，不只给 p-value；
- 人工评审 blind且随机左右顺序，LLM judge先校准、检查长度/风格偏差；
- 对重复样本、数据污染和 cache命中做审计。

### 消融与线上验证

Full system依次去掉/替换方法的子组件，验证预测机制：如果声称“rerank通过减少噪声提升”，应看到 context precision和含噪切片改善，而不是只看总分。最后线上按用户/会话稳定随机 A/B，只改变feature flag，比较业务 primary和延迟/成本/safety guardrail；检查实验桶样本比例、版本污染和 novelty。

不能绝对“证明”复杂现实中的唯一原因，但可以用随机化、控制变量、机制证据和复现把其他解释压低。若区间跨零或只在一个seed有效，应诚实结论为证据不足。

### 面试简答版

我会做控制/因子实验：固定模型、数据、prompt、预算和 evaluator，只开关新方法；数据量和prompt变化分别设组，估计主效应与交互。使用同题 paired、多seed/重复运行，冻结测试集，报告差值置信区间和effect size；人工/LLM judge盲审校准。再做子组件消融验证预期机制，线上只通过flag随机A/B。若增益在等成本、关键切片和多次运行中都稳定，才能归因；区间跨零就承认证据不足。
