## 我的答案

需要建立一份**每次 run 可追溯的物料清单**，而不是只记录应用 Git SHA：

```text
run_id / trace_id
code_commit + image_digest + dependency/SBOM
orchestrator/workflow_version + config_digest + feature_flags
provider + model_id/revision + decoding params + tokenizer
prompt/template/system-policy version + rendered-input digest
embedding model + chunker + retrieval/rerank config
corpus_snapshot + index_build_id/alias_resolution
tool name/version/schema + external API version
evaluator/rubric/dataset version
```

这些版本进入 run metadata和 trace resource/span attributes；大 prompt/文档不直接打 metric或普通日志，只保存受控 artifact URI、digest、长度和敏感级别。发布系统生成不可变 release manifest，将逻辑 alias（如 `prod-model`、`current-index`）在运行时解析到具体 revision并记录，避免日后 alias已移动无法解释。

### 如何监控变化

- 部署/配置/model/index事件作为 change event叠加在质量、错误、p99、成本 dashboard；
- 按版本做低基数 cohort metric；run/task ID只用于 trace/log搜索，不做 metric label；
- 合成 golden prompts定期运行，监控 output schema、核心事实、安全和分布漂移，捕捉供应商静默变化；
- 数据管线产出 manifest：source watermark、doc count、删除/权限、chunk/embedding失败、index coverage和checksum；新旧index shadow对比后原子切 alias；
- tool registry记录 schema兼容、权限和deployment；调用 trace记录 request/response安全摘要、attempt和provider request ID。

版本变化采用审批、canary和自动 guardrail；支持按 manifest重放，但要承认外部模型、实时网页和非确定采样可能无法 bit-for-bit复现，因此保存最小必要输入/输出和外部响应引用。Retention与访问满足隐私，用户删除要传播到 artifact和索引。

告警应基于“版本切换后某切片显著退化”，同时检测版本混跑、unknown revision和旧worker未drain。事故复盘能从任意失败 run反查所有组件，再从某个坏版本列出受影响 run/tenant，才算真正可追溯。

### 面试简答版

我会为每次 run记录 code/image、workflow/config/flag、provider model revision和参数、prompt、安全策略、embedding/chunker/rerank、corpus/index build、tool schema/API以及 evaluator版本，组成不可变manifest。逻辑 alias在调用时解析成具体版本；版本变更事件叠加到质量、p99和成本dashboard，并按版本 cohort、合成canary监控。敏感原文只存受控URI/digest，不进高基数metric；系统支持从失败run反查所有物料，也能从坏版本圈定影响范围。
