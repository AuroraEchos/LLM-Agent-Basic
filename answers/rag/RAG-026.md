## 我的答案

多租户 RAG 的基本原则是：**身份与权限由可信服务端决定，检索前强制过滤，存储/索引/缓存全链路携带租户边界，所有访问可追溯**。不能把 `tenant_id` 交给模型填写，也不能先跨租户检索再让 LLM“不要泄漏”。

### 一、身份和授权模型

请求经认证得到不可伪造的 principal：

\[
P=(tenant\_id,user\_id,roles,groups,attributes)
\]

文档/chunk 携带 owner tenant、ACL、classification、有效期和来源。授权可以用 RBAC、ABAC 或 ACL，最终由 Policy Enforcement Point 将许可谓词注入每一路检索。用户 query 里的“我是管理员”不参与授权。

### 二、隔离层级

- 强隔离：每租户独立账户/数据库/collection/index/加密密钥，安全边界强但成本高；
- 逻辑隔离：共享索引，每条记录带 tenant/ACL filter，资源利用高但对配置与测试要求更严；
- 混合：大客户/高敏租户物理隔离，普通租户共享分区。

选择依据是法规、爆炸半径、规模和成本。即便物理隔离，应用连接池、对象存储、日志和缓存仍要隔离。

### 三、检索和生成边界

所有 dense、BM25、KG、parent 回填和 citation lookup 必须执行同一授权语义。优先 pre-filter/partition-aware search；若数据库只支持 post-filter，应扩大候选仍不能返回未授权文本，并防 timing/count 侧信道。

最终 Prompt 只包含已授权片段；LLM 无权访问跨租户工具。引用链接点击时再次鉴权，不能把签名 URL 长期暴露。embedding 本身也可能泄漏信息，应按敏感数据保护。

### 四、缓存和运维

缓存键至少包含 tenant、principal/permission fingerprint、query、index version、retriever/model/config；共享语义缓存若忽略 ACL 会造成直接泄漏。权限撤销、文档删除和租户迁移时按 lineage 失效检索与答案缓存。

资源层还需 per-tenant quota、rate limit、并发和成本预算，防 noisy neighbor；加密传输与静态数据，可选每租户密钥；备份、导出、删除和灾备均保留隔离。

### 五、审计与验证

追加式审计记录 request ID、用户/租户、授权策略版本、query hash/脱敏文本、候选 IDs、过滤原因、最终证据、模型/索引版本、引用和工具调用。日志本身含敏感信息，需最小化、访问控制和留存策略。

CI 和红队必须包含跨租户相似 query、共享文档、权限刚撤销、parent-child ACL 不一致、缓存命中、导出/删除等测试；安全指标要求 cross-tenant retrieval 为零，而不是“很低”。

### 面试简答版

多租户 RAG 先由认证服务生成 tenant、user、role/group 等 principal，由服务端把 ACL 谓词强制下推到向量、BM25、KG 和 parent 回填，绝不能让模型决定权限。高敏租户可独立索引/密钥，普通租户可共享但每条记录带 tenant filter。最终 Prompt、引用访问、缓存和工具都沿用同一权限；缓存键包含 tenant 和 permission fingerprint，撤权/删除立即失效。审计记录策略版本、候选、过滤和最终证据，并把跨租户检索、缓存泄漏和 ACL 更新做成 CI 安全测试。
