## 我的答案

增量索引要保证的是：源文档的一次逻辑变更，最终让**文档记录、chunks、稀疏索引、向量、图关系和缓存收敛到同一版本**，失败可重试且不会产生重复或“幽灵知识”。

### 一、稳定身份与版本

为文档使用稳定 `document_id`，每次内容或权限变化生成单调 version/content hash。chunk ID 可由以下确定性产生：

\[
chunk\_id=H(document\_id,document\_version,chunker\_version,span)
\]

记录 lineage：source version → parsed artifact → chunks → embeddings/edges。处理事件携带 event ID，写入采用幂等 upsert。

### 二、新增、更新、删除

#### 新增

CDC/webhook/poller 产生事件，解析、切块、embedding 并写入 staging；通过质量检查后原子发布可查询状态。

#### 更新

先比较 hash；内容不变但 ACL 变更时只更新权限索引并失效缓存。内容变化可按结构/span diff 复用未变 chunk，但标题/上下文改变可能影响 child embedding，必须正确传播。新版本完整可用后切 alias/current pointer，再异步回收旧版本，避免用户看见半份新文档。

#### 删除

先写 tombstone 并立即在查询层不可见，再删除所有派生 chunk、向量、倒排项、图边、摘要和缓存。对象存储、备份按合规策略延迟清除，但在线搜索不得继续返回。删除必须有可验证回执和孤儿扫描。

### 三、一致性策略

跨多个系统很难做单一 ACID 事务，常用 outbox/event log + 状态机：

```text
DISCOVERED → PARSED → CHUNKED → EMBEDDED
→ INDEXED → VALIDATED → ACTIVE
```

消费者幂等、事件可重放、失败进入 dead-letter queue。查询只读 `ACTIVE` version；蓝绿索引用 alias 原子切换。若采用最终一致性，公开 freshness SLO，并在关键撤权/删除事件上走同步 deny-list 防护。

### 四、模型与 Schema 升级

Embedding model、chunker、parser 或权限 schema 变化通常需要新 index generation。双写或全量 backfill 后，用 golden queries、计数、hash、recall 和 ACL 检查验证，再灰度切换；新 query embedding 不能搜索旧模型文档向量。

### 五、监控

监控 source-to-index lag、各状态积压、失败/重试率、版本不一致、空块、孤儿 chunk、向量缺失、删除 SLA、ACL propagation lag 和缓存失效率。定期从源系统抽样反向核对索引，并演练事件丢失、乱序、重复和回滚。

### 面试简答版

我会给文档稳定 ID、每次变更版本/hash，并记录源文档到 chunk、向量、倒排和图边的 lineage。事件经 outbox/CDC 进入幂等状态机，新增或更新先写 staging，全部解析和索引验证后原子切 active version；旧版随后回收。删除先 tombstone 使查询立即不可见，再级联清理所有派生物和缓存。跨系统用最终一致性时查询只读 ACTIVE，撤权/删除加同步 deny-list。模型或 chunker 升级建新一代索引、双写验证后切 alias，并监控索引延迟、孤儿、版本错配和删除 SLA。
