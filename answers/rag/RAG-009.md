## 我的答案

三者的核心区别是匹配信号：**向量检索匹配语义，BM25 匹配词项，混合检索用两种互补信号提高鲁棒性**。不存在对所有 query 都最好的单一路线，尤其企业知识库往往同时有自然语言问题和错误码、型号等精确查询。

### 一、向量检索擅长语义改写

Dense retriever 将 query 和 chunk 编码到同一空间，用 cosine/dot product 找近邻。它擅长：

- 同义词、释义和用户口语，例如“怎么退货”匹配“退款与退货流程”；
- query 与文档用词不一致的概念匹配；
- 跨语言检索，前提是 embedding 做过跨语言对齐；
- 问句检索解释性段落、相似案例和意图。

弱点是精确字符串、罕见实体、长数字、版本号和否定条件容易被语义压缩；专有名词从未被模型学好时，相近主题文档可能排在真正匹配前面。长 chunk 多主题也会使向量信号稀释。

### 二、BM25 擅长精确词项

BM25 基于倒排索引，典型评分为：

\[
\operatorname{BM25}(q,d)=\sum_{t\in q}
IDF(t)\cdot
\frac{f(t,d)(k_1+1)}
{f(t,d)+k_1\left(1-b+b\frac{|d|}{avgdl}\right)}
\]

其中词频收益会饱和，\(b\) 控制文档长度归一化。它擅长：

- SKU、API 名、错误码、法规条号、文件名、人名等 exact match；
- query 中稀有词很有区分力的场景；
- 可解释地查看命中了哪些词；
- 低成本、成熟的过滤和大规模倒排检索。

弱点是 vocabulary mismatch：用户说“撤销订单”，文档只写“取消购买”，若分词/同义扩展没覆盖就会漏召回。中文分词、大小写、词干化与停用词配置也直接影响结果。

### 三、混合检索适合真实的混合查询分布

混合检索并行获得 dense 与 sparse 候选，再用 RRF、校准加权或学习排序融合：

```text
query
 ├─ dense top-k：语义候选
 └─ BM25 top-k：精确候选
      → fusion / dedup → reranker → final context
```

它对以下查询尤其稳健：

- “错误 E1042 为什么在升级后出现”——既有精确码，又有语义问题；
- 含产品型号、日期、实体加自然语言意图；
- 多语言/口语 query 中夹杂不可翻译标识符；
- query 分布变化，无法提前判断 dense 或 sparse 谁可靠。

代价是维护两套索引、两路延迟与融合参数。混合并不保证一定提升：若某一路质量很差或 top-k 太小，融合会把噪声推高；还要去除同一 chunk 的重复命中。

### 四、如何路由和融合

简单生产基线是两路并行 + RRF + cross-encoder rerank。数据量大时可做 query routing：

- 正则检测 ID/错误码，提升 BM25 权重；
- 自然语言释义问题提高 dense 权重；
- 很短且歧义大的 query 做扩展或让两路取更多候选；
- metadata/ACL/time filter 尽量在两路一致下推。

分数直接线性相加前必须校准，因为 cosine 与 BM25 的范围和分布不可比；RRF 只用 rank，能提供稳健基线。最终 reranker 处理 query—chunk 交互。

### 五、评测

建立 query taxonomy：exact identifier、entity、semantic paraphrase、跨语言、多条件和多跳。分别报告各类 Recall@k、MRR/nDCG，并比较 dense-only、BM25-only、hybrid 和 hybrid+rerank。在固定总候选数与延迟预算下测试，避免混合方案因看了两倍候选而不公平占优。

### 面试简答版

向量检索擅长同义改写、口语问法、概念和跨语言匹配，但对罕见实体、数字和精确版本号可能不稳；BM25 用词频、IDF 和长度归一化，擅长错误码、SKU、API 名和法规条号等 exact lexical match，却会受同义词和分词造成的词汇不匹配影响。企业查询通常两者混合，所以常用 dense 与 BM25 并行召回，经 RRF 去量纲融合，再用 reranker 精排。选型应按 exact、semantic、跨语言等 query 类型分别测 Recall@k 和 nDCG，并固定总候选与延迟预算。
