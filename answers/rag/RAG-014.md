## 我的答案

判断标准不是“改写后搜到更多文档”，而是：**在不改变原问题必要约束的前提下，相关证据覆盖是否增加、无关证据和错误答案是否受控**。要同时做语义守恒检查、检索级对照和端到端评测。

### 一、先定义语义漂移

改写必须保留实体、时间、版本、地域、否定、比较对象、用户身份和输出目标。以下都属于漂移：把“不能使用 GPU 的方案”改成“GPU 方案”；把 2024 改成“最新”；将产品 A 扩成整个产品系列；HyDE 自行猜出用户未给的故障原因。

可将原 query 抽取成约束集合 \(C(q)\)，检查：

\[
C(q)\subseteq C(q')\quad\text{且新增约束不与原意冲突}
\]

实际用规则保护数字/专名/否定，用 NLI 或 LLM rubric 双向判断 entailment，并对高风险字段做 exact check。相似度高不代表逻辑等价。

### 二、离线检索对照

建立 query—gold evidence 标注，逐条比较原 query 与 rewritten query：

- Recall@k/Hit@k：是否新增原来漏掉的正确证据；
- Precision@k、nDCG/MRR：噪声是否把正确证据挤出头部；
- unique evidence/source recall：多条近重复不算新覆盖；
- regression rate：原本命中的 query 有多少被改写弄丢；
- constraint violation rate：召回文档是否违反时间、实体和权限条件。

采用配对统计：同一批 query 比较 `original only`、`rewrite only`、`original ∪ rewrite + fusion`。通常保留原 query 并融合比完全替换更稳健。

### 三、端到端检查

检索提升必须转化为答案 correctness、faithfulness、citation precision/recall 的提升，同时记录 token、p95 延迟和成本。重点人工审阅四类样本：新增正确命中、新增错误命中、原命中回退、高置信但违反约束。

线上可做 shadow/A-B，记录改写、逐路候选及最终引用；用用户纠正和零结果率发现新分布，但点击不能直接等同相关性。

### 四、上线护栏

- 原 query 始终作为一路，改写结果用 RRF/reranker 合并；
- 数字、ID、引号内容、否定与 ACL filter 不允许自由改写；
- 给改写设置数量、长度、相似度和延迟上限；
- 若改写置信度低或各版本互相矛盾，回退原 query；
- 按 query 类型路由：明确 ID 查询通常无需 LLM 改写；
- 定期按语言、领域、长度和时间条件切片监控漂移。

### 面试简答版

我会先把原问题的实体、数字、时间、否定、版本和权限抽成不可丢约束，用规则加双向语义蕴含检查改写是否守恒；再在 gold query—evidence 集上配对比较原 query、仅改写和两者融合的 Recall@k、nDCG、unique evidence recall、回退率及约束违规率；最后看答案正确性、faithfulness、引用和延迟。生产中不直接替换原 query，而是保留原路、融合后 rerank，对 ID/数字/否定加硬保护，低置信或矛盾时回退。
