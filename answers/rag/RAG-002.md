## 我的答案

一句话区分：**RAG 主要把知识放在模型外部、查询时读取；微调主要把行为模式和部分知识写进参数。** 因而知识更新与可引用事实通常优先 RAG，风格、格式和稳定行为优先微调；真正的新能力往往需要高质量训练数据、工具和训练，而不是简单把文档塞进任一方案。

### 一、知识更新：通常选 RAG

对于产品价格、公司制度、客户私有文档、新闻和经常变化的政策，RAG 更合适：

- 文档更新后重建/增量更新索引即可，不必重新训练模型；
- 可以返回原文引用，便于核验和合规审计；
- 能按用户、租户、部门和文档 ACL 动态过滤；
- 可以删除或回滚某个知识源，控制新鲜度和版本。

微调并不等于可靠地“记住文档”。参数记忆难以保证完整、精确、及时，不能稳定提供出处；更新和删除成本也高。尤其不应指望模型通过微调精确存储大量不断变化的事实。

不过 RAG 的知识也不是自动正确：查询没召回、文档过期、chunk 缺上下文、模型忽略证据时仍会答错。它把问题从“参数是否记住”转成“外部知识链路是否可靠”。

### 二、风格与行为适配：通常选微调

若目标是让模型长期保持某种语气、输出 schema、拒答边界、工具调用格式或任务流程，SFT/偏好优化更适合。它们能让这些模式成为默认行为，不必每次在上下文中放大量示例，节省 token 和延迟。

典型场景：

- 固定 JSON/SQL/DSL 格式；
- 客服语气和品牌表达；
- 何时调用工具、怎样拆解任务；
- 特定分类、抽取或工作流策略；
- 安全偏好与拒答风格。

简单风格也可先用 system prompt 或 few-shot；只有 Prompt 不稳定、太长或调用规模足够大时，微调价值才明显。RAG 检索“风格手册”可以提供规则，却不保证模型在每次输出中稳定内化它。

### 三、能力学习：看能力从哪里来

“能力”要进一步拆分：

1. **只是缺事实或领域上下文**：RAG 即可，例如从维修手册回答设备参数。
2. **需要学会新的输入输出映射或操作习惯**：用 SFT/偏好优化，例如从病例文本抽取固定字段。
3. **需要精确计算、实时查询或执行动作**：接计算器、数据库、代码解释器和业务 API，比让参数死记更可靠。
4. **需要真正提升复杂推理能力**：需要覆盖推理过程/结果的高质量训练、可验证反馈、课程学习与充分评测；单纯 RAG 不能把基础模型变成会做它原本完全不会做的算法。

RAG 可以提供解题规则和示例，微调可以让模型更会使用这些材料，但二者都受基础模型容量和训练信号限制。

### 四、对比

| 维度 | RAG | 微调 |
|---|---|---|
| 知识位置 | 外部文档/数据库 | 模型参数 |
| 更新速度 | 更新索引即可，快 | 需构造数据、训练和部署 |
| 可引用性 | 强，可回原文 | 弱，难说明参数来源 |
| 权限/删除 | 可按请求过滤、定点删除 | 难做细粒度 ACL 和遗忘 |
| 长尾事实容量 | 适合大量文档 | 不适合当精确数据库 |
| 风格/格式一致性 | 依赖 Prompt，较弱 | 通常更稳定 |
| 在线开销 | 检索、重排、额外上下文 | 无检索时延，但模型可能需专用版本 |
| 主要故障 | 漏召回、脏文档、证据未利用 | 灾难性遗忘、过拟合、事实混淆 |

### 五、常见混合架构

```text
基础模型
→ SFT：学会目标格式、工具调用与“依据证据回答”
→ Preference Optimization：改善拒答、引用和风格
→ RAG：运行时提供最新、私有、可追溯知识
→ 工具：完成精确计算、查询和动作
```

例如企业客服可以微调模型遵守回复格式和升级人工流程，用 RAG 检索最新产品政策，用订单 API 查询用户实时状态。三者各自承担稳定行为、动态知识和真实世界状态。

### 六、决策问题

选型前问：内容多久变化？是否要求引用？是否有按用户变化的权限？能否容忍检索延迟？目标是“知道某事实”还是“稳定地怎么做”？基础模型当前不会，是因为缺信息还是缺能力？

最好先做低成本基线：Prompt/few-shot → RAG 或工具 → 仍不稳定再微调。评测时保持相同测试集，分别看事实新鲜度、引用、格式通过率、延迟、成本和维护复杂度。

### 面试简答版

RAG 把知识放在外部索引，适合频繁更新、私有、长尾且要求引用和权限控制的事实；更新和删除方便，但会受解析、召回和上下文利用失败影响。微调把模式写入参数，适合稳定语气、输出格式、工具策略和任务行为，但不适合作为可更新、可审计的事实数据库。能力问题要区分缺知识、缺行为还是缺外部执行：缺知识用 RAG，缺稳定行为用微调，精确计算和实时状态用工具，复杂推理提升则需要专门训练与可验证反馈。生产中通常三者组合。
