> **问题：** HyDE、Multi-Query、Step-Back 和 Query Decomposition 分别适合什么查询？

## 我的答案

四者都在查询前扩展或重构检索意图，但目标不同：HyDE 把短问题变成“像文档的文本”，Multi-Query 覆盖多种表述，Step-Back 抽象到上位概念，Query Decomposition 把复合任务拆成可独立求证的子问题。

### 一、HyDE

让 LLM 先生成一个假想答案/段落 \(\tilde d\)，再用其 embedding 检索真实文档：

\[
\tilde d=LLM(q),\qquad e=E(\tilde d)
\]

适合短 query 与长文档风格不对称、用户用词与知识库差异大时。假想文本不作为事实，只作为检索向量。缺点是模型若猜错实体、数字或方向会把检索带偏，因此应保留原 query 通道并融合，而不是直接相信假想答案。

### 二、Multi-Query

生成多个保持同一意图的改写，从同义词、术语和语言角度分别检索，再用去重/RRF 融合。适合表达歧义、召回词汇不匹配，以及 dense/BM25 多路覆盖。查询数量增加会线性增加检索与合并成本；改写必须保留实体、时间、否定和约束。

### 三、Step-Back

先从具体问题抽象出更一般的原理问题。例如“为什么把 HNSW efSearch 从 40 调到 200 后变慢”可回退为“HNSW 的搜索宽度如何影响 recall 和延迟”。它适合具体问题缺背景、需要概念/机制知识时；但抽象会丢失型号、版本、时间等决定答案的条件，因此通常同时检索原问题与 step-back 问题。

### 四、Query Decomposition

把包含多个实体、条件、比较或多跳关系的问题拆成有依赖的子问题：

```text
“A 与 B 哪个更适合本项目，成本差多少？”
→ 项目约束是什么？
→ A 的能力与成本？
→ B 的能力与成本？
→ 在同一口径下比较
```

适合多跳问答、比较、聚合和跨数据源查询。子问题可能并行，也可能后一个依赖前一个答案。风险是错误分解、遗漏约束和中间错误传播，因此要保留原问题、依赖图和每步引用，最终做全局一致性检查。

### 五、选择原则

| 症状 | 方法 |
|---|---|
| query 太短，query/document 分布不对称 | HyDE |
| 同一意图有多种词汇表达 | Multi-Query |
| 具体问题需要一般原理背景 | Step-Back |
| 问题含多个可验证子任务/多跳关系 | Decomposition |

可以组合，但要限制 fan-out。每种改写都应记录来源，并与“原 query 不改写”基线比较 Recall、噪声、延迟和最终正确率。

### 面试简答版

HyDE 先生成假想文档再用其向量检索，解决短 query 与文档表述不对称，但假想内容可能带偏；Multi-Query 用多个同义改写扩大词汇和视角覆盖；Step-Back 把具体问题提升到上位原理，适合先补背景，但要同时保留具体约束；Query Decomposition 把比较、多跳和多条件问题拆成可独立取证的子问题，并维护依赖。四者都要保留原 query 通道、限制扩展数，并验证改写有没有提升 evidence recall 而不是只增加候选。
