## 我的答案

三个数量对应三道不同的漏斗：**Retrieval Top-K 保证正确证据进入候选集，Rerank Top-N 决定精排多少候选，最终上下文数量决定给生成模型多少证据**。通常满足：

\[
K_{retrieve}\ge N_{rerank}\ge K_{context}
\]

但多路召回时应先分别取候选、融合去重，再确定实际 rerank 数。

### 一、每个参数影响什么

#### Retrieval Top-K

K 越大，理论上 evidence Recall@K 不下降，也更可能覆盖多跳证据；但 ANN/网络传输、融合和去重成本增加，尾部噪声也更多。若正确证据未进这一层，后续 reranker 无法补救。

#### Rerank Top-N

Cross-Encoder 对 query—chunk 联合打分，N 越大，越能从粗召回尾部救回正确证据，但成本大致随候选数与序列长度增加：

\[
C_{rerank}\propto N\times L_{pair}^2
\]

具体复杂度取决于模型架构和 batching。N 太小会截断可救回的候选，太大则增加 GPU 延迟而收益饱和。

#### 最终上下文数量

给 LLM 的 chunk 越多，不代表答案越好。更多上下文会增加 prefill 成本、冲突、重复和 Lost in the Middle；过少又会丢掉必要条件或多跳链。这里最好按**总 token budget 和独立 evidence units**控制，而不只按块数。

### 二、正确的离线调优流程

1. 建立 query—gold evidence 集，覆盖精确事实、多跳、表格、长文档和无答案问题；
2. 先关闭 reranker，画 `K → Recall@K、延迟` 曲线，选能达到召回目标的最小 K；
3. 固定召回候选，扫描 N，观察 rerank 后 Hit@k/nDCG 与 p95；
4. 在固定 context-token budget 下扫描最终 k，测答案 correctness、faithfulness、引用完整性和拒答；
5. 做二维或三维网格时固定总候选/算力，避免大配置因多用资源看似更好；
6. 按 query 类型切片，选择动态策略而非全局一个数字。

可用边际收益停止：

\[
\frac{\Delta Quality}{\Delta Latency\;or\;Cost}<\tau
\]

时不再扩大漏斗。

### 三、动态配置

- 错误码、SKU 等精确命中：BM25 高分且唯一时可用小 K/N；
- 模糊短问句：多路召回并增大 K；
- 多跳问题：保留多个来源和子问题证据，最终 k 可更大；
- 高置信 reranker 且分数断层明显：在断层处截断；
- chunk 较大时按 token budget 减少数量，small-to-big 扩展后重新计算预算；
- 无候选达到校准阈值时拒答，而非机械填满 top-k。

### 四、常见陷阱

重叠 chunk 会让 top-k 看似很多，实际是同一证据副本；应按 source、parent 和位置合并。ANN 加 metadata filter 后可能返回不足 K，要监控 effective K。最终还需考虑 ACL、时间版本、来源多样性和冲突，不能只按相关分数截取。

线上记录每层候选数、正确证据 rank、去重率、rerank 分数、context tokens、p95 和成本，用 shadow/A-B 验证离线结论。

### 面试简答版

Retrieval Top-K 负责高召回，太小会让正确证据永远进不了后续；Rerank Top-N 决定用更贵的 Cross-Encoder 精排多少候选；最终上下文应按 token budget 选少量互补证据，太多会增加冲突、重复和 Lost in the Middle。调优时先画 K 对 Recall/延迟曲线，再固定候选扫描 N，最后在固定上下文 token 下测端到端正确性、faithfulness 和引用。按精确查询、模糊查询和多跳查询动态配置，并对重叠块去重，不应全局盲设一个 top-k。
