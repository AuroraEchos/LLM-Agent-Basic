## 我的答案

Embedding 选型不能只看公开排行榜。正确流程是先定义业务 query、文档与延迟约束，用公开 benchmark 缩小候选，再在自己的 query—relevant chunk 标注集上比较**召回质量、索引资源和在线成本**。

### 一、语言覆盖

先检查 query 与文档可能出现哪些语言，以及是否跨语言检索：

- 单语模型在目标语言上可能更强、更便宜；
- multilingual 模型适合中文 query 检索英文文档等跨语言场景，但容量要在多语言间分配；
- 不能只测翻译后的标准句，要覆盖中英混输、缩写、专名、口语、繁简体和代码；
- 检查 tokenizer 对目标语言的 token 膨胀，影响截断、吞吐和成本。

跨语言评测应显式包含 `query_lang != doc_lang`，否则“支持多语言”只证明各语言内部可检索。

### 二、领域匹配

通用模型不一定理解医学缩写、法律条款、商品编号或代码语义。应在真实领域数据中评估：

- 术语、缩写、实体与长尾编号；
- 问题—答案、查询—段落是否是模型训练过的任务形式；
- hard negatives，例如同产品不同版本、同病名不同条件；
- 文档是自然语言、代码、表格还是混合模态。

领域微调只有在高质量正负对足够时才有价值；错误点击或伪负样本会破坏空间。即使 dense 模型很好，精确 ID/数字查询通常仍应保留 BM25。

### 三、维度

若有 \(N\) 个 float32 向量、维度 \(d\)，仅原始向量存储约为：

\[
M\approx4Nd\ \text{bytes}
\]

更高维通常提供更大表示容量，但会线性增加 embedding 输出流量、存储、内存和相似度计算；ANN 图/元数据还有额外开销。低维更便宜，但过度压缩可能降低细粒度区分。

若模型支持可截断维度或量化，需要在各配置上重新测 Recall 与 ANN latency，不能假设截取任意向量前缀都保持质量。向量库的 distance metric、数据类型和归一化方式也要与模型说明一致。

### 四、最大长度与有效长度

Embedding model 的 context window 必须覆盖实际 chunk 加标题/metadata 的 token 数，否则静默截断会把答案区域丢掉。应记录 p50/p95/p99 token 长度和 truncation rate。

但窗口越大不代表检索越好：单向量压缩长文会产生 semantic dilution。长文可采用结构切块、parent-child 或 late chunking。还要实测模型是否在窗口后部保持质量，而非只看标称最大长度。

### 五、成本和系统约束

成本包括：

- 离线全量及增量 embedding 的吞吐、GPU/API 费用；
- 向量存储、ANN 构建时间、备份与跨区流量；
- 在线 query embedding 的 p50/p95 延迟、并发和可用性；
- 模型版本升级导致的全量重索引成本；
- 自托管显存、批处理效率、运维，或外部 API 的隐私和限流；
- 向量维度对 ANN latency 与 rerank 候选数的连锁影响。

Document embedding 可批处理和缓存；query embedding 在关键在线路径，应单独测短文本小 batch 延迟。

### 六、任务格式与实现细节

有些模型要求给 query/document 加不同 instruction 或 prefix；有些输出需 mean pooling、mask 和 L2 normalization。使用错误模板可能比换模型造成更大损失。必须冻结：

```text
model revision + tokenizer revision
query/document prefix
pooling + normalization
max length + truncation side
向量维度/量化 + similarity metric
```

升级时建双索引做 shadow test，不能把新 query 向量直接搜索旧模型生成的文档向量。

### 七、评测与选型矩阵

建立带 hard negatives 的真实标注集，至少报告 Recall@k、MRR/nDCG、按语言/领域/长度切片的结果，以及 QPS、p95 query latency、每百万 chunk 的存储和重索引时间。最终还要接 reranker/LLM 测答案正确性，因为 embedding 的小幅离线优势未必转化为端到端收益。

满足质量下限后，再选择总体成本最低、版本与部署风险可控的模型；而不是为了排行榜上小数点后的优势承担数倍资源。

### 面试简答版

Embedding 选型先看业务语言与是否跨语言，再看领域术语、hard negatives 和文本模态；维度越高一般容量更大，但存储与计算约随 \(Nd\) 线性增长；最大长度要覆盖实际 chunk，却不能用一个长向量压缩过多主题。成本要同时算全量重索引、向量库存储、在线 query 延迟和版本升级。还必须遵循模型要求的 query/document prefix、pooling、归一化和距离度量。最终用自己的标注集按语言、领域和长度比较 Recall@k、nDCG、p95 与端到端答案质量，在满足效果后选总成本最低的方案。
