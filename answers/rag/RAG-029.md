> **问题：** 如何缓存 Embedding、检索结果和最终回答而不返回过期知识？

## 我的答案

安全缓存的关键不是设置一个短 TTL，而是让 cache key 包含所有影响结果的依赖版本，并能在文档/权限变更时按 lineage 主动失效。不同层可以采用不同新鲜度策略。

### 一、Embedding 缓存

文档向量键可定义为：

\[
K_e=H(content,modelRev,tokenizer,preprocess,chunker,prefix,pooling,dim)
\]

内容寻址可复用真正相同的 chunk；任一表示配置变化都不能复用。ACL 通常不改变向量，但缓存记录与索引写入仍需绑定文档/租户 lineage，防跨权限复用元数据。query embedding 还要包含规范化后的 query 与 query prefix，TTL 可较长，因为它不包含知识结果。

### 二、检索结果缓存

键至少包含：

```text
tenant + permission fingerprint + normalized query
index generation + retriever/reranker config/model
filters + top-k + language/time scope
```

值最好存 chunk IDs、scores 和版本，而非无条件缓存全文；命中时可再次做 ACL/active-version 检查。文档更新或删除时利用 inverted dependency `document_id → cache keys` 精确失效，或切换 index generation 让旧键自然不可命中。

### 三、最终回答/语义缓存

答案键还需包含 Prompt/template、generator model/version、生成参数、上下文证据版本和安全策略。相似 query 缓存尤其危险：语义接近不等于权限、时间和意图相同。只应用在低风险、稳定、公共知识；私有/实时/个性化问题默认不共享。

缓存值保存 citations 与 evidence hashes，读取时验证来源仍 ACTIVE、用户仍有权限、freshness policy 未超期。价格、库存、告警等实时数据使用极短 TTL 或完全绕过答案缓存。

### 四、失效策略

- TTL：兜底限制陈旧时间，不是唯一机制；
- event-driven invalidation：文档、ACL、模型、Prompt 变更主动失效；
- versioned namespace：新索引/模型切版本即隔离旧缓存；
- stale-while-revalidate：只用于允许短暂陈旧的低风险场景，并显示数据时间；
- negative cache：空结果 TTL 更短，避免新增文档后仍持续无答案；
- stampede protection：single-flight、抖动 TTL 和并发限流。

删除、撤权和安全隔离属于强失效事件，不能等待 TTL。

### 五、监控与测试

报告各层 hit rate、节省延迟/成本、命中答案 correctness、stale serve rate、ACL cache rejection、失效传播延迟和热点。测试同 query 不同租户/角色、刚更新/删除、索引切换、模型升级和并发失效；日志不能记录未脱敏私有 query 或答案。

### 面试简答版

Embedding 缓存按内容 hash 加模型、tokenizer、prefix、pooling 和维度版本化；检索缓存再加 tenant、permission fingerprint、index generation、filter、top-k 与 reranker；最终答案缓存还要包含 Prompt、生成模型和每条证据版本。TTL 只是兜底，文档更新、删除、撤权和安全隔离必须按 lineage 主动失效，或通过新 generation namespace 切断旧缓存。命中答案时重验 ACL、证据 ACTIVE 和 freshness；实时、私有、个性化问题不共享语义缓存，并监控 stale serve 与失效延迟。
