## 我的答案

Knowledge Graph Retrieval 与向量 RAG 是互补的：**图擅长精确实体、关系约束和多跳路径；向量擅长自然语言语义、长尾描述和图中尚未结构化的原文**。可靠系统通常双路召回，在统一 provenance 下融合，而不是把全部文本强行变成三元组。

### 一、各自优势

| 能力 | Knowledge Graph | Vector RAG |
|---|---|---|
| 精确实体/关系 | 强，可按类型和方向约束 | 易受语义近似干扰 |
| 多跳与路径解释 | 显式路径 | 需检索多个片段再推理 |
| 长叙述与隐含语义 | 结构化时会丢信息 | 强 |
| 构建与更新 | schema、消歧、抽取成本高 | 切块和 embedding 较简单 |
| 覆盖 | 仅已抽取事实 | 原文长尾覆盖广 |
| provenance | 需专门保留到每条边 | chunk 天然链接原文 |

### 二、三种组合方式

#### 并行召回

query 同时做实体链接/图查询与 dense/BM25 检索，结果规范成统一 evidence object，经 RRF/rerank 融合。适合无法提前确定查询类型的通用问答。

#### 图引导向量

先由 KG 找到相关实体、邻居或关系路径，再用这些实体 ID、别名和关系去过滤/扩展向量检索，补回原始段落。这样路径负责结构，文本负责限定条件和引用。

#### 向量引导图

先从自然语言 chunk 找候选实体，再做 entity linking，沿图扩展后回取相关原文。适合 query 用词模糊、直接链接实体困难的情况。

### 三、多跳执行示例

用户问“项目 X 的供应商母公司还投资了哪些同领域企业？”：

```text
向量/BM25 找到“项目 X—供应商 A”的原文
→ 链接 A 到 KG 节点
→ 沿 subsidiary_of 找母公司 B
→ 沿 invested_in 找候选企业
→ 用行业关系过滤
→ 回取每条边对应原文并逐 claim 引用
```

图路径只是候选推理骨架；每条边仍要检查时间、方向、来源和置信度，不能把缺边当否定真值。

### 四、路由与融合

含明确实体、关系词、计数/路径约束的 query 提高 KG 权重；解释性、模糊或“为什么”问题提高向量权重；复杂问题两路并行。图路径分数与 cosine 不同量纲，可用 rank fusion 或学习型 reranker，输入相关性、路径长度、边置信、来源权威和新鲜度。

上下文组装时去重同一原文的图边与向量 chunk，展示实体路径加 supporting text。权限必须同时作用于图节点/边与原文；不能通过图路径推断用户无权查看的关系。

### 五、工程边界

两套索引会有双写与新鲜度差异。应采用统一 document/event ID，记录 `source_version → chunks → entities/edges` lineage，增量更新时使相关边失效或重建。监控 entity-link accuracy、edge precision/recall、path success、vector Recall、证据覆盖和端到端成本。

若业务主要是简单文档问答，KG 的维护成本可能不值得；若已有高质量业务图，组合价值远高于从任意文档用 LLM 临时抽一个噪声图。

### 面试简答版

KG 检索擅长精确实体、关系方向和可解释多跳路径，向量 RAG 擅长同义语义和未结构化原文。可并行召回后融合，也可先用图找实体路径再向量补原文，或先用向量找到实体再沿图扩展。最终每条图边必须回到带版本、时间和权限的 supporting text，图路径不能替代证据。融合时用 RRF/reranker处理不同分数尺度，并统一 lineage 解决双索引更新。简单 FAQ 不一定值得建图，已有高质量业务 KG、多跳关系丰富时收益最大。
