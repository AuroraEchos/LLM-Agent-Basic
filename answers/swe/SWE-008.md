## 我的答案

向后兼容的核心是允许新旧生产者、消费者和数据在一段时间内共存，采用 **expand → migrate → contract**：先做旧版本可容忍的扩展，迁移流量/数据并观测，最后确认无旧消费者后再删除。不能把部署顺序当作绝对可靠的一次性切换。

### 配置兼容

- 配置有显式 `schema_version`、类型、范围、默认值和 unknown-field 策略；新增字段先 optional 且默认保持旧行为。
- 重命名用“新旧字段同时接受→冲突时报错/定义优先级→写入只产新字段→告警旧字段→下个 major 删除”，不要静默解释成另一语义。
- 默认值变化属于行为破坏，即使 Schema 没变也要版本化、灰度和文档化。
- 启动时 fail-fast 校验完整配置，日志输出脱敏后的 effective config digest；不认识关键字段不能默默忽略。

### 事件协议

事件含 `event_type、schema_version、event_id、occurred_at、producer`，字段采用稳定语义。新增 optional 字段通常兼容；删除/改类型/改单位/复用枚举值是破坏性变化。消费者应容忍未知 optional 字段和未知枚举的受控 fallback，但不能对安全关键值默认放行。

使用 Schema Registry 和 producer/consumer contract tests；发布前检查新 producer 能被旧 consumer 读、新 consumer 能回放旧事件。事件不可变，修正通过新事件；至少一次投递下 consumer 以 event/idempotency key 去重。大 payload 放对象存储并引用版本/hash。

### 数据库 Schema

典型在线迁移：

1. Expand：增加 nullable/有安全默认的新列、表或索引，旧代码仍工作；
2. Deploy/dual-read-write：新代码兼容旧/新字段，必要时双写；
3. Backfill：分批幂等回填，限速并校验计数/校验和；
4. Read switch：灰度切到新列，监控差异并保留回滚；
5. Contract：确认所有实例、任务、报表都不再读旧字段后，单独迁移删除。

大表加非空/默认/索引要考虑锁和写放大。双写不能天然原子，优先数据库事务/outbox；跨库需对账和补偿。回滚代码前确认它仍能读迁移后的数据。

### 工具接口

工具有稳定 ID、SemVer、输入/输出 JSON Schema、错误、权限、幂等和副作用语义。新增 optional 参数并保持默认行为较安全；把默认从 dry-run 改为 commit、修改金额单位、扩大查询范围都是破坏性变化，必须新 major/tool 名称。

Agent 工作流固定到具体 tool version，adapter 可在过渡期转换 v1↔v2。高风险变更先 shadow/dry-run，比较参数和结果；旧版经历 deprecated、迁移统计、sunset 后下线。不能依赖模型读描述后“自动适应”Schema 变化。

### 治理与验证

建立兼容矩阵、版本 owner、弃用期限和消费者清单；CI 运行旧 fixture 回放、双向 contract、数据库迁移/降级测试。用 feature flag/canary 分阶段发布，观测旧字段/版本调用、解析错误和数据对账。只有调用归零并覆盖长任务、离线消费者、回滚窗口后才 contract。

### 面试简答版

我采用 expand–migrate–contract：先新增 optional 字段/表并保持旧默认，部署能同时读新旧的代码，幂等回填和对账后灰度切读，确认所有在线、长任务和离线消费者迁移完再删除。配置和事件都有 schema version；事件新增字段可兼容，改类型、单位和枚举语义必须升版本并跑 producer/consumer contract。工具接口还要版本化权限、幂等和副作用，默认从 dry-run 改 commit 属于破坏变更。全程保留兼容矩阵、旧 fixture 回放、canary 和可实际执行的回滚路径。
