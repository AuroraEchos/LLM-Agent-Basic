## 我的答案

四者的区别主要是被测范围和失败后能否快速定位。测试体系应呈金字塔：大量快速确定的单元测试，适量真实边界的集成/契约测试，少量高价值端到端测试；回归测试则不是独立层级，而是把历史缺陷固化到合适层级防复发。

### 单元测试

验证最小逻辑单元，在进程内、快速、确定且隔离外部依赖。Agent 例子：

- Prompt/context 截断与 token 预算；
- JSON Schema/工具参数校验；
- 状态机合法/非法转移；
- 重试分类、退避、幂等键；
- RRF、权限规则、坐标映射。

外部模型、时钟、随机数和数据库用 Stub/Fake 注入。单元测试验证自己的业务规则，不应 mock 每个内部私有方法，否则重构就大量破坏测试。

### 集成测试

验证多个真实组件或边界能否正确协作，例如真实 Postgres/Redis、向量索引、对象存储、本地模型 server 或供应商 sandbox。重点看 Schema 迁移、序列化、事务、ACL、超时、流式协议、取消和 SDK 错误映射。

Adapter 的 contract test 是重要子类：对所有模型/工具实现运行同一契约套件，验证 tool call、finish reason、usage、429/超时和流事件语义。集成测试比单元慢，应使用隔离资源、可重复 fixture 和明确清理。

### 端到端测试（E2E）

从用户入口经过网关、模型/RAG/工具、状态和 UI/API，验证完整业务结果与副作用。例如“查询订单→申请退款→审批→只执行一次”，同时检查权限、引用、流式体验和审计。

E2E 最接近生产，但慢、昂贵、易受外部模型波动影响，失败定位难。只保留关键 happy path、高风险路径和跨服务故障；对真实外部 API 固定版本/沙箱、控制预算，非确定输出用结构化不变量和任务成功判定，不做整段字符串 exact match。

### 回归测试

每个线上 Bad Case/缺陷先构造最小复现，再放到最便宜且能覆盖根因的层级：RRF 排序 bug 做单元，SDK 流事件 bug 做 contract integration，跨服务重复退款做 E2E。回归集版本化、标注关联 issue/根因，修复后还测邻近正常样本防过拟合。

模型能力/安全评测也是回归的一部分，但和确定性软件测试分开报告：固定数据、Prompt、模型和 Judge，使用 pass rate、win rate、置信区间与最差切片。统计波动不能让 CI 随机红绿，可设置重复、容差和人工升级。

### 如何分工

| 类型 | 主要问题 | 速度/稳定性 | 典型触发 |
|---|---|---|---|
| 单元 | 一段逻辑对不对 | 最快、最稳 | 每次提交 |
| 集成/契约 | 边界和真实组件兼容吗 | 中等 | PR/合并 |
| E2E | 用户流程与副作用正确吗 | 最慢、易波动 | 核心 PR/发布 |
| 回归 | 历史问题会不会回来 | 取决于所在层 | CI+发布 |

### 面试简答版

单元测试隔离验证状态机、参数校验、预算等小逻辑；集成/契约测试用真实数据库、向量库或模型 sandbox 验证协议、事务和错误映射；E2E 从用户入口跑完整 RAG/工具/审批流程，验证最终结果和副作用；回归测试则把历史 Bug 放到能覆盖根因的最低成本层级。Agent 输出非确定，确定性代码仍严格断言，模型能力用固定版本数据、结构不变量和统计阈值。整体遵循大量单元、适量集成、少量关键 E2E。
