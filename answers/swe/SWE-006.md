## 我的答案

这类系统不能用“多跑几次直到绿”解决不稳定，而要把**确定性业务逻辑、概率模型质量、外部协议和异步时序**分开测试。每层使用与其不确定性匹配的断言，最终再做端到端统计与故障注入。

### 1. 隔离确定性核心

状态机、Schema、权限、路由预算、重试分类、引用映射等应写成纯函数或显式依赖，严格单元测试。随机数、时钟、UUID、sleep、模型和网络通过 port 注入：

```python
runner = AgentRunner(
    model=ScriptedModel([...]),
    clock=FakeClock(),
    rng=random.Random(42),
)
```

模型 Stub 按脚本返回文本、tool call、错误 JSON、429、断流；Fake Clock 瞬间推进 timeout/backoff，无需真实等待。这样首先证明编排代码本身是确定正确的。

### 2. 概率输出测试

不要对完整自然语言 exact match，而是按层断言：

- 硬不变量：合法 JSON、必需字段、引用存在、禁止泄漏、工具 allowlist、总预算；
- 任务结果：代码/SQL执行、数学答案、检索证据支持、业务 API 最终状态；
- 软质量：固定版本评测集上的 pass rate、pairwise win rate、Judge/人评分及最差切片。

固定模型版本、Prompt、采样参数和 seed 能降低波动，但外部 API 即使 temperature=0 也未必逐字确定。统计门禁应预先定义样本量、重复次数、效应和置信区间。例如新旧版本在相同样本做 paired bootstrap，而不是因一次均分差异就回滚。

### 3. 网络依赖

单元层 Stub；adapter 层启动 Fake HTTP/SSE server，覆盖分片、重连、超时、429、5xx、无效 payload 和取消；再对供应商 sandbox/测试账号跑小型 contract suite，验证真实 SDK 与协议。少量生产 smoke test 只做无副作用读取。

Record/replay 可复现真实边界，但必须脱敏、固定 Schema 和到期更新，不能把 token/PII 写入 fixture。测试网络默认阻断，只有明确标记的 integration test 可访问 allowlist，避免 CI 误调用生产工具。

### 4. 异步与并发

- 等待明确事件/condition，不用任意 `sleep(1)`；每个 await 有 timeout；
- Fake Clock 测 deadline、退避和定时器；
- 用 barrier 控制两个协程在关键点交错，测试 CAS、重复提交和取消—完成竞争；
- 验证客户端断连后取消传播、task 被 await/回收、锁和连接在异常路径释放；
- 在 loop 结束检查 pending task、未关闭 session 和 warning，把泄漏当失败。

并发测试可随机化调度/重复运行提高 race 暴露，但失败必须保留 seed 和 trace 以复现。属性测试生成不同事件序列，验证“最多一次副作用、只有一个终态、预算不为负”等不变量。

### 5. E2E 与故障注入

在沙箱中注入模型延迟、向量库部分失败、工具成功后响应丢失、worker 重启、重复消息和慢客户端，检查幂等、补偿、降级和观测。E2E 固定关键任务，不追求穷举；历史 Bad Case 下沉到最低成本回归层。

测试报告区分产品回退、Judge/供应商漂移和基础设施抖动。Flaky test 应隔离、定位并修复，自动重跑可收集证据但不能把首次失败隐藏为绿。

### 面试简答版

我会把系统拆成确定性核心、模型质量、网络契约和异步时序四层。状态机、权限和预算用 Stub/Fake Clock 做严格单测；模型输出不比整段字符串，而检查 Schema、工具/安全不变量、可执行任务结果，并在固定版本数据上用成对统计和置信区间做质量回归。网络先用 Fake SSE/HTTP 覆盖超时、429、断流，再跑少量供应商 sandbox contract。异步测试不用真实 sleep，而用事件、假时钟、barrier 验证取消、竞争、幂等和资源回收，最后用故障注入跑少量 E2E。
