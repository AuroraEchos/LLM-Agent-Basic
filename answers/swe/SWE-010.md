## 我的答案

统一门禁的关键是“一个事实来源”：工具版本、配置和命令写入仓库，开发者本地、pre-commit 和 CI 调同一脚本/任务；CI 只是更严格地执行，不能有另一套隐藏规则。门禁按反馈速度分层，并保证失败可复现、可解释。

### 分层门禁

1. **格式化**：确定性 formatter 统一源码、import 和配置格式；CI 使用 `--check`，不在流水线偷偷改文件。
2. **Lint**：静态检查未使用、危险 API、复杂度、异步误用、安全规则；规则集和忽略必须版本化，例外带原因和最小范围。
3. **类型检查**：核心领域、公共 API、工具 Schema 和 adapter 开 strict；第三方缺类型用窄 wrapper/stub 隔离，避免全局 `Any` 和大范围 ignore。
4. **测试**：快速单元/属性测试→contract/integration→少量 E2E/模型 eval。并行但保留覆盖率合并和失败 artifact。
5. **覆盖率**：设项目最低线和 changed-lines 门槛，更关注分支、错误/取消路径及关键模块。100% 行覆盖不等于正确，generated code、迁移文件应明确排除。
6. **依赖与供应链**：提交 lockfile，CI 用 frozen/locked install；固定直接/传递版本及校验，可信 registry，生成 SBOM，做漏洞、许可证和秘密扫描。

### 命令统一

例如提供：

```text
make fmt       # 修改为标准格式
make lint      # formatter --check + lint
make typecheck
make test-unit
make test-integration
make quality   # CI 与本地共同入口
```

所有命令在固定容器/工具链版本中运行。pre-commit 只跑秒级格式、lint、类型增量和小测试；PR CI 跑全量单元/contract；主干/夜间跑多平台、E2E、模型质量和安全评测。缓存按 lockfile、工具版本和平台 key，不能复用错误环境。

### 依赖锁定边界

应用通常锁定完整依赖图；可复用库需要声明兼容范围，同时在 CI 测最低/最高支持版本，并为发布生成解析后的 lock/SBOM。容器基础镜像和 CI Action 也按 digest/不可变版本固定，而不只是 Python/npm 包。

自动依赖更新由 bot 提 PR，包含 changelog、漏洞、lock diff 与测试；高风险 runtime/模型 SDK 先 contract/canary。紧急漏洞可有审批过的例外，但有 owner、到期日和补偿控制，不能永久 `ignore`。

### 分支保护与治理

Branch protection 要求相同的 named checks、必要 reviewer 和禁止直接 push。生成代码/格式化变化与逻辑尽量分开，便于审查。质量基线逐步提高：遗留仓库可先要求“新代码不增加错误”和 changed-lines coverage，不能因为旧债一次修不完而关闭全部门禁。

门禁本身监控时长、flaky rate、缓存命中和失败类别。慢到开发者绕过、经常误报的门禁没有治理价值；优化并行和增量，但安全/正确性硬门槛不因赶发布静默跳过。

### 面试简答版

我会把 formatter、lint、type check、unit/contract/E2E、coverage 和依赖检查封装成仓库内同一组命令，本地、pre-commit 和 CI 共用。快速检查每次提交运行，集成/E2E和模型评测按 PR、主干、夜间分层。覆盖率同时看 changed lines、分支和错误/取消路径，不迷信 100%。依赖使用 frozen lock、哈希/可信 registry、SBOM、漏洞/许可证/秘密扫描，容器和 CI Action 也固定版本。Branch protection 强制 named checks；所有 ignore/紧急豁免都有原因、owner 和到期日。
