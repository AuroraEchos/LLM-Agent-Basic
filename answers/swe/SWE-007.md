> **问题：** `P0` Property-Based Testing、Golden Test 和 Snapshot Test 分别适合验证什么？

## 我的答案

三者分别强调：Property-Based Testing 用大量生成输入找违反不变量的边界；Golden Test 用少量人工认可的输入—期望结果验证领域行为；Snapshot Test 快速记录大结构并在变化时展示 diff。它们可以组合，但不能互相替代。

### Property-Based Testing（PBT）

开发者定义输入生成器和始终成立的 property，框架生成大量样本，失败后 shrink 成最小反例。适合算法、解析、状态机和边界组合：

- 任意 Unicode/长度 Prompt 经裁剪后 token 不超预算且不破坏消息边界；
- `deserialize(serialize(x)) == x`；
- RRF 分数不因添加无关低排名文档降低已有文档相对顺序；
- 任意事件序列中任务只有一个终态、副作用最多一次、配额不为负；
- bbox 经 resize/pad 及逆变换仍落在原图且误差在容差内。

PBT 不适合“回答好不好”这种无法写清不变量的开放问题。生成器要反映合法与恶意边界，保存随机 seed，避免 property 本身弱到只验证“不崩溃”。

### Golden Test

Golden set 是经过领域专家审核、版本化的代表性输入与期望语义。例如工具选择及参数、Text-to-SQL 结果集、RAG 必须引用哪些证据、历史高危 Bad Case。它适合协议/编译输出和产品关键行为。

自然语言 golden 不宜要求逐字相同，可保存结构化 rubric、必含事实、禁止主张、reference 与执行 verifier。更新 golden 必须由人审说明“需求改变还是模型退化”，不能测试一失败就批量重录。

Golden 数量有限，容易对已知样本过拟合，需隐藏集、反事实变体和线上 Bad Case 补充。

### Snapshot Test

Snapshot 首次运行保存序列化输出，后续用 diff 提醒变化。适合稳定结构较大、逐字段手写断言成本高的内容，例如 tool schema、事件 payload、Prompt manifest、UI 渲染树。

问题是脆弱且易“无脑 approve”：时间、UUID、字典顺序、token usage 和自由文本会制造噪声。应先规范化/删除不稳定字段，只 snapshot 公共契约；对权限、金额、状态等关键字段仍写显式断言。Snapshot 只能说明“变了”，不说明“错了”。

### 组合示例

测试 Agent 事件协议：PBT 生成合法/非法事件验证 parser 永不越权且 round-trip；Golden 保存几个关键版本迁移用例及期望语义；Snapshot 展示完整公共 JSON shape 的 diff；另用显式断言确保 `tenant_id`、幂等键和终态正确。

### 选择表

| 方法 | 最适合 | 主要风险 |
|---|---|---|
| PBT | 大输入空间、不变量、状态序列 | property/生成器写得不正确 |
| Golden | 领域期望、历史 Case、精确契约 | 覆盖有限、维护与过拟合 |
| Snapshot | 大而稳定的结构变化提醒 | 脆弱、机械更新掩盖 Bug |

### 面试简答版

Property-Based Testing 定义不变量并自动生成、缩小边界反例，适合 token 预算、序列化、状态机、幂等和坐标变换；Golden Test 保存专家认可的代表输入与语义期望，适合历史 Bad Case、工具参数和执行结果；Snapshot Test 保存大结构并展示 diff，适合事件 Schema、Prompt manifest 和 UI，但只能说明发生变化。实践中 snapshot 先去掉 UUID/时间等不稳定字段，关键安全字段仍显式断言，golden 更新必须人审，三者配合而不是互相替代。
