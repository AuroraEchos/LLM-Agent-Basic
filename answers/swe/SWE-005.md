## 我的答案

它们都是测试替身（test double），区别在于主要用途：Stub 提供预设回答，Fake 是简化但能工作的实现，Spy 记录发生了什么，Mock 预先声明并验证期望交互。很多库把这些都叫 mock，但设计测试时仍应分清目的。

| 类型 | 核心特征 | Agent 示例 |
|---|---|---|
| Stub | 按输入/顺序返回固定结果或错误 | 模型第一次返回 tool call，第二次返回答案；工具返回 429 |
| Fake | 具有真实简化行为，不用于生产 | 内存 StateRepository、临时向量索引、假邮件 outbox |
| Spy | 包装真实/替代实现并记录调用 | 记录模型请求、工具参数、取消是否传播 |
| Mock | 设定期望调用、次数/顺序/参数并自动验证 | 断言高风险工具在批准前绝未调用 |

### 测试模型 API

单元测试优先使用可编程 Stub，而不是调用真实模型：按 request fixture 返回普通文本、分片流、tool call、malformed JSON、429、超时或中途断流。这样可确定地覆盖重试、解析、状态机和取消。

Spy 用于检查发送给模型的内容是否满足不变量：正确模型/Prompt 版本、没有秘密、tool schema 正确、token budget 未超。不要断言 Prompt 的全部字符串和内部调用顺序，否则正常重构会破坏测试；只验证业务相关字段。

Adapter 还需要 Fake HTTP/SSE server 或 provider sandbox 的 contract test，验证 SDK 序列化、流事件和错误码。纯 Stub 只能证明代码适配了自己的假设，不能发现供应商协议变化。

### 测试外部工具

读工具可用 Fake 数据库/服务实现真实查询语义；有副作用的邮件、支付、删除工具使用 sandbox/fake outbox，保存提交记录但不触达真实系统。Stub 注入限流、权限拒绝、慢响应、重复 delivery 和部分失败。

高风险场景使用 Mock/Spy 验证**未发生**和**只发生一次**：未授权不调用、批准参数 digest 不一致不调用、重试使用同一 idempotency key、取消后不再提交。但最终状态也要断言，不能只验证调用次数。

### 常见误区

- 过度 Mock 内部对象会让测试验证实现而非行为；优先在真正的 I/O port 替换。
- 返回过于理想的 Stub 会漏掉流分片、空字段、乱序和错误；从脱敏真实契约构造边界 fixture。
- Fake 与生产语义可能漂移，所有 port 对 Fake 和真实 adapter 运行共同 contract suite。
- Record/replay 的生产响应可能含 PII/秘密且随 API 版本过期；必须脱敏、固定版本和人工审查。
- 测试不能连接真实付款/邮件生产账号，凭据和网络层都应阻断。

### 一个例子

测试“工具超时后只重试一次”：Model Stub 返回工具调用；Tool Stub 第一次超时、第二次成功；Clock Fake 跳过真实 sleep；Spy 检查两次 idempotency key 相同；断言状态最终成功和审计事件完整。另用真实工具 sandbox 的集成测试验证同一 key 不产生两次副作用。

### 面试简答版

Stub 负责给预设返回，适合模拟模型文本、tool call、429 和断流；Fake 是能工作的轻量实现，如内存状态库或假邮件 outbox；Spy 记录请求和调用，适合检查秘密未进入 Prompt、取消传播和幂等键；Mock 则预先声明并验证调用次数/顺序，适合断言未审批绝不执行高风险工具。单元测试在 I/O port 使用这些替身，真实 SDK/工具还要跑共同 contract 与 sandbox 集成测试，避免 Fake 与生产协议漂移，也避免过度 Mock 私有实现。
