## 我的答案

代码审查不只是看风格，而要沿着**输入—状态—I/O—错误—资源生命周期**追踪真实行为。审查者应先理解变更目标和不变量，再看 diff 是否用了最小机制、所有副作用是否显式、失败路径是否释放资源并保留诊断。

### 识别过度设计

信号包括：只有一个实现却引入多层 Factory/ABC；为了未来假设创建通用 DSL；简单同步调用被拆成多队列/事件；大量 wrapper 只透传参数；配置和泛型比业务逻辑多；新抽象没有独立变化轴。

审查问题：当前具体需求是什么？删掉一层能否仍清晰测试？扩展点是否已有第二个真实用例？抽象是否减少调用方知识，还是只搬运复杂性？优先提交最小可逆设计，必要扩展等真实变化出现再提炼；但认证、幂等等必要边界不能以“简单”为由省略。

### 隐藏副作用

警惕名字像 `get/validate/format` 的函数却写数据库、发网络、改全局状态；property/构造器触发 I/O；读取函数偷偷缓存跨租户数据；重试重复发送邮件；日志打印 PII；import 时注册/启动线程。

副作用应通过命令式命名和显式 port 表达，返回变更/事务结果，写操作有 idempotency key、权限与审计。审查调用图和测试，不只看函数体；尤其检查模型/文档能否间接改变工具参数。

### 异常吞噬

典型反模式：

```python
try:
    await tool()
except Exception:
    return None
```

它把超时、权限、安全、程序 Bug 全变成“无结果”。应只捕获能处理的具体异常，转换为带 cause 的领域错误，添加上下文后 `raise ... from e`；在系统边界统一映射状态码/用户消息。记录一次即可，避免每层重复日志。

`finally` 中也不能无条件覆盖原异常；cleanup 失败需要保留主异常和辅助信息。对异步代码，`CancelledError`/取消信号通常应继续传播，不能被广义 catch 转成重试。重试只针对明确瞬时且幂等的错误。

### 资源泄漏

逐条检查连接、文件、response body、stream、锁、semaphore、临时目录、子进程、GPU tensor、background task：所有成功、异常、取消、超时和早返回路径是否释放？优先 context manager/RAII、task group 和 `try/finally`，不要依赖 GC。

异步常见问题是创建 task 不保存/不 await、客户端断开后模型流仍运行、超时只停止等待却未取消底层请求、锁内 await 慢网络、子进程退出未 kill 整个进程组。测试应检查 pending task、连接池和临时对象计数，并注入中途异常。

### 审查流程

1. 先看需求、威胁模型、数据流和测试计划；
2. 标记所有外部 I/O、状态写、权限和敏感数据；
3. 沿 happy path、每个错误、timeout/cancel/retry 和并发路径走读；
4. 要求最小单元/集成测试证明不变量与 cleanup；
5. 查看观测、回滚、兼容与部署影响；
6. 将阻塞问题与可选建议分级，避免审查变成个人风格争论。

### 面试简答版

我会沿输入、状态、I/O、异常和资源生命周期审查。过度设计看是否为不存在的第二实现建立多层抽象；隐藏副作用看 `get/validate` 是否写库、发网、改全局或在重试中重复写；异常处理要求只捕获能处理的具体错误、保留 cause，取消不能被 `except Exception` 吞掉；资源则检查文件、连接、stream、锁、task 和子进程在成功、失败、超时、取消、早返回都释放。最后要求故障注入测试、幂等/权限证据和可回滚部署，而不只看 happy path。
