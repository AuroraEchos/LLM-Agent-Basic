> **问题：** `P0` 令牌桶与漏桶限流算法有什么区别，如何同时支持租户配额和全局限流？

## 我的答案

### 令牌桶

桶容量 $B$，按速率 $r$ 补充 token（最多 B）；请求消耗相应 token，有则立即通过，无则拒绝或等待。长期平均不超过 $r$，但空闲积累后允许最多约 B 的突发，适合 API 既要平均配额又允许短 burst。

### 漏桶

请求进入容量有限的队列，按固定/受控速率流出；队列满则丢弃/拒绝。它把突发整形成平滑输出，适合保护严格稳定速率的下游，但会增加排队延迟，过期请求应在队列中淘汰。实践中“漏桶”有 meter/queue 两种表述，面试应说明所用模型。

### 租户 + 全局层级限流

一次请求需同时通过多层预算：

```text
global bucket
  -> service/model/provider bucket
      -> tenant plan bucket
          -> user/key/concurrency limit
```

任一层失败则不执行，并返回限制维度、retry-after/剩余额度（避免泄露其他租户）。租户有基础 rate/burst和日/月 quota；全局桶防所有租户总和超过系统/供应商容量。为防大请求钻 QPS 限制，按估计输入+最大输出 token、GPU-seconds或tool cost加权扣费；实际完成后按策略核销/补差，并另设 concurrent in-flight和queue上限。

分布式实现需原子“补充+判断+扣减”（Redis script/function、集中 limiter 或本地分片+全局租约），使用单调时间并处理节点故障。完全强一致全局计数成本高，可用配额分片给实例租 token，接受有界超发；关键计费最终以持久 ledger 对账。hash hot tenant、clock skew、配置版本与 fail-open/fail-closed策略必须明确。

公平性可用 weighted fair queue/DRR，避免一个大租户长期占满全局桶，也给高优先级保留容量。监控 accepted/rejected、tokens、wait time、top tenant、估算与实耗偏差；限流配置要从可持续容量压测和SLO推导。

### 面试简答版

令牌桶按速率 r 补 token、容量 B 允许有限突发，长期均值受 r 限制；漏桶让请求排队后按稳定速率流出，更平滑但增加等待。多租户请求同时经过全局、模型/provider、tenant和用户层桶，任何一层超限就拒绝/排队；除 QPS 还按 token/GPU成本和在途并发限制。分布式扣减需原子，用配额分片可换取可控超发，关键计费由持久 ledger 对账，并用公平队列和保留容量防大租户挤占。
