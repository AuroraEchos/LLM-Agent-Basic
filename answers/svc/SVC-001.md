> **问题：** `P0` 什么是幂等性，创建任务、发送消息和执行支付等接口应如何设计幂等键？

## 我的答案

幂等性指同一个**逻辑操作**执行一次或多次，最终业务效果与执行一次相同。它不要求每次 HTTP 状态码/时间完全相同，也不表示操作无副作用日志；重点是不能重复创建任务、发消息或扣款。

### 幂等键设计

客户端在第一次尝试前生成高熵 key，所有超时重试复用它；服务端的唯一作用域通常是：

```text
(authenticated_tenant_or_principal, operation/resource, idempotency_key)
```

同时保存规范化请求的 fingerprint/hash、状态 `IN_PROGRESS/SUCCEEDED/FAILED_RETRYABLE`、资源 ID/响应摘要、创建与过期时间。在同一数据库事务中原子插入占位记录和执行业务写：

1. 首次 key：取得执行权，创建业务对象并保存结果；
2. 同 key + 同 fingerprint：已成功则返回原语义结果；处理中则等待/返回可查询状态；
3. 同 key + 不同 payload：拒绝冲突，绝不能把旧结果冒充新请求；
4. 执行状态不确定：通过权威业务记录/下游查询对账，而不是盲重试。

### 不同接口

- 创建任务：key 可由客户端 request ID 提供，task 表对 `(tenant,key)` 唯一；返回同一 task ID。若业务已有自然唯一键，可同时使用。
- 发送消息：每个逻辑 message 有稳定 message ID；outbox 与业务状态同事务，consumer 用 inbox/唯一约束去重。不要每次 retry 生成新 message ID。
- 支付：key 绑定 merchant、amount、currency、order 等 fingerprint，并传给支付方；本地 ledger/订单状态机、供应商 idempotency 与 reconciliation 共同保证，不能仅在 Redis 放短 TTL key。

TTL 至少覆盖客户端、broker、人工 replay 和下游重试窗口；支付/账务常需长期业务唯一记录。key 不能由不受信任用户跨租户碰撞/探测他人结果，响应回放前仍要重新授权。清理策略、并发等待、失败能否复用同 key必须写入 API contract并测试 crash-before/after-commit。

### 面试简答版

幂等是同一逻辑操作重复执行，业务效果仍只有一次。客户端首次生成 key，重试复用；服务端以 `(tenant, operation, key)` 唯一，并保存请求 fingerprint、处理中状态和最终资源/响应。相同 key 不同 payload 要拒绝，并发请求只能一个执行。创建任务返回同一 task ID，消息用 outbox+message ID/inbox，支付还要订单 ledger、下游 idempotency 和对账。保留期覆盖最大重放窗口，不能只用易过期的缓存键。
