## 我的答案

秘密管理覆盖**生成、存储、分发、使用、轮换、撤销和审计**整个生命周期，不只是把 `.env` 加进 `.gitignore`。

1. **优先消除长期秘密**：云服务/集群用 workload identity、OIDC 和短期动态数据库凭证；人用 SSO/MFA，不共享生产 API key。
2. **集中存储**：Vault/KMS/云 Secret Manager 保存加密值和版本，访问通过独立服务身份和最小 scope/RBAC；KMS 管加密密钥，secret manager管凭证生命周期，职责不同。
3. **安全分发**：运行时由 sidecar/CSI/受限文件或 SDK 获取，文件权限最小并可放内存文件系统；不要通过 Git、镜像 layer、Docker ARG/ENV、CI artifact、聊天或命令行传递。环境变量也可能经 `/proc`、子进程、debug dump泄漏，需按威胁模型使用。
4. **使用隔离**：每租户/工具凭证独立，限制 audience、scope、IP/资源和额度；高风险工具在隔离 worker执行，prompt/模型永远看不到原始 secret，只由受信工具 adapter附加凭证。
5. **轮换与撤销**：短 TTL优先；静态秘密用双版本重叠：发布新→consumer reload/验证→停止发旧→撤销旧。轮换要覆盖连接池、缓存和失败回滚，定期演练。
6. **审计与检测**：记录谁在何时读取哪个 secret版本和用于哪个服务（不记录值），secret scanning覆盖 commit/history、image和日志；检测异常使用和外泄。

发生泄露时先撤销/轮换、限制影响并查审计，再从仓库历史/镜像/日志清除；删 commit不是撤销。备份中的 secret也要加密和到期策略。日志/trace异常、tool args和错误响应集中脱敏，支持 key pattern与结构化敏感字段，而非靠人工小心。

数据库密码若必须静态存在，应每服务/环境/权限独立，应用账号不能做 DDL/admin；第三方工具 token按 user/tenant加密 envelope storage并记录 consent、scope和删除。根密钥/恢复凭证采用更强隔离、双人控制和 break-glass审计。

### 面试简答版

优先用 workload identity和短期动态凭证，剩余 secret集中放 secret manager/KMS，以服务身份和最小权限运行时获取，绝不进 Git、镜像、ARG、日志或 prompt。每环境/租户/工具隔离 scope，adapter附加凭证而不是交给模型。轮换用新旧版本重叠并验证连接池reload后撤旧，所有读取有审计。泄露先立即吊销/轮换和调查，再清历史；secret scanning与脱敏覆盖仓库、镜像、CI和遥测。
