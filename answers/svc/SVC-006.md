## 我的答案

**Authentication（认证）**回答“你是谁/凭证是否真实”；**Authorization（授权）**回答“这个身份能对这个资源做什么”。认证成功不代表有权读取任意 tenant 的 run；授权必须在每次资源访问时校验，不能只靠前端隐藏按钮。

| 机制 | 本质与适用场景 | 关键边界 |
|---|---|---|
| API Key | 长随机秘密标识应用/项目，适合简单 server-to-server、SDK 调用和计量 | 通常不代表终端用户/细粒度委托；哈希存储、scope、过期、轮换、可撤销，禁止 URL/日志泄漏 |
| Session | 服务端保存会话状态，浏览器持 opaque cookie ID | cookie 用 Secure/HttpOnly/SameSite，防 CSRF/session fixation；便于立即撤销但需共享 session store/粘性设计 |
| JWT | 自包含 signed token 格式，适合跨服务短期传递 claims | 不天然加密/不可撤销；严格验证算法、签名、issuer、audience、exp/nbf和key rotation，不能只 decode |
| OAuth 2.0 | 资源所有者向 client 委托访问 resource server 的授权框架 | 它本身不是用户认证；登录通常用 OpenID Connect。现代 code flow使用 PKCE、精确 redirect URI、state/nonce，token最小 scope/audience |
| RBAC | permission 赋给 role，用户/服务再绑定 role | 适合组织权限矩阵，但 role explosion和对象级越权仍需 tenant/resource ownership或ABAC关系校验 |

典型平台：用户网页登录用 OIDC authorization code + PKCE，后端建立安全 session或持有短期 access token；外部服务账号用 scoped API key/OAuth client credential/工作负载身份；资源服务从经验证 token/session 得 principal 和 tenant，再用 RBAC + resource ownership/ABAC判定 `tool:execute`、`run:read`。服务间不要信任客户端自报 `X-Tenant-ID`。

JWT access token 应短期、audience restricted；refresh token更严格保存、rotation/reuse detection。权限降低与用户停用不能等长期 JWT自然过期，可用短 TTL、token version/introspection/deny list按风险组合。认证/授权决定写结构化审计，但 token、cookie、API key绝不能写日志。

### 面试简答版

认证确认身份，授权决定该身份对具体 tenant/resource 的动作。API Key 适合简单服务调用但需 scope/轮换；Session 适合浏览器且服务端易撤销；JWT 是自包含签名格式，必须验 issuer/audience/exp/算法，不是自动安全；OAuth 2.0 是委托授权，登录通常用 OIDC，现代 code flow配 PKCE；RBAC按角色授予权限，但还要对象所有权/ABAC防越权。每个请求都从可信认证上下文做服务端授权。
