## 我的答案

相似工具误选通常不是模型单点问题，而是**工具边界重叠、一次暴露太多工具、描述缺少反例或训练/评测没有覆盖混淆对**。应先修接口设计，再做分层路由，最后才考虑换模型。

### 一、定位混淆

建立工具选择混淆矩阵，记录用户意图、候选工具、模型选择、参数和真实结果。重点分析名称相似、description 同义、输入 schema 相同，以及一个“万能工具”与多个专用工具竞争的情况。

### 二、重构工具边界

- 合并语义完全重叠的工具，避免别名竞争；
- 按动作或资源拆分过宽工具，例如 search/read/update 分开；
- 名称体现差别：`search_orders` 与 `get_order_by_id`；
- Description 加“用于/不要用于/改用 X”的对照；
- schema 使用互斥字段和 enum，让错误选择尽早暴露；
- 对底层多个 API 可提供一个业务语义 facade，减少模型需要理解的实现差异。

合并不能把所有动作塞进一个危险 `operation` enum；权限和副作用不同的工具应保持分离。

### 三、分层路由

工具很多时先按 domain/capability 路由，再只给模型一个小候选集：

```text
用户请求 → domain router（订单/财务/文档）
→ policy filter（当前身份可用工具）
→ semantic shortlist
→ LLM 在 3～8 个候选中选择
```

确定性的 ID、URL、文件类型可先规则路由；模糊语义用分类器/embedding/LLM。路由器低置信时保留多个候选或澄清，不能自信地强制错误域。

### 四、上下文与示例

提供少量对比示例，尤其是 hard negatives；只暴露当前状态可执行的工具，已完成或未授权工具移除。不要把几十个长 schema 全塞入上下文，这会增加 token 和注意力竞争。

### 五、执行期保护

工具被选中后仍做参数和业务前置条件检查。若错误工具无副作用，可返回结构化 `WRONG_TOOL/use_tool` 提示一次修复；写操作不得“试试看”。连续误选达到上限后请求用户澄清或人工处理。

### 六、评测

对每对易混工具构造最小对比集，报告 macro selection accuracy、危险误选率、top-k router recall、澄清率和端到端成功率。A/B 时固定模型与任务分布，证明收益来自接口/路由，而非候选集恰好更少。

### 面试简答版

先用混淆矩阵找出重叠工具，合并真正同义接口，按 search/get/update 等业务语义拆开边界，并在名称和 Description 中写清“何时用、不要用于什么、应改用哪个工具”。工具多时采用 domain router + 权限过滤 + semantic shortlist，只向模型暴露少量当前可执行工具；低置信则澄清。执行前仍校验业务前置条件，写操作不能靠试错。用混淆对 hard-negative 集评估选择准确率、危险误选和端到端成功率。
