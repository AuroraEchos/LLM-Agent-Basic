> **问题：** MCP 与模型原生 Function Calling 处于什么层级，二者如何协作？
>
> **分类：** Agent 与工具调用

> **来源：** [INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md](../../INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md)

## 我的答案

两者处于不同层级：**模型原生 Function Calling 是模型输出“调用哪个函数及参数”的推理接口；MCP 是 Host/Client/Server 之间发现、描述、调用工具与交换上下文的集成协议**。MCP 不取代模型 tool calling，Function Calling 也不定义工具从哪里来或如何跨应用连接。

### 一、协作链路

```text
MCP Client tools/list
→ Host 过滤并转换 MCP inputSchema 为模型 tool definitions
→ 模型原生 Function Calling 选择 tool + arguments
→ Host 做 schema、ACL、审批与预算检查
→ MCP Client tools/call → MCP Server → backend
→ MCP result 返回 Host
→ Host 规范化/过滤后作为 tool result 回传模型
```

模型 API 可能有自己的 call ID、消息格式和并行调用语义；Host 负责与 MCP JSON-RPC request ID/结果进行映射。

### 二、各自负责什么

| 层 | 职责 |
|---|---|
| Function Calling | 模型理解描述、决定是否调用、生成参数、根据结果继续 |
| MCP | 能力发现、schema/metadata、传输、会话、结果和通知 |
| Host/Orchestrator | 候选过滤、协议适配、授权、执行策略、确认、审计 |

换模型供应商时 MCP server 可复用；换后端集成时模型侧仍看到相似工具。这是解耦价值。

### 三、不能混淆的边界

MCP tool 能被发现不代表当前用户有权调用；模型输出 schema-valid 参数也不代表语义或权限有效；Server annotations/description 是提示性 metadata，不是可信安全策略。Host 必须执行 allowlist、credential delegation、参数限制和高风险确认。

Resources 和 Prompts 也可通过 MCP进入模型上下文，但它们不必转换为 Function Calling；前者是数据，后者是用户选择的模板。

### 四、版本与错误

Host 在 MCP 初始化时协商协议能力，在模型侧适配支持的 schema 子集。工具列表变化要更新缓存/Prompt；输出过大时摘要或以 resource link 返回。MCP transport error、tool execution error 和模型调用错误应分层处理，不能都当成“工具失败”让模型无限重试。

### 面试简答版

Function Calling 位于模型推理接口层：模型依据工具描述选择 name 并生成 arguments；MCP位于应用集成协议层：Host 内 Client 从 Server 发现 tools/resources/prompts，并通过标准消息调用。Host 将 MCP tool schema 转成模型定义，模型提出调用，Host 校验权限和审批后发 `tools/call`，再把结果映射回模型。MCP 提供互操作，Function Calling 提供模型决策，两者之间的 Host 才是真正的安全与编排边界。
