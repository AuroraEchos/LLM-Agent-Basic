## 我的答案

这五个机制共同处理分布式工具调用不可避免的慢、错和重复：超时限制等待，重试处理瞬时故障，幂等防重复副作用，熔断阻止持续压垮故障服务，降级维持有限能力。顺序通常是：

```text
budget/deadline → circuit breaker → bulkhead/rate limit
→ idempotent call → timeout → classified retry → fallback
```

### 一、超时与 Deadline

为连接、读取和总调用分别设上限，更重要的是从任务总 deadline 向下游传播剩余预算：

\[
t_{tool}\le deadline_{task}-now-reserve
\]

超时意味着结果未知，不等于操作未发生。对写操作超时后不能盲重试，要用幂等键查询最终状态。

### 二、重试

只重试瞬时且可安全重放的错误，如部分 429、连接重置、明确 5xx；validation、permission、not_found 等通常不重试。采用指数退避与 jitter：

\[
delay_n=\min(cap,base\cdot2^n)+jitter
\]

设置次数/总时间 retry budget，尊重 `Retry-After`。多层组件不能各自重试造成指数放大，选一个责任层。

### 三、幂等

读取天然较易幂等；创建、支付、发送等使用服务端幂等键：

\[
key=H(tenant,operation,logical\_request\_id)
\]

服务端原子保存 key 与结果；相同 key、相同参数返回原结果，不同参数应冲突。不能用每次重试新生成的 key。对不支持幂等的外部系统，需先查状态、建立本地去重或禁止自动重试。

### 四、熔断与隔离

熔断器在滑动窗口失败/慢调用超过阈值后从 CLOSED 进入 OPEN，快速失败；冷却后 HALF_OPEN 少量探测，成功再恢复。配合 per-tool bulkhead 隔离线程/连接池，防一个工具耗尽整个 Agent。熔断按依赖/区域区分，不能因单租户参数错误打开全局熔断。

### 五、降级

可降级为缓存/稍旧数据、备用 provider、只读模式、较弱但安全的功能，或明确告诉用户暂不可用并保存草稿。降级必须标数据时间和能力差异；付款、权限、医疗等高风险场景宁可失败关闭，不能用不可信近似结果。

### 六、可观测与恢复

记录 attempt、idempotency key 摘要、deadline、错误类别、外部 request ID、熔断状态和最终副作用。监控 success、timeout、retry amplification、breaker open、fallback quality 和重复副作用率。使用故障注入验证超时边界、重试风暴和半开恢复。

### 面试简答版

从任务 deadline 给每个工具分配超时；超时只表示结果未知，写操作先按幂等键查状态。仅对 429、网络和部分 5xx 等瞬时错误做有预算的指数退避加 jitter，权限/参数错误不重试。创建、支付、发送用服务端原子幂等键保证重复请求返回同一结果。故障率/慢调用超阈值时熔断，半开探测恢复，并用 bulkhead 隔离资源。降级可用缓存、备用源或只读模式，但标明陈旧性；高风险任务失败关闭。全链路记录 attempt、外部回执和最终副作用。
