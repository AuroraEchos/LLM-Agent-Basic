> **问题：** Plan-and-Execute、ReWOO、Tree of Thoughts 与 ReAct 各适合什么任务？
>
> **分类：** Agent 与工具调用

> **来源：** [INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md](../../INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md)

## 我的答案

四者的区别主要在于：计划何时生成、工具 observation 是否立刻参与后续推理，以及是否显式探索多个候选路径。

### 一、ReAct：边观察边决定

ReAct 交替产生 action 和 observation，适合下一步高度依赖刚获得结果的开放环境，例如故障排查和网页研究。它适应性强，但模型调用与 observation 反复增长，容易循环、成本高，且全局依赖规划较弱。

### 二、Plan-and-Execute：先全局拆解，再逐步执行

Planner 先生成任务图或步骤，Executor 按计划调用工具；执行结果可触发 planner 修订：

```text
Goal → Plan [S1,S2,S3]
→ Execute S1/S2 → check state
→ replan if needed → Execute S3 → verify
```

适合步骤多、依赖明确、需要进度展示、并行或审批的工程任务。缺点是初始计划可能基于未知信息而脆弱，规划本身增加延迟；简单任务不值得规划。

### 三、ReWOO：计划与观察解耦

ReWOO（Reasoning WithOut Observation）由 Planner 一次生成带 evidence 变量的计划，Worker 执行工具并填入结果，Solver 最后综合，见[原论文](https://arxiv.org/abs/2305.18323)：

```text
Plan: E1 = search(A)
Plan: E2 = lookup(B from E1)
Worker fills E1/E2
Solver(question, plan, evidence) → answer
```

它避免每次工具返回都把全部历史重新送给 Planner，适合工具依赖可提前预测、并行机会多、追求 token/模型调用效率的任务。但 observation 若改变任务结构，固定计划不易及时适应，需失败后重规划或退回 ReAct。

### 四、Tree of Thoughts：显式搜索多个推理分支

ToT 把“thought”作为搜索状态，生成多个候选、评价并用 BFS/DFS/beam search 保留或回溯，见[原论文](https://arxiv.org/abs/2305.10601)：

\[
S_{t+1}=Select(Evaluate(Expand(S_t)))
\]

适合组合搜索、谜题、规划等早期选择会决定成败且可评价中间状态的任务。它能跳出单条 CoT 的错误分支，但模型调用呈分支增长，evaluator 可能误判；普通检索或简单工具流通常不值得。

### 五、选择表

| 场景 | 优先范式 |
|---|---|
| 环境动态、下一步依赖实时反馈 | ReAct |
| 长任务、依赖明确、需进度/审批 | Plan-and-Execute |
| 可预先列出证据调用、追求并行与低 token | ReWOO |
| 候选路径多、可评价和回溯 | Tree of Thoughts |

生产系统常混合：先 Plan-and-Execute 建立骨架，局部不确定步骤用 ReAct，独立证据批量用 ReWOO 式执行，只有困难搜索节点使用有限 beam 的 ToT。

无论哪种范式，工具执行、权限、预算、幂等和完成验证都应由确定性 orchestrator 管理。

### 面试简答版

ReAct 每步根据最新 observation 决定下一动作，适合动态探索，但循环和 token 成本高；Plan-and-Execute 先全局分解再执行，适合长任务、依赖和审批，环境变化时要重规划；ReWOO 预先生成带 evidence 变量的计划，再批量执行、最后求解，效率高却不擅长计划中途突变；Tree of Thoughts 显式扩展、评价和回溯多个思路，适合可搜索的难题但成本最高。工程上通常混合使用，并由 orchestrator 统一限制权限、预算和副作用。
