## 我的答案

Function Calling 是一种结构化协议：应用把允许的工具及参数 schema 告诉模型，模型选择“回答”或“提出工具调用”；**应用而非模型**验证并执行，再把带调用 ID 的结果回传，模型继续推理或生成最终答案。

### 一、工具定义

工具描述通常包含名称、清晰的适用/禁用场景和 JSON Schema：

```json
{
  "name": "get_order",
  "description": "按订单 ID 读取当前用户有权查看的订单状态",
  "parameters": {
    "type": "object",
    "properties": {"order_id": {"type": "string"}},
    "required": ["order_id"],
    "additionalProperties": false
  }
}
```

描述要区分相似工具，enum/范围/格式尽量明确；不要把数据库密码、内部实现或模型不应控制的 `user_id/tenant_id` 暴露为参数。身份由服务端上下文注入。

### 二、模型决策

应用发送用户消息、必要状态和可用工具。模型可能返回普通文本、一个工具调用或多个调用；每个调用含 name、arguments 和 call ID。并行只适用于无依赖且副作用安全的调用。

模型输出只是提案：JSON 合法不代表语义正确、用户有权限或动作安全。

### 三、验证与执行

执行器依次检查：工具是否 allowlist、schema、业务规则、ACL、速率/预算、幂等键、风险和用户确认。然后在超时、网络限制和 sandbox 中调用真实 API。

写操作应带 idempotency key；自动重试只适用于明确幂等/安全的错误。支付、删除、发送等高影响动作在展示目标和参数后由用户确认，且确认后若参数变化必须重新确认。

### 四、结果回传与循环

工具返回结构化 observation，并关联原 call ID：

```json
{
  "call_id": "call_17",
  "ok": true,
  "data": {"status": "shipped", "eta": "2026-08-22"}
}
```

错误也应结构化区分 validation、permission、not_found、timeout、retryable 和 internal，且对模型隐藏 stack trace/secret。模型据此回答、修正参数或调用下一工具，直到完成或达到预算。

### 五、关键边界

- 不可信工具结果按 data 处理，不能覆盖 system policy；
- 模型不得伪造工具结果，UI 只把真实回执标为成功；
- 限制最大调用次数、重复调用和参数爆炸；
- 并发写操作需事务、锁或补偿，不能假定调用顺序；
- 日志记录 tool/version、参数摘要、principal、审批、call ID、结果、耗时和副作用；
- 工具 schema/version 变更需兼容与回归评测。

### 面试简答版

应用先向模型提供工具名称、用途和严格 JSON Schema；模型决定直接回答还是返回带 call ID 的 name/arguments。这个调用只是提案，服务端还要做 allowlist、schema、业务规则、实时 ACL、预算、幂等和审批检查，再在超时/sandbox 中执行。结果或分类错误以结构化 observation 关联同一 call ID 回传，模型再回答或继续调用。用户/租户身份不能由模型传入，高风险写操作必须确认，只有真实工具回执才能标记成功，并对循环、重试、并发副作用和审计做确定性控制。
