## 我的答案

三者不是互斥技术，而是不同抽象：状态机强调有限状态和合法转换；事件循环强调持续接收异步事件并反应；有向图强调步骤依赖、分支与汇合。复杂系统常用事件循环承载运行时、图描述工作流、状态机约束每个节点。

### 一、有限状态机

\[
s_{t+1}=\delta(s_t,event_t)
\]

适合状态少、路径清楚、合规要求强的流程，如 `DRAFT→CONFIRMED→EXECUTING→SUCCEEDED/FAILED`。优点是确定、易验证、审计和测试非法转换；缺点是复杂分支/并行会造成状态爆炸，开放式探索表达笨重。

### 二、事件循环

持续从队列接收 user/tool/timer/message event，handler 更新状态并产生新 event。适合聊天、流式工具、长连接、多 Agent 消息和动态环境。它解耦生产者/消费者、支持异步并发，但顺序、重复投递、背压和最终一致性复杂。

事件必须有 ID、schema、causation/correlation ID，handler 幂等；否则重复消息会产生重复副作用。

### 三、有向图编排

节点代表模型、工具或确定性代码，边代表依赖/条件；DAG 适合批处理和可预先规划的多步骤任务，可并行 ready nodes。允许 cycle 的 state graph 可表达 Agent loop，但必须有终止和 checkpoint。

图适合分支、汇合、map-reduce、human-in-the-loop 和中断恢复；缺点是动态图、共享状态 merge、图版本迁移和可视化调试更复杂。

### 四、选择

| 复杂度/场景 | 首选 |
|---|---|
| 少量确定状态、高风险业务流程 | 状态机 |
| 外部事件持续到达、Agent 间异步通信 | 事件循环 |
| 多步骤依赖、并行、条件与恢复 | 有向图 |
| 开放 Agent + 关键写操作 | 图/事件循环外层，写操作内部 FSM |

简单线性 2～3 步直接代码往往最好，不必为框架而框架。

### 五、共同要求

持久化 state/checkpoint、版本化 schema 与图、幂等 node、timeout/retry、最大步数、补偿和 trace replay。部署新图版本时，在途实例需固定旧版完成或显式迁移，不能无声切换语义。

### 面试简答版

状态机适合状态有限、转换严格、需要审计的订单/审批流程；事件循环适合持续异步接收用户、工具、定时器和多 Agent 消息，但要处理幂等、顺序与背压；有向图适合多步骤依赖、并行、分支汇合和 checkpoint，DAG 表示有限工作流，有环图表示 Agent loop。生产中常组合：事件运行时驱动图，每个高风险节点内部用状态机。简单线性流程直接代码即可，所有方案都需版本、恢复、预算和终止条件。
