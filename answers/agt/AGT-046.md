> **问题：** 为什么任务状态不应只存在于对话文本中，如何建立外部状态存储与 Single Source of Truth？

## 我的答案

对话文本是给模型看的叙事上下文，不适合作为任务真值：它可能被截断、摘要失真、重复、顺序混乱或由模型伪造；并发 Worker 也无法安全地“修改一段聊天”。任务状态必须存在外部、结构化、事务化的 Single Source of Truth（SSOT）。

### 一、为什么对话不能当数据库

- 模型可能说“已完成”，但外部动作其实失败；
- compaction 会丢掉审批、ID、未完成项与错误码；
- 多 Agent 并发产生冲突，last message 不等于最新合法状态；
- 无 schema、约束、查询和原子更新；
- 上下文窗口、缓存与模型供应商变化会改变“当前记忆”；
- Prompt Injection 能在文本中伪造 `SYSTEM/TOOL SUCCESS`。

### 二、外部状态模型

```text
Run: goal, status, workflow_version, budget, owner
Task: id, dependencies, state, attempt, lease, assignee
Action: proposal, policy_result, approval, idempotency_key
Observation: tool_result, source, time, validation_status
Artifact: uri, hash, version, ACL
Event: sequence, actor, state_patch, causation_id
```

状态转换由 orchestrator/工具回执执行，例如只有真实回执才能 `EXECUTING→SUCCEEDED`。数据库当前 view 是 SSOT，append-only event log 提供审计与重建。

### 三、一致性与并发

用事务或 compare-and-swap/expected version 更新；Worker 获取 lease + fencing token，防过期 Worker 覆盖新状态。消息至少一次投递时 handler 幂等，写操作绑定 operation/idempotency ID。跨系统无法 ACID 时用 outbox/saga 和 reconciliation。

### 四、如何给模型使用

每一步由 Context Builder 从 SSOT 生成只读 task view：当前目标、已验证事实、open items、预算与允许动作。模型返回 state patch proposal，执行器验证后才写入。聊天摘要只是派生 view，可以随时从 state/events 重建。

### 五、恢复与治理

checkpoint 保存状态版本和 artifacts，不存 secret；暂停/恢复、审计、HITL 都围绕同一 run ID。数据库 schema 与 workflow 版本化，迁移在途任务需显式规则。定期核对 SSOT 与外部系统，监控 stuck、非法转换、版本冲突和孤儿副作用。

### 面试简答版

对话会被截断、摘要和模型伪造，不能原子并发更新，也不能证明工具副作用，所以不能作为任务真值。应在外部数据库保存 run、task DAG、action、validated observation、artifact、审批、预算和事件日志；只有 orchestrator 与真实工具回执能做合法状态转换。更新用事务/expected version、lease/fencing 和幂等键，跨系统用 outbox/saga。每次调用模型时从 SSOT 生成 task view，模型只提出 patch；聊天摘要是可重建的派生缓存。
