## 我的答案

参数问题应分为**可确定性修复**与**需要用户决策**。Agent 可以规范化格式和使用可信上下文补值，但不能猜测会改变目标、金额、收件人、范围或权限的关键参数。

### 一、分层校验

1. 语法：JSON 是否可解析；
2. Schema：类型、required、enum、pattern、范围；
3. 语义：开始时间早于结束时间、币种与金额匹配、资源 ID 存在；
4. 上下文：资源属于当前租户，状态允许操作；
5. 意图/风险：参数是否与用户原始请求一致，是否需要确认。

执行器返回机器可读错误：

```json
{"code":"MISSING_REQUIRED","field":"end_date","retryable":false,
 "message":"需要结束日期，格式 YYYY-MM-DD"}
```

### 二、何时自动修复

可安全修复：去空格、大小写规范化、明确的日期/单位格式转换、字符串数字转数值、从已认证 session 注入 user/tenant，以及使用无风险且文档化的默认值。修复前后应可审计，不能改用户语义。

模型生成的未知 ID 不能靠格式正确便接受，需查询/校验真实资源。

### 三、何时澄清

参数缺失且存在多个合理值、相对时间/代词歧义、参数互相冲突、影响范围/金额/外部收件人，或用户意图与工具副作用不一致时，应提出一个最小问题：

```text
“你要取消 ORD-123 还是 ORD-456？两笔都符合‘昨天的订单’。”
```

不要一次询问已能推导的字段；展示候选的必要辨识信息但不得泄漏越权数据。

### 四、修复循环

对可修错误允许有限次数：校验 → 结构化反馈 → 模型只修改错误字段 → 再校验。若同一错误重复、工具 schema 可能过期或涉及副作用，停止并澄清/升级。已经确认的高风险参数在修复后发生变化，应重新确认。

### 五、并发与状态变化

校验通过到执行之间资源可能变化，因此工具内仍需原子业务约束和乐观锁，例如 `expected_version`。模型侧预检查不能替代数据库事务。

### 面试简答版

我会依次做 JSON、Schema、跨字段语义、实时资源/ACL 和用户意图校验。空格、大小写、明确单位转换和可信 session 字段可自动修复；多个合理值、时间歧义、范围/金额/收件人或副作用冲突必须用最小问题向用户澄清，不能猜。执行器返回带 code/field/retryable 的结构化错误，允许有限次只修错误字段；参数变化涉及高风险动作则重新确认。最终工具内部还要用事务或版本检查防校验后的并发状态变化。
