## 我的答案

Agent 评测应以环境中的真实终态为主，并把质量分解为 task、trajectory、tool 和 resource 四层。流畅回答或模型自评不能证明任务成功。

### 一、任务集与成功判定

从真实任务分层抽样，覆盖正常、歧义、工具故障、无权限、需要澄清和对抗输入。每题定义初始环境快照、允许工具、预算和确定性验收器：文件 diff、数据库状态、单元测试、引用证据或人工 rubric。

\[
SuccessRate=\frac{\# tasks\ satisfying\ all\ required\ predicates}{\# tasks}
\]

区分 full/partial success 和安全拒绝；危险地“完成”不能算成功。

### 二、步骤效率

在成功任务中测实际步骤与 oracle/最佳已知步骤的比值、无效/重复调用、重规划、并行度和 time-to-success：

\[
Efficiency=\frac{C_{baseline\ or\ oracle}}{C_{agent}}
\]

无统一 oracle 时报告每成功任务的 model/tool calls、tokens、wall-clock，避免失败任务因早停显得高效。

### 三、工具正确率

- Selection accuracy：意图是否选对工具；
- Argument validity/semantic correctness；
- First-call success；
- Result utilization：是否正确使用 observation；
- Unauthorized/dangerous call rate；
- Retry、幂等与副作用正确性。

为相似工具建立 confusion matrix，参数不仅 schema-valid，还需满足业务真值。

### 四、成本与效用

统计 input/output tokens、模型/embedding/reranker、工具/API、计算与人工分钟：

\[
CostPerSuccess=\frac{TotalCost}{\# successful\ tasks}
\]

联合 p50/p95、success 和风险形成 Pareto，而不是只比平均 token。多 Agent 与单 Agent需在相同总预算下公平比较。

### 五、实验可靠性

固定环境、数据、模型版本和随机性；任务多次运行，报告均值/置信区间与按难度切片。设置单 Agent、无记忆、无规划等基线与消融。LLM judge 在人工集上校准，工具/环境 verifier 优先。

### 六、线上评测

shadow/canary 记录真实成功回执、人工接管、用户纠正、循环、预算耗尽和安全事件；将失败 trace 回灌 development set，但保留冻结 holdout。任务成功提升若伴随危险调用上升，不可上线。

### 面试简答版

先给每个任务定义环境快照、允许工具、预算和可验证成功 predicate，用最终文件、测试、数据库或证据而非模型自评计算任务成功率。步骤效率看成功任务的调用数、重复/无效步、重规划、p95 和相对 oracle 成本；工具层看选择、参数语义、首次成功、结果利用、越权及幂等；成本用每成功任务总模型、工具、计算和人工费用。多次运行、置信区间、切片、基线和消融，并把安全拒绝与危险假成功分开。
