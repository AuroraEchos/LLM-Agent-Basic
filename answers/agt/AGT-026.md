> **问题：** 多 Agent 系统如何共享上下文、避免重复工作并处理部分失败？

## 我的答案

多 Agent 不应共享一条无限增长的群聊记录，而应共享**最小必要、结构化、版本化且有所有权的任务状态**。通信围绕 task、artifact、evidence 和 event 展开，才能去重、恢复和审计。

### 一、共享上下文分层

- Global brief：目标、约束、验收标准、预算；
- Task registry：子任务 ID、owner、依赖、状态和 lease；
- Artifact store：文件、代码、查询结果与版本，不在消息中复制全文；
- Evidence/provenance：来源、时间、置信度与 ACL；
- Private scratch：每个 Agent 的局部工作状态，不默认广播。

Agent 收到 task-specific view，而非整个系统历史。摘要必须链接原始 artifact，不能让层层摘要成为唯一事实。

### 二、避免重复工作

用原子 claim/lease：Worker 对 `task_id + input_version` 获取有期限租约；其他 Worker 看见 RUNNING 后不重复领取。为工具和产物使用幂等键：

\[
key=H(task\_id,operation,input\_version)
\]

提交采用 compare-and-set，过期 lease 可被接管。查询/URL 结果缓存、内容 hash 去重；Planner 在分配前检查现有 artifacts 和 capability registry。

### 三、并发与冲突

共享状态使用 append-only event log 加 materialized view，或数据库事务/乐观锁。Agent 提交 patch 而非覆盖整个 state；冲突由字段 owner、版本和可验证证据解决。代码/文档可用 branch + merge，不能 last-write-wins 丢掉他人结果。

### 四、部分失败

每个节点声明 critical、retry policy、fallback、deadline 和 compensation。独立分支可继续，依赖失败的节点标 BLOCKED/SKIPPED；汇总时披露缺失覆盖。瞬时错误重试，确定性错误重规划；Worker 崩溃后 lease 超时，新的 Worker 从 checkpoint/artifact 恢复。

写操作超时先 reconciliation 外部状态，不能简单重新执行。需要 all-or-nothing 的跨系统操作采用 saga/补偿或人工介入。

### 五、可观测性

每条消息带 trace/task/parent ID、sender、schema version 和 dedupe ID。监控重复任务率、lease 冲突、无 owner/阻塞时间、通信 token、artifact 重用、部分失败恢复率和最终 coverage。

### 面试简答版

多 Agent 共享的应是版本化 global brief、task registry、artifact store 和 evidence，不是完整群聊。任务通过原子 lease 分配，工具调用和产物用基于 task/input version 的幂等键，Agent 提交 patch 并用乐观锁合并，避免重复与覆盖。部分失败时独立分支继续，依赖节点阻塞；按错误类型重试、fallback 或重规划，Worker 通过 checkpoint 与 lease 接管恢复。汇总必须标出缺失分支和证据，所有消息带 trace、task 和去重 ID。
