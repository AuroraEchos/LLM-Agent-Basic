## 我的答案

Agent Trace 应能重建“收到什么目标、基于什么状态做了哪项决策、工具实际发生了什么、状态如何变化”。它不是一串聊天日志，而是有父子关系、版本和因果链的 spans/events。

### 一、Trace 模型

一次任务一个 `trace_id`，每次 model、planner、tool、retrieval、approval、memory、node 运行一个 span：

```text
trace_id / span_id / parent_span_id
task_id / step / agent / node / attempt
start/end/status / input-output schema hash
model+prompt+tool+policy+index versions
token/cost/latency / error class
state_before_hash / state_patch / state_after_hash
```

工具 span 记录规范化参数、call/idempotency ID、真实结果与外部 request ID；计划记录依赖、成功条件与修改原因。敏感输入、CoT、secret/PII 不应原样日志，可保存脱敏摘要、hash 与可控的加密 evidence store。

### 二、因果诊断漏斗

1. 目标/约束是否被正确解析；
2. 计划是否覆盖必要子任务、依赖和验收；
3. 工具选择和参数是否正确；
4. 执行器是否按策略调用，工具是否失败/超时；
5. observation 是否通过 schema/语义验证；
6. 状态 patch 是否正确，是否忽略或误读工具结果；
7. 停止是否满足 Done predicate。

### 三、区分规划与工具错误

用 counterfactual replay：保留其余环节，将 gold/修正后的工具结果注入原计划；若仍失败，多为规划/生成问题。将 gold plan 与原工具执行比较，若恢复则原计划有误。工具返回正确但 state 未更新，是 observation handling；工具本身返回错误，是 execution/backend。

Replay 写操作必须在模拟环境或使用录制结果，不能重放真实副作用。

### 四、聚合分析

从 traces 计算各 step 成功/延迟、tool selection confusion、首次调用成功、重试/循环、计划修改、预算耗尽、人工介入和失败路径。对相同任务聚类 traces，比较成功/失败的首个分叉点，而不是只看最终回答。

### 五、工程边界

统一 trace context 跨队列和多 Agent 传播；事件序列号和时间同步；大 payload 以 artifact URI+hash 保存。采样不能丢高风险/失败 trace；访问、留存和删除满足隐私。版本信息缺失的 trace 无法可靠复现。

### 面试简答版

Agent Trace 用 trace/span/parent ID 记录模型、规划、检索、工具、审批、记忆和状态转换，并绑定模型、Prompt、工具、策略和索引版本、参数、回执、延迟、token 与错误类别。诊断时沿目标解析→计划覆盖→工具选择/参数→真实执行→结果验证→状态更新→停止验收逐层检查。用离线 counterfactual replay 注入 gold plan 或 gold observation 区分规划与工具问题，写操作不真实重放。日志要脱敏且跨 Agent 传播因果 ID，失败和高风险 trace 必须保留。
