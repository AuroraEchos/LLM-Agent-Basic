## 我的答案

必须在**序列化后、发送模型 API 前的最后边界**记录 Context Manifest；记录中间组件的输入还不够，因为模板、tokenizer、adapter 和截断可能在最后一步改变实际内容。

### 一、Context Manifest

对每次 model call 保存：

```text
trace/span/call ID
model + tokenizer + chat-template + API adapter versions
每条 message 的 role、source、trust、version、ACL、token count
工具定义名称/schema hash与顺序
检索/记忆 IDs、rank、位置、裁剪与摘要 lineage
task state version / prompt hash / total tokens / max output
```

敏感内容放受控加密存储或仅存 hash/脱敏视图，访问审计和 TTL 不能因调试而失效。

### 二、捕获三个视图

1. Logical view：Context Builder 选择了什么；
2. Rendered view：chat template/工具适配后实际消息；
3. Token view：目标 tokenizer 的 token IDs、边界、长度和截断决定。

三者 diff 能定位选择问题、模板问题还是供应商序列化问题。

### 三、典型诊断

- 截断：检查 pre/post token count、truncation side、被删除 item/字段和输出 reserve；
- 顺序：按 token offset 可视化 gold evidence、policy 和工具 schema 的位置；
- 模板：检查 role mapping、escaping、stop sequence、重复 system 和 tool-call ID；
- 状态同步：manifest 的 state version 与 SSOT current version 比较，查旧 checkpoint/缓存；
- Tool Result 注入：call ID 是否匹配、结果是否在正确 role、是否经过 schema/redaction、是否把 error 当 success；
- 缓存：记录 cache key、hit 和所依赖版本，识别错误复用。

### 四、可重放

在隔离环境用同一 manifest、模型 revision 和参数重放；对不确定采样不能保证逐 token 相同，但应能重现输入。更换单一组件做 counterfactual：仅移动证据、恢复完整工具结果或换新 state，观察故障是否消失。

### 五、自动门禁

在调用前断言 system 存在、必需约束/工具/observation 未丢、token 不超限、无 secret、ACL 正确、tool-call/result 配对完整。线上监控 truncation、平均 item age、重复、stale state、orphan result 和 context build latency。

### 面试简答版

要在最终 API 发送前记录 Context Manifest，而非只记 Prompt 模板：保存模型/tokenizer/chat-template、每条 message 的 role/source/version/ACL/token 与位置、工具 schema hash、检索/记忆 ID、state version、截断和缓存决定。分别保留 logical、rendered、token 三个视图，才能定位是选择、模板还是 tokenizer 问题。通过 call ID 检查工具结果配对，将 manifest 与 SSOT 版本比较查状态陈旧，并在隔离环境做单变量重放。发送前自动断言必需约束、ACL、secret、token 和 tool result 完整性。
