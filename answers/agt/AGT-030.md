> **问题：** Agent 的停止条件、最大步数和预算应如何设计？
>
> **分类：** Agent、工具与上下文工程

> **来源：** [CORE_INTERVIEW_QUESTIONS.md](../../CORE_INTERVIEW_QUESTIONS.md)

## 我的答案

停止设计要同时包含**语义成功条件、失败/无进展条件和资源硬上限**。最大步数只是最后保险；若没有可验证完成标准，Agent 可能很早自信结束，也可能在预算内浪费所有步骤。

### 一、成功停止

将目标转成可验证 predicate：

\[
Done(s)=\bigwedge_i criterion_i(s)
\]

例如代码任务要求测试通过、改动文件存在且无越权修改；研究任务要求所有子问题有引用；业务动作要求真实回执。模型输出 final 只是停止提案，orchestrator 验收后才标 SUCCEEDED。

### 二、失败与阻塞停止

- 不可恢复的权限/参数/业务错误；
- 必要信息只能由用户提供；
- 权威来源冲突且无法消解；
- 工具熔断且无 fallback；
- 连续若干步无新证据/状态变化；
- 用户取消或审批拒绝。

应区分 FAILED、BLOCKED/INPUT_REQUIRED、CANCELLED 和 BUDGET_EXHAUSTED，不能都输出“失败”。

### 三、多维预算

```text
max_steps / max_model_calls / max_tool_calls
max_input_output_tokens / max_cost
wall_clock_deadline / per-tool timeout
max_replans / retries / parallel fan-out
```

任务开始按风险和复杂度分配预算；每步预估剩余成本，若下一 action 超过余额就不启动。子 Agent/子任务预算来自父预算并保留汇总与验证 reserve，防 fan-out 失控。

### 四、动态阈值

简单查询小预算，高价值复杂任务更大；只读探索可多步，不可逆写操作步数少且需确认。根据早期 progress、置信度和工具延迟调整，但绝不能突破用户/系统硬 cap。

### 五、停止后的行为

成功返回结果与证据；预算耗尽返回已完成、未完成、最后有效状态和继续所需资源；需要用户信息时只问最小问题；取消时停止调度新动作并协调在途调用。长任务保存 checkpoint，恢复时不重复副作用。

### 六、调优

用不同 max step 绘制 success–cost 曲线，观察第 k 步边际成功率、过早停止、无效尾步和 p95。选择达到质量 SLO 的最低预算，并按任务类型切片，而不是全局同一个 20 步。

### 面试简答版

停止条件分三层：测试、引用覆盖或业务回执等可验证 Done predicate；权限不可恢复、需要用户输入、工具不可用、冲突和连续无进展等失败/阻塞条件；以及 steps、模型/工具调用、token、费用、deadline、重规划和 fan-out 的硬预算。模型说完成不算，orchestrator 验收才成功。预算按任务风险/复杂度动态分配但不越硬 cap，子 Agent 从父预算领取。终止时区分成功、阻塞、取消和预算耗尽，并保存进度与副作用回执供安全恢复。
