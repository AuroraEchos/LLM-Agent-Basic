> **问题：** 如何设计稳定的 Observation、Action、Tool Result 和 Feedback 协议，使模型与执行环境解耦？
>
> **分类：** Agent 与工具调用
>
> **来源：** [INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md](../../INTERVIEW_QUESTIONS_AGENT_HARNESS_EXPANDED.md)
<!-- AUTO-QUESTION:END -->

## 我的答案

稳定协议的目标是让模型只依赖**规范化的环境语义**，而不依赖某个 API、SDK 或供应商的原始格式。模型产生 Action proposal；Harness 验证并执行；环境产生 Tool Result；Harness 转换为 Observation/Feedback。

### 一、Action

```json
{
  "action_id":"a17", "type":"tool_call", "name":"get_order",
  "arguments":{"order_id":"ORD-1"},
  "expected_state_version":4, "reason_code":"NEED_CURRENT_STATUS"
}
```

字段包含唯一 ID、动作类型、规范化参数、可选前置版本与目的。schema 严格版本化；身份、权限和密钥不由模型填写。Action 是提案，不代表已授权或执行。

### 二、Tool Result

适配器保留后端事实：

```json
{
  "action_id":"a17", "status":"SUCCEEDED", "data":{},
  "error":null, "source":"orders-v3", "observed_at":"...",
  "external_request_id":"r9"
}
```

区分 SUCCEEDED、FAILED、UNKNOWN、CANCELLED；错误含 code、retryable、details_ref。结果可存 artifact，只把引用和必要字段进入状态。

### 三、Observation

Observation 是面向模型的经过验证、裁剪和去敏视图，带 source、freshness、warnings、state delta 和未满足条件。它不应混入命令语气；外部文本用明确 data boundary。不能把工具失败改写成自然语言“可能成功”。

### 四、Feedback

Feedback 告诉模型上一步决策的验证结果及允许的下一步：schema invalid、permission denied、precondition failed、no progress、task criterion passed 等。它来自 validator/policy/verifier，不等于 Tool Result，也不泄露内部 stack trace。

### 五、解耦原则

- 使用 canonical domain types，adapter 负责 API 字段映射；
- envelope 与 payload 分离，版本和 correlation ID 必备；
- unknown fields 可前向兼容，但关键 enum fail closed；
- 大结果分页/artifact 化，所有时间、单位、货币明确；
- 状态更新采用 patch + expected version，防乱序 observation；
- 至少一次消息投递下，consumer 幂等去重；
- 保留 raw result 的受控审计引用，模型只看 sanitized view。

### 六、测试

契约测试覆盖成功、业务错误、超时、部分结果、旧版本、乱序/重复和恶意 payload；录制 fixture 确保换模型/后端时重放结果一致。协议演进采用兼容窗口和迁移，不让 Prompt 解析任意自然语言错误。

### 面试简答版

Action 是模型提出的带 ID、类型、规范参数和前置版本的调用意图，不代表授权；Tool Result 是执行适配器保存的真实状态、数据、错误、来源和外部回执；Observation 是经过 schema 校验、裁剪、去敏后给模型看的事实视图；Feedback 则由 policy/verifier说明参数、权限、进展或验收结果。四者用版本化 envelope、correlation ID、明确状态和 domain schema 解耦，状态通过带 expected version 的 patch 更新，消息幂等去重，大结果用 artifact 引用。
