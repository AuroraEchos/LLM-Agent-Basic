> **问题：** 如何验证工具输出，避免把错误结果继续传播给后续步骤？
>
> **分类：** Agent、工具与上下文工程
>
> **来源：** [CORE_INTERVIEW_QUESTIONS.md](../../CORE_INTERVIEW_QUESTIONS.md)
<!-- AUTO-QUESTION:END -->

## 我的答案

工具调用成功只说明接口返回了，不说明结果完整、正确、适用或安全。应把 observation 当作带来源与置信度的数据，在进入后续步骤前经过**传输、结构、语义、业务与交叉证据**验证。

### 一、验证层次

1. 传输：HTTP/进程状态、超时、响应大小、内容类型和 request ID；
2. Schema：必填字段、类型、enum、范围、额外字段和版本；
3. 语义：日期合法、总额等于明细、单位/币种一致、ID 可解析；
4. 业务：资源状态与请求一致、数据未过期、返回记录属于当前用户；
5. 来源：工具身份、签名/版本、缓存时间和数据 lineage；
6. 交叉验证：高影响事实由独立来源、原始记录或确定性计算复核。

### 二、显式可信状态

不要只返回文本，使用信封：

```json
{"ok":true,"data":{},"source":"orders-v3","observed_at":"...",
 "fresh_until":"...","confidence":1.0,"warnings":[]}
```

将结果标记为 `VERIFIED/PARTIAL/CONFLICTED/INVALID/UNKNOWN`。只有满足下游前置条件的状态才能解锁依赖节点；缺字段不能用空串继续传播。

### 三、防止错误扩散

- 每个派生结论保留来源 call ID 和字段级 provenance；
- 数值用代码重算，不让 LLM心算核验；
- 多工具冲突时保留双方和时间口径，不让模型静默投票；
- 低置信结果触发重试、备用源、重新查询或用户确认；
- 外部文本视为不可信数据，隔离其中指令、HTML 和 URL；
- 下游写操作前做最终 precondition/read-after-write 验证。

### 四、错误与恢复

区分工具业务错误、协议错误、陈旧数据、解析器错误和模型误读。重试只针对瞬时故障；确定性错误应修参数。若无法确认，明确输出证据不足，不用“看起来合理”的值填补。

### 五、监控

记录 schema failure、semantic violation、stale result、source conflict、fallback、下游因无效结果被阻断及 silent corruption。用契约测试、golden response、畸形/恶意结果和 fault injection 验证每个工具适配器。

### 面试简答版

工具输出要先验传输状态和 schema，再检查日期、单位、总计等语义约束、实时业务状态、ACL、新鲜度与来源；高风险事实用独立来源或确定性计算复核。结果使用含 source、observed_at、warnings 和 call ID 的结构化信封，并标 VERIFIED、PARTIAL、CONFLICTED 或 INVALID。只有验证通过才释放下游 DAG，缺字段不能用空串继续。冲突保留双方证据，低置信走备用源或人工确认，写操作前再次检查 precondition。
