## 我的答案

高质量工具定义的目标是让模型回答三个问题：**这个工具做什么、何时用/不用、参数怎样才合法**；同时让执行器能用确定性规则拒绝不安全输入。

### 一、名称

名称应短、唯一、动词开头并体现业务对象，如 `get_order_status`、`cancel_order`。不要用 `process`、`handle_data` 等模糊名，也不要让两个工具只差难辨后缀。读写动作明确区分，危险操作在名称上可见。

### 二、Description

描述应包含：效果、适用场景、禁用场景、重要前置条件和返回语义。例如：

```text
读取当前已认证用户的一笔订单状态。仅用于已知 order_id 的单笔查询；
若需按日期搜索订单，请使用 search_orders。只读，不会修改订单。
```

相似工具的描述要形成互斥决策边界。避免宣传性文字、隐藏规则和把用户可控文本写成高优先级指令。

### 三、JSON Schema

```json
{
  "type": "object",
  "properties": {
    "order_id": {"type": "string", "pattern": "^ORD-[0-9]{8}$"},
    "include_items": {"type": "boolean", "default": false}
  },
  "required": ["order_id"],
  "additionalProperties": false
}
```

用正确类型、required、enum、format、pattern、minimum/maximum 和长度限制缩小空间；单位写入字段名或描述，如 `timeout_ms`。嵌套层级尽量浅，避免一个字符串塞入 JSON。互斥参数可用 `oneOf`，但 schema 过度复杂会降低模型生成成功率，可拆工具或在服务端做语义校验。

### 四、不要暴露给模型的参数

`tenant_id`、真实 user ID、权限、API key、价格、审批状态和幂等规则等应由服务端可信上下文注入。模型只提供完成用户意图所需的业务参数。默认值若影响金额或范围，不能静默采用。

### 五、返回和错误契约

定义稳定、精简的结构化响应，含 `ok/data/error_code/retryable`，避免把巨大 HTML 或 stack trace直接返回模型。分页、上限、时间和金额单位明确。工具版本变更需兼容或发布新版本。

### 六、评测

建立包含“该用、相似工具、不该调用、参数边界、恶意输入”的样本集，测 tool selection accuracy、schema valid rate、首次调用成功率、澄清率和危险误调用率。工具定义是模型接口，应像 API 一样 code review 和版本化。

### 面试简答版

工具名应动词开头、唯一并显式区分读写；Description 写清做什么、何时用、何时不用、前置条件和副作用，尤其让相似工具边界互斥。JSON Schema 用 required、enum、pattern、范围、长度及 `additionalProperties:false` 缩小参数空间，单位和默认值明确。租户、用户、权限、密钥和审批不能由模型传入，应由服务端注入。返回采用稳定精简的 data/error 契约，并用正例、相似工具、缺参和攻击样本评测选择与参数正确率。
