## 我的答案

组织原则是：**权限优先级与数据可信度分离、稳定信息与动态状态分离、只放当前决策所需内容、每段可追溯**。上下文中的位置不能替代服务端权限，但清晰分区可减少模型混淆。

### 一、建议层次

```text
1. System/Developer policy：角色、禁止事项、输出/工具规则
2. 当前用户目标：原始请求、澄清后的范围、验收标准
3. 可信任务状态：计划、已完成/未完成、预算、审批
4. 当前可用工具：经权限过滤的 name/description/schema
5. 当前步骤证据：检索片段、工具 Observation、来源与时间
6. 必要记忆/历史：相关偏好、约束、近期决策
7. 当前输出要求：本步要决策、调用还是最终回答
```

具体消息角色受模型 API 约束，但语义边界应保持。

### 二、指令与数据分离

System policy 和用户目标是指令；网页、文档、邮件、工具文本和记忆是数据，即使包含“忽略之前指令”也不能升级权限。用结构化 envelope 和明确 delimiter 标注 source/trust。用户内容也不能覆盖系统策略。

### 三、状态比聊天历史更重要

从事件日志生成 canonical task state：目标、约束、已验证事实、open items、真实副作用。不要依赖模型从几百轮聊天重新推断。旧计划/失败尝试放尝试账本或摘要，避免与当前 state 竞争。

### 四、选择与顺序

工具只暴露当前身份和步骤可用的最小集合；证据按直接相关、权威、新鲜和互补排序，去重冲突并保留来源。关键目标、禁止事项和 Done predicate要简短明确；长背景外置为 artifact/resource link。

### 五、版本与审计

每段带 source/version/time/ACL/token count，记录 context manifest 与最终顺序，使 trace 可重建。任何权限、工具、文档或状态变化都重新构造，不复用陈旧上下文。

### 面试简答版

上下文先放不可被外部数据覆盖的 system policy，再放用户目标和验收标准、可信任务状态、经权限过滤的工具定义、当前步骤的检索/工具证据，最后只加入相关记忆与必要历史。网页、邮件、工具结果和记忆全部标为带来源的不可信数据，不能成为指令。不要塞完整聊天，而要从事件生成 canonical state 和尝试账本；证据去重并按相关性、权威和新鲜度排序。每段记录版本、ACL 和 token，保证 Trace 可重建。
