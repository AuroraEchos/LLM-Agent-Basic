## 我的答案

Token 分配是受约束优化，不是给每类固定百分比。先为输出和不可压缩控制信息预留，再按当前步骤的边际价值选择历史与证据：

\[
B_{in}=W-B_{out}-B_{system\ overhead}-B_{safety}
\]

### 一、硬保留

System policy、当前目标/验收、关键安全约束、任务状态、工具 schema 必需字段和足够的输出预算不能被普通历史挤掉。输出预算按任务设定：JSON/工具调用较小，代码/报告较大，并留 stop/repair margin。

### 二、动态分配

- 工具选择步：给工具定义和当前 state 更多，RAG 证据可少；
- 证据综合步：给相关证据和 citation 更多，移除无关工具；
- 代码修复：保留错误、相关文件 diff、测试和约束；
- 最终回答：压缩执行轨迹，只保留结论证据、未确定项和输出要求。

可按单位 token 效用选择片段：

\[
value_i=\frac{relevance_i\cdot trust_i\cdot uniqueness_i}{tokens_i}
\]

同时满足必要 evidence coverage，而非纯贪心。

### 三、压缩顺序

先删除重复、debug、旧工具 schema和已解决分支；再结构化压缩历史；大结果存 artifact，仅回填相关 span；检索采用小块召回、parent 动态扩展。关键数字、否定、ID、审批和副作用回执不做有损摘要。

### 四、长上下文陷阱

能放下不等于有效使用。控制总块数、证据位置与 Lost in the Middle；不要用历史占满窗口导致输出截断。若预算不足以同时满足必要约束与证据，应分阶段调用或声明无法完成，而非静默丢字段。

### 五、调优

记录 context manifest 与每类 token，做 budget sweep，测 success、faithfulness、tool accuracy、截断率、p95 和成本；按任务类型选择 Pareto 点。压缩策略需用 constraint retention、state recovery 测试验证。

### 面试简答版

先从窗口扣除输出、系统开销和安全余量，硬保留 policy、用户目标/验收、当前 state 和本步必要工具 schema。剩余预算按当前阶段动态给历史、工具结果和检索证据：工具选择重 schema，证据综合重引用，最终回答移除执行噪声。先去重和删除已解决分支，再摘要；大结果外置，关键数字、否定、ID、审批和副作用回执不有损压缩。用不同预算测成功率、截断、p95 和成本，而不是固定百分比。
