## 我的答案

MCP 是基于 JSON-RPC 2.0 的有状态会话协议。一次连接经历 **Initialization → Operation → Shutdown**；双方只使用协商成功的能力。协议会演进，因此实现应绑定 revision，并以[官方 Lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)和 transport 文档为准。

### 一、初始化与能力发现

Client 首先发送 `initialize`，包含其 protocol version、client info 和 capabilities；Server 返回选定版本、server info 与自身 capabilities。Client 接受后发送 `notifications/initialized`，才进入正常操作。

```text
Client -- initialize(version, capabilities) --> Server
Client <-- version, capabilities, serverInfo -- Server
Client -- notifications/initialized --------> Server
```

若 Server 回的版本 Client 不支持，应断开。Capability negotiation 决定能否使用 tools、resources、prompts、logging、sampling、roots 等及其可选特性；不能因某方法在新规范存在就对所有 server 调用。

进入 operation 后，再通过 `tools/list`、`resources/list`、`prompts/list` 等发现具体条目；列表可能分页并通过 `listChanged` 通知变化。能力声明与条目发现是两层概念。

### 二、传输

当前标准传输是：

- `stdio`：Host 启动本地 Server 子进程，stdin/stdout 只传逐行 JSON-RPC，stderr 可写日志；适合本地集成与进程级隔离。
- Streamable HTTP：远程 Server 通过单一 MCP endpoint 接受 POST/GET，可用 SSE 流式返回消息与通知；可分配 `Mcp-Session-Id` 管理会话。

官方说明见[MCP Transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)。HTTP+SSE 是旧 revision 的传输，不应与 Streamable HTTP 混为一谈。自定义 transport 仍必须保持 JSON-RPC 与 lifecycle 语义。

### 三、请求、通知和关联

Request 有 `id` 并必须收到 result/error；notification 无 `id`、不期待响应。并发请求靠 ID 关联，不能依到达顺序。Progress、cancellation 和 logging 等只有双方支持时使用。收到 progress 可延长软超时，但仍应有最大 deadline。

### 四、错误处理

要区分：

1. Transport error：连接断开、HTTP/TLS/进程退出；
2. JSON-RPC protocol error：解析、未知方法、非法参数；
3. Capability/version mismatch；
4. Tool/resource 业务错误；
5. Timeout/cancellation。

业务工具失败通常应作为 tool result 的错误状态返回，避免把整个 MCP 会话误判为损坏。只对可安全重放的请求重试；工具写操作需幂等键。断线不自动等于请求取消或未执行，需显式取消/状态核对。

### 五、关闭

stdio 通常由 Client 关闭输入、等待进程退出，再逐级 TERM/KILL；HTTP 通过关闭连接/终止会话。关闭前取消或协调在途请求并持久化真实结果，避免工具已执行而 Host 丢失回执。

### 面试简答版

MCP Client 首先发 `initialize`，双方协商 protocol version、实现信息和 capabilities，Client 再发 `initialized` 通知后才能正常调用；随后用 tools/resources/prompts 的 list 方法发现具体能力。标准传输是本地 stdio 和远程 Streamable HTTP，消息统一为 JSON-RPC request、response、notification，并靠 ID 关联。错误要区分传输、协议、版本/能力和工具业务错误，所有请求有超时与显式取消，写操作重试需幂等。只调用协商过的能力，关闭时还要处理在途副作用。
