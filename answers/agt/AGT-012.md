> **问题：** 涉及支付、删除、发信等高风险操作时，如何设计确认和权限边界？
>
> **分类：** Agent、工具与上下文工程
>
> **来源：** [CORE_INTERVIEW_QUESTIONS.md](../../CORE_INTERVIEW_QUESTIONS.md)
<!-- AUTO-QUESTION:END -->

## 我的答案

高风险操作应采用“**模型提议，策略引擎授权，用户对具体副作用确认，执行器原子提交**”。自然语言确认、系统 Prompt 或模型自报权限都不能作为安全边界。

### 一、分级与最小权限

按影响、可逆性、金额、数据敏感度和外部传播分级。读取与草稿可低摩擦；付款、删除、发信、改权限和执行代码需更高控制。工具 token 使用当前用户委托的最小 scope、短 TTL，不给模型管理员密钥。

授权谓词可概括为：

\[
Allow=AuthN\land AuthZ(resource,action)\land Policy\land Consent\land Preconditions
\]

每次执行实时计算，不能相信记忆中的旧角色。

### 二、预览—确认—提交

1. `prepare`：校验参数、权限和当前状态，生成不可执行的 operation preview；
2. UI 显示动作、对象、金额/收件人、不可逆性和预期后果；
3. 用户通过可信 UI 明确确认，不把网页/邮件中的“确认”当用户同意；
4. `commit` 携带短时、一次性 confirmation token，绑定 principal、参数 hash、资源 version 与过期时间；
5. 参数或状态变化则 token 失效并重新确认；
6. 返回真实回执并审计。

确认问题必须具体，例如“向 X 支付 ¥500”，不能只问“继续吗”。批量操作显示数量、范围和抽样详情。

### 三、并发、幂等与补偿

提交使用幂等键和 `expected_version`，防双击/重试重复付款以及确认后资源被替换。可逆操作优先软删除、回收站、延迟发送和撤销窗口；跨系统事务用 saga/补偿，但补偿不保证完全恢复，应向用户说明。

### 四、额外护栏

金额/批量阈值、收件人 allowlist、双人审批、冷却期、速率限制、异常检测和 kill switch。敏感数据在确认页最小披露。间接 Prompt Injection 即使操纵模型，也必须无法伪造 confirmation token 或扩大 scope。

### 五、审计

记录原始用户意图、模型提案、策略版本、principal、确认展示内容及参数 hash、审批者、工具回执、幂等键摘要和补偿。失败/超时状态标 UNKNOWN，先 reconciliation，不盲重试。

### 面试简答版

支付、删除和发信采用 prepare—confirm—commit：模型只生成提案；服务端实时认证授权并生成具体预览；用户在可信 UI 确认对象、金额、收件人和不可逆性；commit 使用绑定用户、参数 hash、资源版本和有效期的一次性 token。参数变化必须重新确认。执行端再用最小权限、幂等键、乐观锁、阈值/双人审批和真实回执，优先软删除或撤销窗口。模型和文档都不能伪造用户同意，超时先核对状态再重试，全链路可审计。
