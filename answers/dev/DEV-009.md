> **问题：** `P1` CI 流水线通常应包含哪些代码检查、测试、构建和安全扫描步骤？

## 我的答案

CI 应从便宜、确定的检查逐步走向昂贵、环境相关的验证，并且产物只构建一次、逐环境提升同一 digest。

1. **仓库与静态门禁**：格式、lint、类型检查、导入/死代码、生成文件一致性、commit/许可证规则；同时做 secret scan，泄密要轮换而不只是删字符串。
2. **测试**：快速 unit 和 property tests；数据库/队列/模型 adapter contract tests；受控 integration；关键 API e2e。并发、超时、取消、幂等和迁移必须覆盖失败路径。
3. **LLM/Agent 专项 eval**：固定数据版本和模型/参数，测任务质量、安全、tool-call 成功率、成本、TTFT/延迟；以置信区间/允许退化门限判断，避免随机一次结果硬门禁。线上 shadow/canary 补足离线分布差异。
4. **构建与制品验证**：锁定依赖，构建 wheel/image，启动最终 image 做 smoke/probe、非 root/只读检查和架构/GPU 兼容测试。生成 SBOM、provenance，按 commit/version/digest 标记并签名。
5. **安全与供应链**：SAST、依赖/SCA、容器 OS 包、IaC/Kubernetes policy、license、secret 扫描。按可利用性、运行路径和 SLA 定阻断级别，并有有时限、可审计的例外，而非把扫描报告全部忽略。
6. **发布门禁**：验证 migration backward compatibility、配置/Secret 引用、资源/probes/PDB；部署测试环境后运行 smoke，再审批或策略化 canary，自动观测并回滚。

PR 流水线追求分钟级反馈，可并行互不依赖的 job并按 changed paths 缩小范围；主干/夜间再跑全矩阵、长时并发、性能和完整 eval。cache 必须把 lockfile、平台和工具版本纳入 key，不能用污染 cache 换“绿色”。不稳定测试要记录 owner、隔离并修复，不能无限 retry 抹掉真实竞态。

CI token 权限最小化，PR 尤其是 fork 的不可信代码不能获得生产 secret；构建与部署身份分离，发布环境使用短期 OIDC/工作负载身份。保存测试报告、coverage/eval diff、SBOM、签名和部署证据，使一个线上 digest 能追溯到源码、依赖和门禁。

### 面试简答版

CI 先做 format/lint/type/secret scan，再跑 unit、contract、integration/e2e；Agent 还要有版本化离线 eval，衡量质量、安全、tool success、成本和延迟。随后只构建一次 wheel/image，对最终镜像做 smoke、SBOM、SAST/SCA/image/IaC/license 扫描、签名与 provenance，再验证迁移/配置并 progressive deploy。同一 digest 晋级环境，PR 不接触生产 secret，cache 可验证，flaky test 有 owner 和修复期限，不能靠无限 retry 伪造绿色。
