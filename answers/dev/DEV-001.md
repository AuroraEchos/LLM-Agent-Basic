> **问题：** `P0` Git 的 Working Tree、Index、Commit 和 Branch 分别是什么，`add` 与 `commit` 实际完成什么操作？
>
> **分类：** Git、Docker 与 CI/CD

> **来源：** [ENGINEERING_FOUNDATIONS_PATCH.md](../../ENGINEERING_FOUNDATIONS_PATCH.md)

## 我的答案

Git 可把一次开发理解为三份状态加一张提交图：

- **Working Tree**：当前目录中实际可编辑的文件。它可同时含未跟踪文件、相对 index 的修改，以及与提交一致的文件。
- **Index / Staging Area**：下一次提交的候选快照，也保存路径、mode 和 blob 等信息。它不是简单的“改动清单”；同一文件可以只 stage 部分 hunk，因此工作区版本和 index 版本不同。
- **Commit**：不可变对象，记录一棵完整目录树、父 commit、作者/提交者、时间与 message。commit ID 是对象内容派生的标识；修改历史会产生新 commit，而不是原地改旧对象。
- **Branch**：`refs/heads/...` 下指向某个 commit 的可移动引用。新提交时当前 branch 向新 commit 前移；branch 本身不是提交副本。`HEAD` 通常符号指向当前 branch，也可 detached HEAD 直接指 commit。

```text
Working tree -- git add --> Index -- git commit --> Commit graph
                                                ^
                                                branch ref / HEAD
```

`git add path` 会读取**当时工作区内容**，生成/复用 blob，并更新 index 中该路径的候选版本；之后继续编辑不会自动更新已 stage 版本。`git commit` 根据 index 写 tree 与 commit 对象，并移动当前 branch 引用；未 stage 的改动不会进入该提交。空目录本身不被 Git 跟踪，Git 跟踪的是路径对应内容，而不是“文件修改动作”。

排查前同时看：

- `git diff`：working tree 相对 index；
- `git diff --cached`：index 相对 `HEAD`，也就是将提交什么；
- `git status`：两类差异及未跟踪文件；
- `git show/ls-tree`：提交中的实际快照。

工程上提交前应审查 staged diff，而不是只看编辑器；生成物、密钥和大模型权重通过 `.gitignore`/hook/制品库治理。`.gitignore` 不会让已跟踪文件自动消失，也不是密钥保护机制。

### 面试简答版

Working tree 是正在编辑的文件，Index 是下一次提交的候选快照，Commit 是包含完整 tree 和父指针的不可变对象，Branch 只是指向 commit、会随新提交移动的引用。`git add` 把路径当时的内容写入 index，`git commit` 从 index 创建新 commit 并移动当前 branch；所以同一文件可以一部分已暂存、一部分仍未暂存。提交前我会用 `git diff --cached` 审核真正要进入历史的内容。
