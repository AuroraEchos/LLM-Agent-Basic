> **问题：** `P0` `merge`、`rebase`、`cherry-pick` 和 `revert` 分别适合什么场景？

> **分类：** Git、Docker 与 CI/CD

## 我的答案

四个命令都改变“当前分支最终包含什么”，但对历史图的处理完全不同：

| 操作 | 本质 | 是否重写相关 commit ID | 适用场景 |
|---|---|---:|---|
| `merge` | 把两条历史汇合；非 fast-forward 时创建双亲 merge commit | 否 | 集成已共享分支，保留真实分叉/合并关系 |
| `rebase` | 将一串 commit 的 patch 在新 base 上依次重放，生成新 commit | 是 | 推送前整理个人分支、让线性历史更易读 |
| `cherry-pick` | 把选定 commit 的变化应用到当前 `HEAD`，生成新 commit | 是（生成副本） | 将独立修复移植到 release/hotfix 分支 |
| `revert` | 创建一个新的反向提交，抵消目标 commit 的效果 | 否 | 安全撤销已经共享/发布的提交 |

`merge` 可能 fast-forward，此时只移动引用而没有 merge commit；是否允许要由团队策略决定。rebase 的“线性”以重写身份为代价，因此不要随意 rebase 他人正在基于其开发的公共历史；若确需更新远端，用团队约定和 `--force-with-lease`，而不是无条件 force。

cherry-pick 复制的是变化，不保留原 commit 的图关系；大量互相依赖的 pick 容易漏 commit、产生重复补丁，整条功能分支更适合 merge/rebase。revert 普通 commit 容易理解；revert merge commit 还要指定 mainline parent，表示保留哪一侧为主线，选错会产生意外结果。以后重新 merge 已被 revert 的分支也要理解 Git 已认为相关 commit 在祖先图中。

冲突时不要机械“选 ours/theirs”，应理解 base、两侧意图，完成测试再继续。所有操作前先确认当前 branch、工作区和目标 commit，保留可恢复引用；reflog 能帮助找回本地曾指向过的 commit，但不能替代远端备份与协作沟通。

### 面试简答版

merge 汇合两条历史并保留分叉，适合共享分支集成；rebase 把本分支 commit 重放到新基线，历史线性但 commit ID 会变，适合未共享的个人分支；cherry-pick 复制少量独立 commit 到当前分支，适合 hotfix 移植；revert 新建反向 commit，不改共享历史，适合线上撤销。公共历史优先 merge/revert，历史重写必须协作并用 `--force-with-lease`，所有冲突都要按业务意图解决并测试。
