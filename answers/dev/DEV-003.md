> **问题：** `P0` 如何处理代码冲突、误提交密钥、错误合并和已经推送的错误 Commit？

## 我的答案

处理原则是先判断：错误是否已推送/部署、是否涉及安全凭据、历史是否被他人共享。不要在慌乱中先强推或删除证据。

### 1. 代码冲突

先 `git status` 确认正在 merge/rebase/cherry-pick，以及冲突文件；查看 base/ours/theirs 和双方提交意图，编辑出**业务上正确的新版本**，而非按标记二选一。运行格式化、静态检查和相关测试后 `git add` 标记已解决，再 continue/commit。判断方向错误时可用对应 `--abort` 回到操作前。生成文件通常由源文件重新生成，不宜手工拼接。

### 2. 误提交密钥

这首先是安全事件，不是 Git 美化问题：

1. **立即在提供方吊销/轮换**密钥，检查访问审计、异常调用和衍生凭据；删 commit 不能使已克隆的密钥失效。
2. 从当前代码移除，改用 secret manager/运行时挂载，并增加 secret scanning、pre-commit/CI 规则。
3. 若政策要求，从所有 refs/tags 的历史用专门历史重写工具清除，并清理 release artifact/cache；通知所有协作者重新同步，协调远端垃圾回收。公开仓库应视为已经泄露。
4. 保留合规事件记录，但不能在 issue/log 中再次粘贴密钥。

### 3. 错误合并或已推送错误 commit

- 尚未共享：可在确认目标后用 amend、interactive rebase 或移动本地引用整理；先保存工作和可恢复点。
- 已共享但未上线：通常用 `git revert <commit>` 创建可审计的反向提交；merge commit 用 `revert -m <parent>` 前必须确认 mainline 含义。
- 已上线：先按影响选择快速 revert/回滚制品或关闭 feature flag，再调查和前滚修复。数据库 schema/外部副作用不能假设 Git revert 能回滚，要有兼容迁移和补偿。
- 只有团队明确协调、分支允许历史重写时才 force push，并优先 `--force-with-lease` 防止覆盖别人新提交。受保护主分支通常禁止这种做法。

本地误删 commit 可通过 `git reflog` 找旧 `HEAD` 并新建恢复 branch；但 reflog 是本地且有保留期限。恢复后要验证 tree、测试、构建制品和部署版本，不能仅看 log “像是恢复了”。

### 面试简答版

冲突先确认正在执行的操作和双方业务意图，解决后跑测试再 continue；不确定就 abort。密钥入库要先吊销/轮换和审计，再从当前代码及必要历史清除，因为重写 Git 不能收回已经泄露的秘密。已推送错误通常用 revert 保持共享历史，merge revert 要确认 mainline；未共享才适合 amend/rebase。线上还要回滚制品或关 flag，数据库与外部副作用需独立补偿；强推仅在协调后用 `--force-with-lease`。
