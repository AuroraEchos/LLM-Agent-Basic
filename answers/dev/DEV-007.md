## 我的答案

| 对象 | 解决的问题 | 不负责什么 |
|---|---|---|
| Docker Compose | 用一个声明文件在单机组织多个 container、network、volume、依赖和环境 | 通常不提供跨节点生产级调度、自愈与集群滚动发布 |
| Kubernetes Deployment | 声明无状态 Pod 模板和副本期望，通过 ReplicaSet 完成自愈、扩缩容、滚动升级/回滚 | 不给 Pod 提供稳定访问地址，也不适合直接管理每副本固定身份/持久盘的 StatefulSet 场景 |
| Kubernetes Service | 用 label selector 为一组动态 Pod 提供稳定 DNS/虚拟 IP 和负载分发 | ClusterIP 默认不对公网暴露；也不自动提供 L7 path 路由、认证或完整服务治理 |
| ConfigMap | 保存非敏感配置，作为 env、命令参数或 volume 文件注入 | 不加密、不适合秘密和大型二进制制品 |
| Secret | 保存敏感配置并限制分发/访问，可注入 env/volume | base64 不是加密；是否静态加密、审计和外部 KMS 取决于集群配置 |

典型模型服务：Deployment 管 replicas、image digest、resources/GPU、probes 和 rollout；Service 根据 app labels 找到 ready Pod；Ingress/Gateway 再提供域名、TLS 和外部路由；ConfigMap 放非敏感模型名/阈值，Secret 或外部 secret provider 放 API key；权重走 image/对象存储/PVC，不塞 ConfigMap/Secret。

更新语义要谨慎：env 注入只在容器启动时读取；volume 投影的 ConfigMap/Secret 可在一定延迟后更新，但使用 `subPath` 等场景不会自动更新，应用也不一定 reload。常用策略是配置版本化或在 Pod template 注入配置 checksum，变化触发 rollout。Secret 要启用 etcd encryption at rest、最小 RBAC、namespace/ServiceAccount 隔离、审计与轮换，避免能创建 Pod 的主体间接读取不该访问的 secret。

Compose 的 `depends_on` 只表达启动关系/条件，不等价于下游已经业务 ready；应用仍要重试与健康检查。Kubernetes Deployment 也不保证新版本业务正确，需 readiness、PDB、容量余量、progressive delivery 和数据库兼容。

### 面试简答版

Compose 适合在单机声明多容器开发/小型部署；Deployment 声明无状态 Pod 副本并负责自愈和滚动升级；Service 给变化的 ready Pod 提供稳定 DNS/IP 和 L4 访问；ConfigMap 放非秘密配置，Secret 放敏感值但 base64 本身不是加密。模型权重不应塞这两者。env 配置通常需重启才生效，volume 更新也要应用 reload；生产还需 RBAC、etcd 加密/KMS、配置版本/rollout 和外部入口。
