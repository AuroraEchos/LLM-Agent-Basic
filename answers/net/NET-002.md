## 我的答案

TCP 是全双工、面向连接的有序字节流。握手要让双方建立连接状态并同步序列号；关闭则要分别终止两个方向的数据流，所以常见的是“三次握手、四次挥手”。

### 1. 三次握手

典型过程（省略其他字段）：

```text
Client                         Server
  | -------- SYN, seq=x -------> |
  | <-- SYN+ACK, seq=y, ack=x+1 -|
  | -------- ACK, ack=y+1 ------>|
```

它主要完成：

- 客户端与服务端分别选择并同步初始序列号（SYN 自身占一个序列号）；
- 双方确认两个方向的发送、接收路径可用，并建立各自 TCP 状态；
- 协商 MSS、窗口扩大、SACK、时间戳等 TCP 选项。

为什么不是两次：第二次后服务端知道客户端能发、自己能收，也知道自己的回复已发出，但还不知道客户端是否收到服务端的 SYN/初始序列号；第三个 ACK 完成这个确认。握手不代表应用一定健康，也不代表连接会永久存活。

### 2. 四次挥手与半关闭

```text
Active closer                  Peer
  | -------- FIN -------------> |
  | <-------- ACK ------------- |
  | <-------- FIN ------------- |
  | -------- ACK -------------> |
```

收到 FIN 表示“对方不会再发送新数据”，但本方向仍可能继续发送剩余数据，这叫 half-close。由于两个方向独立关闭，ACK 与本端 FIN 常分开发出，因而是四个报文；如果对端已经无数据，ACK 和 FIN 可以合并，所以“四次”不是所有抓包都严格四包。RST 则是异常终止，不保证剩余数据优雅送达。

### 3. `TIME_WAIT` 为什么存在

通常主动关闭、最后发送 ACK 的一方进入 `TIME_WAIT`，典型持续 2MSL（具体实现参数可不同），有两个核心目的：

1. **可靠完成关闭**：最后 ACK 若丢失，对端会重传 FIN；处于 `TIME_WAIT` 的一方还能再次 ACK，而不是把它当成未知连接。
2. **隔离旧报文**：让旧连接中延迟、重复的数据段在网络中消失，避免同一四元组很快复用后污染新连接。

大量短连接会积累 `TIME_WAIT`，但它本身是正确性机制，不应第一反应就粗暴缩短。客户端应使用 HTTP keep-alive/连接池，服务端检查是否错误地主动关闭，合理配置端口范围、负载均衡与连接复用。`SO_REUSEADDR` 等选项有明确语义，不是“无风险消灭 TIME_WAIT”。

### 面试简答版

三次握手同步双方初始序列号、确认双向路径并协商 TCP 选项；第三次 ACK 让服务端确认客户端已收到服务端的 SYN。TCP 是全双工，所以关闭两个方向通常是 FIN、ACK、FIN、ACK，ACK 与 FIN 也可能合并。主动关闭方常进入 `TIME_WAIT`：一是最后 ACK 丢失时还能响应重传 FIN，二是等待旧连接重复报文过期，避免污染同四元组的新连接。短连接过多应优先用连接池复用，而不是盲目删除 TIME_WAIT。
