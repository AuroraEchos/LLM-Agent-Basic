## 我的答案

TCP 向应用提供的是**可靠、有序、无消息边界的字节流**。可靠性并非“不丢包”，而是端点通过检测错误/丢失、重传和排序，使应用最终看到按序字节，或者明确得到连接失败。

### 1. 序列号、确认与校验

- 每个字节都有序列号；报文段的 sequence number 通常是其中第一个数据字节的位置。
- ACK 通常是累积确认，`ack=n` 表示小于 `n` 的连续字节已收到，下一步期望 `n`。SACK 选项还能报告不连续的已收区间，帮助只重传缺口。
- 接收端按序列号去重、缓存乱序段并按序交付；校验和检测传输中的比特错误，错误段被丢弃并通过后续重传恢复。

TCP 不保留应用写入边界：一次 `send` 可能被拆成多次 `recv`，多次写也可能合并。HTTP 等上层协议必须靠长度、分隔符或 frame 自己确定消息边界。

### 2. 重传如何发生

- **超时重传**：发送后在 RTO 内未被确认则重传；RTO 根据往返时间及波动动态估计并退避。
- **快速重传/丢失恢复**：重复 ACK、SACK 等信号能在 RTO 前推断缺段并重传。

重传会带来尾延迟，且 ACK 只说明对端 TCP 栈收到了字节，不代表应用已处理、更不代表数据库已提交。因此 TCP 可靠性不能提供业务“恰好一次”；API 重试仍需要幂等键、去重或事务。

### 3. 滑动窗口与流量控制

接收端通过 advertised receive window `rwnd` 告知还能接收多少字节，防止发送方压垮其 socket buffer。窗口随应用消费数据而滑动；若为 0，发送方通过相应机制探测何时恢复。

这是**端点能力保护**，与网络拥塞控制不是一回事。

### 4. 拥塞控制

发送端维护 congestion window `cwnd`，根据 ACK、丢包、ECN、RTT 等网络信号调整在途数据。不同实现可使用 Reno、CUBIC、BBR 等算法，通常涉及启动探测、拥塞避免和丢失后的降速。实际可发送的在途量受两者共同限制：

$$send\ window \le \min(rwnd, cwnd)$$

- `rwnd` 小说明接收应用/主机跟不上；
- `cwnd` 小说明发送端判断网络承载能力有限。

长肥网络还受带宽时延积 $BDP=bandwidth\times RTT$ 影响：窗口小于 BDP 时无法填满链路。模型流式接口中，即使 TCP 有流控，应用仍要设置有界 buffer 并在客户端断连时取消生成，否则数据可能只是在应用层继续堆积。

### 面试简答版

TCP 用字节序列号排序和去重，用累积 ACK/SACK 反馈接收情况，用校验和发现错误，并通过 RTO 或快速恢复重传丢失数据。接收窗口 `rwnd` 做流量控制，保护接收端；拥塞窗口 `cwnd` 根据网络反馈调整速率，实际在途量受 `min(rwnd, cwnd)` 限制。TCP 只提供有序字节流，没有消息边界；ACK 也不等于业务处理成功，所以应用仍需 framing、超时、幂等与事务。
