## 我的答案

三代 HTTP 的语义大体延续，主要差别在**如何把多个请求/响应映射到底层连接与流**。

| 特性 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 传输 | 通常 TCP，TLS 可选（公网实践多为 HTTPS） | TCP；公网浏览器实践通常配 TLS | QUIC，运行在 UDP 上并集成 TLS 1.3 |
| 表示 | 文本式起始行/headers，body 可二进制 | 二进制 frame，多 stream | HTTP frame 映射到 QUIC stream |
| 复用 | 持久连接可复用；同连接并发能力有限，常开多连接 | 一个连接内多路复用多个 stream | 一个 QUIC 连接内多路复用独立 stream |
| Header 压缩 | 无协议级动态压缩 | HPACK | QPACK |
| 丢包影响 | TCP 字节流顺序阻塞该连接后续数据 | 一个 TCP 包丢失可能让该连接上所有 HTTP stream 等待 | 一个 QUIC stream 的丢包通常不阻塞其他 stream 的应用数据 |

### 1. 队头阻塞要分层理解

- HTTP/1.1 常用一个连接一次处理一个在途请求。Pipelining 虽允许连续发请求，但响应必须按请求顺序返回，前一个慢响应会阻塞后面，兼容性也导致实践中较少使用；客户端通常靠连接池并发。
- HTTP/2 用 frame 交错实现应用层多路复用，解决了 HTTP/1.1 的响应顺序队头阻塞。但所有 stream 仍共享一条有序 TCP 字节流，一个 TCP 段丢失时，后到字节即使属于其他 stream 也暂不能交给 HTTP/2，这叫传输层 HOL。
- HTTP/3 的 QUIC 在单连接内提供独立有序 stream，丢包恢复按 stream 隔离，减少跨 stream HOL。但“完全没有阻塞”也不准确：同一 stream 仍有顺序、共享拥塞控制，QPACK 动态表依赖也可能造成 header 解码等待。

### 2. HTTP/3 的其他工程特性

QUIC 把传输与 TLS 1.3 握手结合，支持连接 ID，在合适条件下可降低建连成本并允许网络路径变化时维持逻辑连接。它运行在 UDP 之上，不等于“不可靠”：QUIC 自己实现可靠 stream、丢包恢复、流控和拥塞控制。

协议选择应按端到端支持和实测决定。若入口声称支持 H3，但 CDN 到源站仍是 H1，瓶颈可能没有消失；单个长模型流也未必从多路复用获得明显收益。应看握手耗时、丢包下尾延迟、并发 stream、代理兼容性、CPU 和观测能力，而不是只追求版本号。

### 面试简答版

HTTP/1.1 通常在 TCP 持久连接上复用，但同连接并发有限，pipelining 响应有应用层队头阻塞；HTTP/2 用二进制 frame 和 stream 在一条 TCP 连接多路复用，解决应用层 HOL，但 TCP 丢包仍会阻塞所有 stream；HTTP/3 把 HTTP 映射到基于 UDP 的 QUIC 独立 stream，集成 TLS 1.3，通常把丢包影响限制在相关 stream。它仍有同 stream 顺序、共享拥塞与 QPACK 依赖，是否更快要端到端测量。
