> **问题：** `P0` Connect Timeout、Read Timeout、Write Timeout 和 Total Timeout 分别控制什么？
>
> **分类：** 计算机网络、HTTP 与 RPC

## 我的答案

Timeout 应约束请求的不同阶段；具体 SDK 命名略有差异，但常见语义是：

- **Connect Timeout**：从开始连接到传输连接建立的最长等待，库可能还把 DNS、代理连接、TLS 分开或部分计入。连接池命中时通常不发生新 connect。
- **Write Timeout**：向 socket/stream 写请求数据时，单次持续无进展或一次写操作允许的时间。上传大 prompt、对端不读或发送缓冲满时触发。
- **Read Timeout**：连接建立后等待响应数据的无进展上限，常指相邻数据块之间，而非整个 body 的总时长。流式 LLM 每几秒有 token，可能永远不触发 30 秒 read timeout。
- **Total Timeout / Deadline**：从请求开始到整体完成的墙钟预算，应该覆盖 pool wait、DNS/connect/TLS、写、服务端排队、读、重试与退避。

有些库还单独提供 **pool timeout**（等待可用连接）和 TLS/first-byte timeout，必须读所用库的定义，不能只凭同名参数猜测。

工程上用绝对 deadline 向下传播，比每层各给 30 秒更可靠。某子调用预算可写成：

$$t_i=\min(t_{component}, deadline_{remaining}-cleanup\_reserve)$$

总预算 60 秒不代表每次重试都 60 秒；attempt、backoff 都消耗剩余预算。对非流式请求，同时设置 connect、read 与 total；对流式请求，将 read timeout 作为“多久没有任何数据/心跳就认为卡住”，另设首 token deadline、最大流时长和取消机制。

超时后状态是不确定的：连接超时通常请求尚未送达，但 read timeout 时服务端可能已经执行写操作。只有幂等/去重保证的操作才能自动重试。捕获超时要记录阶段、elapsed、remaining deadline、attempt 和 upstream，并关闭 response/连接、取消上游任务；否则超时只是客户端不等了，计算和费用仍可能继续。

### 面试简答版

Connect timeout 控制建连阶段，write timeout 控制发送请求时长期无进展，read timeout 通常控制等待下一块响应数据的间隔，total timeout/deadline 控制包括排队、握手、重试和读取在内的总墙钟时间。流式接口持续有 token 时不会触发普通 read timeout，所以还需首 token deadline、idle timeout 和最大流时长。所有子调用共享并消耗总 deadline；超时后要取消与清理，写请求是否重试还取决于幂等性。
