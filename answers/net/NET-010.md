> **问题：** `P1` 反向代理、负载均衡、API Gateway 和 Service Mesh 分别位于什么层级并承担什么职责？

## 我的答案

这些组件能力有重叠，区别主要在**部署位置、覆盖范围和治理对象**，不能只按产品名称判断。

| 组件 | 常见位置/范围 | 主要职责 |
|---|---|---|
| 反向代理 | 服务端入口，代表一个或一组 upstream | TLS 终止、Host/path 路由、协议转换、缓存/压缩、隐藏源站 |
| 负载均衡 | L4 或 L7，入口或服务内部 | 从健康实例中按 round-robin、least-request、hash 等分配流量，健康检查、连接排空 |
| API Gateway | 系统/业务 API 的集中 north-south 入口 | 路由之外还做认证授权、配额限流、API key、版本、请求转换、开发者/API 治理与审计 |
| Service Mesh | 服务实例间 east-west 通信，常由数据面代理 + 控制面组成 | 服务发现、mTLS 身份、流量策略、重试/熔断、遥测，尽量不侵入业务代码 |

反向代理可以同时是 L7 load balancer；云 LB 也可终止 TLS；Gateway 也能做负载均衡。因此更准确的辨别方法是问：谁是客户端、流量边界在哪里、策略是某个 API 还是所有服务间通信、配置由哪个团队/控制面下发。

典型链路可能是：

```text
Internet -> L4/L7 LB -> API Gateway/Ingress -> service mesh sidecar/ambient data plane -> service
```

但不是层越多越好。每一跳都会增加连接、缓冲、超时和故障面。模型流式响应尤其要关闭不恰当 buffering，允许长连接并传播断连取消；各层的 route/read/idle timeout 要协调，总 deadline 向下传播。重试只能有一个清晰责任层，否则客户端、Gateway、Mesh 和 SDK 各重试两次会造成指数放大。TLS 终止后要明确下一跳是否重新加密，`X-Forwarded-*`/trace header 只信任受控代理，不能直接接受公网伪造值。

选型上，小系统常以一个 ingress/反向代理 + 应用鉴权足够；多团队对外 API 需要集中产品治理时引入 Gateway；大量微服务确有统一身份、流量和可观测需求时再评估 Mesh，并以延迟、资源和运维成本验证收益。

### 面试简答版

反向代理代表服务端做 TLS、路由、缓存和协议转换；负载均衡在 L4/L7 将流量分给健康实例；API Gateway 是 north-south API 治理入口，增加认证、配额、版本和审计；Service Mesh 治理 east-west 服务通信，以数据面/控制面统一 mTLS、流量策略和遥测。能力会重叠，应按边界和治理对象区分。工程上要减少无价值层级，并统一 deadline、重试责任、流式 buffering、断连取消和可信代理头。
