> **问题：** `P0` Keep-Alive、连接池、DNS 缓存和 TLS Session Resumption 为什么会影响模型 API 延迟？
>
> **分类：** 计算机网络、HTTP 与 RPC
>
> **来源：** [ENGINEERING_FOUNDATIONS_PATCH.md](../../ENGINEERING_FOUNDATIONS_PATCH.md)

## 我的答案

模型 API 常跨地域且请求频繁。首 token 之前如果每次都重新做 DNS、传输建连与 TLS，固定成本会叠加到每个请求上；复用的目标就是把“每请求成本”变成“每一批连接/缓存周期的成本”。

### 1. 各机制降低了什么成本

- **HTTP Keep-Alive / 持久连接**：一个响应完成后不立即关闭底层连接，后续请求可跳过新的 TCP/QUIC 和 TLS 握手。它不同于 TCP keepalive 探测；后者主要发现长期空闲的死连接。
- **连接池**：按 origin/代理等维度管理一组可复用连接，并控制最大连接数、每主机并发、空闲超时与等待队列。HTTP/1.1 常靠多连接并发，HTTP/2/3 可在连接内多 stream，但仍要遵守服务端 stream 上限。
- **DNS 缓存**：在记录 TTL 和 resolver 策略内复用解析结果，省去查询延迟与负载。过久固定 IP 会忽略故障切换、负载均衡和记录更新，所以不能无限缓存。
- **TLS Session Resumption**：用 session ticket/PSK 等复用先前安全状态，减少完整握手的计算和往返；是否成功取决于协议、服务端、ticket、SNI/ALPN 和有效期。它不会消除 TCP 建连，也不能把所有请求安全地当成可 0-RTT 重放。

冷连接延迟可粗略表示为：

$$T_{cold}\approx T_{DNS}+T_{transport}+T_{TLS}+T_{application}$$

复用连接的暖请求近似跳过前三项，但仍受连接排队、拥塞窗口、服务端处理和模型生成影响。

### 2. 连接池配置不当也会变慢

- 池太小：请求等待 lease，表面像“模型慢”；池太大：建立风暴、端口/文件描述符耗尽、服务端过载。
- 空闲时间超过负载均衡/NAT/服务端超时：客户端拿到半失效连接，首写才失败。需要合理 idle TTL、健康策略，并对**幂等请求**谨慎重试。
- 每请求新建 HTTP client：连接池和 DNS/TLS 缓存随对象销毁，复用完全失效。应按应用/worker 生命周期持有 client 并在退出时关闭。
- 多进程 fork 后共享现有 socket 或跨事件循环复用异步 client，可能产生错误；通常每个 worker/loop 创建自己的池。
- 流式响应没有读完或显式关闭：连接不能归还池，最终池耗尽。因此断连、取消和异常路径必须关闭 response。

### 3. 如何验证优化是否有效

分开记录 DNS、connect、TLS、pool wait、TTFB、TTFT 和总耗时，并统计新建/复用连接数、池利用率、空闲连接被重置、DNS 命中和 TLS resumed 比例。预热可以降低部署后的冷启动尖峰，但预热连接要受并发限制，且不能替代正常容量设计。

### 面试简答版

Keep-Alive 让 HTTP 请求复用底层连接，连接池把复用、并发和空闲生命周期集中管理；DNS 缓存省解析往返，TLS session resumption 降低完整安全握手成本，所以都会影响模型 API 的 TTFB/首 token。注意 HTTP keep-alive 不等于 TCP keepalive，TLS 恢复也不消除传输建连。工程上 client 应按 worker 生命周期复用，流式响应必须关闭归还连接，并监控 pool wait、DNS/connect/TLS、复用率和半失效连接，而不是只看模型总耗时。
