> **问题：** `P0` SSE、WebSocket 和普通流式 HTTP 分别适合哪些大模型流式输出场景？
>
> **分类：** 计算机网络、HTTP 与 RPC
>
> **来源：** [ENGINEERING_FOUNDATIONS_PATCH.md](../../ENGINEERING_FOUNDATIONS_PATCH.md)

## 我的答案

三者都能边产生边消费，但交互方向、消息格式和基础设施兼容性不同。

| 方式 | 方向/格式 | 适合 | 主要限制 |
|---|---|---|---|
| SSE | 一个长 HTTP response，服务端到客户端；`text/event-stream`，支持 `data`、`event`、`id`、`retry` | 浏览器中的 token、进度、通知流；客户端只需先发一次请求 | 原生 `EventSource` 主要单向且请求定制受限；文本协议；要处理代理 buffering 和空闲超时 |
| WebSocket | HTTP 握手后形成全双工消息通道，文本或二进制 frame | 实时语音、多模态、客户端中途控制/打断、协同状态 | 连接状态、鉴权刷新、心跳、重连和扩缩容更复杂；部分网关需专门配置 |
| 普通流式 HTTP | response body 分块/持续 DATA frame，格式由应用定义，如 NDJSON、二进制或供应商事件 | 服务间调用、上传/下载、大模型单向流；可继续利用 HTTP 客户端和网关 | 没有 SSE 的浏览器自动事件解析/重连语义；消息 framing、断点恢复需自行设计 |

SSE 不是独立传输层；它运行在 HTTP 响应上，浏览器 `EventSource` 断开时可重连，并用 event id 辅助恢复，但服务端必须实现事件留存/去重，不能因此宣称“不会丢”。普通 chunk 也不等于一个 token：TCP、HTTP frame 和应用事件边界不同，客户端必须按协议增量解析，不能把每次 `read()` 当完整 JSON。

LLM 文本生成通常优先 SSE 或流式 HTTP；需要用户随时发送 audio chunk、取消、tool approval 时更适合 WebSocket，也可用“双 HTTP 通道”保持简单。无论选择哪种，都要有心跳、最大连接时长、连接/租户配额、有界 buffer、慢消费者背压、断连取消上游生成、明确的 `event_id/sequence` 和终止/错误事件。还要关闭代理缓冲与压缩导致的攒包，并让各层 idle timeout 对齐。

### 面试简答版

SSE 是基于 HTTP 的服务端到客户端文本事件流，浏览器支持事件 id 和自动重连，适合 token/进度；普通流式 HTTP 也是单响应持续输出，但 framing 自定义，更适合服务间 NDJSON/二进制流；WebSocket 是全双工消息通道，适合实时语音、客户端中途控制和双向协作。文本 LLM 默认选 SSE/流式 HTTP，真正双向再选 WebSocket；三者都必须处理心跳、代理 buffering、背压、断连取消、序列号和重连去重。
