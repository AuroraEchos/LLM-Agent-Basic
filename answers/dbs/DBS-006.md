## 我的答案

建立数据库连接通常涉及 TCP/TLS、认证、backend/session 内存和初始化；每请求新建会增加延迟和数据库开销。连接池复用已建立连接，并用有限池把数据库并发变成**有界资源**：池满时请求排队或超时，而不是无限创建连接压垮数据库。

池大小不是“越大越快”。数据库可高效并行的查询有限，过多活跃连接会造成 CPU context switch、buffer/cache 抖动、锁竞争、内存和 fd 消耗，反而提高 p99。总预算要按所有实例计算：

$$C_{total}=replicas\times workers\_per\_replica\times pool\_max$$

还要给迁移、管理、监控和故障切换保留连接。可用 Little's Law 粗估某服务的平均并发数据库需求 $L\approx \lambda W_{db}$，再通过压测看 pool wait 与 DB saturation；不能直接令 pool size 等于 Web 并发数。

连接泄漏是借出后未归还，症状包括 in-use 持续增长、pool timeout、请求堆积，而数据库连接数未必达到配置上限。常见原因是异常/取消路径没 close、流式响应跨全生命周期持连接、事务未结束。应使用上下文管理器/`try-finally`，设置 acquire timeout、query/statement timeout、idle-in-transaction timeout 和连接最大寿命，并暴露 active/idle/waiters/acquire latency/leak detection。

归还连接前必须 commit/rollback、清理临时 session 状态；失效连接要验证/回收但避免每次昂贵 health query。异步应用要用异步 driver/pool，不能跨 fork 或不兼容 event loop 共享连接。PgBouncer/RDS Proxy 等外部池能进一步复用，但 transaction pooling 会限制 session prepared statement/temp table 等特性，需明确语义。

### 面试简答版

连接池复用昂贵连接并限制数据库并发，池满应有界排队/超时。大小要看所有副本总和 `replicas × workers × pool_max`、数据库容量和实际 DB 时间，而不是越大越好；过大会增加内存、切换和锁竞争。泄漏会让 in-use/等待持续增长，通常来自异常、取消或长流未 close。用上下文管理器、短事务、acquire/statement/idle timeout、连接寿命与 active/wait 指标，并在归还前 rollback/清理 session。
