## 我的答案

**乐观锁**假设冲突少，不先长期占互斥锁；提交时验证数据自读取后未变化。常用版本号 CAS：

```sql
UPDATE task
SET status = :next, version = version + 1
WHERE id = :id AND version = :expected AND status = :current;
```

affected rows 为 1 表示成功，0 表示已被并发修改，应重新读取、重新验证业务并有限重试/报告冲突，不能把旧结果直接套到新状态。它适合读多写少、离线思考较长、冲突可重算的 Agent 状态；代价是冲突高时反复浪费计算并可能活锁，可用 jitter、重试上限和幂等键控制。版本号也解决 API 的 lost update，可映射为 ETag/If-Match。

**悲观锁**认为冲突概率/代价高，在短事务中先锁定要更新的行，如 `SELECT ... FOR UPDATE`，其他写者等待或按 NOWAIT/SKIP LOCKED 行为处理。适合库存扣减、严格顺序状态迁移、队列 claim 等高竞争且临界区很短的操作。必须固定锁顺序、设置 lock/statement timeout，避免死锁并准备重试。

关键边界：绝不能持数据库锁跨 LLM、HTTP 工具或人工等待。应锁内校验并记录 lease/状态后提交，事务外执行，回来用版本号提交结果。因此实践常混合：悲观锁/CAS 竞争执行权，幂等执行外部调用，乐观 CAS 写回。数据库锁也不能锁住外部系统，跨系统仍需 Saga/outbox。

### 面试简答版

乐观锁不先阻塞，更新时用 `WHERE id=? AND version=?` 并递增 version；影响 0 行代表冲突，需重读并有限重试，适合低冲突、可重算场景。悲观锁用 `SELECT FOR UPDATE` 等先占锁，适合高冲突、临界区短且冲突代价高的操作，但会等待/死锁。Agent 不能持锁跨模型或工具调用，应短事务 claim 后释放，外部执行完再用版本 CAS 写回，并配幂等与补偿。
