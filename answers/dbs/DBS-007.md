## 我的答案

分析慢 SQL 先确认“慢在哪里、慢多少次”，而不是看到全表扫描就立刻加索引：

1. 从慢查询/trace 获取规范化 SQL、绑定参数分布、调用次数、p95/p99、rows、lock/pool wait 和 I/O；总成本约为单次耗时乘频率。
2. 在接近生产的数据量/统计信息上看 `EXPLAIN`；安全环境用 `EXPLAIN ANALYZE`/等价功能取得 actual time、rows、loops、buffers。它会真实执行语句，写 SQL 应放可回滚环境并谨慎使用。
3. 从最耗时/行数最多节点向下看：scan、join 顺序/算法、sort/hash 是否 spill、重复 loops、估算 rows 与 actual rows 偏差、filter 丢弃行、缓存命中与锁等待。
4. 再修根因：更新统计/提高统计精度、改 SQL/数据类型、增加合适联合/覆盖索引、减少返回列/N+1、分区或预计算；最后在真实参数分布回归写入成本和尾延迟。

**全表/顺序扫描**表示读取表的大部分/全部页。小表、查询返回大比例行或顺序 I/O 更便宜时它完全合理；大表只取极少行却扫描全部才可疑。

**回表**常指二级索引找到键后，再访问 heap/聚簇主键取得其他列或判断可见性。大量随机回表会慢；覆盖/index-only 能减少，但更宽索引增加写放大，而且 PostgreSQL 等仍可能因 visibility 访问 heap。

所谓**索引失效**不是统一数据库术语，实际是优化器认为不能或不值得用：缺最左前缀、列被函数/隐式类型转换、前导通配符、collation 不匹配、选择性低、统计过期、参数计划偏差，或排序/范围不匹配。不要用 hint 强迫一个偶然快的计划掩盖数据分布问题。

### 面试简答版

我先从慢查询和 trace 确认参数、频率、锁/pool wait，再在代表性数据上对照 EXPLAIN 的 estimate 与 ANALYZE 的 actual rows/time/loops/buffers，从最重节点找 scan、join、spill、估算偏差。全表扫描对小表或返回大部分数据可能最优；回表是二级索引后再访问基表，覆盖索引可减少但增加写成本；“索引失效”常由前缀、函数/转换、选择性或统计导致。优化后必须用真实参数回归读写与 p99。
