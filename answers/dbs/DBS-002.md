## 我的答案

B+ Tree 是高扇出的平衡搜索树：内部节点主要保存分隔键和子页指针，记录/行定位信息主要在叶子层；所有叶子深度相同，叶子按键有序并通常便于顺序遍历。

它适合数据库的原因：

1. 一个页能放很多 key/pointer，分支因子 $B$ 很大，查找页数约 $O(\log_B N)$，亿级数据也只需少数层。
2. 节点大小与磁盘/page cache 页匹配，访问具有较好局部性；上层热点页容易留在内存。
3. 叶子有序，`=、<、>、BETWEEN、ORDER BY、MIN/MAX` 和前缀范围可从起点顺序扫描，而 hash 索引不擅长范围。
4. 分裂、合并/再平衡使高度受控，适合持续增删；代价是随机插入会分裂、碎片和写放大。

### 联合索引与最左前缀

索引 `(a,b,c)` 按字典序排序：先 a，再在相同 a 内按 b，最后 c。因此通常可直接定位：

- `a = ?`
- `a = ? AND b = ?`
- `a = ? AND b = ? AND c ...`
- 对整个 `(a,b,c)` 的相应排序/范围。

只给 `b=?` 时，不同 a 分组中的 b 分散，通常无法做一次连续定位；优化器可能选择全表/全索引扫描，某些引擎有 skip scan 等优化，但不能把它当普遍保证。遇到第一个范围列后，后续列通常不能继续缩小连续 scan 边界，例如 `a=? AND b> ? AND c=?` 中 c 可能只作为 index condition/filter；具体要看引擎计划。

列顺序按查询设计：等值/租户隔离列在前，随后范围/排序列，同时考虑选择性和复用查询，而不是机械“高基数优先”。若 SELECT 所需列都在索引中，可形成 covering/index-only scan，减少访问基表；但 MVCC 可见性等仍可能要求查表。对列做函数、隐式类型转换、前导 `%` LIKE、排序方向/NULL 规则不匹配，都可能削弱索引使用。

### 面试简答版

B+ Tree 高扇出、平衡且叶子有序，一次查找只需约 $O(\log_B N)$ 个页，既支持点查又支持范围和排序，符合数据库页 I/O 特性。联合索引 `(a,b,c)` 按字典序排列，通常有效前缀是 a、a+b、a+b+c；跳过 a 查 b 无法一次定位，遇到范围列后后续列多半只能过滤。实际仍要用 EXPLAIN 验证，并权衡 covering index 的少回表收益与更宽索引的写放大。
