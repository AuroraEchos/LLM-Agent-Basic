> **问题：** `P1` 关系型数据库、文档数据库、键值存储和对象存储分别适合保存 Agent 系统中的哪些数据？

## 我的答案

| 存储 | 优势 | Agent 中适合的数据 | 主要边界 |
|---|---|---|---|
| 关系型数据库 | 事务、约束、join、索引和成熟查询 | tenant/user、task 状态、消息元数据、tool call、幂等键、计费、事件/outbox | schema 演进要治理；不适合把巨大 blob 全塞热表 |
| 文档数据库 | 聚合文档、嵌套结构和较灵活 schema | 版本多变的 run snapshot、工具 payload、会话聚合读模型 | 跨文档事务/join 与约束通常较弱或成本不同；“无 schema”会演变成隐式混乱 schema |
| 键值存储 | 按 key 低延迟读写、TTL、原子计数/条件更新 | cache、session、rate limit、lease、短期幂等结果、job progress | 查询维度有限；缓存不是唯一真相，过期/淘汰/一致性必须设计 |
| 对象存储 | 低成本高耐久的大对象、按 key 获取、生命周期策略 | 原始文档、模型权重、数据集、音视频、长 trace/export、checkpoint | 通常不提供低延迟行更新/复杂查询；列表与覆盖一致性/语义看实现 |

典型分层：关系库保存 task 权威状态和 `artifact_uri + digest + version`，对象存储保存不可变大 payload；Redis 类 KV 做可丢缓存、lease/限流；文档库仅在聚合文档访问模式确有收益时引入。向量数据库/索引保存 embedding 与引用 ID，是可重建的派生检索结构，不应成为权限、原文和任务状态的唯一真相。

选型看访问模式、事务边界、数据大小、查询、TTL、耐久/RPO、合规删除和运维能力，而不是按 JSON 形状决定。多存储会引入 dual-write：先在关系事务写状态+outbox，再异步写对象/索引并以 digest/idempotency 去重，记录同步状态和修复任务；不能依赖“依次写两个库大概率成功”。

### 面试简答版

关系库适合任务、消息元数据、工具调用、幂等和计费等需要事务约束的数据；文档库适合整体读取、schema 多变的嵌套 run 文档；键值存储适合 cache、TTL、限流、lease 和短期进度；对象存储适合文档、权重、音视频、checkpoint 等大不可变对象。通常关系库保存权威元数据和 URI/digest，大对象外置，向量索引作为可重建派生数据。跨存储用 outbox、幂等和修复流程，不能裸双写。
