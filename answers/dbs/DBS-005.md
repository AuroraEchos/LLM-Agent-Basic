## 我的答案

MVCC（Multi-Version Concurrency Control）的基本思想是：更新数据时保留可识别的旧版本，让每个语句/事务按自己的 snapshot 判断哪个版本可见，而不是所有读都等待写锁释放。

概念上，一行版本带有“由哪个事务创建、何时失效”等元数据，旧版本可能保存在表中（PostgreSQL tuple）或 undo 链（InnoDB）。读取时结合 snapshot 中已提交/活跃事务集合选择可见版本；UPDATE 通常创建新版本并让旧版本失效。

```text
T1 snapshot: 看到 row v1
T2: UPDATE v1 -> v2; COMMIT
T1: 按隔离级别仍可能读 v1
新事务: 读 v2
```

因此普通一致性读通常不阻塞写，写也不阻塞旧快照读，大幅提高读多写多系统并发。但这不是“MVCC 无锁”：两个事务更新同一行仍要仲裁/等待，DDL、唯一检查、外键和显式 `FOR UPDATE` 仍可能加锁；隔离级别决定 snapshot 是每语句还是每事务，以及是否检测序列化异常。

多版本有维护成本：

- 旧版本占空间并增加扫描/WAL/undo；数据库需 VACUUM/purge 等回收不再被任何 snapshot 需要的版本。
- 长事务、`idle in transaction`、长时间一致性导出或复制槽会保留很老的 snapshot，阻止清理，造成 table/index bloat、undo 增长和事务 ID 风险。
- 更新热点行仍会形成写竞争；MVCC 不能修复应用的 lost update/write skew，需原子 UPDATE、version CAS、锁或 Serializable。

Agent 服务应让查询/更新事务短小，流式响应时不要保持 ORM transaction；监控 oldest transaction、dead tuples/undo history、vacuum/purge lag、锁等待和 bloat。连接归还池前必须 commit/rollback，防止一个遗留 snapshot 长期拖住全库清理。

### 面试简答版

MVCC 为一行保存多个版本，读按语句/事务 snapshot 选择可见版本，写创建新版本，因此普通读写通常互不阻塞。版本可放在表 tuple 或 undo 链，具体依数据库；同一行并发写、DDL、唯一检查和 FOR UPDATE 仍需锁，MVCC 也不自动消除 write skew。旧版本由 vacuum/purge 回收，长事务或 idle-in-transaction 会阻止清理并造成 bloat，所以 Agent 外部长调用和流式输出不能持有数据库事务。
