## 我的答案

ACID 描述数据库事务应提供的性质：

- **Atomicity 原子性**：事务中的修改全成功或全回滚，不能只转账一边。
- **Consistency 一致性**：事务从满足约束的状态转换到另一个满足约束的状态。数据库可保证主外键/check 等声明约束，但业务不变量仍需正确事务逻辑。
- **Isolation 隔离性**：并发事务的中间影响按隔离级别被控制；最强 Serializable 的已提交结果等价于某个串行顺序。
- **Durability 持久性**：提交确认后，即使进程/机器故障，结果按系统承诺可恢复，通常依赖 WAL、fsync 和复制策略；异步副本不等于零数据损失。

### Agent 状态为什么需要事务

一次状态转移常同时更新任务状态、追加事件、写 tool call 和 outbox。若只做一半，worker 崩溃后可能出现 `status=RUNNING` 却没有可追踪 attempt，或任务已完成却又重复投递。

```sql
BEGIN;
UPDATE task
SET status = 'RUNNING', version = version + 1
WHERE id = :id AND status = 'QUEUED' AND version = :expected;
-- 只有 affected_rows = 1 才取得执行权
INSERT INTO task_event(task_id, seq, type, payload) VALUES (...);
INSERT INTO outbox(aggregate_id, event_type, payload) VALUES (...);
COMMIT;
```

短事务把“状态 + 审计事件 + 待发布消息”原子写入；独立 relay 在提交后发送 outbox，即使重投也由 event/idempotency key 去重。

### 不能把整个 Agent run 包成一个长事务

LLM、人工审批和工具 I/O 可能持续秒到小时。持有数据库事务/行锁跨越外部调用会占连接、阻塞 vacuum/清理、放大死锁并造成长快照。正确做法是状态机分段：短事务 claim 任务并提交，事务外调用外部系统，再用 `WHERE version=expected` 的短事务提交结果；超时通过 lease/heartbeat 恢复。

数据库事务也不能原子覆盖 HTTP API、消息 broker 和模型计费。跨系统用 idempotency key、transactional outbox/inbox、Saga/补偿与可重放事件；“数据库 rollback”无法撤回已发邮件或已执行支付。隔离级别和重试还需与业务不变量共同设计。

### 面试简答版

ACID 是原子、一致、隔离、持久。Agent 一次状态转移常同时改 task、追加 event 和 outbox，应放在短事务内，避免崩溃留下半状态；用唯一约束/版本条件保证只有一个 worker 获得执行权。不能让事务跨 LLM 或工具长调用，应在事务外执行，再用版本号短事务提交。数据库外副作用不受 rollback 控制，要靠幂等键、outbox/inbox 和 Saga 补偿。
