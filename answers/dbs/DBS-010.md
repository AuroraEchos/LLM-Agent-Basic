## 我的答案

可追溯设计应同时有**当前状态快照**和**只追加事件/执行记录**：快照高效回答“现在怎样”，事件回答“为何变成这样”。一个概念模型：

```text
agent_run(id, tenant_id, status, version, current_step,
          request_id UNIQUE, created_at, updated_at)
run_event(run_id, seq, event_id UNIQUE, type, actor,
          payload_uri/json, occurred_at, schema_version)
message(id, run_id, seq, role, content_uri/json, parent_id, created_at)
tool_call(id, run_id, step_id, call_key UNIQUE, tool_name,
          args_uri/json, status, attempt, started_at, ended_at, error_code)
artifact(id, run_id, uri, digest, media_type, size, retention_class)
run_version(run_id, app_commit, image_digest, model_provider, model_id,
            model_revision, prompt_version, tool_schema_version,
            knowledge_snapshot, config_digest)
outbox(id, aggregate_id, event_type, payload, published_at)
```

关键约束：`(run_id, seq)` 唯一形成稳定顺序，`request_id/call_key/event_id` 唯一支持幂等；状态转移以 `WHERE version=expected AND status IN (...)` CAS 更新；更新 snapshot、追加 event、写 outbox 在同一短事务完成。时间戳只作时间信息，不能单独承担并发顺序；数据库 sequence 也未必连续或随 rollback 回收。

每次运行需冻结/记录能复现语义的 provenance：代码/image digest、模型与供应商版本/参数/seed（即使模型仍可能非确定）、system prompt/tool schema、检索索引/语料 snapshot、feature flags、输入输出 digest。外部 tool 保存 request/response reference、attempt、deadline、幂等键和安全错误，不把“最终答案”覆盖掉中间证据。

隐私与规模同样重要：敏感正文加密或放对象存储，行内只留 URI/digest/脱敏摘要；按 tenant 做行级授权，区分业务保留、审计 legal hold 和用户删除，删除要传播到对象/向量/备份策略。大事件表按时间/租户分区并为 `(run_id,seq)`、状态队列等真实查询建索引，避免把任意 JSON 每个字段都索引。事件 schema 用显式版本和向后兼容 reader，校验 event 到 snapshot 可重放/对账。

### 面试简答版

我会用 run 表保存带 version 的当前快照，用 append-only run_event 保存状态变化，再分表记录 message、tool_call/attempt、artifact 和 outbox。`(run_id,seq)`、request/call/event id 唯一，状态用 CAS；快照、事件和 outbox 同一短事务提交。另记录 image/代码、模型、prompt、tool schema、检索快照和配置 digest，才能解释一次答案。正文按敏感度外置/加密，Schema 有版本、分区/保留/删除策略，并能由事件重放或对账快照。
