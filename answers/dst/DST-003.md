> **问题：** `P0` Redis 中 String、Hash、List、Set、Sorted Set 和 Stream 分别适合哪些场景？

## 我的答案

| 类型 | 核心语义 | 典型用途 |
|---|---|---|
| String | byte sequence，支持 GET/SET、计数、bit 等 | JSON/blob cache、幂等结果、counter、限流计数；单值有大小上限 |
| Hash | 一个 key 下的 field-value record | 用户/session/任务的小字段对象，按字段读改，减少大量小 key；不等于任意深层 JSON |
| List | 按插入顺序的字符串序列，支持两端 push/pop 与 blocking pop | 简单 FIFO/LIFO、最近记录；可靠消费/多消费者恢复更适合 Stream/专业 MQ |
| Set | 无序唯一成员集合 | 去重、标签、集合交并差、成员判断、随机抽样 |
| Sorted Set | 唯一 member + score 排序 | leaderboard、优先/延迟队列、时间窗口索引；相同 score 再按 member 排序 |
| Stream | append-only entry log，带 entry ID、范围读、consumer group、pending/ack | 事件流、工作队列、可恢复消费和 lag/pending 跟踪 |

示例：Agent 的限流计数/短结果用 String；run 的轻量状态字段用 Hash；在线 worker 调度若要超时认领/重投可用 Stream consumer group；按 next-run timestamp 的延迟集合可用 Sorted Set，但“到期取出并删除”要 Lua/transaction 原子化。Set 适合已处理 document ID 去重，但若要求永久强一致，仍应落关系库唯一约束。

选型还要看操作复杂度、元素量和内存编码，而不是只看概念名称。避免 `KEYS *`、超大 Hash/List/Set 的单 key 热点和一次返回全部成员；用 SCAN/分页/分片，并给 cache key TTL 和命名空间。Redis 主线程上的大 O(N) 命令、Lua 长脚本、big key 删除都可能造成延迟尖峰。

Stream 不是 Kafka 的等价替换：保留/trim、复制持久性、故障转移、consumer pending 回收和幂等仍需配置；Pub/Sub 又是即时广播、订阅者离线通常不保留，不能与 Stream 混用语义。

### 面试简答版

String 适合字节值、cache 和计数；Hash 适合按字段读写的小对象；List 是两端操作的有序序列；Set 做唯一成员与集合运算；Sorted Set 按 score 排序，适合排行和延迟队列；Stream 是可保留的 append-only 事件日志，支持 consumer group、pending 和 ack。选型还要控制 big key、O(N) 命令、TTL、持久性和原子组合；需要强一致去重时不能只靠易淘汰 cache。
