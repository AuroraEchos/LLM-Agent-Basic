> **问题：** `P0` Cache Aside、Read Through 和 Write Through 模式分别如何工作？

## 我的答案

三种模式的区别主要是：**谁负责 miss 加载，以及写入先经过谁**。

### Cache Aside（旁路缓存）

应用直接管理缓存与数据库。读时先查 cache，miss 后查 DB，再写 cache；写时通常先提交 DB，再删除/失效 cache：

```text
read:  cache GET -> miss -> DB SELECT -> cache SET(TTL)
write: DB COMMIT -> cache DELETE
```

它最常见、控制灵活，cache 故障时可降级到 DB。但应用代码复杂，首次读有 miss 延迟，DB 与 cache 是双写关系。写后删除通常比“同时更新 cache”少一种并发覆盖窗口，但仍可能出现读 miss 与写并发导致旧值回填；可配 TTL、版本号/CDC invalidation、singleflight 和一致性要求选择解决方案。删除失败要重试/事件化，不能认为顺序写两次具有原子性。

### Read Through（读穿透）

应用只向 cache provider 请求；cache miss 时由 provider/loader 读取权威存储并填充，再返回。它把加载、TTL、并发 miss 合并封装起来，业务代码简单且策略统一；代价是 cache 层要理解数据源，复杂查询/事务不易适配，故障边界更集中。它描述的是逻辑责任，不代表所有 Redis 命令原生会查数据库。

### Write Through（写穿透）

应用向 cache/统一数据访问层写，后者同步写入 cache 与后端存储，只有按约定完成后才返回。后续读命中率高，写路径一致性集中；但写延迟增加，cache 中可能存下永不读取的冷数据，而且跨 cache/DB 并不凭此自动成为分布式原子事务。

与之相对的 write-behind/write-back 是先写 cache/队列、异步落库，延迟低且可合并写，但崩溃、乱序和积压可能丢数据，需要 durable log、幂等和恢复，不能与 write-through 混淆。

无论哪种，都要明确 source of truth、key/version、TTL、负缓存、容量淘汰、cache 故障降级和可接受的陈旧窗口。Agent 中 prompt/model response 缓存还必须把模型、参数、prompt/tool schema、tenant/权限等纳入 key，避免跨版本或跨租户污染。

### 面试简答版

Cache Aside 由应用先查 cache，miss 查库回填，写库后通常删 cache，灵活但要处理双写竞态；Read Through 由 cache loader 在 miss 时查后端并回填，统一读策略；Write Through 由缓存/数据层同步写 cache 和后端再返回，读更易命中但写延迟高且不天然原子。三者都需明确权威源、TTL、版本、失败补偿和并发 miss，LLM 缓存 key 还要包含模型、参数、prompt/schema 与租户安全域。
