> **问题：** `P0` 消息重复、乱序、积压和死信分别如何发生，应该如何处理？

## 我的答案

### 重复

原因：producer 未收到 ACK 重发、broker/consumer 重试、consumer 业务已提交但 ack/offset 未提交就崩溃、人工 replay。处理：稳定 event ID、inbox/业务唯一约束、幂等状态转移和外部 idempotency key；监控 duplicate rate。不能把“consumer 正常时只调用一次”当保证。

### 乱序

原因：多 partition/consumer 并行、重试延迟、网络与批处理、旧任务恢复。多数 broker 只保证**单 partition 内**顺序。按 aggregate/run ID 分区可保同一实体顺序，但会有 hot key；消息带 per-aggregate sequence/version，consumer 拒绝旧版本、缓存有限 gap 或从权威状态重建。要求全局总序通常牺牲吞吐和可用性，应先问业务是否只需每实体/因果顺序。

### 积压

原因：流入长期超过消费能力、下游变慢、毒消息反复重试、consumer crash/rebalance、partition skew。先看各 partition lag 和 oldest message age，再限流 producer、扩 consumer 到有效 partition 并行度、优化/批量处理、隔离慢依赖。重试用独立延迟 topic，避免一个失败消息阻塞主分区。积压消息可能已过业务 deadline，应过期/补偿而不是盲目全处理；恢复时限速保护下游。

### 死信

消息超过重试上限或被判定永久不可处理后进入 DLQ，常见原因是 schema/数据错误、权限、缺少关联数据或代码 bug。DLQ 条目保留原 message ID、payload reference、headers、错误分类、attempt、首次/最后失败时间与 consumer version。告警并由 owner 修复/隔离；重放到受控入口，先验证 schema、幂等和下游容量。DLQ 不是成功，也不能无限保存敏感 payload。

统一策略要区分 transient 与 permanent error，指数退避+jitter、最大 attempt/age、poison message 隔离，并用端到端 trace 将 publish、处理、retry、DLQ 和业务结果关联。

### 面试简答版

重复来自重发和“业务成功但 ack 前崩溃”，用 event ID、inbox/唯一约束和幂等副作用；乱序来自分区并行与重试，按实体分区并带 sequence/version，只在必要范围保证顺序；积压要看 lag/oldest age/partition skew，限流、扩容、批处理并隔离重试，恢复时防下游被冲垮；永久失败进入带完整诊断的 DLQ，由 owner 修复后受控、幂等、限速重放。
