## 我的答案

简单 `SETNX key 1` 至少有三个问题：客户端崩溃会永久死锁；若随后单独 `EXPIRE`，两条命令之间崩溃仍无 TTL；所有 owner 都写同一个值并直接 DEL，旧 owner 可能误删新 owner 的锁。

单 Redis 实例的基本 lease 形式是原子获取：

```text
SET lock:resource <random-owner-token> NX PX <ttl_ms>
```

- value 是每次 acquisition 唯一且不可猜的 owner token，不只是固定 client ID；
- TTL 是安全 lease 上限，要覆盖正常临界区 p99 + 网络/调度抖动，同时不能大到 crash 后长期不可用；
- 获取失败用 deadline、有限重试和随机退避，不能忙等。

释放必须“比较 token 相等才删除”并在服务端原子执行；旧版本可用 Lua，当前 Redis 版本还可使用相应条件删除命令，必须按部署版本选实现。不能先 GET 再 DEL，因为两步之间锁可能过期并被别人获得。

长任务续租同样要原子比较 token 后延长，并在 TTL 的安全余量前进行；续租失败/连接不确定时，owner 必须认为 lease 已丢失并停止进入新的副作用阶段。watchdog 不能解决进程长暂停超过 TTL、网络分区或 failover 异步复制造成双 owner。

### Fencing token 才能保护下游

即使锁正确过期，A 暂停超过 TTL、B 获锁写入、A 恢复后仍可能写旧结果。获取锁时同时取得单调递增 fencing token，下游只接受 token 大于已见 token 的写：

```text
A token=41 (过期)    B token=42 写成功
A 恢复携带 41        下游拒绝，因为 41 < 42
```

若业务绝不能容忍双执行，优先使用数据库唯一约束/行锁/版本 CAS、共识系统提供的 lease，并让副作用幂等；Redis 锁的复制/failover与时钟假设必须与 SLA 匹配。锁只缩小并发窗口，不是 exactly-once 魔法。

### 面试简答版

获取锁要用一条 `SET key unique_token NX PX ttl` 同时建立 owner 和过期 lease；释放、续租都必须在 Redis 端原子比较 token 后操作，防旧 owner 删除/延长新锁。TTL 覆盖临界区 p99 并留抖动余量，重试带 deadline+jitter；续租失败就视为失锁。因为暂停超 TTL 的旧 owner 仍可能恢复写入，高正确性场景还要单调 fencing token 让下游拒绝旧写，或直接用数据库约束/CAS/共识锁与幂等。
