## 我的答案

消息队列在 producer 和 consumer 之间加入可持久化缓冲与独立消费进度：

- **解耦**：生产者依赖事件契约/目的地，不必同步知道每个消费者的地址和部署；新增审计、索引消费者不必改主请求。但 schema、语义和容量仍是耦合点。
- **削峰**：短时到达率 $\lambda$ 大于处理率 $\mu$ 时消息先积压，consumer 按能力拉取。队列只能吸收有限突发；若长期 $\lambda\ge\mu$，lag 必然持续增长，仍需扩容、限流或降级。
- **异步**：HTTP 可在任务可靠入队后返回 job ID，耗时 embedding/eval 后台执行，降低请求等待并隔离故障。
- **失败重试**：consumer 失败不 ack/nack，broker 按策略重投；使用指数退避+jitter、最大次数、retry topic/延迟队列，永久错误进入 DLQ 并保留原因和原消息引用。

可靠链路要闭合：数据库状态与发布消息用 transactional outbox，relay 至少一次发送；consumer 用 event/message ID 唯一约束，在同一事务写 inbox/业务结果后再 ack。超时和 crash 会造成重复，所以 handler 必须幂等。外部 API 副作用也带 idempotency key，不能只在内存记“处理过”。

分区/consumer group 提供并行度与每 key 顺序，key 选择决定热点；prefetch、batch、最大 in-flight 构成背压。监控 publish/consume rate、oldest age/lag、retry、DLQ、处理耗时和 partition skew，并按业务 deadline 对过期消息丢弃/补偿。DLQ 不是坟场，要有告警、分类、修复后受控 replay，重放仍经过幂等与限速。

消息 payload 应小且版本化，大文档放对象存储并传 URI+digest；敏感数据加密/最小权限与 retention。broker ACK 的含义按 durability/replica 配置验证，它不表示消费者业务已经完成。

### 面试简答版

MQ 用持久缓冲让生产消费在时间和部署上解耦，吸收短时峰值并让耗时任务异步执行；失败通过不 ack、退避重投和 DLQ 处理。但长期到达率不小于处理率时队列仍会无限积压。可靠设计用 outbox 防“落库成功但没发消息”，consumer 用唯一 event ID/inbox 和业务事务实现幂等，成功后才 ack；同时限制 in-flight、监控 lag/oldest age、处理 DLQ 并对 replay 限速。
