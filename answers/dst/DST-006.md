> **问题：** `P0` At-Most-Once、At-Least-Once 和 Exactly-Once 分别意味着什么，业务上如何实现幂等消费？

> **分类：** 缓存、消息队列与分布式基础

## 我的答案

- **At-Most-Once**：消息处理 0 或 1 次，不重复但可能丢。典型是先提交 offset/ack 再处理，随后崩溃就丢；适合可丢的指标、下一次更新会覆盖的状态。
- **At-Least-Once**：至少处理一次，不轻易丢但可能重复。通常业务成功后才 ack；若成功后、ack 前崩溃，broker 会重投。大多数可靠消费采用它加业务幂等。
- **Exactly-Once**：在明确故障模型和边界内，一个逻辑输入的效果恰好一次。某 broker 的事务可能保证“消费 Kafka + 生产 Kafka”恰好一次，却未必涵盖数据库、HTTP 支付或邮件。必须问清 end-to-end effect、保留期、producer/consumer 配置与外部系统。

### 幂等消费

最稳妥的是把去重标记和业务写放在同一个数据库事务：

```sql
BEGIN;
INSERT INTO inbox(consumer, message_id)
VALUES (:consumer, :id)
ON CONFLICT DO NOTHING;
-- 仅插入成功者执行受唯一约束/条件保护的业务更新
UPDATE task SET ... WHERE ...;
COMMIT;
-- commit 成功后 ack
```

若检测到已处理，直接 ack；若事务回滚则不 ack、允许重投。`message_id` 要稳定且作用域明确，inbox retention 至少覆盖 broker 最大重投/replay 窗口。只在 Redis/内存 `SETNX` 后再写 DB 存在“标记成功、业务失败”的丢失窗口，除非可接受或有原子边界。

其他幂等方式包括：业务唯一键（order_id）、状态机条件更新、`version/fencing token` 拒绝旧事件、将“set value”代替“increment”。无法天然幂等的外部副作用使用供应商 idempotency key、outbox/Saga 和对账。并发重复、消息乱序和人工 replay 都要测试，不能靠 consumer 单线程假设。

### 面试简答版

At-most-once 不重复但可能丢，at-least-once 不易丢但会重复，exactly-once 只在声明的事务/系统边界内成立，不能自动覆盖数据库和外部 API。业务通常选择 at-least-once：用稳定 message ID，在同一数据库事务原子插入 inbox 去重记录并更新业务，commit 后才 ack；再配唯一约束、状态机/version 和外部 idempotency key。去重保留期必须覆盖重放窗口。
