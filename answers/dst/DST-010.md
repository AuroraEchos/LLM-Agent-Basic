## 我的答案

### 为什么物理时钟不可靠

各机器 oscillator 会漂移，NTP/PTP 只能校准且可能 slew/step；VM pause、闰秒和手工改时也会让 wall clock 跳变甚至倒退。网络延迟不确定，所以收到更晚不代表发生更晚。超时/耗时应使用 monotonic clock，不能用 wall time 相减；业务 timestamp 可展示时间，但不能单独证明全局因果或唯一性。

### 唯一 ID 的选择

- 数据库 sequence/自增：简单、全局唯一和可排序，但有中心依赖、批量分配空洞；自增 ID 还可能泄露业务规模。
- UUIDv4：无需协调、碰撞概率极低但随机，不提供时间顺序，宽随机索引会影响局部性。
- UUIDv7/ULID 类：时间前缀 + 随机/序列，较适合索引和大致时间排序；同毫秒及回拨的单调性依实现，不能推导严格事件顺序。
- Snowflake 类：timestamp + worker ID + per-tick sequence，高吞吐且大致有序；必须可靠分配 worker ID并处理时钟回拨、序列溢出和 epoch。

唯一、不可猜、按时间可排序是不同属性；外部资源 ID常需随机防枚举，幂等键还应表达请求作用域，不能只靠新 UUID 让每次重试都变成“新操作”。

### 事件顺序

- 单 leader/共识日志给某一 shard 一个 total order/commit index，成本是协调和可用性边界；Kafka offset 也只在 partition 内有序。
- Lamport clock 保证若 $a\rightarrow b$ 则 $L(a)<L(b)$，反向不成立，也不能判断并发。
- Vector clock/version vector 可识别因果先后与并发，但元数据随参与者增长，常用于副本/冲突检测。
- Hybrid Logical Clock 把物理时间的可读性和逻辑计数结合，能表达因果并限制与 wall time 偏差，但仍需明确实现保证。

Agent 事件通常用 `(run_id, sequence)` 保每个 run 顺序，另存 `event_id` 去重、`causation_id/correlation_id` 表达因果与 trace、`occurred_at/received_at` 供观测。跨 run 不强造全局顺序；状态更新用 version/CAS 或 fencing token拒绝旧写。时钟监控要告警 offset/drift，节点回拨时 ID generator 应等待、切 worker/逻辑计数或 fail closed，绝不能静默生成重复 ID。

### 面试简答版

分布式节点时钟会漂移、校准和回拨，网络延迟又不确定，所以 wall timestamp 不能保证唯一或全局顺序；超时用 monotonic clock。唯一 ID 可用 DB sequence、UUIDv4、时间有序 UUIDv7/ULID 或 Snowflake，但要分别权衡中心化、索引局部性、可猜性、worker ID 和时钟回拨。顺序按需要用单 shard 共识日志、Lamport、vector/HLC；Agent 通常只保证每 run sequence，并用 event/causation ID、version CAS 和 fencing 处理去重与旧写。
