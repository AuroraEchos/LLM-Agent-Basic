> **问题：** `P0` Linux 中 Zombie Process 与 Orphan Process 分别是什么，服务程序应如何正确回收子进程？

## 我的答案

### Zombie Process（僵尸进程）

子进程已经退出，内核释放了大部分资源，但仍保留 PID、退出码和少量统计，等待父进程通过 `wait/waitpid` 读取，这种状态是 zombie，`ps` 常显示 `Z`/`<defunct>`。它不再执行代码，不能用 `kill -9`“杀第二次”；真正的修复是让父进程回收，或终止/修复父进程使其被合适的 reaper 接管。大量 zombie 会耗尽 PID/task 表资源。

### Orphan Process（孤儿进程）

父进程先退出、子进程仍在运行时，子进程成为 orphan。内核会把它重新托管给 PID 1 或最近的 child subreaper；它仍能正常运行，之后由新的父进程回收。孤儿不是僵尸，两者可先后出现但定义不同。

### 正确回收方式

- 父进程保存子 PID，并在合适位置调用 `waitpid(pid, ...)`；同时管理多个子进程时，在收到 `SIGCHLD` 后循环 `waitpid(-1, ..., WNOHANG)`，直到没有已退出子进程，避免只回收一个。
- signal handler 内只做 async-signal-safe 的最小动作（如设置标志/写 self-pipe），在主事件循环完成复杂处理。
- 使用语言的 `subprocess`/进程池 API 时，对每个 child 调用 `wait/communicate/join`；`communicate` 还能同时排空 stdout/stderr，避免管道写满导致父子互等。
- 容器中的 PID 1 必须承担信号转发和孤儿回收，可使用合适 init；服务管理器或 supervisor 应明确重启和回收责任。
- daemon 化的传统 double-fork 只是特定部署方式；在 systemd/Kubernetes 下通常应前台运行并交给 supervisor，不能用 double-fork 掩盖生命周期。

需要区分“子进程退出但没 wait”和“子进程卡住没退出”。前者看 Z 状态并修复回收；后者要检查阻塞点、pipe、锁或 I/O，必要时按 TERM→宽限→KILL 终止，然后仍然 wait。只设置忽略 `SIGCHLD` 的行为有平台/语义条件，不应替代清晰的 child ownership。

### 面试简答版

Zombie 是子进程已经退出但父进程尚未 wait，内核保留退出信息；它已经死了，kill 无效，必须由父/reaper 回收。Orphan 是父先退出但子仍运行，会被 PID 1 或 subreaper 接管，并不等于异常。服务应保存子 PID，收到 SIGCHLD 后循环 `waitpid(..., WNOHANG)`，使用 subprocess/进程池时调用 communicate/wait/join；容器 PID 1 还要负责信号转发和孤儿回收。
