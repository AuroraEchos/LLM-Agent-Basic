## 我的答案

这些工具回答的问题不同，排障时应先形成假设再交叉验证：

| 工具 | 主要用途 | 常看内容 |
|---|---|---|
| `top` | 实时全局与进程资源概览 | load、CPU user/system/iowait、内存、进程 `%CPU/%MEM`、状态；`-H` 看线程 |
| `htop` | 更易交互的 top 类视图 | 树形关系、逐核/线程、排序过滤、信号；是否安装取决于环境 |
| `ps` | 某一时刻的精确进程快照，适合脚本 | PID/PPID/TID、状态、etimes、RSS/VSZ、CPU、完整 argv；如 `ps -eo ...` |
| `free` | 系统 RAM/swap 概览 | `available`、cache、swap；不要把 `free` 小直接当内存耗尽 |
| `df` | 文件系统整体已用/可用块与 inode | `df -h` 容量，`df -i` inode；看到的是挂载文件系统，不是目录求和 |
| `du` | 遍历目录项统计可达文件占用 | 定位哪个目录大，如 `du -xhd1`；可能慢且受权限/硬链接/稀疏文件影响 |
| `lsof` | 进程打开的 fd/文件/socket | 谁占文件/端口、deleted-but-open 文件、连接、工作目录；大系统全扫成本高 |
| `ss` | 内核 socket 状态与统计 | listening 端口、TCP state、队列、进程，如 `ss -lntp`、`ss -s` |

典型组合：

- 磁盘 `df` 满但 `du` 对不上：检查文件是否已 unlink 却仍被进程打开，`lsof +L1` 可定位；也检查 mount、reserved blocks、snapshot。删除文件名不会释放仍被 fd 持有的空间。
- API 连不上：`ss -lntp` 确认监听地址/端口和进程，再看连接 state/队列、防火墙与 namespace；监听 `127.0.0.1` 与 `0.0.0.0` 含义不同。
- 内存高：`free` 判断系统压力，top/ps 找进程，再用 `/proc/pid/smaps_rollup`、cgroup、应用/GPU profiler 深挖；RSS 不能直接按 worker 相加，因为有共享页。
- CPU 高：top 看全局和线程，ps/pidstat 找持续热点；这些工具只能定位对象，函数级根因还需 profiler/perf。

命令输出会有采样、权限、容器 namespace 与版本差异。生产执行 `lsof`、递归 `du` 等前要评估开销；不要只凭一次快照下结论，应结合历史指标和多次采样。

### 面试简答版

top/htop 看实时系统和进程/线程热点，ps 给可脚本化的进程快照，free 看 RAM/swap 且重点关注 available，df 看文件系统块/inode，du 找目录树占用，lsof 查进程打开的文件和 socket，ss 查监听及 TCP 状态/队列。常见案例是 df 满而 du 不大时用 `lsof +L1` 找已删除仍打开文件；端口问题先 `ss -lntp`。任何单个命令都只是证据，需结合 `/proc`、cgroup、历史指标与 profiler。
