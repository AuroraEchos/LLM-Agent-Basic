## 我的答案

用户态和内核态是 CPU 的不同特权级和执行环境：

- **用户态**运行普通应用，不能直接执行特权指令、配置页表或任意访问设备/内核内存；进程之间也由虚拟内存隔离。
- **内核态**运行内核代码，可管理调度、内存、文件系统、网络和设备。权限更高意味着 bug 的影响更大，所以用户输入必须严格校验。

系统调用是用户程序请求内核服务的受控入口，例如 `read`、`write`、`openat`、`mmap`。以 Linux 的一次 `read(fd, buf, n)` 为例，大致过程是：

1. 应用通常调用 libc/运行时 wrapper，把系统调用号和参数按 ABI 放入寄存器。
2. 执行体系结构规定的陷入指令（如 x86-64 `syscall`），CPU 切换特权级，保存返回所需状态并跳到内核入口。
3. 内核根据系统调用号分派，检查 fd、地址、长度、权限等；用户指针不能直接信任，数据复制需用安全的 user-copy 机制。
4. 内核沿 fd 找到对应对象和操作。若数据就绪，可从 page/socket buffer 复制；若未就绪且 fd 为阻塞模式，当前 task 进入等待，调度器运行其他 task。
5. 完成后内核设置返回值或负 errno，恢复用户上下文并返回用户态；libc 常将负错误转换为 `-1` 并设置 `errno`。

“用户态/内核态切换”不一定等于“进程上下文切换”。系统调用可能在同一线程上下文中进入内核并立即返回；只有阻塞、抢占等导致 CPU 改运行另一 task 时，才发生调度意义上的 context switch。反过来，中断也能使 CPU 进入内核，但不是应用发起的系统调用。

系统调用成本包含边界切换、安全检查、数据复制和可能的调度/I/O；真正慢的常是阻塞设备或网络，而不只是那条陷入指令。可用批量 I/O、缓冲、`readv/writev`、`sendfile`、异步 I/O 或 mmap 减少调用/复制，但这些会引入生命周期、背压和一致性权衡。vDSO 可让少数查询在用户态完成，并非所有 API 都要真正陷入内核。

### 面试简答版

用户态权限受限，不能直接操作硬件和内核内存；内核态负责调度、内存、文件与网络。系统调用由 wrapper 按 ABI 放置 syscall number/参数，执行陷入指令进入内核；内核分派、校验用户参数与权限、执行或阻塞，最后返回结果/errno 并恢复用户态。特权级切换不必然是进程上下文切换，只有调度到另一 task 才是后者。优化应看系统调用次数、复制与实际 I/O 等完整成本。
