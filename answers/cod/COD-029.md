## 我的答案

下面实现异步 Token Bucket：以 `rate` token/秒补充，最多积累 `capacity`，突发流量可消耗桶内余额；共享状态由 `asyncio.Lock` 保护。

```python
import asyncio
import time

class AsyncTokenBucket:
    def __init__(self, rate, capacity):
        if rate <= 0 or capacity <= 0:
            raise ValueError("rate/capacity must be positive")
        self.rate = float(rate)
        self.capacity = float(capacity)
        self.tokens = float(capacity)
        self.updated_at = time.monotonic()
        self.lock = asyncio.Lock()

    def _refill(self, now):
        elapsed = max(0.0, now - self.updated_at)
        self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)
        self.updated_at = now

    async def acquire(self, amount=1.0, timeout=None):
        if amount <= 0 or amount > self.capacity:
            raise ValueError("amount must be in (0, capacity]")
        deadline = None if timeout is None else time.monotonic() + timeout

        while True:
            async with self.lock:
                now = time.monotonic()
                self._refill(now)
                if self.tokens >= amount:
                    self.tokens -= amount
                    return True
                wait = (amount - self.tokens) / self.rate

            # 锁外等待；醒来后重新竞争并重新计算，防止超发。
            if deadline is not None:
                remaining = deadline - time.monotonic()
                if remaining <= 0 or wait > remaining:
                    return False
                wait = min(wait, remaining)
            await asyncio.sleep(wait)  # task 取消会自然抛 CancelledError
```

必须使用 `time.monotonic()`，系统时钟回拨不能令 token 变多/变少。检查余额与扣减在同一锁内；sleep 必须在锁外，否则一个等待者会阻塞所有请求。醒来要重新检查，因为其他协程可能先消费。

这个简单版本不保证严格 FIFO，竞争激烈时可能饥饿；需要公平性可维护 waiter queue，并在补充时按顺序唤醒。单进程锁对多进程/多实例无效，分布式限流要在 Redis/Lua、网关或专门服务中原子执行，并明确按用户、tenant、IP 还是全局 key；还需处理存储故障时 fail-open/fail-closed、时钟和热点 key。

### 面试简答版

Token Bucket 按速率补 token、容量限制突发上限；acquire 在锁内用 monotonic time 补充并原子扣减，不够时计算等待时间，释放锁后 sleep，醒来重新检查。它支持突发且长期平均受 rate 限制。严格公平需 waiter queue，多实例则必须把检查和扣减放到 Redis Lua/网关等原子存储，而不是每进程各自限流。
