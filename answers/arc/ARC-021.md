> **问题：** 为什么主流生成式 LLM 多采用 Decoder-Only 架构？这一判断有哪些例外？

## 我的答案

主流通用生成式 LLM 采用 Decoder-Only，不是因为它对每个任务都绝对最优，而是因为它把**数据、训练目标、任务接口和自回归推理**统一成了“给定前缀，预测下一 token”。这种统一性非常适合大规模预训练和通用能力涌现。

### 1. 预训练目标简单且数据充足

Decoder-Only 直接最大化：

$$
\log p(x_{1:T})=\sum_{t=1}^{T}\log p(x_t\mid x_{<t})
$$

任何文本、代码、对话或结构化序列都可按 token 流训练，不需为每条数据人工构造标签，也不需单独定义输入端和输出端。每个 token 都可作为一个训练目标，数据利用直接。

### 2. 训练与生成推理对齐

训练时使用 Causal Mask 并行预测下一 token，推理时则真正逐 token 生成。两者的条件概率形式一致，配合 KV Cache 可避免重复计算历史 token 的 K/V。

需注意，Teacher Forcing 时上下文来自真实 token，推理时来自模型自己的生成，仍然存在 Exposure Bias；这里的“对齐”指模型因子分解和输出方式一致，不是说训练与推理状态完全相同。

### 3. 一种架构统一多种任务

通过 prompt 和输出格式，翻译、摘要、分类、代码生成、工具调用都可转换为条件续写。System/User/Assistant 消息、工具结果和多轮历史都可放进同一 token 序列。这为 In-Context Learning、Instruction Tuning 和 Agent 提供了非常统一的接口。

### 4. 架构和扩展工程简洁

模型只有一个 Transformer stack，每层都是 Causal Self-Attention + FFN，不需另外维护 Encoder、Decoder 和 Cross-Attention 三种路径。对大规模训练的并行切分、激活重计算、推理缓存和 kernel 优化而言，统一 block 更容易扩展。

### 5. 为什么不能说 Decoder-Only 总是更好

- 对分类、检索、序列标注等纯理解任务，双向 Encoder 可以在同一层中利用完整左右上下文，同等延迟/参数下可能更高效。
- Decoder-Only 在处理输入 prompt 时仍使用 Causal Mask，较早的输入 token 不能利用后续输入信息更新自身表示。
- 在输入很长、输出结构明确的条件生成中，专门 Encoder 可先双向压缩或表示输入，Encoder-Decoder 可能更合适。

### 常见例外

1. **Encoder-Decoder 生成模型**：翻译、摘要、语音转写和文本到文本转换中，源端双向表示 + 目标端自回归生成仍然很有价值。
2. **Prefix LM / 混合 Mask**：输入前缀内使用双向可见性，输出部分使用因果可见性，介于标准 Encoder-Decoder 和 Decoder-Only 之间。
3. **多模态模型**：图像、音频常先经过专门 Encoder，再由自回归 Decoder 生成文本，整体系统并非纯 Decoder-Only。
4. **非自回归/迭代生成**：掩码预测、扩散式文本模型或并行解码使用不同的生成因子分解，可能不以标准 Causal Decoder 为核心。

### 面试简答版

主流通用生成式 LLM 采用 Decoder-Only，核心原因是 Next-Token Prediction 可直接利用海量原始文本，且预训练目标、自回归推理和 prompt 任务接口完全统一。单一 Transformer stack 也更容易做大规模并行和 KV Cache 优化。但 Decoder-Only 并非所有任务都最优：表征和检索任务常适合双向 Encoder，翻译、摘要等明确 Seq2Seq 任务可适合 Encoder-Decoder，多模态系统也常包含专门感知 Encoder，还有 Prefix LM、掩码生成和扩散式文本模型等例外。
