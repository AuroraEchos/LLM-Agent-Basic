## 我的答案

GIL（Global Interpreter Lock）是传统 CPython 构建中保护解释器对象模型的全局锁：同一 interpreter 内通常只有一个 OS 线程能持有 GIL 并执行 Python bytecode。它简化引用计数和内置对象内部安全，但限制纯 Python CPU 密集线程的多核并行。

### 会限制什么

两个线程各自执行纯 Python 大循环或递归算法时，虽然 OS 同时调度线程，它们仍轮流拿 GIL，速度提升通常接近 1，甚至因切换更慢。传统 CPython 下，这类任务通常用进程池、独立服务，或能释放 GIL 的向量化 native 库。

GIL 是每个 interpreter 的约束，不是 CPU 锁，也不阻止多个进程分别使用不同 core。较新的多 interpreter executor 也可让不同 interpreter 并行，但对象隔离和通信成本需考虑。

### 不会明显限制什么

- 阻塞文件/网络 I/O 时 CPython 会释放 GIL，其他线程可以运行；
- NumPy、压缩、哈希和部分 ML/CUDA 扩展在长 native 计算中会释放 GIL，但必须查具体实现；
- GPU kernel 在设备上执行不受 GIL 限制，Python launch、预处理和同步仍可能受影响；
- `asyncio` 的并发来自等待 I/O 时协作调度，不是 GIL 提供的。

### GIL 不等于线程安全

GIL 只保护解释器内部，不保证多步骤业务操作原子。例如“检查 cache 不存在→计算→写入”可在线程切换后重复计算。I/O/C 扩展释放 GIL 后更明显。即使某版本中 `list.append` 看起来原子，也不应把实现细节当业务同步契约；共享余额、状态机和幂等仍需 Lock、Queue、事务或单 owner。

### Free-threaded CPython 的边界

从 Python 3.13 开始，CPython 提供可选 free-threaded build，可禁用 GIL，让多个线程真正并行执行 Python 代码。但不能假设所有生产安装都启用：需确认 build/runtime，某些未适配 C 扩展可能重新启用 GIL，单线程性能和内存开销也可能变化。

Free-threaded 模式中内置容器有内部锁以维持基本安全，但复合操作、迭代器与业务不变量仍需显式同步。原先被 GIL 偶然掩盖的 data race 会暴露，采用前要验证扩展兼容、线程安全和真实性能。

### 选型

纯 Python CPU 在传统构建用 process；I/O 阻塞库用 thread；大量异步网络用 asyncio；native/GPU 能否线程并行看其释放 GIL 和内部线程池，防 oversubscription。free-threaded build 也必须用真实 workload 压测，不能只改解释器开关。

### 面试简答版

传统 CPython 的 GIL 使同一 interpreter 同时只有一个线程执行 Python bytecode，所以纯 Python CPU-bound 用线程通常不能多核加速，多进程可以绕过。它不妨碍阻塞 I/O 期间其他线程运行，NumPy/压缩/部分 CUDA 扩展释放 GIL 后也可并行。GIL绝不等于业务线程安全，多步骤共享状态仍需锁或事务。Python 3.13 起有可选 free-threaded build，但要确认实际构建、扩展兼容和显式同步，不能假设所有环境都已无 GIL。
