## 我的答案

异步函数中的普通阻塞调用会占住运行 event loop 的 OS 线程。在调用返回前，loop 无法处理其他 socket、timer、取消或流式输出，表现为所有请求一起延迟、心跳超时和连接积压；它不是“只阻塞当前协程”。

```python
async def handler():
    time.sleep(5)       # 整个 loop 卡 5 秒
    requests.get(url)  # 同步网络也会阻塞
```

### 首选：真正异步客户端

网络/数据库优先使用原生 async client。socket 等待注册给 loop，当前 Task 暂停，连接池、deadline、stream cancellation 可由同一异步生命周期管理。不要每次请求新建 client；复用有上限的连接池，并在应用关闭时显式 `aclose()`。

### 阻塞 I/O：线程池

无法替换的同步 SDK/文件 I/O 可用：

```python
result = await asyncio.to_thread(blocking_call, arg)
```

或显式有界 `ThreadPoolExecutor`。线程等待 I/O 时不阻塞 loop，且通常没有 pickle 成本。必须限制提交和池大小；无界提交仍会产生长队列、连接耗尽和内存上涨。

外层 await 被取消通常只是不再等待，正在执行的 Python 线程不能被安全强杀。阻塞函数应支持自己的 timeout/cancel token，结果迟到时丢弃；有副作用则用幂等键防重试重复提交。

### CPU-Bound：进程池或独立 worker

纯 Python OCR 后处理、压缩算法等长 CPU任务放 `ProcessPoolExecutor` 或任务服务。它避免占 loop 并利用多核，但参数/结果需 pickle，进程内存和启动昂贵。大 payload 传 URI/shared memory，任务批量化。

取消 Future 也不保证正在运行的子进程立刻停止，需要 cooperative deadline、worker 隔离或明确进程终止策略。释放 GIL 的短 native 计算可能适合线程池，但应压测；GPU 调用若同步等待设备，也要使用异步 stream/专用 worker。

### 检测与防护

- 监控 event-loop lag、slow callback、P99、线程/进程池 queue wait 和 active worker；
- lint/code review 禁止 async 路径中的 `time.sleep`、同步 HTTP/DB；
- 压测一个慢调用是否拖慢无关请求；
- 每层设置总 deadline、连接/并发 Semaphore、背压和 bulkhead；
- shutdown 时停止接收、取消 Task、关闭 client/executor 并等待清理。

线程池/进程池是兼容桥，不应掩盖长期架构问题。高吞吐核心依赖最好迁移到原生 async 或独立服务，才能获得可靠取消、背压和观测。

### 面试简答版

在 event loop 线程里调用 `time.sleep`、同步 HTTP 或长 CPU函数会阻塞整个 loop，使所有协程、timer、取消和流式输出停顿。网络/数据库首选复用的原生 async client；无法替换的阻塞 I/O 用有界线程池/`asyncio.to_thread`；纯 Python CPU任务用进程池或独立 worker。取消 await 不会自动杀死运行中的线程/进程，所以底层也要 timeout、幂等和迟到结果处理。线上监控 loop lag、executor 队列和 P99，并用 Semaphore、deadline 与背压防雪崩。
