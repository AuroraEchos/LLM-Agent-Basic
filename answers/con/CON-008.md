> **问题：** 如何为并发工具调用实现超时、取消、结果聚合和部分失败处理？

## 我的答案

先为每个工具声明风险、依赖、幂等性和失败策略，再并发执行。并发不是简单 `gather(*)`：需要总 deadline、单工具 timeout、并发上限、取消传播、确定性聚合，以及“哪些失败还能继续”的业务规则。

### 请求与策略

每个调用包含 `call_id、tool/version、typed_args、deadline、required/optional、idempotency_key`。先完成授权和参数校验，只有互不依赖、写集合不冲突的工具并行；同一账户写操作或有顺序依赖的步骤应串行/由工作流管理。

总请求 deadline 向下传播，单工具可用：

$$
t_i=\min(tool\_timeout_i,\;deadline_{remaining})
$$

排队和重试也消耗同一预算，不能每层重新获得完整 timeout。

### 并发与超时

使用 TaskGroup/明确 task map 启动调用，并用 Semaphore 限制全局、每工具和每租户并发。超时后取消对应 Task并等待其 cleanup；异步 HTTP 需关闭 response/连接。同步线程或远程系统未必因 coroutine 取消而停止，底层也要 timeout/cancel API，迟到结果按 call id 丢弃。

不要随意 `shield` 正常工作；它适合很短且必须完成的状态/cleanup，仍要有独立 timeout。客户端取消应沿 Orchestrator→Tool client传播，释放 permit 和连接。

### 结果聚合

将每项统一为：

```text
ToolOutcome = Success(value, provenance, latency)
            | Failure(kind, retryable, safe_message)
            | Cancelled(reason)
```

按原始 call id/计划顺序聚合，而非完成顺序；结果通过 Schema，带来源、时间、工具版本和授权范围。不要把异常对象直接喂给模型或用 `None` 同时代表“无结果”和“失败”。

### 部分失败策略

- required 工具失败：取消尚无价值的兄弟任务，有限重试/降级/转人工，整体不宣称成功；
- optional 工具失败：保留成功结果，明确缺失及影响，模型不能假装数据完整；
- quorum/多源查询：达到预设数量或一致性即可早停并取消剩余；
- 写操作：成功与失败混合使用 Saga 补偿或人工，不用“取消 Task”假装回滚。

重试只针对明确瞬时且幂等的调用，指数退避+抖动，沿用 idempotency key。参数、权限和安全错误不重试。熔断/限流防下游故障被并发放大。

### 观测与测试

Trace 记录每个 call 的排队、运行、timeout、取消、重试和结果，指标看 fan-out、并发、required/optional 失败、迟到结果、取消释放时延和整体任务成功。测试工具成功后响应丢失、一个超时其他成功、客户端断连、取消与完成竞争、写操作重复，以及所有失败时的清晰降级。

### 面试简答版

我会先把工具标成 required/optional、幂等/有副作用，并只并发无依赖且写集合不冲突的调用。总 deadline 向下传播，每工具 timeout 取自身上限与剩余预算的最小值；TaskGroup/任务表加全局和每工具 Semaphore。结果统一成 Success/Failure/Cancelled，按 call id 而非完成顺序聚合并保留 provenance。required 失败会取消无价值兄弟并降级，optional 失败则返回部分结果和缺失声明；写操作依靠幂等键和 Saga，取消不能当回滚。
