## 我的答案

先判断任务大部分时间是在执行 CPU 指令还是等待外部资源，再看库是否支持 async、是否释放 GIL、任务粒度、数据传输和隔离要求。传统 CPython 下，“纯 Python CPU 优先进程，大量非阻塞 I/O 优先 asyncio”是良好起点，但不是绝对规则。

| 工作负载 | 首选 | 原因/边界 |
|---|---|---|
| 纯 Python CPU 密集 | 多进程/独立 worker | 利用多核；有启动和 pickle/IPC 成本 |
| 释放 GIL 的 NumPy/C++/GPU | 线程或库自身并行 | 可共享大数组；需防内部线程过度订阅 |
| 大量支持 async 的网络 I/O | `asyncio` | 单线程管理大量连接，易流式、取消和背压 |
| 阻塞 I/O SDK/文件调用 | 有界线程池 | 无需改库；线程过多会耗内存和连接 |
| 强隔离、可能崩溃 | 进程/容器 | 故障和资源边界清楚 |

### CPU-Bound

纯 Python 分词后处理、复杂搜索或图算法可用 `ProcessPoolExecutor`。任务必须可序列化，启动与数据复制昂贵，所以应批量化小任务，大对象传共享内存或 URI。池大小从 CPU core/配额开始压测；内存带宽任务不会随 core 线性扩展。

若 NumPy、PyTorch CPU op 或压缩库释放 GIL，线程可能更合适，避免大数组 pickle；但这类库常已有 OpenMP/MKL 线程池，外层再开大量线程会形成 $N_{outer}\times N_{inner}$ 过度订阅。GPU 任务受显存、stream 和 kernel queue 限制，也不能按 CPU core 开并发。

### IO-Bound

HTTP、数据库、模型流式 API 有 async client 时使用 asyncio，用 TaskGroup、Semaphore、有界连接池、deadline 和背压管理并发。async 的优势来自等待时让出 loop，并不会让单个请求本身更快。

只有同步 SDK 时用 `asyncio.to_thread` 或有界 ThreadPoolExecutor。无界提交只会把阻塞从 socket 移到线程池队列，最后产生超时雪崩。

### 混合架构与边界

Agent 服务常是：asyncio 接请求并调用模型/RAG→线程池适配遗留 SDK→进程/专用服务做 PDF/OCR/CPU 解析→GPU 推理 server。各池有独立容量、queue 和 timeout。

用真实输入测 throughput、P95/P99、CPU、RSS、序列化和 queue wait。取消进程 Future 不代表子进程立即停，线程也无法安全强杀；async timeout 后要保证底层连接释放。外部副作用在重派前必须使用幂等键。

### 面试简答版

纯 Python CPU-bound 在传统 CPython 下优先多进程，绕过 GIL，但要控制 pickle、启动和内存；NumPy/PyTorch 等释放 GIL 的 native 运算可用线程，并防内外线程池过度订阅。大量支持非阻塞客户端的网络 I/O 优先 asyncio，只有同步 SDK 时放有界线程池；强隔离任务用进程/容器。Agent 通常混合使用 async 编排、线程适配阻塞库、进程做 CPU 解析，最终由真实 P99、吞吐、队列和资源压测决定。
