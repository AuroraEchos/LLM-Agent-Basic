## 我的答案

调度器要将“允许进入系统、谁先运行、能占多少资源、如何终止”分开设计。请求数不是充分成本单位，Agent/LLM 任务还要估计 token、工具/GPU slot、deadline 和副作用风险。

### 任务与状态

任务包含 `id、tenant、service_class、base_priority、enqueue_time、estimated_cost、deadline、cancel_token、idempotency_key`。优先级由服务端根据身份/业务映射，客户端不能自报最高级。

状态机：

```text
PENDING → QUEUED → RUNNING → SUCCEEDED/FAILED
                   └──────→ CANCELLING → CANCELLED
```

使用 CAS/version 保证取消、完成和重试竞争只有一个终态。Future/结果句柄让提交者 await、查询或取消。

### 并发上限与准入

入口有界，按任务数和估计成本/token 限制；超出 deadline 可行性或队列上限时尽早拒绝。全局 Semaphore 控制 worker，另设每工具/模型/租户 semaphore 和 token bucket，避免一个租户占满资源。许可在 `finally` 中释放。

任务实际成本偏离估计时按已使用资源结算并更新估算器；超预算可中止/降级。不同资源需求可用资源向量，而不是一个 semaphore 假装 GPU、数据库连接完全可替换。

### 优先级与公平性

严格 PriorityQueue 会饿死低优任务。采用层级队列：先服务等级，再在租户间 Weighted Fair Queuing/Deficit Round Robin，同租户 FIFO；等待时间提供 aging，但不能越过安全硬边界。

近似 WFQ 可按虚拟完成时间：

$$
F_i=\max(V(a_i),F_{i-1})+\frac{cost_i}{w_i}
$$

成本用 token/GPU-second 等估计，防用户把大任务拆小或用超长请求占便宜。实时任务可预留少量 worker，批任务填充剩余容量并可在安全点抢占。

### 可取消性

排队任务取消时标记 tombstone/从索引移除并释放预留；运行任务将 cancel token 传播到模型、HTTP、子任务和工具，在 await/decode 等安全点清理。Priority heap 中任意删除昂贵，可用 `id→entry` + lazy deletion，但要定期 compact 防 tombstone 泄漏。

线程/外部写不一定可强制取消：底层有 timeout，迟到结果丢弃；写操作以幂等键和事务/Saga处理，取消不等于回滚。shutdown 时停止准入、给运行任务 grace period，再取消并持久化可恢复状态。

### 调度循环与观测

单 owner scheduler coroutine 持有队列状态，通过 condition/event 在新任务、资源释放和取消时唤醒，避免多个 scheduler 竞争。不要持锁执行任务；选出任务、扣资源后立即释放锁再启动。

指标按优先级/租户记录 queued cost、等待 P50/P99、最老年龄、deadline miss、实际/估计成本、份额、公平性、取消时延和 worker 利用率。测试突发高优、大/小任务混合、恶意拆单、取消风暴、资源泄漏和低优最终进展。

### 面试简答版

我会设计有界准入、层级公平队列和资源 semaphore。任务带租户、服务等级、deadline、估计 token/GPU成本和取消 token；服务等级决定基础优先级，租户间用 WFQ/DRR，同级 FIFO，并用 aging 防饥饿。全局、每模型/工具和每租户分别限并发与配额。排队取消移除/标记 tombstone，运行取消传播到子任务并在安全点释放资源；状态 CAS 保证取消—完成只有一个终态，外部写仍靠幂等/Saga。监控最大等待、deadline miss、公平份额和取消释放时延。
