## 我的答案

选择同步原语时先问：是保护一个临界区、限制并发数量、等待某个状态谓词、广播一次状态，还是在生产者/消费者之间转移数据所有权？

| 原语 | 语义 | 典型场景 |
|---|---|---|
| Lock/Mutex | 同时只有一个 owner 进入临界区 | 保护共享 map、状态转移、非线程安全 client |
| RLock | 同一线程可重复获取并计数释放 | 递归/分层代码确实会重入同一锁 |
| Semaphore | 同时允许最多 $N$ 个持有者 | 模型 API、连接、GPU slot、工具并发上限 |
| Condition | 持锁等待某个谓词，变化后通知 | 缓冲区非空/未满、状态达到特定版本 |
| Event | 一个可设置/清除的广播 flag | 启动就绪、shutdown、配置已加载 |
| Queue | 有序传递 item，解耦生产消费 | worker pool、流事件、带背压流水线 |

### Lock 与 RLock

Lock 保护最小共享不变量，使用 context manager/finally 保证释放；锁内不做未知耗时 I/O。RLock 只解决“同一线程再次获取自己持有的锁”，不会解决两个线程的死锁，也可能掩盖职责混乱。能重构为不重入通常优于默认使用 RLock。

`asyncio.Lock` 是 Task 级而非线程互斥；`threading.Lock` 会阻塞 OS 线程，不能在 event loop 中用来等待。它们也不能替代跨进程/分布式锁。

### Semaphore

Semaphore 维护许可计数，适合限制并行 I/O/GPU资源而非保护单一变量。`Semaphore(10)` 允许最多 10 个任务进入；`BoundedSemaphore` 可发现多 release。并发上限应与上游限流、连接池和 deadline 配套，否则只是把无界压力移到 semaphore 等待队列。需在 `finally/async with` 释放，取消路径也不能漏 permit。

### Condition

Condition 绑定 Lock：等待者在锁内反复检查 predicate，不满足时 `wait()` 原子释放锁并睡眠，被通知后重新获取锁。必须使用 `while not predicate`，因为可能虚假唤醒，或其他消费者先拿走条件。`notify` 表示“状态可能变化”，不是把数据本身传给某个等待者。

### Event

Event 是 level-triggered flag：`set()` 后当前和未来 `wait()` 都通过，直到 `clear()`。适合“一旦就绪所有人继续”或 shutdown。它不计数、不携带 payload，多次 set 会合并；若每个事件都不能丢，应使用 Queue，而非 Event。

### Queue

Queue 将 item 和所有权从 producer 传给 consumer，通常是最安全的解耦方式。设置 `maxsize` 可提供 backpressure；consumer 要在完成后 `task_done`（对应实现），shutdown 用显式 sentinel/close 协议。PriorityQueue 需要稳定 tie-breaker，避免相同优先级比较不可比较对象。

### 面试简答版

Lock 保护单一临界区；RLock 允许同一线程重入，适合确有递归的场景但不能防跨线程死锁；Semaphore 限制最多 N 个并发 API/连接/GPU slot；Condition 在持锁状态下等待某个谓词，必须循环重查；Event 是广播式布尔状态，适合 ready/shutdown，不计数；Queue 传递数据所有权并通过 maxsize 提供背压。asyncio、threading 和跨进程原语不能混用，所有 permit/lock 都要覆盖异常和取消释放路径。
