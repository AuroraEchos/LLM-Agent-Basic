## 我的答案

异常体系的目标是：让调用方能根据**失败语义**采取动作，同时保留足够的根因信息。好的异常不是把每个函数都包一层 `try/except`，而是在能恢复、能增加领域上下文、或必须清理的边界处理。

### 1. 异常层次与捕获原则

`BaseException` 顶层还包含 `KeyboardInterrupt`、`SystemExit`、`GeneratorExit` 等控制流异常；业务代码通常捕获 `Exception` 的具体子类，不应使用裸 `except:` 把退出信号也吞掉。异步取消的继承关系和框架行为还可能有特殊约定，应显式传播取消。

```python
try:
    result = tool_client.call(request)
except TimeoutError as exc:
    # 只有这里知道超时可如何降级或重试
    return cached_result
```

捕获异常的合理时机：

- 当前层能恢复：重试、降级、补偿或返回明确错误；
- 把底层异常转换成稳定的领域接口；
- 增加 request/tool/model 等上下文后重新抛出；
- 在进程、任务、HTTP handler 等边界统一记录和映射状态码。

如果既不能恢复也不能增加信息，应让异常自然向上传播，避免“捕获—打印—再抛”造成重复日志。

### 2. 重新抛出、包装与异常链

```python
class ToolExecutionError(Exception):
    def __init__(self, tool_name: str, message: str):
        super().__init__(message)
        self.tool_name = tool_name

try:
    raw = transport.send(payload)
except TransportError as exc:
    raise ToolExecutionError(tool.name, "tool transport failed") from exc
```

- 在 `except` 内用裸 `raise` 保留原异常及 traceback；`raise exc` 会改变 traceback 的呈现起点，不是等价写法。
- `raise NewError(...) from exc` 显式保存因果链，适合跨抽象层包装。
- `from None` 可隐藏对用户无帮助的实现链，但日志/可观测系统仍应有根因，不能用于掩盖故障。

自定义异常应按调用方的处理策略分层，例如 `AgentError -> ToolError -> ToolTimeoutError`，而不是为每个函数建一种异常。异常对象可携带结构化且非敏感的信息，如 `tool_name`、`retryable`、`error_code`；不要塞完整 prompt、密钥或巨大响应。

### 3. `else`、`finally` 和资源清理

```python
try:
    value = parse(raw)
except ParseError:
    handle_bad_input()
else:
    persist(value)       # 这里的错误不会误报成 parse 失败
finally:
    release_resource()   # 无论成功、失败、return 都执行
```

`try` 范围应尽量小，避免一个宽泛 except 错抓不相关异常。资源优先交给 `with` 管理。不要在 `finally` 中 `return` 或抛无关异常覆盖原故障。

### 4. Agent 服务中的错误分类

可按是否重试和责任边界分类：输入/校验错误、鉴权错误、配额错误、瞬时依赖错误、永久依赖错误、内部 invariant 破坏。HTTP/API 对外只暴露稳定错误码和安全信息，内部日志保留异常链、trace id 与 attempt。只对幂等操作的瞬时错误做有限重试；“捕获所有异常并返回空字符串”会把系统故障伪装成模型幻觉或空答案。

### 面试简答版

我只在能够恢复、转换抽象、补充上下文或统一映射的边界捕获异常，并优先捕获具体类型；业务代码通常不捕获 `BaseException`。同层重新抛出用裸 `raise` 保留 traceback，跨层包装用 `raise DomainError(...) from exc` 保留异常链。自定义异常应按调用方处理策略分层并携带结构化安全信息。`finally`/上下文管理器负责清理，异常只在最合适的边界记录一次；重试必须限定瞬时错误、幂等性、次数和 deadline。
