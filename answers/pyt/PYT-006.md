## 我的答案

Context Manager（上下文管理器）把“获取资源—使用资源—无论成功失败都释放资源”封装成协议，`with` 是协议的语法糖。它解决的重点不是少写一个 `close()`，而是让异常、提前 `return` 和多分支下的清理仍然可靠。

### 1. 同步进入与退出协议

```python
with manager as resource:
    body()
```

概念上等价于：

1. 调用 `manager.__enter__()`，其返回值绑定给 `resource`；
2. 执行 body；
3. 无论 body 正常结束还是抛异常，都调用 `manager.__exit__(exc_type, exc_value, traceback)`；
4. 正常结束时三个异常参数都是 `None`；异常时，`__exit__` 返回真值表示异常已处理、应被抑制，返回假值/`None` 表示继续传播。

```python
class ModelSession:
    def __init__(self, factory):
        self.factory = factory
        self.model = None

    def __enter__(self):
        self.model = self.factory.load()
        return self.model

    def __exit__(self, exc_type, exc, tb):
        if self.model is not None:
            self.model.close()
        return False  # 不吞掉业务异常
```

也可用 `contextlib.contextmanager` 配合单个 `yield` 实现，`yield` 前是进入逻辑，`finally` 是退出逻辑。多个动态资源用 `contextlib.ExitStack`，它会按后进先出顺序清理，特别适合数量运行时才确定的文件或连接。

### 2. 异步协议

需要等待的获取/释放使用 `async with` 和 `__aenter__` / `__aexit__`，例如异步数据库连接、HTTP client 或流式响应。同步上下文的 `__exit__` 不能 `await`；异步清理也不能粗暴塞到普通 `with` 中。

### 3. 常见资源的正确语义

- **文件**：`with open(...) as f` 保证刷新并关闭文件，但不能把关闭后的句柄泄漏给外部继续用。
- **锁**：`with lock` 保证异常时释放；临界区应短，不在锁内做模型调用或慢 I/O。
- **数据库**：连接池获取/归还与事务提交/回滚是两个层次。事务上下文通常成功提交、异常回滚，但具体语义要以驱动为准，不能假设退出连接上下文一定提交。
- **模型/GPU 资源**：初始化若部分成功，退出逻辑要能清理已获得的子资源；若模型是进程级共享单例，不能在每个请求结束时卸载，应由应用 lifespan 管理。
- **推理模式**：有些上下文只临时改变状态，如 `torch.no_grad()`；退出时恢复先前状态，并不销毁模型。

### 4. 设计原则

`__enter__` 失败意味着 `__exit__` 不会自动为这个 manager 调用，所以进入过程获得多个资源时要自行回滚，或用 `ExitStack` 边获取边登记清理。`__exit__` 中不要无差别 `return True`，否则会静默吞掉真实故障；清理失败与业务异常同时发生时，也应尽量保留原异常上下文。上下文对象通常不保证可重入或可重复使用，需要明确文档。

### 面试简答版

同步上下文管理协议是 `__enter__` 获取并返回资源，`__exit__(type, value, traceback)` 无论成功失败都做清理；退出返回真值会抑制异常，通常应返回 `False`。异步资源使用 `async with` 和 `__aenter__/__aexit__`。文件、锁、连接、事务和模型生命周期都可用它管理，但要注意 `__enter__` 失败时不会自动调用退出、事务与连接归还是不同语义、请求级与进程级资源生命周期不同；多个动态资源适合 `ExitStack`。
