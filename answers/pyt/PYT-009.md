## 我的答案

选择数据模型时主要看四件事：是否需要运行时校验/转换、是否需要行为与不变量、是否要兼容 tuple、以及是否处在不可信数据边界。

| 方案 | 核心特点 | 适合场景 | 主要边界 |
|---|---|---|---|
| `NamedTuple` | 不可变的 tuple 子类，有字段名，支持索引、解包、hash（字段可哈希时） | 很小的只读记录、需要 tuple 兼容的返回值 | 不做运行时类型校验；字段多、默认值和演化复杂时可读性下降；字段指向的可变对象仍可变 |
| `dataclass` | 根据注解生成 `__init__`、`repr`、比较等样板代码，可选 `frozen`、`slots`、`kw_only` | 内部可信数据、配置、领域 value object、算法中间状态 | 类型注解默认不校验；`frozen=True` 只是模拟只读，不能让嵌套对象真正不可变 |
| 普通类 | 生命周期、封装、descriptor、继承和方法完全可控 | 有复杂不变量、懒加载、资源管理、丰富行为的领域对象 | 样板代码较多；序列化、schema、校验需自行实现或组合库 |
| Pydantic `BaseModel` | 根据类型和约束运行时校验/转换，提供嵌套模型、错误详情、序列化和 JSON Schema | API 请求/响应、配置、工具参数、LLM 结构化输出等不可信边界 | 有额外成本；默认可能发生类型转换，严格需求要开启 strict；不是 ORM/业务行为的万能替代 |

### 1. 典型选择

```python
from dataclasses import dataclass, field
from typing import NamedTuple
from pydantic import BaseModel, ConfigDict, Field

class TokenUsage(NamedTuple):
    prompt: int
    completion: int

@dataclass(frozen=True, slots=True)
class Chunk:
    doc_id: str
    text: str
    tags: tuple[str, ...] = field(default_factory=tuple)

class ToolRequest(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)
    name: str
    timeout_s: float = Field(gt=0, le=60)
```

- `TokenUsage` 是稳定、轻量且需要解包的二元记录。
- `Chunk` 是进程内部已经可信的值对象；`default_factory` 避免共享可变默认值。
- `ToolRequest` 位于外部输入边界，拒绝额外字段并使用严格类型与数值约束。

普通类则适合 `ModelPool`、`AgentRuntime` 等管理连接、锁和生命周期的对象，因为它们的价值主要是行为与不变量，而不是“字段集合”。

### 2. 容易混淆的点

- 类型注解本身通常不会在运行时拒绝错误类型；`dataclass` 和 `NamedTuple` 也不会自动验证构造参数。
- Pydantic 所谓 validation 保证的是**处理后的模型**符合字段类型/约束，输入可能被转换；若不能接受 `"123" -> 123`，应使用 strict 配置/字段。
- Pydantic v2 的常用 API 是 `model_validate`、`model_dump`、`model_json_schema`；`model_construct` 绕过校验，只能用于已经可信且性能确有必要的路径。
- “frozen”不等于深度不可变：frozen dataclass/Pydantic model 中的列表仍能被修改，若需要值语义应使用 tuple、frozenset 等不可变字段。
- 不要让一个模型同时承担传输 DTO、数据库 ORM、领域实体和模型供应商 payload。边界模型分层能避免外部 schema 变化污染核心逻辑。

性能上应以基准测试决定，不要先验地认为某个类“一定最快”。大量短命数据若不需要校验，可优先 dataclass/轻量结构；进入系统时校验一次，内部不要在每一层反复反序列化和验证。

### 面试简答版

`NamedTuple` 适合极小、只读且需要 tuple 兼容的记录；`dataclass` 适合可信的内部数据和值对象，自动生成样板方法但不做运行时校验；普通类适合复杂行为、不变量和资源生命周期；Pydantic 适合 API、工具参数和结构化输出等不可信边界，提供校验/转换、错误、序列化和 JSON Schema。要注意 Pydantic 默认可能转换输入，严格接口需 strict；`frozen` 也不是深度不可变。大型项目最好区分边界 DTO 与核心领域对象。
